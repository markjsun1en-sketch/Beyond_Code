# 第1章 软件工程的角色演进
## 从工具增强到受托执行

我最初把 AI 进入软件开发理解成一个效率问题。

最直观的变化确实发生在局部工作里：代码候选可以更快出现，测试和报错解释也不必每次从空白开始。这样的帮助没有必要被贬低。只是，一个函数更快写出来，和整个项目更快交付并不是一回事；后者还要算上 Review、返工、集成和长期维护。没有完成这种项目级比较，也不能把已经发生的局部帮助一笔勾销。

在长期项目里继续使用软件 Agent 之后，我面对的问题逐渐变了。我不再只是让 AI 写一段代码，而是把一个目标交给它，让它自己阅读项目、寻找修改位置、调用工具、检查失败，再决定下一步怎么办。

软件 Agent 真正扩展的，是一段工作可以被委托多远。人不必逐步指定每个动作，系统也可以沿着反馈继续推进。正因为这种能力有实际用途，工程问题才从“它能不能生成”走到了“它被允许替我们决定什么”。

变化就发生在这里。

如果 AI 只是把我已经决定好的步骤做得更快，原有的软件工程方法通常仍能接住它。如果它开始替我决定一部分中间路径，并且能够通过工具改变真实项目状态，那么工程上需要管理的就不再只是它交回来的代码。

我们还要知道：它理解了什么目标，看见了哪个项目状态，被允许做什么，留下了什么证据，以及结果最终由谁接受。

这不是关于 AI 是否“像人”的争论。它首先是工程责任的重新分配。

---

## 1.1 软件工程从来不只管理代码

写出一个能运行的程序，与长期建设一个软件系统，并不是同一件事。

随着系统扩大，模块、接口、状态、数据和运行环境会彼此牵连。一个看似局部的修改，可能在远处产生意外后果。模块化、抽象、封装、架构和测试，首先是在应对这种 Product Complexity（产品系统复杂性）。

与此同时，软件还要跨越人和时间。需求需要传递，修改需要合并，决定需要留下来，缺陷需要被复现，原始开发者离开之后，系统仍要能够继续维护。版本控制、Issue、Code Review、CI/CD 和项目管理机制，处理的是另一种 Collaboration Complexity（协作复杂性）。

传统软件生产经常被简化成这样一条关系：

```text
Human Intent
→ Human Interpretation and Design
→ Human-authored Change
→ Engineering Tools
→ Running Software
```

它不是一段精确的技术史，也从来不是绝对事实。优化器、调度器、搜索系统和自动运维早已能够作出复杂选择。它描述的是一种长期常见的责任安排：人通常直接控制目标解释和主要工程路径，工具则在预先建立的规则与接口内完成转换、检查或执行。

软件工具不断改变这条链路，却很少一次改变链路里的所有责任。

---

## 1.2 工具接手了越来越多步骤

高级语言让开发者不必逐条处理机器指令。它提高了表达层级，却没有替开发者决定产品应该成为什么。

IDE、静态分析和自动化测试缩短了反馈距离。它们让一部分检查从人的记忆进入可重复机制，却只能判断已经被形式化的规则。测试可以告诉我们某个断言是否成立，不能独自决定一次体验取舍是否值得，也不能把部署成功自动变成产品批准。

版本控制和持续集成又扩大了协作范围。Git 保存了代码如何变化，CI 让一些集成问题更早暴露。但 Git 不知道一项业务决定为什么作出，也不能只凭 Repository State 回答线上到底运行着什么版本、使用什么配置、面对什么数据。

每一代工具都在重新分配工作：

- 有些细节不再需要人手工完成；
- 有些检查可以交给系统重复执行；
- 有些变化和协作关系只有留下外部记录，才能跨越人员与时间继续追踪；
- 无法被规则表达的判断仍然需要人承担。

所以，工具变得更复杂，并不等于它自然获得了目标解释权。真正值得注意的也不是“工具有没有智能”，而是它在一次生产过程中被托付了什么。

---

## 1.3 AI 先延续了工具增强的路径

代码补全和生成式助手最初带来的体验，与过去的工具演进有明显连续性。

人提出一个局部问题，AI 给出代码、解释或测试候选，人决定是否采用，再由既有工程流程验证结果。在这种模式下，AI 扩展了人的表达和检索能力，但输出仍然主要是候选：

```text
Human frames a local problem
→ AI proposes
→ Human selects and applies
→ Existing process verifies
```

即使代码生成速度提高很多，这种变化也不必然要求一套新的生产体系。人仍然知道修改在哪里发生，仍然逐项决定是否应用，也仍然能够用原有的版本控制、测试和 Review 管住结果。

这并不让这种用法变得次要。它只说明，局部效率收益和生产责任变化是两个问题，不能用一个标签回答。

软件 Agent 触及的是另一条边界。它获得 Repository、Terminal、Browser、Build 或其他工具后，可以在一个任务里连续地：

```text
解释限定目标
→ 检查项目状态
→ 选择局部路径
→ 通过工具行动
→ 观察反馈
→ 调整下一步
```

部分日常开发任务已经出现这种能力。但“能循环调用工具”还不足以说明工程角色发生了多大变化。一个被严格 Workflow 约束的 Agent，拥有的开放式裁量可能少于某些传统优化系统。

更有用的判断来自三个维度：

| 维度 | 要问的问题 |
|---|---|
| Delegated Interpretation（受托解释） | 它被委托解释多大范围的开放式目标？ |
| Action Surface（行动面） | 它能够读取、写入或触发哪些真实状态？ |
| Feedback Horizon（反馈跨度） | 它能根据多少轮环境反馈继续行动和修正？ |

本书因此把 Agent 看作一种受托执行系统：它在外部 Context、Tool、Policy 和 Runtime 的支持下，对限定目标进行多步解释与行动。

这一定义不把 Agent 当成员工。它没有天然的组织身份、项目所有权或责任。它表现出来的能力，来自模型、上下文、工具、环境以及人或制度授予的委托。

## 1.4 真正改变的是中间过程

设想两种看起来相近的工作。

在第一种工作里，人已经确定要修改哪个函数、采用什么方案，只让 AI 生成一个候选实现。这里主要改变的是操作速度。

在第二种工作里，人只给出目标与边界。Agent 阅读多个文件，判断问题落在哪里，尝试一种方案，运行测试，再根据失败修改计划。最后，人看到的是一组变化和一份结果说明。

第二种工作吸引人的地方，正是一段完整的搜索、修改与验证可以在不被逐步遥控的情况下向前推进。它的价值与管理难题来自同一项能力：Agent 开始选择中间路径，并通过工具把选择变成真实变化。

两者都使用 AI，却形成了不同的责任结构。

第二种工作首先改变的是谁决定中间路径。Intent Owner（意图责任人）仍然拥有目标，但部分路径选择被委托给了 Agent。委托可以很窄，也可以很宽；它不是 Agent 天然拥有的权利。

接着，人不再天然拥有 Agent 执行时接触的全部上下文。系统可以记录哪些资料被装配、哪些文件被读取，却不能假装由此知道模型“心里使用了什么”。我们真正能管理的是外部可观察的输入、动作、结果与限制，而不是隐藏的推理过程。

代码本身也不再完整解释变化是怎样产生的。要理解一次高影响修改，可能还需要它对应的目标版本、起始状态、使用过的上下文来源、工具权限、遇到的失败、验证结果和后续裁决。这里并不是要求保存全部会话，更不是把每个低风险任务都变成审计工程；需要保留多少，应当由影响、可逆性和恢复成本决定。

另一个变化是生产与理解可能失去同步。在某类工作和相关时间窗内，如果候选产生能力持续快于 Review、集成和人的系统理解，瓶颈就可能从“写不出来”转向“来不及判断这些变化是否值得进入系统”。测试全部通过，也不能替代这种判断。

这不是对生产收益的否定。它要求把“生成了多少候选”与“多少变化经过理解、验证和接受，最终进入系统”分开观察。

最后，过去容易被一句“工具执行、人来负责”带过的关系，现在必须拆开：

```text
Capability      技术上能够做什么
Permission      当前获准执行什么
Authority       能否对具名事项作出决定
Responsibility  对具名工作承担执行、维护、响应或恢复义务
```

这四者可能落在不同的人、Agent、Tool、Policy 和 Gate 上。能修改文件，不等于获准修改；测试通过，不等于允许采用；能够提出一个判断，也不等于拥有裁决它的 Authority。

结果需要由谁解释、纠正并承担组织后果，是第18章展开的 Accountability（问责关系）问题；本章不把它压回 Responsibility。

## 1.5 价值与成本来自同一份委托

Agent 的进入没有取消产品复杂性和协作复杂性。在一部分项目中，它增加的是 Delegated Execution Complexity（受托执行复杂性）：把部分目标解释和行动委托给软件执行系统以后，为了保持边界、理解结果和处理失败而新增的协调成本。

这种复杂性通常来自几处断点：目标可以有多种解释；Agent 得到的 Context 与项目当前 State 可能冲突；工具能力可能大于实际授权；一次执行会跨越多轮反馈；完成声明可能超过证据覆盖；多个执行者可能同时触碰同一工作面。

它与委托价值来自同一个地方。一个只能给出只读、一次性候选的系统，很少需要新的工程设施；一个能够跨文件修改、接触数据、调用外部系统并沿着反馈继续行动的系统，被委托的工作范围更广，也会让错误更难恢复、让决定边界更重要。

所以，受托执行复杂性不是所有 AI 使用都会面对的固定税负。真正决定治理强度的，也不是项目用了几个 Agent，或者模型参数有多大，而是委托范围、行动面、风险、可逆性和可验证性。新增控制只有保护了相称的决定或风险，才值得它的维护成本。

这也意味着，AI-native 不能被理解成“尽可能自治”。第3章会给出本书的工作定义；这里先保留一个更朴素的判断：如果项目没有把 Agent 当成真实存在的执行条件来设计，增加更多自动化也可能放大原有的不清楚。

## 1.6 我们开始同时设计两个系统

传统开发者主要设计最终要运行的产品。受托执行扩大以后，开发者还需要关心生产这个产品的那套智能执行环境。

第3章会把它们正式区分为：

- Product System：交付给用户或组织、实际运行的软件、数据、配置与基础设施；
- Production Intelligence System：参与生产的 Agent、Harness、Context、Tool、Skill、Memory 与 Workflow。

第二个系统不是一层装饰。相同模型在不同 Context、Permission、Tool、Workflow 和完成要求下，可能形成完全不同的结果。只升级模型，却让它运行在过期文档、宽松权限和弱验证环境中，并不会自动得到更可靠的工程能力。

两个系统之间还需要横切的控制与证据能力：谁声明目标，当前状态依据什么，Agent 可以做什么，系统观察到了什么，哪些结果支持哪些判断，失败后由谁停止和接管。

这些关系不要求每项任务都建立一套独立 Schema。低风险工作可以借用现有 Issue、测试和版本记录表达。只有当隐式关系开始造成误解、冲突或恢复困难时，才值得把它们变成更明确的工程对象。

“管理生产软件的智能系统”也不是让开发者都变成 Agent 管理员。它只是承认：当一部分生产路径由软件执行系统承担时，那套执行环境本身也会产生缺陷，也需要被设计、观察和修正。

## 1.7 人类保留的不是每一步，而是有效控制

把更多执行交给 Agent，并不意味着人类从软件工程中消失。真正变化的是人的注意力应该落在哪里。

产品目标、风险接受、架构方向、用户体验、法律与组织责任，不能因为 Agent 能够生成一个看似完整的方案就被自动转移。另一方面，如果所有低风险动作仍要逐项等待批准，受托执行也只会退化成昂贵的远程操作。

人类保留的裁决权需要通过实际能力体现出来，而不能只停留在原则声明里。负责的人必须能定位关键证据，理解结论的适用范围，暂停或否决动作，在失败时接管，并改变以后允许怎样委托。

这与“Human in the Loop”式的机械确认不同。有效控制的目的，是让委托可以在边界内继续，而不是把已经交出去的每一步重新拿回。系统可以按已授权 Policy 自动处理低风险、可逆事项，把稀缺的人类注意力留给真正影响方向、数据、安全、发布和产品体验的决定。

人类不必亲手写下每一行代码，才能继续拥有软件。但如果人只能在最后按下批准按钮，既看不清发生了什么，也无法改变执行边界，那么所谓“最终责任”就只剩下一句空话。

---

## 1.8 什么时候值得工程化这份委托

并非每次使用 AI 都值得引入新的架构。Gate、记录和流程的数量本身也不产生价值。开始建设之前，可以先问几个具体问题：

- Agent 是否会直接改变真实项目状态，而不只是给出候选？
- 它是否需要在多条路径之间作选择，并根据反馈继续行动？
- 任务是否跨文件、跨工具、跨会话或跨多个执行者？
- 错误是否会触及数据、安全、发布或其他难以恢复的状态？
- 现有测试与 Review 能否覆盖 Agent 最终提出的完成结论？
- 人是否仍能在必要时理解、停止和接管这项工作？

如果大多数答案是否，传统软件工程加上轻量的 AI 使用规范通常已经足够。如果多个答案为是，项目需要的就不只是更强模型，而是更明确的 Intent、Context、State、Authority、Evidence 和 Recovery。

本章的结论不是“效率不重要”。软件 Agent 之所以值得讨论，正是因为它可以承担比一次代码生成更长的工作路径。一个团队完全可能先感受到局部帮助，却还说不清整个项目是否更快、更好或更划算。这两种判断并不冲突。缺少后者，不应被写成成功证明，也不应被写成无用证明。

更窄的结论是：软件 Agent 没有推翻传统软件工程，也没有创造一条所有项目都必须追随的升级路线。它带来的新条件，是部分目标解释和行动路径可以被委托给软件系统。

一旦这种委托足以改变责任关系，软件工程就必须把生产者本身纳入设计。

下一章要追问的，是怎样保留这种委托的用途，同时判断现有方法依赖的哪些操作条件仍然可靠，哪些已经需要重新检查。
