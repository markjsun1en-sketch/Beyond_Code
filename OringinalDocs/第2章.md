# 第2章  
# 当传统软件工程的隐含假设开始失效

第一章讨论了一个关键变化：AI Agent 与过去的软件工具之间，真正重要的区别并不只是能力更强，而是它开始承担过去主要由人类承担的一部分生产职责。

当 AI 只是提供代码补全、解释错误或生成候选方案时，传统软件工程体系仍然可以基本照常运行。人类提出目标、控制修改、理解变化、执行验证，并承担最终责任。

但当 Agent 开始：

- 读取整个项目；
- 解释自然语言目标；
- 制定执行计划；
- 修改多个模块；
- 调用构建、测试和 Git；
- 根据反馈修改方案；
- 与其他 Agent 并行工作；
- 在较长时间内持续参与项目；

问题的性质开始变化。

我们需要重新检查一个很少被明确讨论的问题：

> 传统软件工程的许多方法，是在什么样的生产环境假设下建立起来的？

这些假设通常不会出现在某一本教材的第一页。

没有人会正式规定：

> “软件变化速度必须低于人的理解速度。”

也不会有标准声明：

> “项目的主要生产者必须是人类。”

但几十年来，大多数软件工程制度、工具和流程，事实上都是在这些条件下发展起来的。

它们是一种**隐含的运行环境**。

当环境稳定时，我们不需要特别注意这些前提。

当环境发生变化时，原本合理的工程机制就可能开始出现边界。

这一章要讨论的，不是传统软件工程“错了什么”。

恰恰相反。

传统软件工程能够如此成功，是因为它很好地适应了过去的软件生产条件。

真正的问题是：

> 当软件生产者、生产速度、执行方式、知识结构和组织规模同时发生变化后，哪些原本成立的默认条件开始不再可靠？

这是理解 AI 原生软件工程为什么有必要存在的基础。

---

# 2.1 “隐含假设”并不意味着传统软件工程存在缺陷

在开始之前，需要先澄清一个容易产生误解的地方。

所谓“传统软件工程的隐含假设”，并不是指软件工程领域曾经错误地规定了某些东西。

更准确地说，它们是长期实践中自然形成的**操作性前提**。

例如，Code Review 为什么通常要求另一个开发者阅读 Pull Request？

因为过去一个合理的默认条件是：

> 一个开发者在一段时间里产生的修改量，大致仍处于另一个人可以阅读和理解的范围内。

为什么 Git Commit、Issue 和 Pull Request 可以承担大量协作信息？

因为过去一个合理的默认条件是：

> 软件变化主要由数量有限的人类开发者产生，而任务之间的因果关系可以通过人工描述和团队交流补充。

为什么自动化测试通常被看作对人类开发过程的质量增强，而不是整个生产系统的控制机制？

因为过去的生产者本身也是软件设计者。

测试帮助他发现错误，但测试不需要负责解释：

> “这个生产者为什么选择了这条实现路径？”

这些机制在原有环境中完全合理。

AI 的出现并不会使它们失效。

真正发生变化的是：

> 它们不再足以单独覆盖整个生产系统。

这与云计算出现以后，传统运维知识没有失效类似。

服务器、网络、进程、文件系统仍然存在。

但当基础设施规模、变化速度和动态性上升之后，行业需要额外发展：

- Infrastructure as Code；
- Observability；
- Site Reliability Engineering；
- 自动扩缩容；
- 更系统的故障恢复机制。

AI 原生软件工程也具有类似性质。

它不是传统软件工程的替代物。

它是环境改变以后的一层扩展。

---

# 2.2 隐含假设一：人类是软件生产的主要解释者和执行者

传统软件开发中，即使团队使用大量自动化工具，人类通常仍然承担四个核心角色：

```text
Understand
→ Decide
→ Implement
→ Explain
```

也就是：

- 理解需求；
- 做出设计决策；
- 实施修改；
- 解释为什么这样修改。

工具可以介入其中很多环节，但通常不会同时承担这四个角色。

编译器负责转换。

测试框架负责验证预先定义的断言。

版本控制负责记录变化。

CI 负责执行流水线。

静态分析器负责检查形式化规则。

它们都非常重要，但其职责相对明确。

因此，传统软件工程中存在一种天然的责任链：

```text
Requirement
    ↓
Developer Understanding
    ↓
Developer Decision
    ↓
Code Change
    ↓
Review / Test
```

如果代码出现问题，我们至少可以尝试追问：

> 当时为什么这样设计？

开发者可能记错，也可能已经离职。

但整个工程制度默认存在一个可被追踪的人类认知过程。

---

## 当 Agent 进入执行层

Agent 改变了这一点。

现在可能出现：

```text
Human Requirement
    ↓
Agent Interpretation
    ↓
Agent-generated Plan
    ↓
Agent Tool Use
    ↓
Agent Code Change
    ↓
Agent Self-correction
```

人类仍然提出目标，却不再天然参与每一个中间判断。

例如，一个人可能只提出：

> 重构 Player Status，让 Stage 信息层级更清楚，同时保持现有 HP 和 Block 方向。

Agent 随后可能自行决定：

- 阅读哪些文件；
- 哪些组件应该重构；
- 哪些代码可以复用；
- 是否抽象新的 Widget；
- 是否改变数据绑定；
- 是否需要修改资源；
- 如何验证结果。

最终人类看到的是一组修改。

此时出现了一个新的结构：

> **Intent Owner 与 Execution Path Owner 开始分离。**

人类拥有目标。

Agent 在很大程度上拥有实现路径。

---

## 为什么这会改变软件工程

如果软件生产者不再只由人类组成，那么很多过去隐式存在于“开发者脑中”的信息必须被显式工程化。

例如：

- 为什么允许修改这些文件？
- 哪些区域不能碰？
- 哪个目标优先级最高？
- 哪些行为属于范围扩张？
- 什么情况下 Agent 必须停止？
- 哪些设计决策必须由人类作出？

过去，这些信息可能通过：

- 经验；
- 团队默契；
- 角色责任；
- 长期项目参与；

存在于人类组织之中。

Agent 并不天然拥有这些隐性知识。

因此，第一项变化是：

> 软件工程必须开始显式管理生产者的目标、角色、权限和行为边界。

这会直接引出后续的：

- Intent Engineering；
- Agent Contract；
- Controller / Worker；
- Governance；
- Traceability。

---

# 2.3 隐含假设二：生产速度大致不会长期超过人类理解速度

传统软件工程有一个极少被明确写出的重要条件：

> 人类通常能够对自己和团队产生的主要变化保持大致理解。

这当然从来不是绝对成立的。

大型系统中早就存在：

- 信息过载；
- 巨型 Pull Request；
- 无人理解的 Legacy Code；
- 文档落后；
- 架构知识流失。

但在人类作为主要代码生产者的情况下，生产速度本身受到人的时间、注意力和操作速度限制。

一个人能够在一天内设计、实现和调试的内容有自然上限。

团队规模增加能够提高吞吐，但同时也需要增加沟通、Review、测试和协调成本。

因此，软件生产速度与人类理解速度之间虽然存在张力，却通常不会完全脱钩。

---

## AI 改变了生产速率

Agent 可以在较短时间内：

- 阅读大量文件；
- 搜索大量引用；
- 重写重复代码；
- 生成测试；
- 修改配置；
- 更新文档；
- 并行启动其他 Worker。

当多个 Agent 并行工作时，产出速度甚至可以进一步叠加。

此时可能出现：

```text
AI Production Capacity
        ↑↑↑↑↑

Human Cognitive Capacity
        →
```

人的阅读速度没有同步提高。

人的工作记忆没有同步扩大。

人的系统理解能力也没有因为模型变强而自动提升。

---

## 生产瓶颈开始发生迁移

过去一个项目可能主要受限于：

> 代码写不完。

未来部分项目可能更受限于：

> 代码已经生成，但没人能够可靠确认这些变化意味着什么。

这会让生产瓶颈从：

```text
Implementation Throughput
```

向：

```text
Understanding
Verification
Decision
Integration
```

迁移。

这里需要避免一个误解：

这并不意味着 AI 提高生产率没有意义。

恰恰相反。

它意味着：

> 当一个瓶颈被显著突破以后，系统中的其他瓶颈会变得更加重要。

这是一种典型的工程现象。

如果编译从十分钟缩短到十秒，测试可能成为新瓶颈。

如果部署完全自动化，审批流程可能成为新瓶颈。

如果代码生产能力增加十倍，Review 和理解能力就可能成为新瓶颈。

---

## 传统 Code Review 机制因此受到压力

传统 Review 经常依赖：

```text
Diff
+
Reviewer Experience
+
Tests
```

但如果一次 Agent 任务产生：

- 40 个文件；
- 5000 行变化；
- 多个模块重构；
- 新增依赖；
- 测试和文档同时修改；

“提供 Diff”并不能保证 Review 仍然有效。

技术上：

> 人可以看到所有变化。

认知上：

> 人未必真正吸收所有变化。

这两者是不同的。

因此，第二项变化是：

> 软件工程开始需要显式管理 Human Cognitive Bandwidth。

这将引出后续的：

- Review Budget；
- Cognitive Compression；
- Decision Surface；
- Cognitive Debt。

但认知问题只是整个变化的一部分，而不是全部。

---

# 2.4 隐含假设三：执行工具的行为相对确定

传统软件工具的一个重要工程优势，是它们通常具有较强的可预测性。

给编译器相同：

- 源代码；
- 编译器版本；
- 配置；
- 环境；

我们通常期望得到一致结果。

测试框架也是如此。

Git 命令也是如此。

CI Pipeline 中的脚本也是如此。

它们当然会受到：

- 环境；
- 网络；
- 时间；
- 并发；
- 外部依赖；

影响，但它们的核心行为原则是明确的。

因此，传统软件工程可以大量使用：

```text
If X
Then Y
```

式的自动化机制。

---

## Agent 的执行不是简单确定函数

Agent 的行为取决于更多条件：

```text
Goal
+
Model
+
Context
+
Context Order
+
Tools
+
Tool Results
+
Environment
+
Intermediate Decisions
```

即使任务表面相同，不同执行可能：

- 阅读不同文件；
- 采用不同架构；
- 选择不同修复方案；
- 运行不同验证步骤；
- 在某个失败点做出不同调整。

因此：

```text
Same Task
≠
Guaranteed Same Execution Path
```

这不是单纯的 Bug。

它是 Agent 这种执行者的重要特征。

---

## 软件工程因此需要管理“行为分布”

传统工具治理通常关心：

> 这个工具按规则运行了吗？

Agent 治理还需要关心：

> 在一组可能行为中，它选择了哪一种？

以及：

- 这个选择是否允许？
- 是否符合项目目标？
- 是否出现漂移？
- 是否超出风险范围？
- 能否恢复？
- 能否重现关键条件？

因此，第三项变化是：

> 软件工程的可靠性对象从“确定性工具是否正确运行”，扩展到“概率性执行者是否在可接受行为范围内运行”。

这会带来：

- Sandbox；
- Scope Control；
- Checkpoint；
- Retry Policy；
- Fallback；
- Recovery；
- Evaluation；
- Behavioral Regression。

AI 原生软件工程追求的并不是把 Agent 强行变成完全确定的软件。

而是：

> 让不完全确定的执行者仍然能够被可靠地纳入工程系统。

---

# 2.5 隐含假设四：项目知识主要可以通过代码、文档和人类记忆维持

传统软件项目的主要知识载体通常包括：

```text
Code
Documentation
Issue / Ticket
Version History
Human Memory
```

不同组织还可能拥有：

- Wiki；
- ADR；
- 设计文档；
- QA Case；
- 产品需求；
- Runbook；
- 内部培训。

虽然知识管理从来都不完美，但这些载体基本围绕人类消费设计。

人类拥有一个非常重要的能力：

> 能够利用大量隐含背景补全文档中的缺失部分。

一个长期参与项目的人看到：

> “不要再使用旧版 Input Manager。”

他可能知道：

- 为什么不能用；
- 哪次事故导致这个规则；
- 哪些老模块还没有迁移；
- 哪些例外仍然存在。

文档只记录一句话，人脑中却存在整个背景网络。

---

## Agent 没有天然的组织记忆

Agent 每次工作的知识来自被加载的 Context。

如果没有提供，它可能不知道。

如果提供了错误版本，它可能相信错误信息。

如果两个来源冲突，它可能自行推断。

如果某个历史结论只存在于过去讨论中，而没有进入当前 Context，它在实际执行中等价于不存在。

因此，AI 环境中：

```text
Existing Knowledge
≠
Available Agent Knowledge
```

组织知道，不代表 Agent 知道。

文档存在，不代表当前任务读取了它。

Memory 保存了，不代表它仍然正确。

---

## 新的项目资产开始出现

AI 参与长期项目以后，项目知识不再只有：

```text
Code + Docs
```

还会增加：

```text
Context Rules
Agent Instructions
Skills
Memory
Tool Descriptions
Examples
Prompt Templates
Decision Summaries
Evaluation Cases
```

这些内容会直接影响 Agent 行为。

于是它们开始具有类似代码的工程重要性。

一个错误 Skill 可能反复制造错误修改。

一条过期 Memory 可能让后续多个任务基于错误事实执行。

一份错误 Context Summary 可能影响整个 Worker Thread。

这意味着：

> 上下文和记忆不再只是辅助信息，而开始成为生产基础设施。

因此，第四项变化是：

> 软件工程必须管理“Agent 所知道的项目”与“项目真实状态”之间的关系。

这会引出：

- Context Engineering；
- Context Provenance；
- Truth Architecture；
- Memory Governance；
- Decision Record。

---

# 2.6 隐含假设五：软件团队规模受到人力和沟通成本的自然限制

传统软件团队的规模不会无限增长。

增加人手能够提高部分生产能力，但会同时增加：

- 沟通；
- 协调；
- Onboarding；
- 冲突；
- 管理；
- Integration；

成本。

因此，组织结构通常围绕有限人数设计。

例如：

```text
Product / Producer
        ↓
Tech Lead
        ↓
Developers
        ↓
QA
```

或：

```text
Feature Team
├── Design
├── Engineering
├── Art
└── QA
```

角色和沟通流程的复杂度受到真实人力成本约束。

---

## Agent 显著降低“增加执行者”的边际成本

未来一个负责人可能同时拥有：

- Research Agent；
- Planner Agent；
- Coding Agent；
- Test Agent；
- Review Agent；
- Documentation Agent；
- UI Agent；
- Data Agent。

甚至每个角色还可以继续拥有多个 Worker。

理论上：

```text
1 Human
    ↓
Controller
    ↓
────────────────────────
Worker A
Worker B
Worker C
Worker D
Worker E
...
```

Agent 数量的物理限制远低于人类员工。

但这并不意味着组织复杂性消失。

恰恰相反。

---

## 执行者数量增加，会产生新的协调成本

多个 Agent 可能：

- 重复分析同一问题；
- 修改相同文件；
- 使用不同历史状态；
- 作出互相冲突的设计；
- 各自产生大量输出；
- 对相同任务得出不同结论。

这形成一种新的工程现象：

> Compute Scalability 不等于 Organizational Scalability。

你可以非常容易地启动十个 Agent。

但你未必能够：

- 给十个 Agent 正确分工；
- 保持它们 Context 一致；
- 控制修改冲突；
- Review 十份输出；
- 正确合并它们的结果。

---

## 多 Agent 的问题本质上是组织设计问题

因此，需要回答：

- 谁拥有全局目标？
- 谁负责局部任务？
- 谁可以修改共享区域？
- 谁负责验证？
- 谁负责汇总？
- 谁解决冲突？
- 谁决定停止？
- 什么时候应该升级给人类？

这些问题与企业组织设计非常相似，但不能直接把 Agent 当成人类员工照搬公司结构。

因为 Agent：

- 没有天然持续身份；
- 没有人类式责任；
- 上下文可能相互隔离；
- 输出速度远高于人类；
- 可以快速创建和销毁；
- 能力高度依赖模型和工具。

因此，第五项变化是：

> 软件团队从固定规模的人类组织，开始向动态的人机执行网络演化。

这会引出：

- Multi-Agent Organization；
- Controller / Worker；
- Structured Handoff；
- Authority Model；
- Escalation；
- Conflict Resolution。

---

# 2.7 隐含假设六：人工 Review 可以作为主要的高层质量防线

传统软件工程中，自动化测试并不能覆盖所有问题。

因此，人类 Review 承担了许多无法完全形式化的判断：

- 架构是否合理；
- 代码是否易维护；
- 命名是否清晰；
- 设计是否符合项目习惯；
- 有没有隐藏风险；
- 这个方案是否过度复杂。

这种 Review 的价值来自人类能够：

> 把局部变化放回整个项目上下文中理解。

---

## AI 时代出现 Verification Gap

如果 Agent 生产速度显著提升，就可能出现：

```text
Generation Capacity
        >
Automated Verification
        >
Human Verification
```

生成可能最快。

自动验证次之。

真正深入的人工理解最慢。

于是软件工程面临一个危险诱惑：

> 既然人看不过来，就让另一个 AI Review。

Review Agent 的确有价值。

它可以：

- 检查代码；
- 搜索潜在 Bug；
- 对照规则；
- 分析 Diff；
- 运行更多测试。

但这里存在一个重要问题：

> 如果生产 Agent 和 Review Agent 都属于概率性执行系统，那么“AI Review AI”本身仍然需要工程约束。

我们不能简单形成：

```text
Agent A says correct
+
Agent B says correct
=
Therefore correct
```

两个模型同意，不等于事实成立。

---

## Review 必须从角色转向系统

未来 Review 更合理的结构可能是：

```text
Intent
    ↓
Plan Review
    ↓
Execution
    ↓
Checkpoint
    ↓
Automated Evidence
    ↓
Review Agent
    ↓
Human Decision
```

不同验证机制承担不同职责。

测试验证形式化行为。

静态分析检查规则。

Runtime Evidence 验证真实运行。

Review Agent 寻找遗漏和异常。

人类则集中判断：

- 高风险；
- 高影响；
- 不可逆；
- 战略性；
- 难形式化；

的问题。

因此，第六项变化是：

> 人工 Review 不能继续通过“阅读全部产出”单独承担最终质量控制。

它需要进入一个多层验证系统。

这将引出：

- Evidence Engineering；
- Review Engineering；
- Risk-based Review；
- Cognitive Compression；
- Human Decision Surface。

---

# 2.8 隐含假设七：当前系统状态相对容易确定

传统软件工程从来都存在状态不一致问题。

例如：

- 文档落后于代码；
- 本地环境和生产环境不同；
- Branch 不一致；
- Feature Flag 不一致；
- 配置漂移。

因此，版本控制、配置管理和部署工程一直都很重要。

但在 AI 环境下，“Agent 认为当前系统是什么”本身变成了新的状态层。

---

## 一个典型冲突

假设：

文档写着：

> Player Status 使用旧版 Stage Chip。

代码已经切换到新版结构。

当前 Worktree 又存在一组尚未提交的 UI 修改。

Agent 的历史 Memory 中还保留着旧版 Widget 命名。

现在让 Agent：

> 继续优化 Stage 显示。

它面对至少四个现实：

```text
Documentation State
Code State
Worktree State
Memory State
```

如果这些状态没有明确优先级，Agent 可能：

- 按旧文档恢复已淘汰设计；
- 覆盖当前未提交修改；
- 误把实验代码当正式基线；
- 根据 Memory 引用已经删除的结构。

Agent 并不是一定会这样做。

问题在于：

> 系统没有提供足够机制保证它不会这样做。

---

## “事实”需要被显式定义

因此可以区分：

### Intent

希望未来成为什么。

### Truth

当前可以验证的状态。

### Assumption

在缺乏完整事实时暂时采用的推断。

例如：

```text
Doc = Intent
Code = Implementation Truth
Runtime = Behavioral Truth
Assumption = Unverified Working Model
```

这种区分非常重要。

因为 AI 很容易把流畅的自然语言描述解释成事实。

一份写得非常肯定的旧设计文档，可能比一段复杂代码更容易被模型理解。

但“更容易理解”并不等于“更真实”。

因此，第七项变化是：

> 软件工程需要显式管理事实层、意图层和假设层。

这将成为后续 Truth and State Architecture 的核心。

---

# 2.9 一个更深的变化：过去许多“隐性组织能力”需要变成“显性系统能力”

把前面七项变化放在一起，可以看到一个共同趋势。

传统软件工程中，很多重要能力事实上存在于团队内部：

```text
Shared Understanding
Tacit Knowledge
Professional Judgment
Role Responsibility
Historical Memory
Social Coordination
```

这些东西很难完全写进系统，但人类组织可以通过长期合作维持。

例如，一个资深程序员可能知道：

> 这个模块虽然看起来可以重构，但两个月后有另一个系统依赖它，所以现在不要动。

这个信息可能没有文档。

却存在于组织认知中。

当 AI 参与越来越多执行以后，如果这类知识仍然只存在于人脑里，Agent 就无法可靠使用。

于是：

```text
Tacit Organizational Capability
```

需要逐步变成：

```text
Explicit Engineering Infrastructure
```

例如：

| 过去主要依赖 | AI 环境下需要增加 |
|---|---|
| 人类理解需求 | Intent Model |
| 人类知道项目背景 | Context Architecture |
| 老员工知道什么是真的 | Truth Hierarchy |
| Lead 控制开发范围 | Agent Contract / Permission |
| Reviewer 知道哪里风险高 | Risk Model |
| QA 判断是否完成 | Evidence-Driven DoD |
| 团队经验 | Governed Memory |
| 资深成员传帮带 | Skill / Knowledge System |
| Producer 协调多人 | Controller / Agent Organization |

这可能是 AI 原生软件工程最重要的变化之一：

> 过去存在于组织内部的隐性工程能力，需要越来越多地被外部化、结构化并写入系统。

---

# 2.10 软件工程的“控制面”正在扩大

可以借用基础设施领域中的一个概念来理解这个变化：

**Control Plane。**

传统软件工程的控制面主要包括：

- Git；
- Issue；
- CI；
- 权限；
- Code Review；
- Deployment；
- Monitoring。

这些系统控制：

> 人类提交的软件变化如何进入生产环境。

AI 环境中，需要进一步增加：

```text
Intent Control
Context Control
Agent Permission
Execution Scope
Evidence Requirement
Memory Update
Skill Evolution
Human Decision
```

也就是说，控制对象从：

```text
Software Change
```

扩展为：

```text
Software Change
+
Change-producing Intelligence
```

我们不仅需要控制修改本身。

还需要控制：

> 产生修改的智能执行过程。

这也是为什么单纯给 Agent 一个更强模型，并不能自动构成成熟的软件生产体系。

---

# 2.11 从“代码可信”到“生产链可信”

传统软件工程最终交付的是代码和运行系统。

因此很多质量机制都集中在：

> 代码本身是否可信？

AI 环境进一步要求：

> 这段代码是通过怎样的生产链产生的？

例如：

```text
Human Intent
    ↓
Context Selection
    ↓
Agent Plan
    ↓
Tool Execution
    ↓
Change
    ↓
Evidence
    ↓
Review
    ↓
Approval
```

其中任何一层出错，都可能产生看起来合理的代码。

### Intent 错误

正确实现错误目标。

### Context 错误

基于过期状态做出合理修改。

### Plan 错误

采用不符合长期架构的路线。

### Execution 错误

实际修改与计划不一致。

### Evidence 错误

测试覆盖不足，却被误认为已经验证。

### Review 错误

Reviewer 依赖错误摘要做判断。

因此未来的软件可信性将越来越依赖：

> 整个生产链是否可信。

这就是为什么：

- Traceability；
- Evidence；
- Provenance；
- Decision Record；

会变得更加重要。

---

# 2.12 传统软件工程与 AI 原生软件工程的差异可以怎样概括

到这里，可以建立一个初步对照。

| 维度 | 传统软件工程的典型环境 | AI 原生环境 |
|---|---|---|
| 主要执行者 | 人类开发者 | 人类 + Agent |
| 目标解释 | 人类完成 | 人类与 Agent 共同完成 |
| 执行路径 | 人类直接决定较多 | Agent 自主决定较多 |
| 生产速度 | 受人类操作速度明显限制 | 可快速扩张 |
| 工具行为 | 相对确定 | 部分执行具有概率性 |
| 项目知识 | Code、Doc、人类经验 | Code、Doc、Context、Memory、Skill |
| 团队规模 | 人力成本限制明显 | Agent 数量可快速扩张 |
| Review | 人工阅读为重要防线 | 多层验证 + 风险化人工 Review |
| 状态理解 | 人类整合多来源信息 | 必须显式帮助 Agent 解析状态 |
| 责任链 | 与人类生产者较强绑定 | 授权、执行、Review、批准分离 |
| 演化 | 人类学习和流程改进 | 人类 + Memory + Skill + Agent Evolution |

需要再次强调：

这不是非黑即白的区别。

现实项目会处于连续谱上。

一个团队可能：

- 代码生成是 Agentic；
- 架构决策仍完全 Human-driven；
- QA 部分自动；
- 部署仍采用传统 CI/CD；
- Memory 尚未正式建立。

AI 原生软件工程不是一个开关。

它更像：

> 随着 Agent 逐渐进入更多生产环节，传统体系需要逐步增加新的控制能力。

---

# 2.13 哪些旧原则反而会变得更重要

讨论传统假设失效，很容易产生一种错误印象：

> AI 来了，所以以前的软件工程方法都过时了。

事实可能正好相反。

很多传统原则在 AI 环境下会变得更加重要。

---

## 小步修改

过去推荐小 Pull Request，是为了：

- 降低 Review 成本；
- 减少冲突；
- 提高回滚能力。

AI 时代更需要小步修改，因为 Agent 可以轻易一次产生过大变化。

---

## 自动化测试

过去测试用于防止人类引入回归。

现在还需要防止 Agent 快速放大错误。

---

## 清晰架构

AI 可以处理复杂代码，但这不意味着复杂架构没有代价。

相反，清晰模块边界能够：

- 限制 Agent 修改范围；
- 提高 Context Selection；
- 降低 Blast Radius；
- 改善 Evidence Coverage。

---

## 版本控制

Agent 生产速度越快：

- Commit；
- Branch；
- Worktree；
- Rollback；

越重要。

---

## 最小权限

安全工程中的 Least Privilege 原则，在 Agent 获得实际工具执行能力后会更加关键。

---

## 可观测性

如果 Agent 能够长时间运行，人类就更需要知道：

- 它在做什么；
- 为什么；
- 是否异常；
- 何时需要介入。

所以 AI 原生软件工程不是“传统工程 + AI 功能”。

更像是：

```text
Traditional Engineering Principles
        ×
New Agent Constraints
```

许多旧原则需要被重新解释，而不是被丢弃。

---

# 2.14 一个可能更准确的理论起点

因此，我们可以把 AI 原生软件工程的起点描述为：

> 软件工程的核心目标没有改变，但其运行环境改变了。

核心目标仍然是：

- 构建正确的软件；
- 控制复杂性；
- 降低风险；
- 支持协作；
- 保持可维护性；
- 让系统长期可演化。

变化的是：

> 参与完成这些目标的生产者不再只有人类。

因此，我们需要从：

```text
How do humans engineer software?
```

逐渐扩展到：

```text
How do humans engineer software
with intelligent execution systems?
```

这多出来的一层“with intelligent execution systems”，就是整本书后续内容所要处理的对象。

---

# 2.15 本章结论：不是旧软件工程失效，而是生产环境发生了变化

这一章讨论了七个过去长期相对稳定、今天开始受到挑战的操作性前提：

### 假设一

人类是软件生产的主要解释者和执行者。

### 假设二

生产速度大致不会长期超过人的理解速度。

### 假设三

执行工具的核心行为相对确定。

### 假设四

项目知识主要可以通过代码、文档和人类记忆维持。

### 假设五

团队规模受到人力和沟通成本的自然限制。

### 假设六

人工 Review 可以承担主要高层质量防线。

### 假设七

当前系统状态相对容易由人类整合和确定。

AI Agent 没有让这些假设在一夜之间全部失效。

它们仍然在大量项目中部分成立。

真正值得注意的是：

> 随着 Agent 自主执行范围增加，这些条件会一个接一个地变得不再可靠。

因此，软件工程需要新增一系列与这些变化对应的能力：

```text
生产者变化
→ Intent Engineering

知识结构变化
→ Context Engineering

状态复杂化
→ Truth Architecture

执行概率化
→ Agent Reliability

验证能力不足
→ Evidence Engineering

Review 失配
→ Review Engineering

生产速度失配
→ Cognitive Engineering

权限扩大
→ Governed Autonomy

执行者数量扩大
→ Multi-Agent Organization

长期参与
→ Memory Governance

能力持续变化
→ Self-Evolution Engineering

责任链拉长
→ Traceability and Accountability
```

这就是整本书接下来要展开的问题空间。

AI 原生软件工程并不是因为传统软件工程“不够先进”才出现。

它出现的原因更简单：

> 软件工程正在面对一种以前没有大规模存在过的生产者。

这种生产者能够理解语言、处理上下文、选择行动、使用工具和修改系统，同时又具有概率性、上下文依赖、不完整记忆和非人类责任结构。

当这样的执行者开始长期参与软件生产之后，我们不能只给它更好的 Prompt。

我们必须重新设计它所处的工程环境。

而在所有这些新问题中，最先需要解决的是：

> 人类到底怎样把“想要什么”表达成一个 Agent 能够可靠执行、又不至于自行漂移的工程对象？

这就是下一章要进入的主题：

**Intent Engineering。**

---

# 本章原则

## 原则一：把传统假设视为环境条件，而不是错误

传统软件工程是在不同生产环境中形成的成熟体系。

AI 原生软件工程是在其基础上的扩展。

## 原则二：生产者变化比工具能力变化更重要

判断是否需要新的工程机制，不应只看模型有多强，而应看 Agent 已经承担了多少解释和执行责任。

## 原则三：隐性组织知识必须逐渐显性化

Agent 无法天然获得团队默契、历史经验和隐含约束。

这些能力需要逐步进入：

- Context；
- Decision Record；
- Skill；
- Policy；
- Memory。

## 原则四：生产速度提升会重新分配瓶颈

生成更快以后，瓶颈可能转移到：

- Verification；
- Review；
- Cognition；
- Integration；
- Governance。

## 原则五：管理对象从软件扩展到“生产软件的智能系统”

AI 原生软件工程需要同时管理：

```text
Product System
+
Production Intelligence System
```

---

# 常见反模式

## 反模式一：把所有问题归因于模型不够强

很多失败来自：

- 错误 Context；
- 模糊 Intent；
- 过大 Scope；
- 权限失控；
- 证据不足；

而不是纯模型能力不足。

## 反模式二：认为模型越来越强以后治理自然不再需要

能力越强，潜在影响范围往往越大。

更强执行能力通常意味着更高治理要求，而不是更低。

## 反模式三：继续依赖团队默契管理 Agent

人类可以理解暗示，Agent 未必拥有相同背景。

重要隐含规则需要显式化。

## 反模式四：用更多 Agent 直接解决产能问题

如果 Context、Handoff 和 Review 没有准备好，更多 Agent 可能只会增加冲突和认知负担。

## 反模式五：认为测试通过等于生产链可信

测试只是 Evidence 的一部分。

错误 Intent 下的正确实现同样可以通过测试。

---

# 本章检查清单

当一个项目开始大量使用 Agent 时，可以检查以下问题：

- Agent 是否已经自行解释需求？
- Agent 是否自行决定重要执行路径？
- Agent 是否会修改多个模块？
- Agent 是否使用项目长期 Context？
- Agent 是否会调用其他 Agent？
- Agent 是否拥有写文件、运行命令或 Git 权限？
- Agent 是否可以在没有逐步人工确认的情况下持续执行？
- 人类是否还能理解主要改动？
- 项目是否存在 Agent 专用 Memory 或 Skill？
- Agent 是否可能使用过期信息？
- 当前事实、未来意图和 Assumption 是否明确区分？
- Review 是否仍然主要依赖人工读 Diff？
- 自动测试是否能够覆盖主要风险？
- 多 Agent 是否有明确责任和 Handoff？
- 出现错误时能否重建 Agent 当时使用的 Context 与执行路径？

如果越来越多答案是“是”或“不能确定”，项目面对的就已经不再只是传统 AI Coding 问题。

它正在进入 AI 原生软件工程的问题空间。
