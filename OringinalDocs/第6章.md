# 第6章  
# Truth and State Architecture：在 Intent、Code、Runtime 与 Assumption 之间建立事实秩序

上一章讨论了 Context Engineering。

Context Engineering 解决的是：

> Agent 为了完成当前 Intent，应该看到什么信息？

但信息进入 Context 以后，还有一个更困难的问题：

> **这些信息里面，什么才是真的？**

一份文档说系统使用方案 A。

当前代码实现的是方案 B。

运行时截图看起来又像方案 C。

测试依然按照旧行为验证。

项目 Memory 里记录着三个月前的一次结论。

当前 Worktree 还有一组尚未提交的修改。

如果 Agent 同时看到这些信息，它面对的并不是“信息不足”，而是：

> **多个彼此冲突的现实版本。**

人类长期参与一个项目时，往往能够通过经验判断：

“那份文档已经旧了。”

“这个 Branch 只是实验。”

“代码虽然写成这样，但生产环境还没有部署。”

“这个决定已经被后来的会议推翻。”

这些判断过去大量依赖 Human Smoothing Effect。

Agent 也可能正确判断。

但软件工程不能把：

> “模型大概会判断对”

作为长期系统的事实管理机制。

因此，AI-Native Software Engineering 在 Intent 和 Context 之后，需要建立第三个基础层：

# Truth and State Architecture

它解决的不是哲学意义上的“什么是真理”。

它解决的是一个非常工程化的问题：

> **在一个不断变化的软件项目中，当多个信息源对当前状态给出不同描述时，系统如何确定哪些 Claim 可以被当前任务作为可靠事实使用。**

---

# 6.1 “Code as Truth”是一个起点，而不是终点

在 AI Game Dev OS 的早期原则中，一个非常有价值的规则是：

> **Doc as Intent, Code as Truth。**

它解决了一个现实问题。

很多 Agent 在进入项目以后，会优先依赖语言清晰、结构完整的设计文档。

但文档可能描述的是：

- 原始设计；
- 未来方案；
- 已废弃方向；
- 尚未实现的目标。

如果 Agent 把这些内容当成当前现实，就容易出现：

> 根据“应该是什么”修改“实际是什么”。

所以：

```text
Doc
→ Intent

Code
→ Current Implementation
```

是一个非常有效的初始原则。

但随着系统变复杂，我们会发现：

> **Code 也不是全部 Truth。**

---

# 6.2 代码可以正确，却不代表系统实际这样运行

例如代码中写着：

```text
feature_enabled = true
```

但 Production 中：

```text
Feature Flag = false
```

那么用户实际看到的行为由：

> Runtime Configuration

决定。

又例如：

代码已经支持 Save Schema v4。

但当前线上数据库仍然是：

> Schema v3。

那么：

```text
Code Capability
≠
Operational State
```

再比如：

代码里某个函数已经被修改。

但构建服务器部署的仍然是上一个 Commit。

当前运行的真实软件并不包含这次变化。

所以：

> Code 更准确地说是 **Implementation Truth**。

它描述：

> 当前代码库实现了什么。

而不是：

> 整个系统此刻实际上处于什么状态。

---

# 6.3 Truth 是分领域的

因此，本书不建议建立一个简单的：

```text
One Source of Truth
```

然后假设所有问题都可以由一个来源回答。

更合理的是：

> **Truth is domain-scoped。**

不同问题需要不同的权威来源。

例如：

### “当前代码实现是什么？”

Authority：

> Current Repository State

### “当前用户实际运行什么版本？”

Authority：

> Deployment / Runtime State

### “数据库当前是什么 Schema？”

Authority：

> Database Metadata / Migration State

### “这个功能现在应该怎样工作？”

可能需要：

> Approved Intent / Decision

### “这次任务从哪个状态开始？”

Authority：

> State Snapshot

因此：

> **Source of Truth 应该按照 Truth Domain 定义。**

---

# 6.4 Truth Domain

可以把软件项目中的 Truth 粗略分成几个 Domain。

```text
Implementation Truth
Runtime Truth
Data Truth
Configuration Truth
Environment Truth
Decision Truth
Evidence Truth
```

不同 Domain 回答不同问题。

---

## Implementation Truth

描述：

> 当前代码和资产实际是什么。

来源可能包括：

- Git；
- Repo；
- Scene；
- Config file；
- Asset metadata。

---

## Runtime Truth

描述：

> 软件实际运行时发生什么。

来源：

- Runtime observation；
- Logs；
- Screenshot；
- Telemetry；
- Runtime inspection。

---

## Data Truth

描述：

> 当前数据状态是什么。

来源：

- Database；
- Save file；
- Migration record；
- Data snapshot。

---

## Configuration Truth

描述：

> 当前实际启用的配置是什么。

例如：

- Feature Flag；
- Environment Config；
- Server Setting；
- Build Flag。

---

## Environment Truth

描述：

> 当前执行环境是什么。

例如：

- OS；
- Dependency Version；
- Engine Version；
- Hardware；
- Deployment Region。

---

## Decision Truth

这个名称需要谨慎。

Decision 不是“自然事实”。

它表达：

> **当前组织已经授权采用的规则或方向。**

例如：

> “SP122 当前不得重新设计 HP / Block。”

这是一个 Approved Decision。

它不描述世界物理状态。

但在生产体系里，它具有：

> Normative Authority。

---

## Evidence Truth

描述：

> 哪些现象已经被直接观察或验证。

例如：

- Test passed；
- Screenshot shows overlap；
- Benchmark = 4.7ms。

它通常是其他 Truth Claim 的重要支撑。

---

# 6.5 Descriptive Truth 与 Normative Truth

这一点值得进一步区分。

软件项目中的 Claim 可以粗略分成：

## Descriptive

描述：

> 世界现在是什么。

例如：

> 当前 Runtime 使用 Save Schema v3。

---

## Normative

描述：

> 系统现在应该遵守什么。

例如：

> 当前 Sprint 禁止修改 Save Schema。

前者是：

> State。

后者是：

> Decision / Policy。

如果两者混合，就容易出现：

> 把“应该怎样”误认为“已经怎样”。

这正是：

> Doc as Intent, Code as Truth

最初要解决的问题之一。

---

# 6.6 Intent、Decision、Truth 与 Assumption 必须分开

到这里，可以正式建立四类信息。

```text
Intent
Decision
Truth
Assumption
```

它们分别回答不同问题。

---

## Intent

> 我们希望未来达到什么状态？

例如：

> Stage 信息需要更容易识别。

---

## Decision

> 当前已经批准采用什么规则或方案？

例如：

> HP / Block 已接受，不在本任务重做。

---

## Truth

> 当前可以验证的现实状态是什么？

例如：

> 当前 Commit 中 HP / Block 使用 v008b icon。

---

## Assumption

> 当前尚未验证，但执行暂时需要采用什么工作假设？

例如：

> Stage 读取问题主要来自视觉层级，而不是数据语义。

---

四者不能互相静默转化。

尤其不能：

```text
Assumption
→ silently become
Truth
```

也不能：

```text
Intent
→ silently become
Current State
```

---

# 6.7 Claim-based Architecture

一个更成熟的 Truth System 不应该只管理文档。

它应该管理：

> **Claims。**

也就是：

> 关于系统的一条可判断陈述。

例如：

```text
Claim:
Player Status runtime uses Stage layout v017.
```

这条 Claim 可以拥有：

```text
Type
Domain
Source
Timestamp
Scope
Status
Evidence
Owner
```

于是系统不再只是：

> “这里有一个 Markdown 文件。”

而是知道：

> 这个文件中包含一条关于 Runtime State 的 Claim。

---

# 6.8 Truth Claim 的基本结构

可以设计：

```text
Claim ID:
Statement:

Type:
- Truth
- Decision
- Intent
- Assumption

Domain:
- Implementation
- Runtime
- Data
- Configuration
- Policy

Source:
Owner:
Timestamp:
Version:
Scope:

Evidence:
Confidence:
Status:
```

其中 Status 可以包括：

```text
Verified
Observed
Approved
Unverified
Superseded
Stale
Rejected
```

这就比：

> 一堆自然语言文档

更容易被 Agent 正确消费。

---

# 6.9 Provenance 是 Truth Architecture 的基础

第五章已经讨论 Context Provenance。

在 Truth Architecture 中，Provenance 的意义更进一步。

它回答：

> 为什么我们相信这条 Claim？

例如：

```text
Claim:
Current HUD height is 118 px.

Source:
runtime capture measurement

Commit:
abc123

Timestamp:
2026-08-10

Status:
Observed
```

和：

```text
Claim:
Current HUD height is 118 px.

Source:
old design note

Timestamp:
2026-05-01
```

两者文字相同。

权威程度完全不同。

因此：

> **Truth cannot be separated from provenance。**

---

# 6.10 Authority 不等于 Confidence

模型可以说：

> “我有 95% 把握。”

这并不让一个 Claim 成为 Truth。

真正重要的是：

- Source；
- Evidence；
- Scope；
- Freshness；
- Ownership。

所以：

```text
Model Confidence
≠
Engineering Authority
```

这与上一章的 Context Confidence 原则一致。

---

# 6.11 Truth Hierarchy：冲突时应该相信谁

当多个来源冲突时，需要：

> Conflict Resolution Policy。

最简单的方法是建立：

> Truth Hierarchy。

例如：

```text
Direct Runtime Observation
        >
Executable Verification
        >
Current Repository State
        >
Approved Decision Record
        >
Current Documentation
        >
Historical Documentation
        >
Agent Assumption
```

但这个排序不能被当成全项目绝对真理。

因为不同 Domain 有不同优先级。

---

# 6.12 为什么不能只有一个全局 Truth Hierarchy

例如：

“当前 API 代码是什么？”

当然：

> Code > Documentation。

但问题：

“当前 API 应不应该继续保持兼容？”

答案可能来自：

> Approved Product Decision。

Runtime 无法回答这个问题。

因此：

> Truth Hierarchy 必须 Domain-aware。

---

# 6.13 Authority Matrix

一个更实用的设计是：

> Authority Matrix。

例如：

| Question | Primary Authority | Secondary Evidence |
|---|---|---|
| 当前实现 | Repo / Commit | Static analysis |
| 当前运行行为 | Runtime | Logs / Capture |
| 当前数据版本 | DB / Save Metadata | Migration records |
| 当前产品目标 | Approved Intent | Decision record |
| 当前工程约束 | Approved Policy | Project rules |
| 当前任务基线 | State Snapshot | Git status |
| 历史原因 | Decision Record | Archive |

这样：

> 不同问题有不同 Source of Truth。

---

# 6.14 Source of Truth 应该回答一个问题，而不是统治整个项目

软件团队常说：

> “Git 是 Source of Truth。”

这句话只有在明确 Domain 时才准确。

Git 可以是：

> Implementation Truth 的 Source of Truth。

但它通常不是：

- 用户运行状态；
-数据库实时状态；
- 当前 Feature Flag；
- 产品方向；
-法律要求；

的 Source of Truth。

所以更严谨的表达是：

> **Source of Truth is always scoped to a question.**

---

# 6.15 Current State 是一个组合对象

一个软件任务真正需要的“当前状态”通常不是一个值。

而是一组状态：

```text
Current State

├── Repository State
├── Branch / Worktree
├── Runtime Version
├── Data Version
├── Configuration
├── Dependency Versions
├── Active Decisions
└── Open Assumptions
```

这可以称为：

> **State Model。**

---

# 6.16 State Architecture

State Architecture 解决：

> AI 执行任务时，哪些状态必须显式存在并保持一致？

例如：

一个 Coding Worker 的 State 可能包含：

```text
Repo commit
Branch
Worktree
Dirty files
Build status
Dependency versions
Related feature flags
```

而一个 Art Worker 的 State 可能包含：

```text
Accepted art direction
Current source asset
Runtime target size
Export settings
Review version
```

State 同样具有 Role 和 Task Scope。

---

# 6.17 State Boundary

在前面 Tight Boundaries 中，我们已经提出：

> State Boundary。

它解决：

> Agent 被允许基于哪个状态开始工作？

例如：

```text
Baseline Commit:
10da1ef3

Allowed Worktree:
SP122-player-status

Known Dirty Changes:
SP120 / SP121 unrelated

Do not assume:
main branch contains local experimental art
```

这类信息非常重要。

因为 Agent Failure 经常不是逻辑错误，而是：

> 在错误基线上正确执行。

---

# 6.18 Baseline 是 AI 执行的重要概念

任何需要比较变化的任务，都需要：

> Baseline。

例如：

### Refactor

Baseline：

> 当前 tests / behavior。

### Performance

Baseline：

> 修改前 Benchmark。

### UI

Baseline：

> 当前 runtime capture。

### Migration

Baseline：

> 当前 schema / data sample。

没有 Baseline：

Agent 很难证明：

> 自己真的改善了什么。

因此：

> **Baseline 既属于 State Architecture，也属于 Evidence Planning。**

---

# 6.19 State Snapshot

对于长任务、并行任务或跨 Thread 工作，需要把当前状态冻结成一个可引用对象。

例如：

```text
Snapshot ID:
STATE-SP122-017

Intent:
INT-SP122-003 v2

Commit:
abc123

Branch:
sp122-player-status

Worktree:
clean within task scope

Runtime:
Godot 4.x build xyz

Active Decisions:
- HP / Block accepted
- HUD height locked

Open Assumptions:
- Stage issue mainly visual

Pending:
- Stage top layout review
```

这就是：

> State Snapshot。

---

# 6.20 Snapshot 的目标不是复制整个项目

Snapshot 不需要保存：

- 全部 Repo；
- 全部聊天；
- 全部日志。

它只保存：

> 重新建立执行状态所需的关键引用和 Claim。

所以：

```text
Snapshot
=
State Index
+
Critical Claims
+
References
```

而不是：

```text
Snapshot
=
Archive Copy
```

---

# 6.21 Snapshot 与 Context Snapshot 不完全相同

Context Snapshot 回答：

> Agent 当时看到了什么？

State Snapshot 回答：

> 项目当时处于什么状态？

两者有大量重叠。

但概念上最好区分。

例如：

Agent 没有读取某个 Server Flag。

这个 Flag：

> 属于 State。

但不属于：

> 当时 Agent Context。

如果以后调查错误，这个区别非常关键。

---

# 6.22 Execution Snapshot

进一步可以定义：

> Execution Snapshot。

它由：

```text
Intent Version
+
State Snapshot
+
Context Pack Version
+
Agent Contract
+
Policy Version
+
Tool / Model Version
```

组成。

它回答：

> 这个 Agent 在什么目标、现实和规则下执行了这次任务？

这对：

- Debug；
- Audit；
- Regression；
- Reproduction；

都很重要。

---

# 6.23 AI-native 的“可复现”不一定是输出完全一致

传统确定性软件中，可复现通常意味着：

> 相同输入产生相同输出。

Agent 具有概率性。

所以我们未必能要求：

> 完全重现每一步推理和输出。

但至少应该能够重建：

```text
Intent
State
Context
Policy
Tools
Evidence
```

也就是：

> **Decision Environment Reproducibility。**

---

# 6.24 Reproducible Environment 比 Reproducible Reasoning 更现实

这是一个重要原则。

不要追求：

> 复刻 Agent 每一步内部 reasoning。

更现实的目标是：

> 能够重建影响其行为的外部工程环境。

这与：

> Contract over Reasoning Process

完全一致。

---

# 6.25 Decision Architecture：为什么决定也必须成为工程对象

前面一直提到 Decision。

为什么 Decision 不能只存在于聊天和会议记录里？

因为长期项目中的很多当前状态，都只能通过历史决定解释。

例如：

代码中保留了一个看起来多余的兼容层。

如果没有 Decision Record：

Agent 可能判断：

> 这是 Legacy Debt，应该删除。

实际原因可能是：

> 未来两个版本必须兼容旧 Save。

因此：

> Decision 是连接 Intent、Truth 与未来执行的重要桥梁。

---

# 6.26 Decision 不是 Truth，但可以拥有 Authority

Decision：

> 不一定描述客观状态。

但它可以规定：

> 当前生产系统应该怎样行动。

例如：

```text
Decision:
Do not modify public save schema before v1.0.
```

它拥有：

> Governance Authority。

所以：

```text
Truth
→ describes reality

Decision
→ constrains future action
```

两者需要明确分离。

---

# 6.27 Decision Record

一个成熟 Decision Record 可以包含：

```text
Decision ID
Statement
Owner
Date

Context
Options Considered
Chosen Option
Reason

Trade-offs
Scope
Effective Version
Supersedes
Review Condition
```

这与传统 ADR 很接近。

AI-native 环境中，其价值更大。

因为 Agent 无法自动拥有：

> “大家都知道当时为什么这么决定。”

---

# 6.28 Rejected Options 也应该被记录

很多项目只记录：

> 最终采用什么。

但 Agent 很可能重新提出：

> 已经被否决过的方案。

如果不记录 Why：

它会不断重新探索同一个死胡同。

因此 Decision Record 还应保留：

```text
Rejected Option
Reason
Conditions under which it may be reconsidered
```

注意：

> 被否决不代表永远错误。

它可能只是在当前条件下不适合。

---

# 6.29 Superseded Decision

Decision 也会失效。

例如：

```text
DEC-001:
Use system A.
```

后来：

```text
DEC-014:
Migrate to system B.
Supersedes DEC-001.
```

如果 Archive 中两个 Decision 都存在，但 Agent 不知道：

> 哪个 Active，

就会产生 Context Conflict。

因此 Decision 需要：

```text
Active
Superseded
Deprecated
Temporary
```

等状态。

---

# 6.30 Decision Freshness

Decision 不是因为“历史上被批准”就永远有效。

某些决定绑定：

- Version；
- Sprint；
- Platform；
- Feature；
- Risk condition。

例如：

> “当前 Sprint 不重构 Combat。”

Sprint 结束后它可能自动失效。

因此 Decision 也有：

> Scope + Expiry。

---

# 6.31 Assumption Layer：允许系统在不知道时继续工作

现实工程中，Agent 不可能每次都拥有全部事实。

如果任何未知都必须停止：

> 系统会非常低效。

如果所有未知都让 Agent 自己猜：

> 系统会非常危险。

因此需要中间层：

# Assumption Layer

也就是：

> 显式管理未验证但暂时允许使用的工作假设。

---

# 6.32 一个好的 Assumption 至少包含什么

```text
Assumption ID
Statement
Source
Reason
Confidence
Impact
Validation Method
Expiry
Owner
```

例如：

```text
Assumption:
Stage readability issue is primarily visual.

Reason:
current data appears correct;
runtime capture shows hierarchy problem.

Impact:
medium

Validation:
compare two layout prototypes.

Expiry:
before final SP122 acceptance.
```

---

# 6.33 Assumption 应当有风险等级

不是所有 Assumption 风险相同。

例如：

### Low Impact

> 这个私有函数没有外部调用。

可以通过搜索快速验证。

### Medium Impact

> UI 问题只存在于当前分辨率。

需要多分辨率测试。

### High Impact

> 数据迁移不会影响旧用户。

如果没有强证据：

> 不应该允许直接执行。

因此：

> Assumption 使用权限应该由 Impact 决定。

---

# 6.34 High-risk Assumption 不应该作为执行基础

可以定义：

```text
Low-risk assumption
→ execute + validate

Medium-risk assumption
→ explicit checkpoint

High-risk assumption
→ block / human decision
```

这与 Risk-based Autonomy 一致。

---

# 6.35 Assumption Promotion

一条 Assumption 经过验证以后，可以：

```text
Assumption
    ↓ Evidence
Verified Claim
```

例如：

```text
Assumption:
Bug only occurs at 16:9.

Test:
16:9 fail
21:9 pass
4:3 pass

→ Observed Claim
```

但这个升级必须显式。

---

# 6.36 Assumption Rejection

如果验证失败：

```text
Assumption
→ Rejected
```

并且依赖它的：

- Plan；
- Context；
- Decision；

可能需要重新评估。

这说明 Assumption 也存在：

> Dependency。

---

# 6.37 Derived Truth

一些 Truth 不是直接观察得到。

而是根据多个 Claim 推导。

例如：

```text
Test A passed
Test B passed
Runtime state correct
```

因此我们得出：

> Feature is compatible with v3 save.

这属于：

> Derived Claim。

它应该保存：

> Supporting Evidence。

否则以后只看到：

> compatible = true

却不知道为什么相信。

---

# 6.38 Observed、Verified 与 Derived 应区分

可以定义几个状态。

### Observed

直接观察。

### Verified

经过明确验证规则确认。

### Derived

由其他 Truth / Evidence 推导。

### Assumed

尚未验证。

这比简单：

```text
True / False
```

更符合软件工程现实。

---

# 6.39 Evidence 与 Truth 的关系

Evidence 不是 Truth 本身。

Evidence 是：

> 支持 Truth Claim 的材料。

例如：

```text
Evidence:
runtime screenshot
```

支持：

```text
Claim:
UI overlaps at 1920x1080.
```

所以：

```text
Evidence
→ supports
Claim
```

而不是：

```text
Evidence = Claim
```

---

# 6.40 Evidence 也可能过期

例如：

一张 Screenshot 证明：

> v017 存在重叠。

代码更新到 v018 后：

这张截图仍然是有效历史 Evidence。

但不能继续证明：

> 当前版本仍然重叠。

因此 Evidence 也必须绑定：

- Version；
- State；
- Time。

---

# 6.41 Truth Freshness

Truth Claim 和 Context 一样，也会随时间失效。

例如：

```text
Claim:
Current build passes all tests.
```

这条 Claim 的寿命可能只有：

> 当前 Commit。

一旦代码改变：

它就应该：

> Expire。

因此可以定义：

```text
Truth Scope
+
Validity Window
```

---

# 6.42 Event-driven Invalidation

成熟系统可以在关键事件发生时自动失效相关 Claim。

例如：

```text
Code changed
↓
previous build-pass claim stale
```

或者：

```text
Schema migration
↓
old data compatibility claim requires revalidation
```

这就是：

> Truth Invalidation。

---

# 6.43 Truth Dependency Graph

如果系统复杂，可以进一步建立：

```text
Claim A
depends on
Claim B + Evidence C
```

当 B 失效：

A 自动：

> needs revalidation。

这可以称为：

> Truth Dependency Graph。

这不是所有项目都需要。

但在高风险长期 Agent 系统中很有价值。

---

# 6.44 State Transition

State 不只是 Snapshot。

项目持续变化：

```text
State A
↓ Change
State B
↓ Change
State C
```

每一次变化都应该能够回答：

> 什么改变了状态？

可以表示为：

```text
Previous State
+
Change Set
+
Decision
+
Evidence
→
New State
```

这就是：

> State Transition。

---

# 6.45 Agent 执行也是 State Transition

Agent Task 不应该只被记录成：

> “Done。”

更准确是：

```text
Input State
↓
Agent Execution
↓
Change
↓
Verified Output State
```

如果 Output State 没有被验证：

任务只完成了：

> Change。

而不是：

> Verified State Transition。

---

# 6.46 State Transition 与 Git Commit 的关系

Git Commit 是非常强的 Implementation State Transition。

它记录：

- 文件变化；
- Parent；
- Commit ID。

但它无法完整记录：

- Runtime；
- Data；
- Deployment；
- Decision；
- Evidence。

因此 AI-native 环境中可能需要：

```text
Commit
+
State Metadata
+
Evidence
+
Intent Link
```

形成更完整的 Transition Record。

---

# 6.47 Dirty State 是 Agent 系统必须正式处理的问题

人类开发者看到：

```text
git status
```

通常能理解：

> 哪些改动是自己刚才做的。

Agent Worker 如果进入一个脏 Worktree：

可能不知道：

- 哪些属于当前任务；
- 哪些来自其他 Agent；
- 哪些是实验；
- 哪些不能覆盖。

因此：

> Dirty State 必须被显式处理。

策略可能包括：

- Block；
- Snapshot；
- Isolate；
- Declare unrelated changes。

---

# 6.48 Worktree 是 State Boundary 的实现之一

这一点可以和前面的 Agent Harness 章节连接。

Worktree 的价值不只是：

> 并行方便。

它实际上建立了：

> Implementation State Boundary。

让 Worker 拥有相对独立的：

```text
Filesystem State
Branch State
Change Set
```

但它不自动解决：

- Goal Boundary；
- Decision；
- Evidence；
- Context。

所以：

> Worktree 是 State Architecture 的机制之一，而不是完整 State Architecture。

---

# 6.49 Configuration Drift

很多系统问题来自：

> Code 一样，Configuration 不一样。

例如：

Developer：

```text
FeatureFlag = on
```

Production：

```text
FeatureFlag = off
```

Agent 如果只读取 Repo：

> 会建立错误现实。

因此 Configuration State 必须进入高风险 Context。

---

# 6.50 Environment Drift

同样：

```text
Dependency v1.8
vs
Dependency v2.0
```

或者：

```text
Windows
vs
Linux
```

都可能改变行为。

因此 Runtime Truth 和 Environment Truth 不应被代码完全替代。

---

# 6.51 Data State 是最高风险的 Truth Domain 之一

代码可以回滚。

数据变化有时不可逆。

因此涉及：

- Migration；
- Save；
- Database；
- User Data；

的任务，需要更严格 State Snapshot。

至少包括：

```text
Schema Version
Data Version
Backup
Migration History
Rollback Capability
```

---

# 6.52 State Readiness Gate

在执行高风险任务前，可以设置：

```text
Baseline identified?
State current?
Dirty changes understood?
Runtime version known?
Data version known?
Config known?
Active decisions loaded?
High-risk assumptions unresolved?
```

如果其中关键项失败：

> 不应该直接执行。

---

# 6.53 Truth Readiness Gate

类似地：

```text
Critical claims verified?
Sources authoritative?
Conflicts resolved?
Stale claims detected?
Assumptions explicit?
```

这形成：

> Truth Readiness Gate。

---

# 6.54 Conflict Resolution Pattern 1：Authority-based

最直接的模式：

> 高 Authority Source 优先。

例如：

```text
Runtime
>
old documentation
```

适合：

- 简单冲突；
- Domain 明确。

---

# 6.55 Pattern 2：Freshness-based

如果 Source Authority 类似：

> 更新的版本优先。

但前提是：

> 新信息没有被明确否决。

---

# 6.56 Pattern 3：Evidence-based

多个 Claim 冲突时：

> 证据强度更高者优先。

例如：

一份设计文档写：

> 没有重叠。

实际 Runtime Screenshot 显示：

> 有重叠。

Observed Runtime 更强。

---

# 6.57 Pattern 4：Human Arbitration

高影响冲突不应自动解决。

例如：

Product Decision 与 Security Policy 冲突。

Agent 不应：

> 自己选一个。

需要：

> Human / Authorized Role Arbitration。

---

# 6.58 Pattern 5：Preserve Conflict

有些冲突暂时无法解决。

不要强行压成一个答案。

可以保存：

```text
Claim A
conflicts with
Claim B

Status:
Unresolved
```

然后限制：

> 依赖该事实的任务不能越过特定 Gate。

这比模型“选一个最合理的”更安全。

---

# 6.59 Truth Resolution 不应该隐藏不确定性

这是很重要的一点。

系统目标不是：

> 永远给 Agent 一个确定答案。

而是：

> 清楚地区分确定和不确定。

例如：

```text
Verified:
Current code uses v3 loader.

Unknown:
Production users still on which save versions.

Assumption:
Most active saves are v3.
```

这种状态比：

> “系统使用 v3。”

更可靠。

---

# 6.60 Truth Compression 的风险

与 Context Compression 一样，Truth Summary 也可能破坏信息。

例如原始状态：

```text
Decision:
Use A temporarily until migration B completes.
```

被总结成：

> Use A.

临时条件消失。

因此 Truth Summary 应保留：

- Scope；
- Condition；
- Expiry；
- Source。

---

# 6.61 Snapshot 应优先保存结构化 Claim，而不是散文摘要

例如：

较弱：

> 当前基本上已经迁移到新版系统，还有几个旧地方没处理。

更强：

```text
Implementation:
v3 migration code active

Pending:
legacy loader still referenced by X

Decision:
do not remove legacy loader before SP130

Evidence:
test suite A passes
```

结构化状态更适合 Agent 继续执行。

---

# 6.62 State Index

长期项目可以建立：

> State Index。

它不是全文 Archive。

而是告诉系统：

- 当前主要模块状态；
- Active Intent；
- Active Decision；
- Runtime Version；
- Snapshot；
- Open Risk。

这样 Agent 冷启动时先获得：

> 当前状态地图。

再按需下钻。

---

# 6.63 AI Game Dev OS 中的 State / Truth 原型

结合前面已经讨论过的 Context 架构，可以看到一个初步结构：

```text
Doc Hotspace
→ Active Intent / Working Docs

Code / Repo
→ Implementation Truth

Runtime Capture / Evidence
→ Behavioral Truth

Sprint Snapshot
→ State Summary

Decision / Handoff
→ Authorized Direction

Archive
→ Historical Sources

Memory
→ Compressed Retrieval Entry
```

这已经具备 Truth / State Architecture 的一些雏形。

但要进入更成熟阶段，还需要：

- Typed Claim；
- Authority；
- Freshness；
- Superseded State；
- Assumption；
- Invalidation；
- Domain-specific Source of Truth。

---

# 6.64 “Code as Truth”应升级为什么

因此，随着体系成熟，可以把：

> Code as Truth

升级成更精确的版本：

> **Code as Implementation Truth。**

同时：

```text
Runtime
→ Behavioral Truth

Data
→ Operational Data Truth

Approved Decision
→ Normative Authority

Doc
→ Intent / Explanation

Assumption
→ Unverified Working Claim
```

这样比单一：

> Code is Truth

更完整。

---

# 6.65 为什么仍然值得保留“Doc as Intent, Code as Truth”

因为这句原则非常适合作为：

> 简单默认规则。

在没有更复杂 Truth Architecture 时，它能显著降低 Agent 被旧文档带偏的风险。

所以不需要废弃。

更合理的方式是：

```text
Simple Rule:
Doc as Intent, Code as Truth

Advanced Rule:
Domain-scoped Truth Architecture
```

前者是：

> Default Heuristic。

后者是：

> Mature Engineering Model。

---

# 6.66 Truth Architecture Pattern 1：Code-centric

最简单模式：

```text
Code
=
Primary Truth
```

文档只作为辅助。

适合：

- 小型代码项目；
- Runtime 状态简单；
- 无复杂部署和数据。

优点：

- 简单；
- 容易实现。

缺点：

- 无法处理 Runtime / Data / Config 差异。

---

# 6.67 Pattern 2：Evidence-backed Code Truth

结构：

```text
Code
+
Tests
+
Runtime Evidence
```

适合：

> 普通 Agentic Software Development。

它比单纯 Code-centric 更强，因为：

> 当前代码必须经过执行验证。

---

# 6.68 Pattern 3：Domain-scoped Truth

结构：

```text
Implementation → Repo
Runtime        → Deployment / Observation
Data           → DB
Decision       → Decision Registry
Intent         → Intent Registry
```

这是更成熟的软件项目模式。

---

# 6.69 Pattern 4：Snapshot-driven State

适合：

- 长任务；
- 多 Agent；
- Worktree；
- Sprint。

核心：

```text
Current State Snapshot
↓
Task
↓
New Verified Snapshot
```

---

# 6.70 Pattern 5：Claim / Evidence Graph

更成熟系统可以建立：

```text
Claim
↓ supported by
Evidence
↓ scoped by
State / Version
↓ linked to
Decision / Intent
```

适合：

- 高风险；
- 长生命周期；
- 企业软件；
- 复杂 Agent organization。

---

# 6.71 Pattern 6：Governed Truth Resolution

最终可以根据：

```text
Question
Domain
Sources
Authority
Freshness
Evidence
Policy
```

自动得到：

```text
Resolved Claim
or
Unresolved Conflict
```

重要的是：

> 系统允许输出“无法确定”。

---

# 6.72 Truth Architecture 的成熟度

可以粗略分成：

## Level 0 — Implicit

Agent 自己判断。

---

## Level 1 — Code-centric

Code as Truth。

---

## Level 2 — Evidence-backed

Code + Test + Runtime。

---

## Level 3 — Typed Truth Domains

区分：

- Implementation；
- Runtime；
- Data；
- Decision；
- Intent；
- Assumption。

---

## Level 4 — Governed State

拥有：

- Provenance；
- Authority Matrix；
- Snapshot；
- Freshness；
- Invalidation。

---

## Level 5 — Adaptive Truth Resolution

按：

- Question；
- Domain；
- Risk；

动态解析 Authority，并暴露 unresolved conflict。

---

# 6.73 Truth Debt

与 Context Debt 类似，长期项目还可能出现：

> **Truth Debt。**

可以工作性定义为：

> 项目中大量 Claim 已经无法确定是否仍然有效，导致当前状态越来越依赖人工经验重新解释。

例如：

- 不知道哪个文档有效；
- 不知道哪个 Snapshot 最新；
- 多个 Decision 冲突；
- Runtime 与 Code 不一致却没有记录；
- Memory 保留旧状态；
- Assumption 已经长期未验证。

这种系统的危险不是：

> 没有信息。

而是：

> 信息很多，但无法快速判断哪个是真的。

---

# 6.74 Truth Debt 与 Context Debt 的区别

### Context Debt

问题：

> 信息没有被正确管理。

### Truth Debt

问题：

> 当前事实无法被快速、可靠确定。

两者相关，但不同。

Context Debt 可能导致 Truth Debt。

---

# 6.75 State Debt

还可以观察另一类现象：

> 系统长期没有可靠 Snapshot。

结果：

每次 Agent 开始任务，都要：

- 扫 Git；
- 查文档；
- 问历史；
- 重新建立状态。

这是一种：

> State Reconstruction Cost。

是否需要单独定义 State Debt，可以暂时保持谨慎，不必急着扩展术语。

更重要的是：

> Snapshot 的缺失会显著增加长期 Agent 成本。

---

# 6.76 Truth Architecture 与 Cognitive Engineering

如果 Truth 层混乱，人类 Review 也会受到影响。

Reviewer 可能花大量时间判断：

> 到底哪个版本才是真的。

因此良好的 Truth Architecture 同时降低：

- Agent Context Cost；
- Human Cognitive Load。

---

# 6.77 Truth Architecture 与 Memory Engineering

Memory 不应该直接保存：

> “当前事实永远是 X。”

更合理：

```text
Claim
Source
Version
Scope
Status
```

尤其是：

> Current state

类 Memory。

因为它们最容易过期。

---

# 6.78 Truth Architecture 与 Self-Evolution

Self-Evolution 更依赖 Truth。

系统要从过去经验中提取规则，首先必须知道：

- 什么真的成功；
- 什么只是偶然；
- 当时环境是什么；
- 哪个 Assumption 后来被否决。

如果历史事实不可靠：

> Self-Evolution 会学习错误经验。

因此：

> **Truth Governance 是 Self-Evolution 的前置条件。**

---

# 6.79 Truth Architecture 与 Agent Organization

不同 Agent 不能各自拥有一套现实。

否则：

```text
Controller Truth A
Worker Truth B
Reviewer Truth C
```

组织无法稳定工作。

因此多 Agent 应尽量：

```text
Shared Truth
+
Role-specific Context
```

而不是：

```text
Role-specific Reality
```

这是非常重要的区别。

---

# 6.80 Shared Truth, Local Context

可以把这个原则概括为：

> **Shared Truth, Local Context。**

也就是：

> 关键事实应尽量共享一致；不同 Agent 只对相关 Context 做局部投影。

例如：

所有 Agent 都应该一致知道：

> 当前基线 Commit 是 abc123。

但 UI Worker 不需要知道：

> Server Deployment Details。

---

# 6.81 State Authority 与 Agent Authority 分离

Agent 可能发现：

> 当前文档和 Runtime 不一致。

它可以：

- 报告；
- 收集 Evidence；
- 提出 Resolution。

但不一定拥有：

> 修改正式 Truth Registry

的权限。

因此：

```text
Can observe state
≠
Can declare authoritative state
```

重要 Truth Promotion 可能需要：

- Tool；
- CI；
- Reviewer；
- Human；
- Authorized Controller。

---

# 6.82 Truth Write Permission

成熟系统甚至可以对不同 Truth Domain 规定谁能写。

例如：

| Domain | Authoritative Writer |
|---|---|
| Implementation | Git / Merge |
| Runtime | Monitoring / Runtime Tool |
| Data Schema | Migration System |
| Decision | Authorized Human / Gate |
| Intent | Intent Owner |
| Assumption | Agent / Human |
| Evidence | Test / Tool / Reviewer |

这就是：

> Truth Write Permission。

---

# 6.83 Agent 可以创建 Claim，但不自动创建 Truth

这是一个很好的设计原则：

```text
Agent
→ creates Claim

Evidence / Authority
→ promotes Claim

Registry
→ records Truth status
```

不要：

```text
Agent says X
→ X becomes project truth
```

---

# 6.84 Truth Registry

如果项目足够复杂，可以建立：

> Truth Registry。

它不一定是一个新数据库。

早期完全可以由：

- Markdown；
- JSON；
- Registry File；
- Index；

实现。

它的核心不是技术，而是：

> 关键 Claim 具有明确类型和状态。

---

# 6.85 Truth Registry 应该很小

一个危险方向是：

> 把所有项目知识都变成 Truth Registry。

这会产生巨大维护成本。

真正值得进入 Registry 的是：

- 高影响；
- 高复用；
- 高频冲突；
- 容易过期；
- 需要多 Agent 共享；

的关键 Claim。

这和 Context 显式化原则一致。

---

# 6.86 Truth Resolution 不能制造新的官僚主义

小型低风险任务不需要：

> 十层 Truth Gate。

例如：

修正文档 typo。

直接：

```text
Current file
→ edit
→ verify
```

足够。

高风险任务才需要：

- State Snapshot；
- Authority；
- Evidence；
- Conflict Resolution。

因此：

> Truth Governance 同样需要 Adaptive Governance。

---

# 6.87 一个完整案例：Save Migration

假设 Intent：

> 支持旧 Save v2 在当前版本中安全加载，并保持现有 v3 Save 不受影响。

Agent 开始前可能面对：

```text
Design Doc:
Current schema = v3

Code:
Migration v2 → v3 exists

Test:
old migration test last updated 2 months ago

Production telemetry:
unknown save distribution

Memory:
previous workaround references v2 loader
```

如果没有 Truth Architecture：

Agent 可能直接：

> 读取代码 → 修改 → 测试。

成熟流程则先解析：

### Intent

支持 v2 compatibility。

### Implementation Truth

当前 code 有 migration v2 → v3。

### Runtime / Data Truth

需要确认当前生产 Save Schema 和真实样本。

### Decision

不得破坏 v3 compatibility。

### Assumption

旧用户中仍有 v2 saves。

### Evidence Requirement

- v2 samples；
- v3 samples；
- migration test；
- rollback capability。

之后才开始执行。

这说明：

> Truth Resolution 本身就是执行准备的一部分。

---

# 6.88 一个完整案例：Player Status

假设任务：

> 继续优化 Stage / Limit 显示。

项目中存在：

### Doc

旧设计仍包含 dense Stage chip。

### Current Code

已经接入新版 Player Status。

### Runtime Capture

显示新的 Stage 信息仍偏弱。

### Decision

HP / Block 方向已接受。

### Dirty Worktree

还有 SP120 / SP121 无关修改。

成熟 Truth / State 描述可能是：

```text
Intent:
Improve Stage / Limit readability

Implementation Truth:
current Player Status baseline = commit X

Behavioral Truth:
latest runtime capture shows Stage hierarchy issue

Approved Decision:
HP / Block accepted and out of scope

State Boundary:
SP120 / SP121 dirty changes unrelated

Assumption:
problem is primarily visual hierarchy
```

Worker 得到的是：

> 一个被整理过的真实世界。

而不是：

> 自己从几十个文件和历史讨论中猜当前状态。

---

# 6.89 Truth and State Architecture 的最终目标

这套体系不是为了让系统永远拥有一个：

> 完美、唯一、无争议的事实数据库。

现实项目不可能这样。

它真正的目标是：

> **让关键事实的确定性、来源、不确定性和冲突都显式可见。**

因此成熟系统应该允许输出：

```text
Verified
Observed
Approved
Assumed
Unknown
Conflicted
Superseded
```

而不是只有：

```text
True
False
```

---

# 6.90 本章结论：Agent 不应该生活在一个“看起来一致”的世界里

Intent Engineering 解决：

> 我们希望未来达到什么状态。

Context Engineering 解决：

> Agent 当前应该看到什么信息。

Truth and State Architecture 进一步解决：

> 这些信息中，哪些能够代表当前现实，以及它们在什么范围、版本和条件下有效。

如果缺少这一层，Agent 很容易：

> 在一组语言上自洽、工程上冲突的信息中，自行构造一个“看起来合理”的现实。

而强模型最大的风险之一恰恰在这里：

> 它非常擅长让不完整世界变得连贯。

软件工程真正需要的不是：

> 连贯。

而是：

> 可验证的现实。

因此，本章的核心原则不是：

> 找到唯一 Source of Truth。

而是：

> **为不同 Truth Domain 定义正确 Authority，并显式管理 State、Decision、Assumption 和 Evidence 之间的关系。**

一个成熟的 AI-native 项目应该能够回答：

```text
What do we want?
→ Intent

What is currently implemented?
→ Implementation Truth

What is actually happening?
→ Runtime / Data Truth

What have we decided?
→ Decision

What do we still not know?
→ Assumption / Unknown

What proves the claim?
→ Evidence

What exact state is this task based on?
→ State Snapshot
```

这使：

> Doc as Intent, Code as Truth

从一个非常有用的简单原则，逐渐演化成：

> **Domain-scoped Truth and State Architecture。**

如果需要用一句话总结本章：

> **Agent 不需要一个看起来没有矛盾的世界；它需要一个知道哪些是事实、哪些是决定、哪些是假设、哪些仍然未知的世界。**

当 Intent、Context 和 Truth 都被建立之后，下一步才真正进入行动问题：

> Agent 应该如何在这些目标、现实和边界之中自主完成复杂任务？

这就是下一章的主题：

# Agent Execution Engineering  
## 从模型调用到受约束的智能执行闭环

# 本章原则

## 原则一：Code as Implementation Truth

Code 是当前实现的重要权威来源，但不是整个系统唯一 Truth。

---

## 原则二：Truth is Domain-scoped

不同问题对应不同 Source of Truth。

---

## 原则三：Intent、Decision、Truth、Assumption 必须分离

“想要什么”“决定什么”“现在是什么”“暂时认为是什么”不能混为一谈。

---

## 原则四：Source of Truth 必须绑定 Question

不存在一个可以回答所有问题的全局唯一 Source。

---

## 原则五：Provenance before Confidence

工程可信度首先来自来源、证据和状态，而不是模型自报置信度。

---

## 原则六：Shared Truth, Local Context

多 Agent 可以拥有不同 Context，但关键现实应保持一致。

---

## 原则七：Assumption 必须显式并具有验证路径

未知可以存在，但不能静默成为事实。

---

## 原则八：State Snapshot 比 Conversation History 更适合恢复项目状态

聊天记录描述过程，Snapshot 描述可恢复的当前状态。

---

## 原则九：Reproduce the Decision Environment, not the hidden reasoning

可复现重点应是 Intent、State、Context、Policy 和 Tool Environment。

---

## 原则十：Agent 可以提出 Claim，但不能自动定义 Truth

关键 Truth 需要 Evidence 和 Authority。

---

# 常见反模式

## 反模式一：把 Code 当成所有 Domain 的唯一 Truth

Runtime、Data、Configuration 和 Decision 可能有不同 Authority。

---

## 反模式二：把文档写得很确定就当成事实

语言语气不等于 Authority。

---

## 反模式三：让 Agent 自己解决所有信息冲突

高风险 Conflict 需要明确 Resolution Policy。

---

## 反模式四：把 Intent 当 Current State

“应该支持”不代表“已经支持”。

---

## 反模式五：把 Assumption 藏在执行过程里

没有显式记录的 Assumption 很容易变成未来错误 Context。

---

## 反模式六：Snapshot 保存整个聊天历史

Snapshot 应保存状态和引用，不是复制全部过程。

---

## 反模式七：Decision 永久有效

Decision 也有 Scope、Version 和 Expiry。

---

## 反模式八：认为测试通过是永久 Truth

Test Claim 通常绑定具体 Commit 和环境。

---

## 反模式九：忽略 Dirty Worktree

未知修改会破坏 Agent 对 Baseline 的理解。

---

## 反模式十：为了“统一”强行消除所有冲突

Unresolved Conflict 本身也是需要保存的真实状态。

---

# 本章检查清单

在一个 Agent 开始高风险任务前，可以检查：

- 当前 Intent 是什么？
- Current Implementation Truth 来自哪里？
- Runtime Truth 是否已确认？
- Data / Configuration State 是否相关？
- 当前 Commit 是什么？
- Branch / Worktree 是否明确？
- 是否存在 Dirty Changes？
- Dirty Changes 是否属于当前任务？
- Active Decisions 有哪些？
- 是否存在 Superseded Decisions？
- 当前有哪些 Assumptions？
- 哪些 Assumption 属于高风险？
- 关键 Claim 是否有 Provenance？
- Claim 是否仍然 Fresh？
- 是否存在多个互相冲突的来源？
- 当前问题对应哪个 Truth Domain？
- 这个 Domain 的 Primary Authority 是什么？
- 是否需要 Human Arbitration？
- Baseline 是否已经保存？
- 是否需要 State Snapshot？
- Context Snapshot 和 State Snapshot 是否区分？
- Evidence 是否绑定当前版本和环境？
- 当前 Test 结果是否已经因为代码变化失效？
- 是否有 Runtime / Data 证据支持关键 Claim？
- Agent 是否有权修改权威 Truth？
- Agent 只能提出 Claim，还是可以 Promote Claim？
- 任务完成后应生成什么 New State？
- 是否可以从 Input State → Change → Output State 重建状态迁移？
- 如果半年后调查这个决策，能否知道当时系统到底处于什么状态？

如果这些问题能够得到明确回答，Agent 才不是在一个由文档、Memory 和代码临时拼成的“可能现实”里工作。

它开始拥有一个真正可以被软件工程管理的状态世界。
