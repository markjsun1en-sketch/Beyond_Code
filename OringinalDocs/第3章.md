# 第3章  
# 什么是 AI 原生软件工程

前两章建立了两个基础判断。

第一个判断是：AI 带来的变化不只是代码生成速度提高，而是软件生产者的构成正在发生变化。

第二个判断是：当 Agent 开始解释目标、选择路径、调用工具并持续修改真实项目之后，传统软件工程长期依赖的一些操作性前提开始变得不再可靠。

人类仍然负责软件。

代码仍然重要。

测试、版本控制、CI/CD、软件架构、安全工程和质量保证也没有失效。

发生变化的是：

> 软件工程开始需要同时管理软件系统，以及参与生产软件的智能执行系统。

这使我们有必要给本书反复使用的一个概念下一个更明确的定义：

**AI-Native Software Engineering。**

在正式定义之前，需要先解决一个问题。

这个词究竟描述什么？

是使用 AI 写代码？

是使用 Claude Code、Codex 一类 Agent？

是让多个 Agent 并行工作？

还是让 AI 尽可能自主地完成整个软件开发过程？

如果这些边界没有先说清楚，“AI 原生软件工程”很容易成为一个过于宽泛的标签，最后什么都能放进去，却失去工程上的实际意义。

这一章的任务，就是把这条边界画出来。

---

# 3.1 为什么需要一个新的工程定义

今天，一个团队只要开始使用生成式 AI，就很容易声称自己已经进入“AI-native”。

但以下几种情况实际上有很大差异。

第一种：

```text
Developer
    ↓
Ask AI
    ↓
Receive Code
    ↓
Copy / Modify
    ↓
Traditional Development
```

AI 是新的知识和代码生成工具。

第二种：

```text
Human Task
    ↓
Agent
    ↓
Read Repository
Plan
Modify Files
Run Tests
    ↓
Human Review
```

AI 已经成为任务执行者。

第三种：

```text
Human Intent
    ↓
Governed Agent Organization
    ↓
Context / Truth / Skills / Tools
    ↓
Parallel Execution
    ↓
Evidence / Review / Cognition
    ↓
Human Decision
    ↓
Memory / Evolution
```

此时整个软件生产体系已经默认：

> Agent 会长期参与生产。

这三种模式都使用 AI，但它们面对的软件工程问题完全不同。

如果只是第一种模式，传统软件工程加上一些 AI 使用规范通常已经足够。

如果进入第二种模式，就开始需要：

- Sandbox；
- Permission；
- Plan；
- Scope；
- Test；
- Rollback；
- Review。

而当进入第三种模式时，问题进一步扩展到：

- Intent；
- Context；
- Truth；
- Agent Contract；
- Evidence；
- Cognitive Load；
- Memory；
- Multi-Agent Organization；
- Self-Evolution；
- Accountability。

因此，“AI-native”不能简单由：

> 是否使用 AI

来定义。

真正重要的是：

> **AI 在生产系统中承担了什么角色，而软件工程是否已经针对这种角色重新设计。**

---

# 3.2 一个工作定义

本书暂时采用以下定义：

> **AI 原生软件工程，是研究和实践如何设计、构建、验证、治理、运行与演化由人类和智能代理共同参与的软件生产系统的一套工程方法。**

这个定义有几个关键词。

---

## 第一，Software Engineering

它首先仍然是软件工程。

因此目标没有根本改变：

- 构建正确的软件；
- 控制复杂性；
- 降低风险；
- 支持多人协作；
- 保持可维护性；
- 支持长期演化；
- 对结果承担责任。

AI 并没有取消这些目标。

---

## 第二，Human and Intelligent Agents

软件生产者不再假定只有人类。

系统必须同时考虑：

```text
Human
+
AI Agent
```

两种不同性质的生产参与者。

人类拥有：

- 真实组织身份；
- 长期责任；
- 社会关系；
- 隐性项目经验；
- 价值判断；
- 法律和管理责任。

Agent 则具有：

- 高速信息处理；
- 自然语言理解；
- 代码和内容生成；
- 工具调用；
- 大规模搜索；
- 快速并行；
- 概率性输出；
- 上下文依赖；
- 非持续性身份；
- 外部提供的 Memory 和权限。

两者不能简单互换。

---

## 第三，Production System

本书讨论的对象不只是最终代码。

还包括：

> 代码是怎样被生产出来的。

因此工程对象从：

```text
Software System
```

扩展成：

```text
Software System
+
Software Production System
```

当生产系统本身开始包含智能执行者时，它也需要：

- 架构；
- 接口；
- 权限；
- 状态；
- 监控；
- 测试；
- 版本；
- 回滚；
- 治理。

---

## 第四，Govern and Evolve

AI-native 并不止于“让 Agent 可以工作”。

还必须回答：

> Agent 怎样长期可靠工作？

这包括：

- 权限如何调整；
- 失败如何恢复；
- Context 如何更新；
- Memory 如何清理；
- Skill 如何修改；
- Agent 组织如何调整；
- 新模型如何重新评估；
- 哪些经验可以进入下一轮生产。

所以一次成功的 Agent Task，不等于成熟的 AI 原生软件工程。

真正困难的是：

> **长期重复成功。**

---

# 3.3 AI 原生软件工程管理两个系统

传统软件工程主要关注一个系统：

## Product System

也就是最终交付的软件。

包括：

- Code；
- Data；
- Architecture；
- Runtime；
- Configuration；
- Infrastructure。

AI-native 环境中还必须正式管理第二个系统：

## Production Intelligence System

即负责参与生产软件的智能执行系统。

包括：

```text
Agents
Context
Skills
Tools
Memory
Policies
Permissions
Workflows
Evaluations
```

因此可以建立一个最基础的双层模型：

```text
┌──────────────────────────────┐
│     Production Intelligence  │
│                              │
│ Intent                       │
│ Context                      │
│ Agents                       │
│ Skills                       │
│ Tools                        │
│ Memory                       │
│ Governance                   │
└──────────────┬───────────────┘
               │
               │ produces / changes
               ↓
┌──────────────────────────────┐
│        Product System        │
│                              │
│ Code                         │
│ Data                         │
│ Assets                       │
│ Runtime                      │
│ Infrastructure               │
└──────────────────────────────┘
```

过去，我们主要设计下面这一层。

未来，我们还需要设计上面这一层。

---

## 生产系统本身也可能产生缺陷

例如：

Product System 的缺陷可能是：

> Save System 无法正确读取旧版本数据。

Production Intelligence System 的缺陷则可能是：

> Agent 得到了错误的历史 Context，因此选择了错误的迁移方案。

又例如：

Product Bug：

> API 返回错误状态。

Production Intelligence Bug：

> Worker 没有获得禁止修改公共 API 的 Scope Constraint。

前者存在于软件产品。

后者存在于生产软件的系统。

两者最终都可能表现为代码问题。

但根因并不相同。

这意味着未来的 Root Cause Analysis 可能需要问两层问题：

```text
Why did the software fail?

and

Why did the production intelligence
produce this change?
```

---

# 3.4 AI 原生不等于 Agentic

这是一个非常重要的区分。

Agentic Development 描述的是：

> AI 能够自主完成多步任务。

AI-Native Software Engineering 描述的是：

> 软件工程体系是否围绕这种执行者重新设计。

因此，一个项目可以非常 Agentic，却并不成熟地 AI-native。

例如：

```text
Agent:
- 自主修改代码
- 自主运行测试
- 自动提交
- 并行工作
```

看起来自动化程度很高。

但如果没有：

- Context Governance；
- Truth Baseline；
- Scope Boundary；
- Evidence Requirement；
- Risk Escalation；
- Memory Governance；

它可能只是：

> **高自治、低治理。**

相反，一个 AI-native 项目在早期甚至可以采取较低自治：

```text
Agent plans
    ↓
Human approves
    ↓
Agent executes
    ↓
Evidence generated
    ↓
Human decides
```

它的自动化程度没有那么高。

但其：

- 意图；
- 边界；
- 状态；
- 证据；
- 责任；

已经被系统化。

所以：

> **Agentic 描述能力和行为方式；AI-native 描述工程体系。**

---

# 3.5 AI 原生也不等于最大自动化

“Native”很容易让人联想到：

> AI 应该尽可能自动完成全部工作。

本书并不采用这种定义。

一个系统完全可能：

```text
Highly Autonomous
but
Poorly Engineered
```

例如：

Agent 可以：

- 自动接任务；
- 自动改代码；
- 自动测试；
- 自动合并；
- 自动部署。

如果缺乏：

- 风险模型；
- Evidence；
- Rollback；
- Trace；
- 权限分层；

它并不会因为“更自动”而变得更 AI-native。

成熟的 AI-native 系统关心的是：

> **正确的自治程度。**

这意味着：

```text
Autonomy
≠
Maximum possible autonomy
```

而应是：

```text
Autonomy
=
Capability
constrained by
Risk + Evidence + Authority + Recoverability
```

低风险任务可以高度自治。

高风险任务需要更强治理。

不可逆决策可能始终需要人类批准。

因此：

> AI-native 的目标不是移除 Human，而是重新分配 Human Attention。

---

# 3.6 AI 原生软件工程不是替代传统软件工程

如果只看新增术语，很容易产生一种印象：

> 传统软件工程已经过时，现在需要全部重新发明。

这是错误的。

实际上，很多传统原则在 Agent 环境中反而更加重要。

例如：

### Modular Architecture

模块边界越清楚，Agent 越容易获得准确 Context，也越容易限制 Scope。

### Automated Testing

AI 生产速度越高，自动回归检测越重要。

### Version Control

并行 Agent 越多：

- Branch；
- Worktree；
- Commit；
- Rollback；

越重要。

### Least Privilege

Agent 获得真实执行能力以后，最小权限不再只是 Security Best Practice，而成为基础治理能力。

### Small Changes

AI 很容易一次产生巨量修改，因此小批次、可验证、可回滚的变化更加重要。

### Observability

执行者越自主，人类越需要知道它：

- 正在做什么；
- 做到了哪里；
- 为什么停住；
- 什么时候需要介入。

因此更准确的关系不是：

```text
Traditional Software Engineering
    ↓
replaced by
AI-Native Software Engineering
```

而是：

```text
Traditional Software Engineering
        +
Agent-specific Engineering
        +
Human-AI Governance
        =
AI-Native Software Engineering
```

---

# 3.7 一些传统原则会向“生产系统”上移

AI-native 最值得注意的变化之一，是很多过去作用于代码的原则，现在会进一步作用于 Agent。

例如传统软件架构强调：

> High Cohesion, Low Coupling。

一个模块应该围绕清晰职责组织内部功能，同时尽量减少与其他模块之间不必要的依赖。

在 Agent 系统中，同样的思想可以表现为：

## High Agent Cohesion

一个 Worker 应围绕一个明确任务，拥有：

- 所需 Context；
- 对应 Skill；
- 必要 Tool；
- 合理局部决策权；

尽可能在内部完成一个完整任务闭环。

而不是每两步就回到 Controller 请求微观指令。

---

## Low Agent Coupling

不同 Agent 之间不应该依赖：

- 彼此完整历史；
- 彼此内部推理；
- 大量共享隐式 Context；
- 模糊的角色默契。

它们应该通过明确结构交换：

```text
Intent
State
Contract
Evidence
Handoff
```

因此，可以建立这样的映射：

| 传统软件架构 | AI-native Agent 系统 |
|---|---|
| Module | Agent / Worker |
| Responsibility | Goal |
| Interface | Agent Contract |
| Parameters | Intent + Context |
| Encapsulation | Execution Autonomy |
| API Boundary | Scope / Permission Boundary |
| Return Value | Result + Evidence |
| Exception | Escalation |
| Unit Test | Eval / Evidence |

这说明：

> AI 原生软件工程很多时候不是抛弃传统工程思想，而是把传统成熟原则从代码层提升到了“生产代码的智能系统”层。

---

# 3.8 从 Human Smoothing 到 Explicit Engineering

第二章讨论过一个重要现象。

传统软件开发流程并没有真的把所有事情规定清楚。

需求可能含糊。

文档可能落后。

不同角色可能理解不一致。

历史决定可能只存在于某几个资深成员脑中。

项目之所以仍然可以运行，很大程度上依赖人类不断进行隐性的修补：

- 主动询问；
- 判断异常；
- 补充背景；
- 解释模糊表达；
- 临场协调；
- 发现“虽然符合文字，但明显不对”的情况。

本书把这种能力称为：

> **Human Smoothing Effect。**

AI Agent 并不是没有判断能力。

它甚至可能在很多任务上表现出很强的问题发现能力。

真正的区别在于：

> 软件工程不能把 Agent 每一次都会正确进行这种隐性修补，当成一个可靠前提。

于是产生：

> **Smoothing Gap。**

过去存在于：

```text
Common Sense
Tacit Knowledge
Professional Judgment
Social Communication
```

中的部分能力，需要逐渐转换成：

```text
Explicit Intent
Explicit Context
Explicit Truth
Explicit Boundaries
Explicit Evidence
Explicit Escalation
```

这就是为什么 AI-native 环境在某些地方反而需要比传统流程更加精确。

但这里存在一个重要平衡。

更加精确不等于：

> 把 Agent 的每一步都写死。

真正需要严格的是：

> 边界。

而不是：

> 内部执行路径。

---

# 3.9 Tight Boundaries, Flexible Execution

这一原则可以概括为：

> **Tight Boundaries, Flexible Execution。**

中文可以理解为：

> **明确边界，灵活执行。**

它是本书最重要的基础原则之一。

Agent 不应该得到：

```text
“你自己看着办。”
```

也不应该得到：

```text
1. 打开 A 文件
2. 找第 97 行
3. 修改 X
4. 打开 B
5. 运行 C
6. 返回
```

前者边界过松。

后者又把 Agent 退化成了脚本。

更合理的结构是：

```text
Goal
Constraints
Non-goals
Truth Baseline
Allowed Scope
Permissions
Required Evidence
Escalation Conditions
```

然后在其中允许：

```text
Search
Analyze
Plan
Experiment
Implement
Test
Debug
Revise
```

由 Agent 自主完成。

因此：

> **AI-native 的严格性主要是边界精确性，而不是流程微操。**

---

# 3.10 六类 Boundary

“Tight Boundaries”如果只是一句原则仍然太抽象。

至少可以拆成六类基础边界。

---

## 1. Goal Boundary

解决：

> 这个任务究竟要解决什么？

包括：

- Goal；
- Non-goal；
- Priority；
- Acceptance。

防止：

> 完成了很多有价值的工作，却没有解决原始问题。

---

## 2. Scope Boundary

解决：

> 可以动哪里？

例如：

- 哪些模块；
- 哪些文件；
- 哪些系统；
- 哪些工作流；

属于当前任务范围。

---

## 3. State Boundary

解决：

> 基于什么当前状态工作？

包括：

- Commit；
- Branch；
- Worktree；
- Runtime Version；
- Dependency Version；
- Data Snapshot。

这对于并行 Worker 尤其重要。

---

## 4. Authority Boundary

解决：

> Agent 可以决定什么？

例如：

可以：

- 修改局部实现；
- 添加测试。

不能自动：

- 改公共 API；
- 改数据 Schema；
- Merge 主线；
- Deploy Production。

---

## 5. Risk Boundary

解决：

> 什么情况下必须停止自治？

例如：

- 需要修改存档；
- 引入新外部依赖；
- 影响安全权限；
- 修改核心玩法；
- 改变不可逆数据。

---

## 6. Evidence Boundary

解决：

> 什么证据不足时不能声称完成？

例如：

- Build；
- Unit Test；
- Integration Test；
- Runtime Capture；
- Performance；
- User-facing Validation。

因此一个 Agent Contract 的核心并不是：

> 告诉 Agent 每一步该怎么走。

而是：

> 把这些 Boundary 定义清楚。

---

# 3.11 Contract over Reasoning Process

这个原则可以进一步表达为：

> **Contract over Reasoning Process。**

传统模块设计不会要求调用方理解模块内部所有实现。

调用方关心：

- Input；
- Interface；
- Output；
- Error Contract。

Agent 系统也应该逐渐如此。

上层系统不需要持续微操：

> Agent 下一步应该读哪个函数。

它真正应该管理的是：

```text
Input
Boundary
Authority
Expected Output
Evidence
Escalation
```

也就是说：

> **治理 Agent 的契约，而不是治理 Agent 的每一步内部推理。**

这还有一个非常实际的价值。

模型会变化。

工具会变化。

Repo 会变化。

如果 Workflow 与 Agent 的每一个执行步骤高度耦合，那么：

> 每次能力变化都会破坏整个流程。

相反，如果 Contract 稳定：

```text
Goal
Boundary
Evidence
```

而内部实现可以变化，那么系统就能够吸收：

- 更强模型；
- 新工具；
- 新搜索能力；
- 更好的 Debug 策略。

这与软件架构中的：

> Interface over Implementation

具有相似思想。

---

# 3.12 Encapsulate Execution, Expose Evidence

但是 Agent 具有执行自治以后，会产生另一个风险：

> 会不会变成黑箱？

答案不是要求人类阅读所有执行步骤。

如果一个 Worker 搜索了数百个文件、尝试了三个方案、运行了二十次测试，让人类阅读全部记录不仅没有必要，还会加剧认知过载。

因此需要另一个原则：

> **Encapsulate Execution, Expose Evidence。**

中文可以表述为：

> **封装执行过程，暴露验证证据。**

结构可以是：

```text
Intent
    ↓
┌────────────────────┐
│                    │
│ Flexible Execution │
│                    │
│ Search             │
│ Plan               │
│ Experiment         │
│ Debug              │
│ Revise             │
│                    │
└────────────────────┘
    ↓
Result
Evidence
Risk
Trace
```

内部执行可以封装。

但以下内容必须向外暴露：

- 做了什么；
- 为什么这样做；
- 改动范围；
- 关键决策；
- 证据；
- 未验证假设；
- 风险；
- Scope 是否变化；
- 必要执行 Trace。

因此：

```text
Transparency
≠
Show Everything
```

更合理的是：

```text
Transparency
=
Expose what is required
for verification and decision
```

---

# 3.13 Evidence over Confidence

语言模型有一个很容易误导人的特点：

> 它可以非常流畅地描述自己的结果。

一份结构完整、逻辑清晰的总结，很容易让人产生：

> 这项工作应该完成得很好。

但软件工程不能使用语言流畅度作为正确性指标。

因此：

> **Evidence over Confidence。**

Agent 说：

> “已经修复。”

不是完成。

Agent 说：

> “测试全部通过。”

也仍然只是一个声明，直到对应结果可以被确认。

一个更可靠的结构应该是：

```text
Claim
    ↓
Evidence
    ↓
Verification
    ↓
Acceptance
```

不同 Evidence 的强度不同：

```text
Explanation
<
Diff
<
Static Analysis
<
Automated Test
<
Runtime Observation
<
Real-world Validation
```

具体任务需要哪一层证据，由风险和验收目标决定。

---

# 3.14 Human Cognitive Authority

如果 Agent 能够执行大量工作，人类控制权不能继续主要依靠：

> “我看过所有代码。”

在大规模 Agent 生产环境中，这很可能不现实。

因此，本书提出：

> **Human Cognitive Authority。**

即：

即使人类不再亲自完成全部工作，也应该保有：

- 知情权；
- 理解权；
- 判断权；
- 否决权；
- 接管权；
- 最终责任。

这并不要求：

> Human reads everything.

而是要求系统能够回答：

- 发生了什么；
- 为什么；
- 有什么影响；
- 有什么证据；
- 哪里有风险；
- 哪里需要人决定。

所以未来人类控制软件，不应只依赖操作权限。

还需要：

> **认知权限。**

一个人技术上拥有 Merge 按钮，却无法理解系统发生了什么，并不构成真正有效的控制。

---

# 3.15 Automation Default Off 与 Risk-based Autonomy

从上述原则可以自然得到两个治理原则。

第一个是：

> **Automation Default Off。**

含义不是：

> 默认禁止 AI。

而是：

> **能力存在，不自动等于自治权限存在。**

一个 Agent 可能技术上能够：

- Commit；
- Merge；
- Deploy；
- 修改 Memory；
- 修改 Skill。

但这些能力是否自动开放，是另一个问题。

---

第二个原则：

> **Risk-based Autonomy。**

自治程度应当由风险决定。

例如：

```text
Low Risk
    ↓
High Autonomy

Medium Risk
    ↓
Supervised Autonomy

High Risk
    ↓
Explicit Human Decision
```

风险可以来自：

- 影响范围；
- 可逆性；
- 数据；
- Security；
- Business；
- Architecture；
- Evidence Coverage；
- Historical Reliability。

因此：

> AI-native 不是固定自治等级，而是动态治理模型。

Requirement
→ Design
→ Implementation
→ Test
→ Deployment
→ Maintenance

每一步解决不同问题。

## Intent Formalization

解决：

> 到底想实现什么？

---

## Context Assembly

解决：

> Agent 为完成这个任务需要知道什么？

---

## Truth / State Resolution

解决：

> 当前真实状态是什么？

---

## Agent Planning

解决：

---

## Plan Review

解决：

---

## Governed Execution

解决：

## Continuous Observation

---

## Verification and Evidence

解决：

---

## Cognitive Compression

解决：

> 人类应该怎样理解大量变化？

---

---

## Memory Update

解决：

它描述的是：

> 完整系统需要具备哪些能力。

真正的执行流程应根据风险裁剪。

# 3.18 AI-native 不是更重的流程，而是更精确的流程

看到这么多：

- Intent；
- Context；
- Boundary；
- Evidence；
- Review；
- Memory；

很容易得出一个结论：

> AI-native 会不会把开发变得非常官僚？

如果所有任务都走完整流程，答案当然可能是会。

但这不是目标。

成熟系统应该采用：

> **Adaptive Governance。**

例如，一个低风险格式调整：

```text
Small Intent
→ Execute
→ Automated Test
→ Summary
```

可能已经足够。

一个局部 UI 修改：

```text
Intent
→ Context
→ Execute
→ Runtime Evidence
→ Human Visual Review
```

而数据库迁移：

```text
Intent
→ Context
→ Truth Snapshot
→ Plan Review
→ Sandbox
→ Migration
→ Data Verification
→ Rollback Test
→ Human Approval
```

需要完全不同的治理强度。

所以：

> **AI-native 的成熟度不是流程步骤越多越好，而是能否把正确强度的治理放到正确任务上。**

这与 Tight Boundaries, Flexible Execution 是同一思想。

# 3.19 如何判断一个项目是否正在变得 AI-native

可以提出几个判断问题。

### 1. AI 是否已经直接作用于真实项目？

如果只是聊天和代码建议，通常仍然属于 AI-assisted。

### 2. Agent 是否自行选择部分执行路径？

如果是，就开始进入 Agentic。

### 3. 项目是否正式管理 Agent 的 Context？

如果 Context 仍然完全依赖临时 Prompt，成熟度有限。

### 4. Agent 是否存在明确 Scope 和 Permission？

如果没有，自治主要靠信任而不是工程。

### 5. 完成是否由 Evidence 定义？

如果仍然依赖：

> “Agent 说完成了。”

体系尚不成熟。

### 6. 多个 Agent 是否存在 Contract 和 Handoff？

如果没有，多 Agent 只是并行工具，不是组织。

### 7. 人类是否能够在不阅读全部原始产出的情况下理解关键变化？

如果不能，规模扩大后会遇到认知瓶颈。

### 8. Memory 和 Skill 是否存在治理？

如果可以自由积累，却没有来源、范围和回滚，长期风险会增加。

### 9. Agent 失败以后是否可以恢复？

成熟系统必须假设失败会发生。

### 10. 最终责任是否仍然清晰？

如果人类只负责点击 Approve，却不知道自己批准了什么，治理并没有真正成立。

# 3.20 什么不属于本书所说的 AI 原生软件工程

为了进一步收紧边界，还需要明确几个反例。

---

## 只有 Prompt Engineering

Prompt 很重要。

但：

```text
Good Prompt
≠
Software Engineering System
```

Prompt 解决输入表达问题。

AI-native 还要解决：

- State；
- Permission；
- Evidence；
- Review；
- Memory；
- Accountability。

---

## 只有一个 Agent Framework

能够：

- Tool Calling；
- Loop；
- Multi-Agent；

并不自动构成完整工程体系。

Runtime 解决：

> Agent 怎么运行。

Software Engineering 还要解决：

> 为什么这样运行、允许运行到哪里、怎样验证、怎样长期维护。

---

## 只有大量自动化

Automation 本身不是目标。

如果自动化无法：

- 验证；
- 回滚；
- 解释；
- 限制；

它可能只是更快地扩大错误。

---

## 只有多 Agent

```text
Many Agents
≠
Organization
```

组织需要：

- Role；
- Authority；
- Contract；
- Handoff；
- Conflict Resolution；
- Accountability。

---

## 让 AI 替代所有代码

AI-native 也不是：

> Natural Language replaces Code.

代码仍然承担：

- 精确行为；
- 可执行状态；
- 版本；
- 测试；
- Runtime Reality。

自然语言 Intent 与 Code 承担的是不同角色。

---

## Agent 自由修改自己的规则

Self-Evolution 不等于：

> Agent 可以自由改变自己的 Skill、Memory 和权限。

真正的演化必须：

- 有来源；
- 有评估；
- 有 Gate；
- 可回滚。

# 3.21 AI 原生软件工程最终优化什么

如果只使用传统效率指标，AI 很容易看起来非常成功。

例如：

- Lines of Code ↑
- Tasks Completed ↑
- Time to First Draft ↓
- Agent Count ↑

但这些指标可能具有误导性。

真正应该优化的是：

```text
Useful Outcome
        /
Total Production Cost
```

这里的 Production Cost 不只是 Token。

还包括：

- Human Review；
- Rework；
- Integration；
- Failure Recovery；
- Cognitive Load；
- Security Risk；
- Maintenance；
- Governance Overhead。

因此一个 AI-native 体系真正希望达到的是：

> **更高的有效生产能力，而不是更高的原始生成能力。**

可以进一步分解为：

### Outcome Quality

最终软件是否真的更好？

### Reliability

成功是否可以重复？

### Evidence Coverage

我们为什么相信结果？

### Human Cognitive Cost

人类理解和决策需要付出多少注意力？

### Recovery Cost

错误发生以后恢复有多困难？

### Governance Cost

控制 Agent 是否比完成任务本身还复杂？

### Learning Efficiency

系统是否真正从经验中变得更好？

这一点很重要。

因为 AI 最大的诱惑之一，就是：

> 把 Generation Throughput 当成 Engineering Productivity。

两者不是同一个东西。

# 3.23 AI-Native Software Engineering 的核心设计原则

到这里，可以将目前形成的主要原则集中列出。

它们将在后续章节分别展开。

---

## 原则一：Intent over Instruction

> 定义目标和约束，而不是机械规定所有执行步骤。

---

## 原则二：Doc as Intent, Code as Truth

> 文档主要表达目标和设计意图；当前代码表达实现现实，Runtime 与可执行 Evidence 则进一步验证真实行为。

因此更完整地说：

```text
Doc
→ Intent

Code
→ Implementation Truth

Runtime Evidence
→ Behavioral Truth

Assumption
→ Unverified Model
```

---

## 原则三：Tight Boundaries, Flexible Execution

> 明确 Goal、Scope、State、Authority、Risk 和 Evidence Boundary，在其中保留 Agent 自主执行能力。

---

## 原则四：Contract over Reasoning Process

> 管理 Agent 的输入、责任、权限、输出和升级条件，而不是微操或依赖它的内部推理过程。

---

## 原则五：High Agent Cohesion, Low Agent Coupling

> 一个 Worker 应围绕明确职责完成尽可能完整的闭环；Agent 之间通过 Contract 和 Structured Handoff 协作。

---

## 原则六：Encapsulate Execution, Expose Evidence

> 不要求人类阅读所有内部执行过程，但必须暴露支持验证和决策的信息。

---

## 原则七：Evidence over Confidence

> 完成依赖证据，不依赖 Agent 的自信描述。

---

## 原则八：Automation Default Off

> Agent 拥有能力，不自动意味着它拥有自主使用该能力的权限。

---

## 原则九：Risk-based Autonomy

> 自治程度应该根据风险、影响范围、可逆性、历史可靠性与证据覆盖动态调整。

---

## 原则十：Human Cognitive Authority

> 人类即使不再直接完成全部执行，也必须保持理解、判断、否决、接管和最终责任能力。

---

这些原则共同形成一条很清晰的关系：

```text
Intent
    ↓
Truth
    ↓
Boundary
    ↓
Contract
    ↓
Flexible Execution
    ↓
Evidence
    ↓
Human Understanding
    ↓
Human Decision
```

这可以视为本书后续所有章节的最小理论骨架。

# 3.24 本章结论：从管理代码到管理智能生产

第一章指出：

> 软件生产者正在变化。

第二章指出：

> 当生产者变化后，传统软件工程的一些隐含环境条件开始不再可靠。

这一章进一步给出了本书的回答：

> **AI 原生软件工程不是新的 AI 编程技巧，而是软件工程在智能执行者进入生产系统之后的一次工程边界扩展。**

它管理的不只是：

```text
What software should be built?
```

还包括：

```text
Who / what builds it?

What does the agent know?

What is true?

What can it change?

How autonomous can it be?

How do we know it succeeded?

How does a human understand the result?

What should the system remember?

How should the production system evolve?
```

传统软件工程的基本目标仍然存在。

真正增加的是：

> **生产软件的智能系统本身，也成为需要被工程化的对象。**

因此，本书不把 AI-native 定义为最大自治。

也不把它定义为最复杂流程。

它追求的是另一种平衡：

```text
Explicit Intent
+
Reliable Truth
+
Tight Boundaries
+
Flexible Execution
+
Explicit Evidence
+
Adaptive Governance
+
Human Cognitive Authority
```

如果需要用一句话概括这一章：

> **AI 原生软件工程，就是在不牺牲人类理解、治理与责任的前提下，把智能执行能力正式纳入软件工程体系。**

从下一章开始，我们将离开宏观定义，进入这套体系的第一个具体基础层。

如果 Agent 不再只接受确定指令，而开始接受自然语言目标，那么第一个需要回答的问题就是：

> 人类到底如何把“我想要什么”，转化成一个 Agent 可以可靠理解、执行和验证的工程对象？

这就是下一章的主题：

# Intent Engineering  
## 从模糊需求到可执行意图

---

# 本章原则

## 原则一：AI-native 是工程体系，不是工具标签

使用 AI 或 Agent，并不自动意味着项目已经 AI-native。

---

## 原则二：工程对象扩展为两个系统

需要同时设计：

```text
Product System
+
Production Intelligence System
```

并通过 Control and Evidence Plane 管理二者关系。

---

## 原则三：Agentic 不等于 AI-native

Agentic 描述 Agent 的行为能力。

AI-native 描述围绕这些能力形成的软件工程体系。

---

## 原则四：自治不是最终目标

真正目标是：

> 在可靠边界中使用尽可能高效的自治。

---

## 原则五：传统软件工程原则继续成立

模块化、测试、版本控制、最小权限、可观测性和高内聚低耦合不仅不会消失，很多原则还会进一步作用于 Agent 系统。

---

## 原则六：隐性组织能力需要逐渐显式工程化

AI 暴露了过去由 Human Smoothing 吸收的一部分流程缺口。

但显式化应主要发生在边界、契约和证据层，而不是把 Agent 的每一步脚本化。

---

# 常见反模式

## 反模式一：有 Agent 就认为自己已经 AI-native

Agent 是执行能力。

AI-native 是工程体系。

---

## 反模式二：把最大自治当成成熟度

没有 Evidence 和 Governance 的高自治，可能只是高风险。

---

## 反模式三：为了可靠性而微操 Agent 的所有步骤

这样会失去 Agent 本身的适应和推理价值，并使 Workflow 高耦合。

---

## 反模式四：把 Agent 当成真正的人类员工

角色比喻可以帮助组织流程，但不能忽略 Agent 在责任、记忆、上下文和稳定性上的根本差异。

---

## 反模式五：用更多 Context 解决所有问题

Context 的价值来自正确性和相关性，不来自体积。

---

## 反模式六：把测试通过等同于最终正确

测试只证明被测试的行为。

Intent、体验、架构和未覆盖风险仍然需要其他 Evidence 和判断。

---

## 反模式七：把更多 Agent 等同于更高生产率

如果 Agent Coupling、Handoff、Review 和 Cognition 没有解决，增加 Agent 可能只是扩大协调成本。

---

## 反模式八：把 AI-native 做成新的流程官僚主义

所有任务都使用最高治理强度，会使工程成本失控。

成熟体系需要 Adaptive Governance。

---

# 本章检查清单

一个项目是否正在形成真正的 AI 原生软件工程体系，可以检查：

- AI 是否已经是实际生产参与者，而不仅是建议工具？
- Agent 是否会自行选择部分执行路径？
- 是否正式管理 Intent？
- 是否正式管理 Context？
- 是否区分 Intent、Truth 和 Assumption？
- 是否存在明确 Goal / Scope / State / Authority Boundary？
- Agent 是否能够在边界内自主完成闭环？
- Agent 之间是否主要通过 Contract 和 Handoff 交互？
- 是否存在 Evidence-Driven DoD？
- 是否区分 Agent 自述和独立 Evidence？
- 是否存在执行前、中、后的 Review 机制？
- 人类是否能快速理解系统关键变化？
- 自治权限是否根据风险调整？
- Agent 是否可暂停、接管和回滚？
- Memory 是否有来源、范围、验证和过期机制？
- Skill 更新是否可以评估和回滚？
- 多 Agent 是否有明确组织结构？
- 是否可以追踪 Intent → Agent → Change → Evidence → Decision？
- 是否评估总生产成本，而不只是生成速度？
- 最终责任是否仍然明确？

如果这些问题开始成为项目正式设计的一部分，那么 AI 已经不再只是进入代码编辑器。

它开始进入软件工程本身。
