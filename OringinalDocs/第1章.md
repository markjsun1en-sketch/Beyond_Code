# 第1章  
# 软件工程的角色演进：从工具增强到智能协作

## 1.1 软件工程一直在管理两种复杂性

软件工程经常被理解为一组开发方法：需求分析、架构设计、编程、测试、部署和维护。

但如果向下追问一步，就会发现这些方法长期以来主要在管理两种复杂性。

第一种是**软件系统本身的复杂性**。

随着软件规模扩大，开发者需要处理更多模块、状态、接口、依赖和运行环境。系统越复杂，局部修改引发意外后果的可能性就越高。模块化、抽象、封装、架构设计和自动化测试，都是为了让这种复杂性保持在人类能够理解和控制的范围内。

第二种是**人类协作的复杂性**。

软件并不是只由一个人在一个时间点完成。它通常需要多个人在不同阶段、不同专业和不同环境中持续协作。需求需要传递，代码需要合并，决策需要记录，缺陷需要追踪，版本需要发布，系统还需要在原始开发者离开之后继续维护。

版本控制、Issue 系统、代码审查、持续集成和项目管理流程，主要是在管理这种协作复杂性。

在这两类复杂性背后，传统软件工程长期保留着一个相对稳定的角色关系：

```text
Human Intent
    ↓
Human Understanding
    ↓
Human Design
    ↓
Human-written Code
    ↓
Deterministic Tools
    ↓
Running Software
```

人类提出目标、理解问题、设计方案并承担主要判断责任。

工具可以帮助人类表达、检查和执行，但工具通常不自行解释项目目标，也不自主决定应当采取哪一条工程路径。

编译器不会判断某项需求是否值得实现。

版本控制系统不会决定一个架构方案是否符合产品方向。

持续集成系统不会自行解释测试失败背后的业务含义。

它们可以非常复杂，但它们的职责边界相对确定。

AI Agent 的出现，开始改变这组关系。

要理解这种变化为什么不仅仅是一次效率升级，需要先回看软件工具过去究竟改变了什么，又始终没有改变什么。

## 1.2 从直接控制机器到提高表达层级

早期编程要求人类以非常接近机器执行方式的形式描述计算过程。

开发者需要直接处理：

- 指令；
- 地址；
- 寄存器；
- 内存布局；
- 硬件限制；
- 非常具体的控制流程。

软件生产能力因此受到两方面限制。

一方面，表达成本很高。人类需要把问题逐步翻译成机器可以执行的细节。

另一方面，人的认知能力必须同时承担业务问题和硬件实现问题。开发者不仅要思考“要计算什么”，还要持续处理“机器具体怎样计算”。

高级语言开始改变这种关系。

以 Fortran 为代表的早期高级语言，将大量机器级细节交给编译器处理。IBM 的历史资料显示，Fortran 在20世纪50年代被设计和实现，其核心影响之一，就是让开发者能够以更接近数学和问题领域的方式描述计算，而不必直接编写全部机器级指令。

这一变化非常重要，但其本质仍然是：

> 工具提升了人类表达意图的层级。

过去，人类需要描述机器如何完成每一步。

高级语言出现后，人类可以使用更高层次的结构表达算法，由编译器完成向机器指令的转换。

角色关系变为：

```text
Human Design
    ↓
High-level Code
    ↓
Compiler
    ↓
Machine Instructions
```

编译器承担了大量转换工作，但它没有成为需求解释者或方案决策者。

它不会判断程序员真正想解决什么问题，而是按照语言规范处理程序员已经形式化表达的内容。

这是软件工具演进中一个反复出现的模式：

> 人类保留目标和判断，工具吸收重复、精确和可形式化的工作。

## 1.3 软件工程的出现：当“能写程序”不再等于“能建设系统”

高级语言降低了局部编程成本，却没有消除大型软件系统的复杂性。

当软件规模、参与人数和生命周期继续增长时，行业逐渐发现：能够编写正确的局部程序，并不意味着能够按期、按预算地建设和维护大型软件系统。

1968年在德国加米施举行的 NATO 软件工程会议，成为软件工程历史上的一个重要节点。会议及其报告集中讨论了大型软件生产中的设计、管理、质量、组件、维护和工程训练等问题，并推动“Software Engineering”成为一个被广泛讨论的学科概念。

这个阶段体现了一次认识升级：

```text
Programming
≠
Software Engineering
```

编程主要回答：

> 怎样把一个解决方案写成机器可以执行的程序？

软件工程还要回答：

- 问题是否被正确理解？
- 系统应如何分解？
- 多个人如何协作？
- 变化如何被控制？
- 正确性如何验证？
- 失败如何发现？
- 软件如何交付和维护？
- 原始开发者离开后，系统是否仍然可理解？

也就是说，软件工程从一开始就不只是关于代码。

它管理的是：

> 围绕代码形成的一整套人类生产系统。

这也是理解 AI 原生软件工程的重要基础。

今天讨论“Beyond Code”，并不是第一次声称代码之外还有重要问题。传统软件工程早已证明，软件的质量并不只由语法正确或局部实现决定。

真正的新问题在于：过去这套生产系统主要围绕人类开发者建设；现在，具有解释和执行能力的 Agent 正在进入其中。

## 1.4 IDE：把局部反馈带回人的工作现场

高级语言提高了表达层级，集成开发环境进一步缩短了人类与软件之间的反馈距离。

编辑器、语法高亮、自动完成、错误定位、调试器、重构工具和项目导航逐渐被整合到同一工作环境中。

这种整合的价值不只是减少操作步骤。

它使开发者能够在编写代码时更快获得反馈：

```text
Write
→ Compile
→ Observe
→ Debug
→ Revise
```

反馈循环越短，开发者越容易在问题仍然局部、心智上下文尚未丢失时修正错误。

IDE 还改变了人类理解大型系统的方式。

开发者不再只依靠顺序阅读文件，而可以通过：

- 定义跳转；
- 引用搜索；
- 类型信息；
- 调用关系；
- 断点；
- 运行时变量；
- 重构预览；

建立和更新系统心智模型。

但这里仍然有一个明确边界：

> IDE 帮助人理解和修改系统，却不代替人确定系统应该成为什么。

自动重命名工具可以安全修改大量引用，但“这个概念是否应该被重新命名”仍由人判断。

调试器可以显示变量状态，但“这个状态为什么违反产品意图”仍需要人解释。

IDE 是强大的认知增强工具，却仍然属于工具增强范式。

## 1.5 版本控制：从个人修改到集体历史

当多人共同修改同一个系统时，软件工程需要回答的不再只是“当前代码是什么”，还要回答：

- 谁修改了什么？
- 什么时候修改？
- 为什么修改？
- 哪些修改属于同一目标？
- 如何回到之前状态？
- 多条工作路径如何合并？

版本控制系统通过记录文件随时间发生的变化，使团队能够恢复历史版本、比较修改并管理并行工作。Git 官方文档对版本控制的基本定义，就是记录文件或文件集合随时间的变化，以便之后取回特定版本；Git 本身则采用分布式模型支持不同规模的项目与协作方式。

这使代码从一个当前状态，变成了一段可以查询的演化历史：

```text
Current Code
+
Change History
+
Author
+
Branch
+
Merge
+
Rollback
```

版本控制显著提高了协作能力，但它仍然存在一个重要限制：

> 它记录变化，却不天然理解变化。

Git 可以告诉我们哪些行发生了修改，却不一定能告诉我们：

- 原始业务意图是什么；
- 为什么选择这个方案；
- 哪些替代方案已经被否决；
- 修改所依赖的假设是什么；
- 测试通过究竟证明了什么；
- 这个决定是否仍然适用于今天。

因此，团队又发展出了：

- Commit Message；
- Issue；
- Pull Request；
- Code Review；
- Architecture Decision Record；
- Release Note。

这些机制都在尝试把代码变化重新连接到人类意图和组织决策。

这里已经能看到后来 AI 原生软件工程问题的雏形：

> 单纯记录结果不够，还需要追踪结果背后的意图、上下文、证据和责任。

## 1.6 自动化测试与持续集成：把检查从人脑移入反馈系统

随着系统和团队规模扩大，仅依靠开发者手动确认所有变化是否正确，逐渐变得不可行。

自动化测试把一部分质量判断形式化为可重复执行的断言。

持续集成则进一步要求团队频繁整合代码，并通过自动构建和测试尽早暴露不同修改之间的冲突。Martin Fowler 对持续集成的早期讨论强调，其重要价值之一，就是缩短修改与集成问题被发现之间的时间，避免不同开发者的工作在长期分离后产生难以定位的交互缺陷。

持续交付在此基础上进一步将构建、验证和部署过程组织为可以重复执行的流水线。

这形成了新的反馈结构：

```text
Human Change
    ↓
Version Control
    ↓
Automated Build
    ↓
Automated Tests
    ↓
Deployment Pipeline
    ↓
Human / System Feedback
```

这一阶段非常接近今天 Agent 系统中的 Evidence Engineering。

它确立了一项重要原则：

> 软件质量不能只依赖生产者对自己工作的信心，还需要独立、可重复执行的反馈机制。

开发者说“这个功能应该没问题”，不能替代测试。

某个修改在本机运行，不能替代集成环境验证。

一次部署成功，也不能替代生产监控。

但是，即使 CI/CD 已经承担大量自动检查，传统关系仍未改变：

- 人类决定实现目标；
- 人类设计修改；
- 人类提交代码；
- 自动系统按照预定义规则检查；
- 人类处理规则无法判断的问题。

流水线不会主动重新定义需求，也不会自行决定需要怎样重构整个系统。

它拥有自动执行能力，却不拥有开放式任务解释权。

## 1.7 Agile 与 DevOps：优化人类组织的反馈速度

软件工程后来进一步认识到，问题不只存在于代码进入系统的速度，也存在于需求、开发、测试、运维和用户反馈之间的距离。

2001年的《敏捷软件开发宣言》强调个体互动、可工作的软件、客户协作和响应变化，其核心方向是缩短计划与现实之间的反馈循环，而不是假设所有需求都能在项目开始时被完整预测。

DevOps 和持续交付进一步削弱开发与运维之间的组织断层，让构建、部署、监控和反馈成为更连续的生命周期。

这些变化再次扩大了软件工程的管理对象：

```text
Requirement
→ Design
→ Development
→ Test
→ Deployment
→ Operation
→ User Feedback
→ Requirement Update
```

软件不再被看作一次性交付的静态产品，而是一个持续变化、持续反馈的运行系统。

但无论是 Agile 还是 DevOps，中心角色仍然主要是人类团队。

流程被重新设计，是为了让人类：

- 更快发现错误理解；
- 更早获得真实反馈；
- 更频繁地调整计划；
- 减少部门和阶段之间的信息损耗；
- 更稳定地交付变化。

换句话说，传统软件工程的主要演进路径可以概括为：

```text
更高层的表达
+
更强的协作
+
更快的反馈
+
更多的自动验证
```

这些进步极大增强了人类团队，却没有从根本上改变“谁在理解目标、设计方案和承担主要判断”这一问题。

## 1.8 Copilot：AI 首先作为新一代认知工具出现

生成式 AI 进入软件开发的早期形态，延续了工具增强路径。

开发者提出问题，AI 提供：

- 代码补全；
- 函数实现；
- 错误解释；
- 测试样例；
- 重构建议；
- 文档草稿。

基本关系仍然是：

```text
Human decides
    ↓
AI suggests
    ↓
Human reviews
    ↓
Human applies
```

在这种模式中，AI 类似一种拥有更强语言理解能力的 IDE 功能。

它扩大了开发者能够快速调用的知识范围，也降低了部分局部工作的表达成本。

开发者可以用自然语言描述意图，由 AI 将其转化为代码候选。

这与高级语言替代机器语言存在某种相似性：

```text
Machine Instructions
← High-level Language
← Natural-language Intent
```

人类表达的抽象层级再次上升。

但只要 AI 主要提供局部候选，而人类仍然：

- 选择修改位置；
- 控制任务范围；
- 决定是否采用；
- 亲自运行验证；
- 负责最终集成；

它就仍然主要属于 Copilot 范式。

此时传统软件工程虽然需要适应 AI 生成代码的质量与知识产权问题，却尚未发生完整的生产角色变化。

真正的分界出现在 AI 不再只给出候选，而开始接收一个目标并独立完成多步工程行动时。

---

## 1.9 Agent：AI 开始进入执行闭环

截至2026年，Claude Code 和 Codex 等产品已经明确采用 Agentic Coding 的产品形态。

Claude Code 官方将其描述为能够读取代码库、编辑文件、运行命令并与开发工具集成的 Agentic Coding Tool。其 Agent SDK 则把 Agent 定义为能够自行规划步骤并调用文件、命令和代码编辑工具完成任务的应用。

Claude Code 还提供：

- Plan 模式；
- 权限控制；
- Hooks；
- Skills；
- 项目记忆；
- 独立上下文的 Subagents；
- Worktree 并行工作；
- 自动或专用 Code Review。

其中，Hooks 被官方描述为可以在 Agent 生命周期特定节点执行的确定性控制机制；Subagents 则可以在独立上下文中执行专门任务，只将摘要返回主会话。

Codex 的官方定位也已经从代码生成工具扩展为软件工程 Agent。它能够在隔离环境中执行任务、修改代码、运行测试、处理重构与迁移，并通过 Worktree 和多个 Agent 并行完成不同任务。OpenAI 对 Codex Agent Loop 的技术说明，则明确把模型、工具、上下文和循环控制共同视为 Agent 执行系统的一部分。

此时工作关系已经发生变化：

```text
Human Goal
    ↓
Agent interprets
    ↓
Agent plans
    ↓
Agent selects tools
    ↓
Agent changes system
    ↓
Agent observes results
    ↓
Agent revises
    ↓
Human reviews result
```

AI 不再只生成某个中间产物。

它开始参与：

- 目标解释；
- 任务拆分；
- 路径选择；
- 工具调用；
- 状态观察；
- 错误修正；
- 完成判断。

这就是工具增强与生产者变化之间的关键分界。

## 1.10 工具与 Agent 的差异不在于“是否智能”

把传统工具与 Agent 区分为“没有智能”和“有智能”，并不严谨。

编译器、静态分析器、数据库优化器和自动调度系统都可能包含非常复杂的算法。

真正重要的差异，是它们在生产流程中承担的职责类型。

传统工程工具通常具有以下特征：

1. 输入和输出形式相对明确；
2. 执行规则由人预先定义；
3. 操作边界相对固定；
4. 工具不需要自行解释开放式目标；
5. 失败通常可以映射到相对明确的规则或状态。

Agent 则通常具有以下特征：

1. 接收的是不完全形式化的目标；
2. 需要根据上下文解释任务；
3. 可以在多条路径中选择行动；
4. 会根据工具反馈修改计划；
5. 可能生成原始要求中没有明确指定的中间步骤；
6. 行为受到模型、上下文和环境共同影响；
7. 输出和执行路径具有一定概率性。

因此，Agent 可以被看作：

> 被赋予开放式目标解释能力和工具行动能力的软件执行系统。

它仍然不是人。

它没有天然责任，也不应被简单拟人化为员工。

它的“理解”来自模型对上下文的处理，它的“行动”受到工具与权限限制，它的“记忆”取决于外部存储和加载机制，它的“自治”则完全是系统设计与权限授予的结果。

但从软件工程角度看，它已经不再只是一个被动工具。

它成为了需要被：

- 分配任务；
- 提供上下文；
- 限定权限；
- 观察状态；
- 验证结果；
- 处理失败；
- 管理交接；

的执行主体。

软件工程的管理对象由此发生扩展。

## 1.11 生产者变化为什么比效率变化更重要

假设一个 AI 工具只是让开发者编写同一段代码的速度提高一倍。

这会带来生产率变化，但不会必然要求重新设计整个软件工程体系。

人类仍然理解全部修改，控制全部操作，并能够使用现有 Review、测试和版本控制流程验证结果。

但如果一个 Agent 可以：

- 自行读取数百个文件；
- 判断修改位置；
- 设计实现方案；
- 引入新依赖；
- 调整架构；
- 运行测试；
- 并行调用其他 Agent；
- 根据失败反复修改；
- 最终提交一组大规模变化；

那么变化就不再只是“写得更快”。

此时至少有五个传统前提开始松动。

### 第一，人类不再直接决定所有中间步骤

人类给出的是目标，而不是完整执行过程。

### 第二，人类不再天然拥有全部执行上下文

Agent 可能读取、筛选和压缩了大量信息，其中只有一部分回到人类视野。

### 第三，代码不再完整表达生产过程

还需要追踪：

- Agent 收到了什么 Intent；
- 使用了什么 Context；
- 作出了哪些计划；
- 调用了哪些工具；
- 遇到了哪些失败；
- 为什么选择最终方案。

### 第四，生产速度可能超过验证和理解速度

更多产出并不自动等于更多被验证的价值。

### 第五，权限与能力开始分离

Agent 能够执行某项操作，不意味着组织应允许它自动执行。

这五个变化共同说明：

> 软件工程正在从管理“人类使用工具”转向管理“人类与智能执行系统共同生产”。

---

## 1.12 AI-assisted、Agentic 与 AI-native

为了避免把所有 AI 编程实践都归入同一类别，可以将软件生产形态粗略划分为三个层次。

### 第一层：AI-assisted Development

AI 主要提供局部辅助。

```text
Human controls task
→ AI generates suggestion
→ Human applies and verifies
```

典型特征：

- 人类保持完整执行权；
- AI 输出主要是候选；
- AI 不直接操作生产环境；
- 传统软件工程流程基本不变。

### 第二层：Agentic Development

AI 可以在限定环境中独立完成多步任务。

```text
Human delegates task
→ Agent plans and executes
→ Human reviews result
```

典型特征：

- Agent 可读取项目；
- Agent 可修改文件和运行工具；
- 任务可能持续多个步骤；
- 需要 Sandbox、权限、Plan 和 Review；
- 人类从直接执行转向任务监督。

### 第三层：AI-native Software Engineering

项目从设计之初，就假定人类与多个 Agent 将长期共同生产。

```text
Human Intent
→ Governed Agent Organization
→ Evidence and Cognition Layer
→ Human Decision
→ Memory and Evolution
```

典型特征：

- Intent 被结构化和版本化；
- Context 被视为工程资产；
- Agent 角色和权限被正式定义；
- Review 覆盖执行前、执行中和执行后；
- 完成由 Evidence 支持；
- 人类认知负载被显式管理；
- Memory 和 Skill 受到治理；
- 多 Agent 被组织为生产系统；
- 执行轨迹、责任和成本可以追踪。

这三个层次并非简单的产品代际，也不是所有项目都必须追求最高层级。

很多任务使用 AI-assisted 模式已经足够。

小型、低风险、易验证的任务可能适合 Agentic 模式。

只有当 AI 长期参与复杂项目，并承担持续执行、协作和经验积累时，完整的 AI-native 工程体系才真正必要。

因此，AI-native 不应被理解为：

> 尽可能让 AI 自主。

更准确的理解是：

> 从一开始就按照智能执行者真实存在的条件设计工程系统。

---

## 1.13 软件工程开始管理“生产系统的智能部分”

传统软件工程的直接产物主要是：

- 代码；
- 配置；
- 数据；
- 构建产物；
- 运行系统。

AI 原生软件工程还需要管理一组新的生产资产：

```text
Intent
Context
Agent Contract
Skills
Tools
Permissions
Execution Trace
Evidence
Memory
Evaluation
```

这些资产共同影响 Agent 最终做出什么修改。

例如，同一个模型在以下条件不同的情况下，可能产生完全不同的工程结果：

- 获得的项目文档不同；
- 读取的代码范围不同；
- 使用的 Skill 不同；
- 可以调用的工具不同；
- 文件权限不同；
- 当前 Branch 不同；
- 是否必须先提交 Plan 不同；
- 完成所需 Evidence 不同；
- 历史 Memory 不同。

因此，未来评价一个 AI 开发系统，不能只问：

> 使用了哪个模型？

还要问：

- 模型运行在什么 Harness 中？
- 系统如何构造 Context？
- Agent 可以使用哪些工具？
- 哪些操作需要审批？
- 如何确定当前事实？
- 如何验证完成？
- 如何处理失败和回滚？
- 如何向人类解释变化？
- 如何更新长期记忆？

OpenAI 在关于 Harness Engineering 的实践总结中，也将工程团队的工作描述为逐渐从直接编写代码，转向设计环境、表达意图和建立反馈循环，使 Agent 能够可靠工作。

这正是角色变化的进一步结果：

```text
传统开发者
主要设计软件系统

AI-native 开发者
同时设计软件系统
和生产软件的智能执行系统
```

开发对象由一层变成了两层：

### 第一层：Product System

最终运行的软件产品。

### 第二层：Production Intelligence System

用于理解目标、组织上下文、执行任务、验证结果和积累经验的 Agent 生产系统。

如果第二层缺乏工程设计，更强的模型也可能只是在不稳定环境中更快行动。

---

## 1.14 人类角色不会简单消失，而会重新分配

生产者变化并不意味着人类从软件工程中退出。

更可能发生的是，人类职责从大量直接执行，逐步转向几个更高杠杆的位置。

### 目标与价值判断

Agent 可以优化一个目标，却不能自行决定组织真正应该追求什么目标。

### 约束和责任

哪些风险可以接受，哪些数据不能暴露，哪些体验不能牺牲，最终仍然是人类和组织责任。

### 系统与组织设计

人类需要设计：

- Agent 角色；
- 权限；
- Context；
- Gate；
- Evidence；
- Handoff；
- Intervention；
- Memory 和 Evolution 规则。

### 非形式化质量

很多软件质量无法被简单测试完全表达，例如：

- 产品品味；
- 架构清晰度；
- 用户体验；
- 长期维护成本；
- 业务伦理；
- 战略一致性。

### 最终责任

Agent 没有法律和组织意义上的责任能力。

软件造成的后果，仍然需要由设计、授权、批准和运营它的人类组织承担。

所以更合理的变化不是：

```text
Human Developer
→ Replaced by AI
```

而是：

```text
Human as direct producer
→
Human as intent owner,
system designer,
governor,
reviewer,
and accountable decision-maker
```

这不意味着所有开发者都会成为抽象管理者。

人仍然会写代码、调试和直接设计系统，尤其是在高风险、创新性强或上下文不足的领域。

但“亲自编写每一行代码”将不再是人类拥有软件所有权的唯一基础。

新的基础必须包括：

- 能够解释目标；
- 能够理解系统；
- 能够验证证据；
- 能够判断风险；
- 能够在需要时接管；
- 能够对结果负责。

---

## 1.15 角色变化带来的新问题

当 Agent 进入软件生产闭环后，传统工程问题没有消失，只是增加了一组新问题。

### 意图问题

Agent 是否理解了真正目标？

### 上下文问题

Agent 得到的信息是否正确、相关且没有过期？

### 事实问题

文档、代码、测试、运行时和 Assumption 冲突时，应当相信什么？

### 执行问题

Agent 是否遵循正确范围和路径？

### 可靠性问题

概率性执行如何被限制、恢复和重现？

### 验证问题

Agent 声称完成时，什么证据足以支持这个结论？

### Review 问题

Review 应发生在什么时候，又应检查代码、计划还是证据？

### 认知问题

当 AI 生产速度超过人类理解速度时，如何防止 Review 形式化和认知债累积？

### 治理问题

Agent 可以自动执行到什么程度？

### 记忆问题

哪些经验应被保留，错误经验又如何被清除？

### 组织问题

多个 Agent 如何分工、交接、解决冲突并向人类升级？

### 责任问题

当修改由 Agent 生成、Reviewer Agent 检查、人类批准时，责任如何分配和追踪？

这些问题共同构成了本书后续讨论的主体。

---

## 1.16 本章结论：软件工程的管理对象正在扩展

回顾软件工程的发展，可以看到一条持续演进的路径：

```text
机器语言
→ 高级语言
→ IDE
→ 版本控制
→ 自动化测试
→ CI/CD
→ Agile / DevOps
→ AI Copilot
→ AI Agent
```

每一步都扩大了人类能够建设和管理的软件规模。

但此前大多数工具主要完成三类工作：

- 提高人类表达层级；
- 加速人类协作；
- 自动执行形式化规则。

Agent 首次开始大规模承担另一类工作：

- 解释开放式目标；
- 选择执行路径；
- 调用多种工具；
- 根据环境反馈调整；
- 产出人类未逐步指定的系统变化。

因此，AI Agent 并不只是软件工具链中的又一个更强组件。

它使软件工程需要同时管理：

```text
Software Complexity
+
Human Collaboration Complexity
+
Agent Behavior Complexity
```

传统软件工程关注如何让人类可靠地建设复杂系统。

AI 原生软件工程则需要进一步回答：

> 如何让人类与智能代理共同建设复杂系统，并在扩大生产能力的同时，保持意图清晰、事实可信、执行可控、结果可验证和责任可追踪？

这不是对传统软件工程的否定。

它是传统软件工程在生产者构成发生变化之后的下一次扩展。

代码仍然是核心资产。

测试、架构、版本控制和 DevOps 仍然是基础。

但从现在开始，软件工程还必须管理生产代码的智能系统本身。

这就是从工具增强到智能协作的真正含义。

# 本章原则

## 原则一：区分效率提升与角色变化

AI 生成代码更快，不一定意味着进入了 AI 原生软件工程。

真正的分界是：

> AI 是否开始解释目标、选择路径并实际改变系统。

## 原则二：Agent 不是普通工具，也不是人类员工

Agent 应被视为：

> 具有开放式目标解释能力、上下文依赖和工具行动能力的软件执行系统。

## 原则三：传统软件工程仍是基础

AI 不会替代：

- 架构；
- 测试；
- 版本控制；
- CI/CD；
- 安全；
- 质量管理。

它要求这些能力进一步扩展。

## 原则四：模型不是完整生产系统

最终结果由以下因素共同决定：

```text
Model
× Context
× Tools
× Permissions
× Workflow
× Evidence
× Human Decisions
```

## 原则五：AI-native 不等于最大自治

AI-native 的核心是：

> 按照 Agent 真实存在的条件设计软件工程，而不是默认把所有工作交给 Agent。

# 常见反模式

## 反模式一：把代码生成能力等同于软件工程能力

能写代码，不等于能理解长期项目、控制风险和完成可靠交付。

## 反模式二：把 Agent 当作更快的程序员

这种比喻容易掩盖 Agent 在责任、记忆、稳定性和上下文方面与人类的根本差异。

## 反模式三：只升级模型，不升级工程环境

更强模型运行在混乱 Context、宽松权限和弱验证环境中，仍可能产生更大范围的问题。

## 反模式四：沿用传统 Review，不控制 Agent 产出规模

如果 AI 的修改规模超过人工理解能力，保留 Pull Request 并不意味着保留了有效 Review。

## 反模式五：把 AI-native 理解成无人化开发

真正的 AI 原生软件工程强调受治理协作，而不是取消人类判断和责任。

# 本章检查清单

在判断一个开发流程是否正在从 AI-assisted 走向 Agentic 或 AI-native 时，可以检查：

- AI 是否直接修改项目？
- AI 是否自行决定修改位置和执行步骤？
- AI 是否调用测试、Git、构建或部署工具？
- AI 是否根据中间结果改变计划？
- AI 是否拥有长期项目 Context？
- AI 是否可以并行调用其他 Agent？
- 人类是否仍然理解主要变化？
- 完成是否由独立 Evidence 支持？
- 是否存在明确权限和停止条件？
- 是否能追踪 Agent 使用的 Context 和执行路径？
- 是否能在失败后回滚和恢复？
- Memory 和 Skill 是否受到治理？
- 最终责任是否明确？

回答“是”的项目越多，软件工程需要管理的就越不只是代码生成，而是一个真正的智能生产系统。
