# 第4章  
# Intent Engineering：从模糊需求到可执行意图

前三章完成了本书的总论部分。

我们已经讨论了：

- 为什么 AI Agent 带来的变化不只是编码效率提升；
- 为什么传统软件工程的一些隐含前提在 Agent 环境下开始变得不再可靠；
- 什么是 AI-Native Software Engineering；
- Agent Harness、Agentic Execution 与完整 AI 原生软件工程之间有什么区别。

从这一章开始，我们进入具体方法论。

第一个问题不是：

> Agent 应该使用什么模型？

也不是：

> Agent 应该调用什么工具？

而是一个看起来更基础、实际上更困难的问题：

> **人到底想让 Agent 做什么？**

这句话看起来简单。

现实软件项目里却很少存在完全明确、没有歧义、没有隐含背景、不会发生变化的需求。

一个人说：

> “把这个 UI 优化一下。”

可能真正想解决的是信息层级。

也可能是视觉风格。

也可能是战斗中读取速度。

也可能是某个高风险状态没有被玩家及时注意到。

如果 Agent 只是把字体放大、颜色调亮，然后运行测试并报告完成，从字面上看它可能执行得非常高效。

但它也可能完全没有解决真正的问题。

这就是 AI 原生软件工程面对的第一类风险：

> **Agent 可以高效执行一个错误理解的目标。**

传统软件工程同样长期面对需求理解问题。

区别在于，人类团队中大量模糊信息过去可以通过会议、经验、默契、追问和临场判断被补齐。

当任务直接交给 Agent 后，这种 Human Smoothing Effect 不能被稳定依赖。

因此，软件工程需要把过去大量存在于人脑和团队关系中的“真实意图”，逐渐显式化为一个可以被系统处理的工程对象。

这就是本章所说的：

# Intent Engineering

---

# 4.1 Requirement 不等于 Intent

传统软件工程已经拥有成熟的 Requirements Engineering。

为什么还需要 Intent Engineering？

首先必须避免重新命名一个已经存在的问题。

Requirements Engineering 关注：

- 用户需要什么；
- 系统应具备什么功能；
- 非功能需求是什么；
- 利益相关者之间有什么冲突；
- 如何验证需求；
- 需求如何变化和追踪。

这些问题在 AI 环境中仍然成立。

Intent Engineering 并不是取代 Requirements Engineering。

它更像是：

> **当需求开始直接驱动具有自主解释和执行能力的 Agent 时，对需求表达、执行边界和验证条件进一步工程化。**

传统需求可能写：

> 玩家状态栏需要更清楚地显示当前 Stage。

对于人类团队，这句话可能已经足够启动讨论。

策划知道为什么。

UI Designer 知道现有问题。

程序知道当前结构。

制作人知道哪些方向已经被否决。

QA 知道实际需要验证什么。

需求本身只是团队共享认知网络中的一个入口。

但对于一个 Agent：

```text
"Make Stage information clearer."
```

这句话可能只是：

> 一段需要自行解释的自然语言。

Agent 必须自行推断：

- “更清楚”是什么意思；
- 哪个信息需要更突出；
- 当前问题是什么；
- 什么不能改变；
- 哪些方案已经被否决；
- 如何判断真的变好了。

因此：

```text
Requirement
≠
Execution-ready Intent
```

Intent Engineering 的目标就是完成中间这一步。

---

# 4.2 Intent 是“为什么、什么、边界和完成条件”的组合

在本书中，Intent 不是一句命令。

也不是 Prompt 的另一个名字。

一个完整 Intent 至少回答四类问题：

```text
WHY
WHAT
BOUNDARY
DONE
```

即：

### WHY

为什么要做？

### WHAT

真正想实现什么结果？

### BOUNDARY

什么不能被破坏、扩大或擅自决定？

### DONE

什么证据能够说明目标已经达成？

因此，一个 Intent 可以表示为：

```text
Intent
├── Motivation
├── Goal
├── Scope
├── Non-goals
├── Constraints
├── Assumptions
├── Acceptance Criteria
├── Required Evidence
└── Human Decision Points
```

这与普通 Task Description 的区别非常重要。

Task 常常描述：

> 做什么动作。

Intent 描述：

> **为什么做、期望什么结果、允许怎样变化、什么不能变化，以及如何判断结果。**

---

# 4.3 Intent over Instruction

这是本书的第一条核心设计原则：

> **Intent over Instruction。**

中文可以理解为：

> **意图优先于操作指令。**

这并不是说步骤没有价值。

而是：

> 对具有自主推理能力的 Agent，首先应该定义正确目标与边界，而不是直接规定一连串机械动作。

例如，一个任务：

> 优化 Player Status 顶部 Stage / Limit 信息。

一种写法是：

```text
1. 打开 PlayerStatus.gd
2. 把 Stage 字体改成 24px
3. 左移 12px
4. 增加黄色描边
5. 保存
```

这非常明确。

但它实际上已经决定了实现方案。

Agent 不再需要理解问题。

它只是执行一个脚本。

如果当前真正的问题是：

- Stage 与 HP 层级冲突；
- Stage 信息占据过多横向空间；
- 颜色与战斗场景对比不足；
- 字体增大反而压缩其他资源；

那么这套精确指令可能精确地执行一个错误方案。

---

另一种写法是：

```text
Goal:
提高战斗中 Stage / Limit 状态的瞬时可读性。

Motivation:
当前顶部信息层级弱于 HP / Block，
玩家容易忽略 Stage 状态变化。

Must preserve:
- 已接受的 HP / Block 方向
- 当前 runtime 数据结构
- gourd / item 信息完整性

Non-goals:
- 不重构 combat logic
- 不改变 Stage 数值规则
- 不重新设计整个 HUD

Evidence:
- runtime screenshot
- before / after comparison
- 目标分辨率下可读性检查

Escalate if:
- 需要修改 runtime data model
- 需要改变整体 HUD layout
```

这里没有告诉 Agent：

> 字体必须改多少。

但它明确规定了：

- 问题；
- 目标；
- 不可破坏部分；
- 证据；
- 升级条件。

这才符合：

> **Tight Boundaries, Flexible Execution。**

Agent 在边界内拥有解决问题的空间。

---

# 4.4 Instruction 什么时候仍然必要

Intent over Instruction 并不意味着永远不要给具体步骤。

在以下情况中，Instruction 可能非常合理。

---

## 确定性操作

例如：

> 将这个文件从 A 路径移动到 B 路径。

这里没有必要让 Agent重新设计路径。

---

## 高风险程序

例如数据库迁移：

```text
Backup
→ Verify
→ Migration
→ Validation
→ Rollback Check
```

特定步骤可能属于安全协议。

---

## 工具限制

某些内部系统必须按照固定流程使用。

---

## 法规或安全要求

例如某些操作必须经过：

- Approval；
- Audit；
- Signature。

---

## 可重复机械工作

Agent 的自由推理没有明显价值。

---

因此，更准确的原则不是：

```text
Intent good
Instruction bad
```

而是：

> **在需要智能判断的问题上优先表达 Intent；在确定性、安全性或合规性要求较高的步骤上使用 Instruction。**

两者可以共同存在。

---

# 4.5 为什么 Motivation 必须被保留

传统 Task 经常只有：

> What。

例如：

> 把角色状态 UI 缩短 15%。

但如果 Agent 不知道 Why，它就很难判断：

- 哪些结果值得保留；
- 什么属于等价解决；
- 什么时候应该挑战原方案。

Motivation 是：

> 当前动作背后的问题定义。

例如：

```text
Instruction:
把 UI 缩短 15%。

Motivation:
当前 UI 在 16:9 分辨率下与右侧敌人状态重叠。
```

如果 Agent 发现：

> 缩短 12% 已经可以消除冲突，同时保持更好的可读性，

它是否应该坚持 15%？

如果 Instruction 是最终规定：

应该。

如果 15% 只是人提出的初始解决方案，而真正 Intent 是：

> 消除重叠同时最大程度保持可读性，

那么 Agent 应该有机会提出更好的方案。

因此：

> **Motivation 让 Agent 能够区分“目标”和“人提出的第一种解决方法”。**

这在 AI 环境中非常重要。

因为强 Agent 最大的价值之一，就是：

> 能够在理解目标后发现更好的执行路径。

如果只给它步骤，我们实际上主动关闭了这部分能力。

---

# 4.6 Goal：描述结果，而不是活动

一个好的 Goal 应尽量描述：

> 完成以后世界发生了什么变化。

而不是：

> Agent 做了什么。

例如：

差的 Goal：

```text
重构 SaveManager。
```

这是 Activity。

为什么重构？

重构到什么程度？

---

更好的 Goal：

```text
使 SaveManager 的版本迁移逻辑能够独立测试，
并减少新增 Save Version 时对主加载流程的修改。
```

这是 Outcome。

---

同样：

差：

> 优化加载速度。

更好：

> 在目标测试场景中，将冷启动时间降低到 2 秒以内，同时不增加超过 100 MB 的常驻内存。

---

因此可以区分：

```text
Activity
→ what work happens

Outcome
→ what changes when work succeeds
```

Intent Engineering 应优先表达 Outcome。

---

# 4.7 Non-goal：告诉 Agent 什么“不应该顺便做”

Non-goal 是 AI 环境中非常重要，却经常被忽略的内容。

人类开发者通常会根据经验理解：

> 这个任务虽然相关，但现在不要碰。

Agent 如果发现：

> 当前问题可以通过更大的架构重构解决，

它可能非常积极地继续扩大范围。

这种行为从局部推理上甚至可能是合理的。

例如：

任务：

> 修复 Item Tooltip 显示错误。

Agent 发现：

> Tooltip 数据来自旧 Item Metadata 架构。

于是决定：

> 顺便重构整个 Item Database。

技术上可能很漂亮。

工程上却可能完全错误。

因为当前 Sprint：

- 不允许动存档；
- 另一个功能依赖旧结构；
- Item Database 重构计划在下一个版本进行。

因此，一个好的 Intent 应明确：

```text
Non-goals:
- 不迁移 Item Database
- 不修改 Save Schema
- 不重新设计 Item Definition
```

Non-goal 的价值是：

> **限制合理但不属于当前任务的优化冲动。**

这对于高能力 Agent 尤其重要。

模型越强，越可能看到更大的解决空间。

但项目管理的核心从来不是：

> 所有值得做的事情都现在做。

而是：

> **正确的事情在正确时间做。**

---

# 4.8 Constraint：把真实工程世界带进 Intent

Goal 描述：

> 想实现什么。

Constraint 描述：

> 必须在什么现实条件下实现。

软件项目中的 Constraint 可能包括：

### 技术约束

- Godot 4.x；
- 不引入新第三方库；
- 必须支持旧 Save；
- 不改变 Public API。

### 性能约束

- 内存；
- CPU；
- 帧率；
- 包体。

### 平台约束

- Windows；
- Quest；
- PS5；
- Web。

### 产品约束

- 保留已确认交互；
- 不改变核心玩法；
- 不影响现有用户数据。

### 时间约束

- 当前 Sprint；
- Release Freeze；
- Hotfix 范围。

### 安全约束

- 不访问 Production；
- 不输出 Secret；
- 不修改权限策略。

Constraint 与 Goal 一起构成：

```text
Desired Outcome
within
Allowed Reality
```

没有 Constraint 的 Goal，很容易变成理想化优化。

---

# 4.9 Assumption：必须允许未知存在

一个常见错误是：

> 为了让 Intent 更精确，把所有不确定性都伪装成确定事实。

这反而很危险。

现实项目中，人经常不知道全部信息。

例如：

> “我认为这个问题只发生在 16:9。”

这不是 Truth。

是 Assumption。

如果直接写成：

> “问题只发生在 16:9。”

Agent 就可能完全不检查 21:9 或 Steam Deck。

因此 Intent 应明确允许：

```text
Assumption:
问题目前观察到主要发生在 16:9；
尚未验证其他 aspect ratio。
```

Assumption 的工程价值在于：

> **允许系统在不知道时明确说不知道。**

而不是让模型自动填满空白。

---

# 4.10 Assumption 不是自由想象的许可证

因为 Agent 擅长推断，所以 Assumption Layer 也可能带来另一个风险：

> Agent 开始制造大量没有来源的假设。

因此，Assumption 至少应该包含：

```text
Statement
Source
Confidence
Impact
Validation Method
Expiry
```

例如：

```text
Assumption:
Stage layout issue may be caused by width allocation.

Source:
runtime screenshot + current layout code

Confidence:
medium

Impact:
may affect proposed UI direction

Validation:
capture at 1920x1080 and 2560x1440
```

关键原则是：

> **Assumption 必须显式，而且必须有验证路径。**

它不能静默升级为 Truth。

---

# 4.11 Acceptance Criteria：把“感觉完成”变成工程完成

如果 Goal 是：

> UI 更清楚。

Agent 如何判断完成？

没有 Acceptance Criteria 时，它只能：

- 自己判断；
- 根据通用审美；
- 根据 Prompt 语气；
- 或直接询问人。

这会把完成判断重新变成模糊推理。

因此 Intent Engineering 必须与 Verification Engineering 在一开始就连接起来。

例如：

```text
Goal:
提升 Stage 状态可读性。
```

Acceptance Criteria 可以是：

```text
AC1:
Stage 状态在目标运行分辨率中
不与 HP / Block 竞争主要视觉层级。

AC2:
玩家在正常战斗截图中可以在一眼内定位 Stage 状态。

AC3:
现有 HP / Block / gourd / item 信息仍完整。

AC4:
不修改 combat logic 和 Stage calculation。
```

这里仍然有主观部分。

但主观并不是问题。

真正的问题是：

> 主观目标有没有被显式定义成要验证的对象。

---

# 4.12 Acceptance Criterion 与 Evidence 必须成对设计

这是 Intent Engineering 与 Evidence Engineering 的关键连接。

一个 Acceptance Criterion 如果没有验证方式，往往只是愿望。

因此可以建立：

```text
Acceptance Criterion
        ↓
Evidence Requirement
```

例如：

| Acceptance Criterion | Evidence |
|---|---|
| Build 不失败 | Build Log |
| 旧 Save 可加载 | Migration Test |
| UI 不重叠 | Runtime Screenshot |
| 性能不下降 | Benchmark |
| API 不变化 | API Diff |
| 玩家更容易识别状态 | Human Visual Review / UX Test |

于是 Intent 不只是：

> 告诉 Agent做什么。

它同时告诉系统：

> **未来如何证明 Agent 做到了。**

这会显著减少后期 Review 的模糊性。

---

# 4.13 Required Evidence 应在执行前定义

一个常见低质量流程是：

```text
Agent executes
    ↓
Agent finishes
    ↓
Then asks:
How should I prove it?
```

这时往往已经太晚。

因为如果一开始没有准备：

- 测试环境；
- Benchmark；
- Before Snapshot；
- Baseline；
- 数据样本；

很多证据无法事后可靠补齐。

例如性能优化。

如果修改前没有 Baseline：

修改后说：

> 现在 4.8 ms。

并不能证明优化有效。

因此：

> **Evidence Planning 是 Intent Engineering 的一部分。**

执行前至少应该知道：

```text
What must be proven?
How will it be proven?
What baseline is required?
```

---

# 4.14 Human Decision Points：明确 Agent 不能自己跨越的判断

不是所有问题都应该在任务开始前完全决定。

有些任务会在执行中发现新的信息。

因此 Intent 还应该定义：

> 什么情况下必须回到 Human。

例如：

```text
Escalate if:
- 需要修改 public API
- 需要引入外部 dependency
- 发现当前文档与 runtime 不一致
- 需要迁移 Save Schema
- 核心玩法行为必须改变
```

这比一句：

> “有问题问我。”

更工程化。

因为“有问题”是模糊条件。

Agent 很可能认为：

> 我能解决，所以不算问题。

真正应该定义的是：

> **Decision Right。**

即：

哪些决定属于 Agent。

哪些决定属于人。

---

# 4.15 Intent Object：把意图变成正式工程对象

综合前面的内容，可以定义一个基础 Intent Object。

例如：

```text
Intent

ID:
Owner:
Version:

Motivation:
Goal:

Scope:
Non-goals:

Constraints:
Assumptions:

Truth Baseline:

Acceptance Criteria:
Required Evidence:

Allowed Authority:
Human Decision Points:

Priority:
Risk Level:

Related Decisions:
Related Tasks:
```

这个结构并不要求所有项目都使用同一种格式。

它真正重要的是：

> Intent 开始具有明确 Schema。

当 Intent 具有 Schema 以后，就可以：

- Version；
- Compare；
- Review；
- Validate；
- Trace；
- Link Evidence；
- Link Decision；
- Feed Agent。

于是 Intent 从：

```text
Conversation
```

逐渐变成：

```text
Engineering Artifact
```

---

# 4.16 Intent 不是 Prompt

这是一个必须明确的边界。

Prompt 是：

> 某一次模型调用的输入。

Intent 是：

> 项目层面的目标对象。

同一个 Intent 可以被不同系统消费：

```text
Intent
  ├── Controller Agent
  ├── Worker
  ├── Reviewer
  ├── QA
  ├── Human
  └── Evidence System
```

而每个角色可能需要不同 Prompt。

例如：

Controller Prompt：

> 根据 Intent 制定任务计划。

Worker Prompt：

> 在给定 Scope 内完成实现。

Review Prompt：

> 根据 Acceptance Criteria 检查结果。

因此：

```text
Intent
≠
Prompt
```

更合理的是：

```text
Intent
    ↓
Context + Role + Policy
    ↓
Prompt / Agent Input
```

Intent 是上游资产。

Prompt 是运行时表达。

---

# 4.17 为什么 Intent 需要独立于具体模型

如果 Intent 与某个模型 Prompt 高度绑定，例如：

```text
You are Claude...
First think...
Then...
```

那么更换：

- Model；
- Agent Runtime；
- Tool；
- Workflow；

时，项目目标就会和执行机制纠缠在一起。

一个更稳定的架构应该是：

```text
Stable Intent
      ↓
Runtime Adapter
      ↓
Claude Code / Codex / Other Agent
```

也就是说：

> **Intent 应尽可能是 Model-agnostic。**

模型可能换。

执行路径可能换。

目标不应该因为 Runtime 变化而丢失。

---

# 4.18 Intent Decomposition：从 Outcome 到 Task

一个复杂 Intent 通常不能直接交给单个 Worker。

需要拆解。

但拆解存在一个巨大风险：

> 原始意义在层层任务分解中丢失。

例如：

```text
Intent:
提升新玩家前三场战斗对防御机制的理解
```

拆成：

```text
Task 1:
改 Tooltip

Task 2:
改 Block Icon

Task 3:
增加 Tutorial Text
```

几轮以后，Worker 只知道：

> 调整 Block Icon。

它不知道：

> 最终目标是帮助新玩家理解防御机制。

于是局部任务可能越来越偏向视觉优化。

这就是：

> **Intent Dilution。**

---

# 4.19 Intent Inheritance

解决这个问题的一种方法是：

> 子任务继承必要的父级 Intent。

例如：

```text
Parent Intent:
提高新玩家对防御机制的理解

Worker Goal:
优化 Block Icon

Why:
Block 的语义辨识度不足，
是新玩家理解问题的一部分

Local Scope:
Block Icon only

Must preserve:
HP visual hierarchy
```

这意味着 Task 不应该只有局部动作。

还需要保存：

```text
Local Goal
+
Parent Intent
```

这样 Worker 才知道：

> 自己为什么存在。

---

# 4.20 Intent Decomposition 的三层结构

一个实用模型是：

```text
Outcome
    ↓
Capability / Milestone
    ↓
Task
```

例如：

```text
Outcome:
提高 Player Status 的战斗读取效率

Capability:
建立清晰的 Stage / HP / Block 信息层级

Tasks:
- Stage visual optimization
- HP / Block spacing adjustment
- runtime capture validation
```

这里 Outcome 不应该随着任务拆分消失。

每一个 Task 都需要能追溯到：

> 它支持哪个上级 Outcome。

---

# 4.21 Local Optimization Trap

Agent 很容易完成局部优化。

软件工程最危险的问题之一却是：

> 局部成功破坏整体目标。

例如：

Worker：

> 为提高 Stage 可读性，把 Stage 做得非常大。

局部 Goal：

成功。

整体 Player Status：

失败。

因此每个任务至少需要两种验收：

```text
Local Acceptance
+
Parent Intent Alignment
```

也就是说：

> 不仅要问这个 Worker 有没有完成任务，还要问这个结果有没有继续服务上一级 Intent。

---

# 4.22 Intent Drift：目标如何在长期项目中逐渐改变

即使最初 Intent 很清楚，长期项目仍会发生漂移。

Intent Drift 的来源很多。

---

## 需求变化

业务真的改变了目标。

这是正常变化。

---

## 局部实现替代原始目标

例如原来：

> 提高读取效率。

后来讨论全部变成：

> 字体大小多少。

手段逐渐替代目标。

---

## Agent 推断固化

Agent 曾经做出一个合理假设：

> Stage 应该视觉优先。

几轮任务以后，这个 Assumption 被不断引用，最后变成事实。

---

## Context Compression

长历史被压缩以后：

> 为什么做

被压成：

> 现在怎么做。

---

## Handoff Loss

Controller → Worker → Review → 新 Worker。

每次传递都可能丢掉：

- Motivation；
- Non-goal；
- Constraint。

---

## 人类自己改变了想法

这个同样非常常见。

但如果没有记录：

> 什么时候改变、为什么改变，

后续 Agent 会面对多个互相冲突的 Intent。

---

# 4.23 Intent Drift 不一定是错误

需要区分：

```text
Intent Evolution
vs
Intent Drift
```

Intent Evolution：

> 人类明确决定改变目标。

Intent Drift：

> 目标在没有明确决策的情况下逐渐变化。

因此重要的不是：

> Intent 永远不能改变。

而是：

> **变化必须显式。**

---

# 4.24 Intent Versioning

如果 Intent 是正式工程对象，它就应该有版本。

例如：

```text
INT-SP122-001 v1
Goal:
提高 Stage 可读性

v2
Added:
不得增加 HUD 总高度

Reason:
runtime capture showed bottom overlap
```

版本化的价值：

- 知道当前执行基于哪个 Intent；
- 解释历史结果为什么不同；
- 避免 Worker 使用旧目标；
- 支持 Decision Trace。

---

# 4.25 Intent Registry

当项目规模扩大后，可以建立 Intent Registry。

它不是简单的 Task List。

Task List 回答：

> 有哪些事情要做？

Intent Registry 回答：

> **当前项目为什么在做这些事情？**

可以包含：

```text
Intent ID
Status
Owner
Version
Goal
Parent Intent
Children
Constraints
Decision History
Evidence Status
```

这形成一种：

```text
Intent Graph
```

例如：

```text
Product Intent
    ↓
Feature Intent
    ↓
Sprint Intent
    ↓
Task Intent
```

任务可以关闭。

Intent 可能继续存在。

这两者不应该混淆。

---

# 4.26 Intent Owner

Intent 需要 Owner。

因为 Agent 不能成为最终目标的责任主体。

Owner 负责：

- 解释目标；
- 批准重大变化；
- 判断目标是否仍然有效；
- 解决利益冲突；
- 接受最终 Outcome。

在不同规模项目中可能是：

- Developer；
- Product Owner；
- Producer；
- Tech Lead；
- Architect；
- Team。

Owner 不意味着：

> 每一步都要亲自批准。

而是：

> **最终目标归属清晰。**

---

# 4.27 Controller 在 Intent Engineering 中的职责

在 Controller / Worker 模式里，Controller 最重要的职责之一不是：

> 分任务。

而是：

> **维持 Intent Continuity。**

也就是：

在多个 Worker、多个 Thread 和长时间执行中，确保原始目标没有消失。

Controller 应负责：

### Intent Interpretation

把人类表达转成执行对象。

### Intent Distribution

为不同 Worker 提供必要层级的 Parent Intent。

### Scope Assignment

为每个 Worker 定义局部范围。

### Drift Detection

检查局部结果是否偏离整体目标。

### Escalation

需要改变 Intent 时回到人类。

因此：

```text
Controller
≠
Message Router
```

更接近：

> **Intent Custodian。**

即意图的维护者。

---

# 4.28 Worker 不应该自行重写 Intent

Worker 在执行中当然可能发现：

> 原目标不可行。

例如：

- 技术限制；
- 当前架构不支持；
- 需求冲突；
- 风险超过预期。

但正确行为通常不是：

```text
Original Intent
    ↓
Worker rewrites goal
    ↓
Continue
```

而应该是：

```text
Conflict detected
    ↓
Evidence
    ↓
Escalation
    ↓
Intent Decision
```

这就是：

> Tight Boundaries。

Agent 可以灵活执行。

但不能随意移动自己的球门。

---

# 4.29 Intent 与 Truth 必须分离

Intent Engineering 很容易和 Truth Architecture 混在一起。

例如文档：

> 系统支持三种 Save Version。

这句话可能是：

### Intent

未来目标：

> 我们计划支持三种。

也可能是：

### Truth Claim

当前系统已经支持三种。

如果 Agent 无法区分，它可能：

> 根据未来设计假设当前代码已经存在某能力。

因此：

```text
Intent
=
Desired State

Truth
=
Verified Current State
```

Intent 告诉系统：

> 去哪里。

Truth 告诉系统：

> 现在在哪里。

没有 Truth 的 Intent，就像：

> 只知道目的地，不知道出发点。

---

# 4.30 Intent 与 Context 也必须分离

Intent 回答：

> 要做什么。

Context 回答：

> 为了完成它，应该知道什么。

例如：

Intent：

> 保持 HP / Block 已接受方向，只优化 Stage。

Context：

- 当前 PlayerStatus 文件；
- v017 screenshot；
- 设计历史；
- HUD style guide；
- current commit。

不要把所有 Context 塞进 Intent。

否则 Intent 会变成巨大的项目知识包。

两者应该：

```text
Intent
+
Context
```

组合，而不是合并。

---

# 4.31 Intent 与 Contract 的关系

Agent Contract 也不是 Intent。

Intent：

> 描述目标。

Contract：

> 描述某个 Agent 在这个目标下如何被使用。

例如：

```text
Intent:
优化 Stage 信息层级
```

Controller Contract：

```text
负责拆分、分配和保持全局目标。
```

Worker Contract：

```text
只修改 Player Status UI 范围，
必须返回 runtime evidence。
```

Reviewer Contract：

```text
检查视觉结果和 scope violation，
不能自行修改实现。
```

因此：

```text
One Intent
    ↓
Multiple Agent Contracts
```

这是 Multi-Agent Organization 的基础。

---

# 4.32 Intent Review：执行前第一道 Gate

如果 AI 可以快速执行，错误 Intent 的成本会被迅速放大。

因此在高风险任务中，最值得 Review 的东西之一不是代码。

而是：

> **Intent 本身。**

Intent Review 可以检查：

- Goal 是否清楚？
- Motivation 是否真实？
- Scope 是否合理？
- Non-goal 是否遗漏？
- Constraint 是否冲突？
- Assumption 是否伪装成事实？
- Acceptance 是否可验证？
- Evidence 是否可获得？
- Decision Right 是否清楚？

这是：

> Pre-execution Review 的最前端。

---

# 4.33 Intent Quality 的几个判断维度

可以定义一组基础质量维度。

---

## Clarity

不同执行者是否会得到大致相同的问题理解？

---

## Completeness

完成任务所需的关键边界是否存在？

---

## Testability

目标是否能够被验证？

---

## Traceability

能否追溯到上级目标和相关决策？

---

## Stability

哪些部分稳定，哪些仍可能变化？

---

## Risk Awareness

是否显式暴露高风险假设和决策点？

---

## Delegability

是否足够明确，可以交给另一个执行者而不依赖大量隐性知识？

其中最后一项：

> **Delegability**

对于 Agent 尤其重要。

如果一个 Intent 只有原作者自己知道是什么意思：

它不是一个适合委托的 Intent。

---

# 4.34 一个简单的 Intent Readiness Gate

在任务交给 Agent 前，可以检查：

```text
Goal clear?
Why clear?
Scope clear?
Non-goal clear?
Truth baseline known?
Critical assumptions explicit?
Acceptance defined?
Evidence feasible?
Escalation defined?
```

如果大部分答案是否定的：

> 更强模型通常也不能从根本上解决问题。

它只是会更聪明地猜。

---

# 4.35 Intent Precision 不等于 Intent Length

Intent Engineering 很容易退化成：

> 写越来越长的任务说明。

这是错误方向。

更长不代表更精确。

例如：

5000 字历史背景，可能仍然没有说清：

> 当前任务到底不能动什么。

真正的 Precision 来自：

- 结构；
- 边界；
- 层级；
- 可验证性。

一个高质量 Intent 可能很短：

```text
Goal:
修复启动崩溃。

Scope:
Startup config loader only.

Constraint:
不得修改 config schema。

Evidence:
3 个历史 config 样本全部可启动。

Escalate:
如果需要 schema migration。
```

比几千字散文式描述更可执行。

因此：

> **Structured brevity often beats unstructured completeness.**

可以翻译为：

> **结构化的简洁，往往优于无结构的完整。**

---

# 4.36 Intent Engineering 不应该制造新的文档负担

如果每个两分钟修改都需要：

- Motivation；
- Parent Intent；
- Non-goal；
- Risk；
- Evidence；
- Approval；

那系统很快就会变得无法使用。

因此同样需要 Adaptive Governance。

---

## Low-risk Intent

例如：

> 修正文档 typo。

可能只需要：

```text
Goal
Scope
```

---

## Medium-risk Intent

例如：

> 局部 UI 修改。

需要：

```text
Goal
Constraint
Non-goal
Evidence
```

---

## High-risk Intent

例如：

> 数据迁移。

需要完整：

```text
Motivation
Goal
Scope
Non-goal
Constraint
Truth Baseline
Assumption
Acceptance
Evidence
Risk
Rollback
Human Decision Point
```

所以：

> **Intent Schema 可以分层，而不是所有任务使用同一模板。**

---

# 4.37 Intent Profiles

可以建立不同 Profile。

例如：

### Lean

```text
Goal
Scope
Done
```

### Standard

```text
Motivation
Goal
Scope
Non-goal
Constraint
Acceptance
Evidence
```

### Expanded

增加：

```text
Assumption
Truth Baseline
Risk
Decision Point
Parent Intent
```

### Full

增加：

```text
Version
Decision History
Rollback
Dependencies
Evidence Mapping
Governance
```

这种设计与 Context Pack 的 Lean / Standard / Expanded / Full 思路高度一致。

原则不是：

> 越完整越好。

而是：

> **风险越高，需要越完整的 Intent。**

---

# 4.38 AI 可以帮助生成 Intent，但不能拥有 Intent

这里存在一个有趣的悖论。

Intent Engineering 很复杂。

为什么不让 AI 自己生成？

当然可以。

Agent 非常适合：

- 总结需求；
- 发现歧义；
- 提取 Constraint；
- 提议 Non-goal；
- 生成 Acceptance；
- 找出缺失 Evidence。

例如人说：

> 帮我优化这个界面。

AI 可以返回：

```text
Possible intent:
- improve combat readability
- preserve HP/Block hierarchy

Open questions:
- Stage priority?
- target resolution?
```

这是非常有价值的。

但 AI 应该：

> **帮助形成 Intent。**

而不是：

> **最终拥有 Intent。**

因为目标最终来自：

- 用户；
- 产品；
- 业务；
- 组织；
- 人类价值判断。

Agent 可以提出：

> 我认为真正问题是 X。

但最终决定：

> 是否把 X 作为正式目标，

应该属于 Intent Owner。

---

# 4.39 Intent Confirmation 不应该变成无休止追问

另一个极端是：

为了避免误解，Agent 每次都不断问：

> 你确定吗？

> 那这个呢？

> 那那个呢？

这同样降低生产率。

Intent Engineering 的目标不是：

> 消除一切不确定性。

而是区分：

### 可以合理假设的

低影响、可逆。

### 应显式记录的 Assumption

有一定影响，但可验证。

### 必须询问的

高影响、不可逆、涉及核心目标。

这就是：

> Risk-based Clarification。

Agent 是否需要追问，也应该由风险决定。

---

# 4.40 Intent 与 Human Smoothing 的关系

现在可以回到第二章提出的 Human Smoothing Effect。

过去一个资深开发者收到模糊任务：

> 优化加载。

他可能自然问：

> 目标是首屏速度，还是整个启动过程？

这种追问本身就是一种 Intent Engineering。

只不过它过去主要存在于：

> 人类行为。

AI-native 的变化是：

> **把这种优秀从业者隐性采用的方法，逐步变成系统可重复执行的机制。**

例如：

```text
Ambiguous Request
    ↓
Intent Extraction
    ↓
Risk Analysis
    ↓
Clarification / Assumption
    ↓
Execution-ready Intent
```

所以 Intent Engineering 并不是凭空创造新的复杂流程。

它是在系统化：

> 过去优秀团队成员已经在做，却没有正式编码进生产系统的工作。

---

# 4.41 Intent 也是降低 Agent Coupling 的关键

如果没有清晰 Intent，多个 Agent 之间容易通过大量共享历史保持一致。

例如：

```text
Worker A needs full conversation
Worker B needs full conversation
Reviewer needs full conversation
```

系统高度耦合。

如果 Intent 被结构化：

```text
Stable Intent
+
Role-specific Context
+
Agent Contract
```

不同 Agent 可以独立工作。

这就是：

> Low Agent Coupling。

因此 Intent 不只是需求管理工具。

它也是：

> **Agent Architecture 的接口对象。**

---

# 4.42 一个完整示例

假设原始人类请求是：

> Player Status 顶部 Stage / Limit 还是不好看，再优化一下。

直接执行的问题很多：

- “不好看”指什么？
- 视觉问题还是信息问题？
- 哪些方向已经接受？
- 是否可以重做整个 HUD？
- 是否可以改 runtime 数据？
- 什么结果算更好？

经过 Intent Engineering，可以形成：

```text
Intent ID:
SP122-STAGE-READABILITY

Motivation:
当前 Stage / Limit 信息在实际战斗中视觉层级偏弱，
且与 HP / Block / gourd / item 的整体组合关系不够清晰。

Goal:
提高 Stage / Limit 的瞬时可读性和层级辨识，
同时维持当前 Player Status 整体紧凑度。

Parent Intent:
提升 Player Status 在战斗过程中的信息读取效率。

Scope:
Player Status 顶部 Stage / Limit 展示及其局部 layout。

Non-goals:
- 不重新设计 HP / Block
- 不修改 combat logic
- 不修改 Stage calculation
- 不重构整体 HUD
- 不修改 save data

Constraints:
- 保留已接受 HP / Block 方向
- 使用当前 runtime 数据结构
- 保持现有 HUD material language
- 不显著增加整体高度

Truth Baseline:
以当前已确认 commit 和最新 runtime capture 为基准。

Assumptions:
主要问题来自视觉层级和比例，
而不是数据内容本身。

Acceptance:
1. Stage / Limit 在战斗截图中能被快速定位。
2. 不压制 HP / Block 的主要层级。
3. gourd / item 不发生新的布局冲突。
4. runtime data binding 保持不变。

Evidence:
- Before / After runtime capture
- target resolution screenshots
- diff summary
- runtime smoke test

Allowed Authority:
可调整 layout、尺寸、spacing 和 visual hierarchy。

Escalate if:
- 需要修改 runtime data model
- 需要改变 HP / Block 已接受方向
- 需要重做 Player Status 整体结构
```

这个对象可以同时提供给：

- Controller；
- UI Worker；
- Reviewer；
- Human。

而不同角色只加载自己需要的 Context。

这就是 Intent 成为工程资产后的价值。

---

# 4.43 Intent Engineering 的最终目标

Intent Engineering 不是为了写出完美需求文档。

它真正要达到的是：

> **让智能执行者在拥有足够自由度的同时，不失去目标。**

这需要同时做到两件看似矛盾的事。

第一：

> 给 Agent 足够明确的方向。

第二：

> 不把 Agent 的所有执行步骤写死。

也就是说：

```text
Intent Precision
+
Execution Flexibility
```

这正是：

> Tight Boundaries, Flexible Execution

在任务起点的具体体现。

---

# 4.44 本章结论：软件工程首先要工程化“想要什么”

传统软件工程已经长期研究需求。

AI-native 并没有否定这些工作。

真正变化的是：

> 需求现在可能直接驱动一个能够自行解释、计划和执行的智能系统。

因此，人类表达中的模糊性会更快传递到：

```text
Plan
→ Code
→ Test
→ Commit
```

甚至被快速放大。

Intent Engineering 的目标就是在这种放大发生之前，建立第一道结构化边界。

一个可执行 Intent 至少应明确：

```text
Why
What
Scope
Non-goal
Constraint
Assumption
Acceptance
Evidence
Decision Right
```

并且能够：

- Version；
- Decompose；
- Inherit；
- Review；
- Trace；
- Evolve。

它不是 Prompt。

不是 Ticket。

也不是传统需求文档的简单改名。

它是：

> **连接 Human Intent 与 Agent Execution 的正式工程接口。**

如果需要用一句话总结本章：

> **在 AI 原生软件工程中，最先需要被工程化的不是 Agent 如何做，而是人究竟想让它实现什么。**

Intent 清楚以后，下一个问题随之出现：

> Agent 为了实现这个 Intent，到底应该知道什么？

给得太少，它会缺乏背景。

给得太多，它会受到噪音和过期信息影响。

给错了，它甚至会在错误世界里做出非常合理的决定。

因此，下一章将进入：

# Context Engineering  
## 为 Agent 构建正确的工作世界

---

# 本章原则

## 原则一：Intent over Instruction

优先表达目标、动机、边界和完成条件，而不是过早规定实现步骤。

---

## 原则二：Outcome over Activity

Goal 应描述成功后的系统状态，而不是 Agent 做了哪些动作。

---

## 原则三：Non-goal 也是正式需求

明确什么不做，可以有效限制 Scope Drift。

---

## 原则四：Assumption 必须显式

未知可以存在，但不能伪装成 Truth。

---

## 原则五：Acceptance 与 Evidence 成对设计

无法验证的完成标准无法稳定支撑 Agent Completion。

---

## 原则六：Intent 可以演化，但不能静默漂移

Intent Evolution 是显式决策。

Intent Drift 是未被意识到的目标变化。

---

## 原则七：Intent 属于人类组织，AI 可以协助形成

Agent 可以提取、挑战和完善 Intent，但最终目标所有权属于人。

---

## 原则八：Intent Precision 不等于更多文字

真正的精确来自结构、边界和可验证性。

---

# 常见反模式

## 反模式一：把解决方案当成目标

例如：

> “把字体放大。”

应该继续问：

> 为什么？

---

## 反模式二：只给 Goal，不给 Non-goal

高能力 Agent 很容易扩大范围。

---

## 反模式三：把 Assumption 写成事实

Agent 会在错误世界模型上高效执行。

---

## 反模式四：任务完成以后才想怎么验证

没有 Baseline 时，很多 Evidence 无法可靠补建。

---

## 反模式五：所有 Task 都复制完整项目历史

这会造成 Context 噪音和 Agent Coupling。

---

## 反模式六：子任务完全失去 Parent Intent

Worker 局部正确，但整体目标逐渐漂移。

---

## 反模式七：为了精确把 Agent 变成脚本

过度规定执行步骤，会失去 Agent 适应性。

---

## 反模式八：为了避免误解不断要求 Human Clarification

只有高影响的不确定性才应该升级；低风险问题可以使用显式 Assumption 继续执行。

---

## 反模式九：用 Prompt 代替 Intent Registry

Prompt 是运行时输入，不应成为长期目标的唯一存储。

---

# 本章检查清单

一个准备交给 Agent 的任务，可以检查：

- 为什么要做这件事？
- Goal 描述的是 Outcome 还是 Activity？
- Scope 是否清楚？
- 哪些内容明确不属于当前任务？
- 有哪些技术、产品、安全或时间 Constraint？
- 当前有哪些未经验证的 Assumption？
- Truth Baseline 是什么？
- Acceptance Criteria 是否明确？
- 每个关键 Acceptance 是否有对应 Evidence？
- 是否需要 Before / Baseline 数据？
- Agent 拥有哪些局部决策权？
- 哪些决定必须由 Human 批准？
- 是否定义 Escalation Condition？
- 是否存在 Parent Intent？
- 子任务是否仍然知道自己为什么存在？
- Intent 是否有 Owner？
- Intent 是否需要版本化？
- 当前任务应该使用 Lean、Standard、Expanded 还是 Full Intent Profile？
- Agent 是在理解目标，还是只是在机械执行人提供的第一种方案？
- 如果 Agent 找到更好的实现路径，边界是否允许它采用？
- 如果 Agent 发现原目标有问题，它是否知道应该如何停止并升级？

如果这些问题能够得到清晰回答，任务才真正从：

> “一句交给 AI 的要求”

转化成：

> **一个可以被智能执行系统可靠消费的工程对象。**
