# 前言  
## 我为什么开始思考代码之外的软件工程

我最初并没有打算提出一套新的软件工程理论。

我面对的是一个更具体的问题：怎样让 AI 真正参与一个长期、复杂、持续变化的游戏项目，而不只是偶尔生成几段代码、整理一份文档，或者在某个局部问题上提供建议。

在游戏行业工作的二十年里，我做过 QA、项目管理和制作人，也参与过设计以及部分技术工作。这些经历让我逐渐形成了一个基本判断：复杂项目真正困难的地方，通常不在于某个功能能不能实现，而在于整个生产系统能否长期保持一致。

项目可能因为目标逐渐偏移而失控，也可能因为信息在专业和人员之间传递时不断损失而失控。设计、美术、程序和 QA 对同一个问题可能各自拥有合理但并不一致的理解；临时方案可能在压力下不断累积；文档可能仍然描述着原来的设计，代码和运行结果却已经走向了另一个方向。几年之后，团队或许仍然能够继续开发，却很难准确解释系统为什么变成了现在这样。

生成式 AI 和软件开发 Agent 的出现，似乎为这些问题提供了一种全新的可能。

AI 可以读取代码库、分析系统、修改文件、生成测试、整理历史讨论、研究技术方案，并在很短时间内完成过去需要数小时甚至数天的工作。当多个 Agent 可以并行承担程序、设计、QA、研究和协调任务时，一个人能够调动的生产能力也被迅速放大。

最初，这看起来主要是效率问题。

但当我尝试把 AI 放进长期开发流程后，真正困难的问题很快显现出来。

AI 可以完成任务，却不一定沿着项目预期的路径完成。

它可以理解一段自然语言要求，却未必知道这段要求背后的历史原因、已否决方案和隐含限制。

它能够读取文档，却可能无法判断文档表达的是未来意图，还是对当前系统状态的准确描述。

它可以运行测试并宣布任务完成，但测试通过并不总能证明原始目标已经达成。

它也可能在局部上做出合理优化，却在不知不觉中偏离项目的长期方向。

这些问题使我逐渐意识到，真正需要解决的不是如何写一个更复杂的 Prompt。

如果 AI 只是回答一次问题，Prompt 的质量可能决定大部分结果。但当 Agent 开始持续读取项目、制定计划、调用工具、修改代码、生成资产、执行测试并与其他 Agent 协同时，单次 Prompt 已经无法承担整个生产体系的控制责任。

此时需要管理的，不只是输入给模型的一段文字，而是一个完整的软件生产环境。

这个环境需要回答：

AI 正在执行的真实目标是什么？

哪些信息是当前事实，哪些是未来意图，哪些只是未经验证的假设？

Agent 可以访问哪些文件、工具和外部系统？

它可以自主做到哪一步，在哪些节点必须停下来等待人类决定？

完成任务时需要提交什么证据？

不同 Agent 之间如何传递状态、决策、风险和未完成事项？

成功与失败的经验如何保存，又如何避免一次错误被沉淀为长期规则？

在不断尝试解决这些问题的过程中，我逐渐形成了一些原则。

其中之一是：

> Doc as Intent，Code as Truth。

文档首先表达我们希望系统成为怎样，代码和运行状态则表达系统目前实际上是什么。当两者发生冲突时，Agent 不能静默选择一个看起来合理的版本，而需要识别冲突、确认当前状态，并把未验证部分作为显式假设处理。

另一个原则是：

> Evidence-Driven Definition of Done。

AI 不能仅仅声明“任务已经完成”。完成需要由与目标相对应的证据支持，例如测试结果、运行时表现、截图、Diff、性能数据、回归检查或其他可复现材料。

还有一个重要原则是：

> Automation Default Off。

Agent 具备执行能力，不代表它默认拥有执行权限。是否允许自动运行，应该由任务风险、影响范围、可逆性、历史可靠性和证据覆盖共同决定。

为了保持长期目标与局部执行之间的分离，我也开始尝试 Controller / Worker 模式。

Controller 负责维护整体意图、任务边界和项目状态；Worker 负责在限定范围内执行具体工作。Worker 不应擅自扩大任务，也不应自行修改治理规则；Controller 则不能只充当消息转发器，而需要承担上下文选择、冲突处理、结果汇总和人类决策升级。

这些原则后来逐渐构成了我所称的 AI Game Dev OS。

但随着系统继续发展，我开始发现，这些问题并不属于游戏开发独有。

只要 AI 从辅助工具变成能够解释目标、制定计划、调用工具和实际修改系统的生产参与者，同样的问题就会出现在其他软件领域：

如何把模糊的人类要求转化为可执行意图？

如何为 Agent 提供正确而不过载的上下文？

当文档、代码、运行时和历史记录相互冲突时，如何确定当前事实？

如何管理一个输出具有概率性、执行路径可能变化的智能执行者？

如何验证结果，而不是接受 Agent 对自身工作的描述？

如何组织多个 Agent，使它们形成生产能力，而不是制造重复劳动、冲突和信息噪音？

如何积累项目经验，同时防止错误记忆、过期知识和局部经验污染整个系统？

还有一个不能被忽视的问题：AI 的生产速度可能逐渐超过人类的理解速度。

当 Agent 可以在很短时间内完成大量修改时，人工 Review 很容易从真正的理解退化成浏览 Diff、检查测试和阅读总结。久而久之，系统可能仍然能够运行，负责它的人却逐渐失去完整的系统心智模型。

本书把这种尚未被团队真正吸收和理解的变化称为认知债。

认知过载和认知债是 AI 原生软件工程的重要问题，但并不是全部问题。它们与意图、上下文、事实、验证、自治、记忆和组织共同构成了一套更大的工程挑战。

这也是本书使用 **Beyond Code** 作为标题的原因。

代码仍然重要，而且会继续是软件系统最关键的可执行资产之一。但在 AI 参与开发以后，代码越来越可能成为一套更大生产机制的结果。

这套机制还包括：

- 人类意图；
- 项目上下文；
- 当前真实状态；
- Agent 的角色与权限；
- 计划、工具调用和执行轨迹；
- 验证证据；
- 人类决策节点；
- 长期记忆；
- Skill 与 Workflow；
- 责任、治理和演化历史。

Claude Code、Codex 以及未来出现的更多软件开发 Agent，正在成为这种生产模式的执行基础设施。它们让 Agent 可以进入代码库、调用工具、隔离任务、并行工作和复用技能。

但执行基础设施并不等于完整的软件工程体系。

Agent 能够做什么，与一个项目应该如何组织、验证和治理这些能力，是两个不同层次的问题。

本书关注的是后一个层次。

它不是某个 AI 编程产品的使用手册，也不是模型训练教材。它试图讨论一套更普遍的方法，用于理解和建设由人类与智能代理共同参与的软件生产系统。

全书将讨论：

- Intent Engineering；
- Context Engineering；
- Truth and State Architecture；
- Agent Execution and Reliability；
- Verification and Evidence；
- Review Engineering；
- Cognitive Engineering；
- Governed Autonomy；
- Observability and Intervention；
- Memory Governance；
- Self-Evolution；
- Multi-Agent Organization；
- Traceability、Security 与 AgentOps。

这些概念并非全部从零产生。它们与需求工程、软件架构、测试、DevOps、分布式系统、人机协作、知识管理和组织设计都有直接联系。

真正需要重新思考的是：

> 当这些传统工程能力共同面对一个具有推理能力、上下文依赖、行为概率性并能够自主行动的软件生产者时，它们应当如何重新组合？

本书并不声称已经为所有问题提供成熟答案。

AI 原生软件工程仍处于形成阶段。一些概念需要进一步定义，一些机制需要更多实验，一些判断需要长期项目数据支持。随着模型、工具和生产方式继续变化，部分术语也可能被更准确的表达取代。

但这些问题已经实际存在，无法再被简单归入 Prompt 技巧或工具使用经验。

如果我们只关注 AI 能生成多少代码，而忽视意图漂移、上下文污染、事实混淆、证据缺失、权限失控、认知债和错误经验积累，那么更强的 AI 不一定带来更可靠的软件，只可能带来规模更大、速度更快并且更难被察觉的问题。

因此，这本书的核心立场不是反对自动化，也不是要求人类重新检查 AI 所做的一切。

它主张的是一种受工程约束的智能生产方式：

> 让 AI 承担更多执行，让证据承担更多验证，让系统承担更多治理，让人类集中于真正需要目标判断、风险责任、产品品味和创造力的部分。

AI 原生软件工程最终需要解决的，不只是如何让 AI 写出软件。

它要解决的是：

> 当人类不再亲手完成每一项工作时，我们如何继续理解软件、控制软件，并对软件负责。

这就是我开始写这本书的原因。
