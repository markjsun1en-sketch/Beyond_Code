# Chapter 7. Agent Execution Engineering
## Turning Work into a Bounded Attempt You Can Stop and Resume

The first six chapters established boundaries among Intent, Context, Claim, State, Decision, Assumption, and Evidence. Knowing the goal and current state answers two of the questions an executor needs. It still needs a basis to act.

Which Work is underway? Which execution is this? Which Intent, Baseline, and Context does it depend on? What may it do and affect, and which human or system authorized it? When must it stop, recover, get a new decision, or be safely discarded? Who will judge the result, and with what evidence?

*Agent Execution Engineering* organizes adaptive tool use and environmental actions into executions with an identity, boundaries, observable effects, and a way to stop. It governs the externally inspectable goal, inputs, authority, actions, state changes, and stop conditions. The relationships in this chapter are candidate mechanisms. A project can choose how much of the schema to persist and whether it needs an Execution Epoch or separate Controller and Worker roles.

---

## 7.1 Agent Execution and Traditional Automation Share a Range

Conventional automation is often pictured this way.

```text
fixed input
→ fixed procedure
→ output
```

An agent loop is often pictured this way.

```text
goal
→ plan
→ act
→ observe
→ revise
```

These diagrams help explain the work. Actual systems can operate anywhere along this range. Traditional automation can branch, retry, and take dynamic inputs. An agent can follow a very narrow deterministic path.

The engineering question is what the system can decide at runtime. Can it choose a tool, change the path, get new information, or cause an external effect? As discretion grows, keep enough of the execution to identify the Work, Contract, Attempt, boundaries, and stop or recovery path.

---

## 7.2 Four Objects in the Execution Path

```text
Intent Artifact
→ Work
→ Execution Contract
→ Attempt
→ Attempt Outcome / Target Result / Evaluation Result
```

Chapter 8 defines the three result objects. The four preceding objects answer different questions.

| Object | Question it answers | What remains a separate question |
|---|---|---|
| Intent Artifact | Why do we want the change, and what result do we want? | Whether this execution is authorized |
| Work | Which traceable unit of work needs to move forward? | Which run occurred |
| Execution Contract | Within what boundaries can an Attempt or class of Attempts proceed? | The source of the Authority Grant |
| Attempt | Which individual execution took place? | Whether the Work is complete |

A Task in Chapter 4 can still be the unit of decomposition, scheduling, or allocation. An Assignment in Chapter 17 can bind a role to a piece of Work. Use a stable Work identity when you need to follow the goal, owner, scope, and meaning of closure across runs.

## 7.3 Work Persists Across Attempts

*Work* is referenceable engineering work with a named goal, scope, owner, constraints, and conditions for closure. Its identity lets us follow the same work through several executions.

At a minimum, make it possible to find the identity, goal and current scope, the owner or responsible role, non-goals and prohibited expansion, important dependencies and blockers, the target or criterion for closure, and the next permitted action.

For example, one Work item can include all three of these Attempts.

```text
Attempt A → blocked before target
Attempt B → candidate produced but rejected for scope
Attempt C → narrower candidate accepted for named use
```

A failure in Attempt A leaves the Work open to another attempt. A test pass in Attempt C still leaves the Work's closure to the applicable target and authorized disposition.

A low-risk local edit can keep its identity, scope, and closure criteria in an issue, commit message, or brief. A fuller Work Record earns its cost when the work crosses times, participants, or environments, or when several downstream decisions depend on it.

---

## 7.4 The Execution Contract Constrains an Attempt

An *Execution Contract* is a normative interface for an Attempt or class of Attempts. It describes the target, actions allowed, input boundaries, context, resources, stop conditions, evidence requirements, and recovery boundaries. It tells the executor what the current goal and authority allow and how to respond when conditions change.

| Reference | Purpose |
|---|---|
| Work / Intent / Acceptance Target | Identifies the purpose of execution |
| Execution Baseline | Fixes references to State, Decision, Assumption, Conflict, and sources |
| Context Contract / Manifest | Identifies accessible information, provenance, and freshness |
| Subject / Tool / Environment | Identifies who or what acts, and where |
| Allowed Action / Effect | Limits files, data, network, deployment, and other effects |
| Authority Grant / Permission | Identifies applicable authority and capability limits |
| Budget | Limits time, cost, calls, or impact |
| Evidence Requirement | Specifies material that must be inspectable after execution |
| Stop / Escalation Trigger | Says when to pause, block, or request a decision |
| Recovery Boundary | Says when rollback, forward correction, fallback, or safe discard applies |

A contract might say that changes to `src/parser/` are allowed. It has force when the authority and permission it references or follows are valid. Existing technical write access alone gives the executor no authority to write for the current Work.

Prefer stable references and the details specific to this execution. Link to the Intent, Baseline, Context, and authority. Keep the contract focused on the boundaries the executor uses.

---

## 7.5 Plans Propose Paths Within the Contract

The Plan says how the executor proposes to act. The Execution Contract says what the executor may do. The executor can often change a Plan during execution.

- Search in a different order.
- Choose an equivalent tool.
- Split a step.
- Add a check inside the allowed scope.
- Try another local implementation after a failure.

The Work goal and non-goals, Authority Grant, protected Policy Floor, permitted external effects, triggered Hard Stops, and decisions reserved to a particular party all remain governed by their own boundaries. A path change within the contract can proceed. A change that crosses it can require narrowing, new authorization, a Rebase, or a new Attempt.

## 7.6 Bounded Execution Is a Property of the Execution

*Bounded Execution* means the project can identify the execution, its permitted effects, the named authority, what outcomes are visible, and the conditions for stopping, recovering, or safely discarding it.

Five functions provide a minimum control boundary.

1. Work or Attempt identity.
2. Scope and Allowed Effects.
3. Named human or system authority.
4. Visibility of a Result, Failure, Unknown, or `non-result`.
5. A stop and recovery path, or conditions for safely discarding the Attempt.

A single record can carry several of these functions. A short, read-only, disposable task might need a clear brief and an exit condition. A task that writes production data, spans environments, or lasts several hours might need a versioned contract, checkpoints, independent authorization, and a recovery exercise.

Choose the controls based on duration, concurrency, impact, reversibility, uncertainty, policy, contractual obligations, rights, downstream Decision Use, and recovery needs.

---

## 7.7 An Attempt Identifies One Actual Execution

An *Attempt* records a particular execution from a specific starting point. An identifiable subject initiates it under a named Work item and an Execution Contract or an equivalent boundary.

An Attempt needs to make several things locatable.

- Attempt identity.
- Work and the current contract or equivalent scope and allowed effects.
- The executor and its current authority boundary.
- Start and stop boundaries.
- Output, unknowns, failures, or `non-result`, with references to outcomes and results defined in Chapter 8.

Where risk, duration, environmental differences, external effects, recovery, or decision use warrant it, the Attempt can also reference its Start Baseline or Input Snapshot, Context Manifest, agent, model, tool, environment, permission or credential scope, full timing, observed actions and effects, checkpoint, handoff, and stop event. A low-risk task can capture the necessary relationships together.

Plan revisions, tool calls, key Decisions, and Observations are all externally inspectable. Keep the record grounded in that observable environment and what it lets us establish about the execution.

Consider assigning a new Attempt identity when a material reference changes.

- Intent or Work scope.
- Baseline or input identity.
- Contract version.
- Subject, agent, tool, or environment.
- Permission, authority, or Policy Floor.
- Evaluation requirement.
- Recovery path.

Project identity rules determine when a new identity is required. Preserve earlier stops, failures, and `non-result` records in either case.

## 7.8 The Agent Loop Adapts Within the Contract

```text
understand current target
→ propose or revise plan
→ select allowed tool
→ act within scope
→ observe external result
→ compare with contract and stop conditions
→ continue / retrieve / pause / escalate / close
```

Keep events that could change the next decision.

- The interpretation of the goal or scope changes.
- A new dependency invalidates the Baseline.
- A tool causes an unexpected effect.
- The agent requests greater permission.
- Cost, time, or impact exceeds the budget.
- A Checkpoint is reached.
- A Stop, Escalation, or Handoff triggers.
- Execution never reaches the target.

The record serves control, recovery, evidence, and explanation of responsibility. More logging is useful when it helps with those decisions.

---

## 7.9 Tool Use Depends on Capability, Permission, and Authority

A tool in the agent's list tells us that some technical capability may be available. For a particular action, ask these questions.

| Question | What answers it |
|---|---|
| Can the tool perform this kind of action? | Capability or technical permission |
| Will the platform allow this subject to call it? | Permission and credential boundaries |
| Has this Work authorized the call? | Authority Grant and Execution Contract |
| Does the result fit the goal? | Observation, Result, and subsequent Evidence |

A write can go to a disposable sandbox, the current worktree, a shared branch, production configuration, or an external service or user data. The command may look identical. Specify the *Action Sink*, the state or destination that would receive the effect.

For external side effects, record whether the request was sent, accepted, executed, observed, and, if necessary, compensated. An API success response establishes what its interface promises. Confirm downstream state separately when the decision depends on it.

---

## 7.10 Stop, Pause, and Escalation Are Valid Outcomes

Stop new side effects when execution encounters conditions like these.

- The action is outside the current authority.
- The Baseline, Intent, or contract has expired.
- Scope is expanding into a non-goal.
- The tool, environment, or credential identity is uncertain.
- The evidence generator changed a key input or a protected surface that it needs to observe.
- An irreversible action lacks a required Checkpoint or grant.
- Cost, time, retries, or impact reached the limit.
- A condition requiring a human or other authority has triggered.

A stop can safely close the current Attempt, leave Work waiting for context, require a narrower or updated contract, seek new authority, start another attempt from a new baseline, or send the Work for authorized cancellation.

An explicit stop path makes the condition and its consequences inspectable. Whether that mechanism improves a project's outcomes would need evidence about the implementation and its use.

---

## 7.11 A Checkpoint Gives Recovery a Point of Reference

A *Checkpoint* is a recovery reference in a Work item or Attempt. It records the current Baseline, observable state, open risks, evidence references, authority boundaries, and next allowed action. It answers where a later executor can resume and which conditions apply.

A useful Checkpoint may contain the following.

- References for Work, Attempt, and Contract.
- Current baseline and known uncommitted changes.
- Completed and unfinished observable actions.
- Output, unknowns, and blockers.
- Evidence already produced and its scope.
- Current permission and authority, with any triggered Stops.
- Next permitted action, recovery prerequisites, and owner.

Progress percentage, review, Work acceptance, access to hidden reasoning, and whether effects can be rolled back each require their own basis. Short tasks may need no separate Checkpoint. Longer and cross-session tasks, multi-agent handoffs, expensive runs, and irreversible actions are more likely to need one.

---

## 7.12 Resume, Retry, Rebase, and Restart

| Action | When it applies |
|---|---|
| Resume | Continue the current Attempt from a Checkpoint while the contract and key baseline remain valid |
| Retry | Make another attempt at the same target. Chapter 8 covers failure categories and retry limits |
| Rebase | Explicitly update dependencies and the contract after a change in external State, Intent, Decision, or Context |
| Restart | Discard the current run state and execute from an explicit starting point under a new Attempt identity |

Keep the original basis of execution after a Rebase and retain evidence of the previous failure after a Retry. Resume requires continuity of authority and baseline. A change to unimportant search order can remain in the same Attempt. A change to the goal identity, effects, authority, Policy Floor, or interpretation of results calls for another boundary decision.

## 7.13 The Interface With an Optional Execution Epoch

Chapter 21 defines an *Execution Epoch* as an optional lifecycle interval for a longer execution in which the contract version and key Intent, Baseline, Context, and Policy references remain clear until closure, restart, or explicit Rebase. An Epoch can organize several compatible Attempts.

It can be useful for long runs, shared fixed references, frequently changing external state that must enter explicitly, records of risk escalation and closure, or stable boundaries for a sprint, batch, migration, or persistent session.

The Epoch refers to the Contract and Baseline. Intent, Context, Authority, environment bytes, results, and historical replay records retain their own sources.

Inside an Epoch, an executor can add checks, pause, or ask for greater permission. Expansion of authority, lowering the Policy Floor, overriding a mandatory gate, and removing recorded risks or conflicts require the appropriate authority. An authorized party can still adjust nonessential checks based on new evidence. Monotonicity applies to the guardrails the executor itself may change. Most short tasks can do without an explicit Epoch. Duration, concurrency, external change, and recovery cost determine its value.

---

## 7.14 Controller and Worker Roles Are One Way to Organize Execution

The original outline separated maintaining the goal from local execution with two roles.

- A Controller maintains Work, boundaries, assignments, conflicts, and escalation.
- A Worker acts in a bounded scope, returns evidence, and reports blockers. It requests any expansion.

One agent can plan and execute low-risk work. Several agents can instead collaborate under other role contracts. In any topology, identify who maintains the Work and contract, who may perform each action, who can change scope or authority, who checks evidence, and who handles conflict, stops, and handoffs.

Independent roles can add challenge and isolation. More agents can also introduce diverging context, handoff, and integration costs. Chapter 17 explores the organization design.

## 7.15 A Minimal Implementation Proportional to Risk

### Local, Read-Only, and Disposable

One sentence may suffice.

> Inspect the parser's current error path with read-only tools. Use the current commit as the baseline. Report findings and unknowns, leave files untouched, and stop if reproduction conditions are missing.

### Ordinary Reversible Change

Typically include the Work and Attempt identity, file or module scope, allowed tools and write surfaces, acceptance target and evidence requirement, rollback or safe discard, and an owner for decisions outside scope.

### High-Impact, Long-Running, or Cross-Boundary Work

Consider a versioned contract and baseline, a separate Authority Grant, checkpoints and handoffs, credential and network boundaries, data and environment boundaries, rehearsal, fallback, compensation, human takeover, and an Epoch or other interval with fixed references.

Let risk and recovery needs determine the structure.

## 7.16 Common Anti-Patterns

1. **Merging Work and Attempt.** Treating the end of a run as closure of the underlying Work.
2. **Treating Permission as Authority.** Letting a tool's ability to write stand in for the current task's grant.
3. **Treating the Plan as a Contract.** Letting a planned path silently change scope or a protected floor.
4. **Reusing Attempt identity.** Letting a retry overwrite a failure, stop, or `non-result`.
5. **Listing tools without Action Sinks.** Assuming a command means the same thing in a sandbox and production.
6. **Keeping only a Checkpoint summary.** Losing baseline, open risks, authority, or recovery conditions.
7. **Treating stops as exceptional.** Forcing execution to continue without authority or prerequisites.
8. **Defaulting to Controller and Worker.** Adding coordination objects to a short task.
9. **Making the Epoch an all-purpose container.** Duplicating Intent, Context, State, and Evidence.
10. **Claiming to record hidden reasoning.** Treating an external trace as a record of the model's private chain of thought.

## 7.18 Checklist

### Open Work

- Does the Work have a named goal, scope, owner, and closure criterion?
- Can we reference its Intent, Acceptance Target, and non-goals?
- Could the end of one Attempt be mistaken for closure of the Work?

### Open an Attempt

- Can we identify the contract, baseline, context, and subject?
- Can we distinguish Allowed Effects, Permission, and Authority?
- Are stop, escalation, recovery, and safe discard available when needed?
- Does the Attempt have its own identity?

### During Execution

- Are Plan changes still inside the contract?
- Are new risks, external changes, and scope expansion visible?
- Did we observe the actual sink and the result of the tool action?
- Do we need to pause, checkpoint, hand off, or Rebase?

### Close an Attempt

- What action actually took place?
- Did execution reach and observe the target?
- Did we retain Unknown, Failure, and `non-result`?
- What evidence and authority will the next decision need?

## 7.19 Conclusion

An agent can choose how to act inside a boundary that the project can identify and govern.

```text
named Work
→ bounded Execution Contract
→ identifiable Attempt
→ observable action, stop and checkpoint
→ explicit handoff to Outcome / Result
```

Work preserves the goal's identity across runs. The Execution Contract binds actions to the applicable boundaries. An Attempt records which execution occurred. A Checkpoint preserves the conditions for recovery. Bounded Execution gives the project a way to explain, stop, or safely discard the run.

The next questions concern whether execution succeeded, whether the target was observed, whether the verifier was valid, where the failure belongs, and whether to retry, recover, or stop. The next chapter takes up Agent Reliability Engineering.
