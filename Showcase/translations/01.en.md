# Chapter 1. How the Role of Software Engineering Has Changed
## From Better Tools to Delegated Execution

The history of software engineering is often told as a history of increasingly capable tools. It usually runs from high-level languages, IDEs, version control, and automated tests through continuous integration and cloud platforms to generative AI and software agents. This is one way to understand the history. Each set of tools changed a different part of the work, and projects have adopted them in different orders.

Some tools let us work at a higher level of abstraction. Others shorten feedback loops, lower the cost of collaboration, or extend the range of what can run automatically. In some real engineering tasks, software agents change something more specific. Teams can delegate the interpretation of an open-ended goal, some of the choices about how to pursue it, and actions that change the project through tools. That shift is the subject of this chapter. Chapter 3 defines AI-assisted, Agentic, and AI-native engineering.

---

## 1.1 Software Engineering Has Long Managed Two Kinds of Complexity

The first is *Product Complexity*. As software grows, developers have more modules, interfaces, state, dependencies, data, and operating environments to contend with. Modularity, abstraction, encapsulation, testing, and architecture make it possible to understand and control local changes.

The second is *Collaboration Complexity*. People maintain software together across time, roles, and environments. Requirements have to reach the people doing the work. Changes have to be integrated, decisions traced, and defects reproduced. The software has to keep evolving even after its original developers leave.

Version control, issue trackers, code review, CI/CD, and project management address the cost of carrying work across people and time.

A familiar picture of traditional software production looks like this.

```text
Human Intent
→ Human Interpretation and Design
→ Human-authored Change
→ Deterministic or Bounded Tools
→ Running Software
```

Compilers, optimizers, schedulers, search systems, and automated operations have long made complex choices. The diagram describes a common division of responsibility. People directly control the interpretation of the goal and the main engineering path. Tools transform, check, or execute within defined interfaces and rules.

---

## 1.2 Tools Change How We Express Work, Get Feedback, and Collaborate

Three patterns recur in the evolution of software tools.

### A Higher Level of Abstraction

High-level languages, frameworks, and declarative configuration let us describe work in terms closer to the problem domain. A compiler, runtime, or platform takes care of some machine-level details. The engineering responsibilities move with that change.

- Choose an appropriate abstraction.
- Understand its boundaries.
- Verify the result of automatic transformations.
- Handle failures and cases where the underlying details become relevant.

### Shorter Feedback Loops

IDEs, static analysis, tests, and CI bring feedback about mistakes into the development process. They move some checks out of people's memory and into repeatable mechanisms. Their coverage depends on which rules the team has formalized. A test can establish behavior within its stated scope. Product direction, experience trade-offs, and release risk still call for their own judgments.

### Collaboration at Greater Scale

Version control, code review, issue tracking, and deployment systems give people a shared history to work from. They record some of the changes, responsibilities, and decisions that shape a project.

Git can describe the state of a repository. Current deployment, data, configuration, and product authority each have other sources. As tools improve, the division of responsibilities changes. We still have to decide what people do directly, what the system executes, and what needs a record or a check.

---

## 1.3 AI First Arrived as a Tool for Thinking and Generating

Code completion, question answering, and generative assistants extend what people can reason about and express within a local task. A common pattern looks like this.

```text
Human frames a local problem
→ AI proposes code or explanation
→ Human selects and applies
→ Existing engineering process verifies
```

The output in this arrangement is usually a candidate. People still control most of the execution path, even when the suggestions are excellent. The work may go considerably faster. Existing scope, version control, tests, and review may still be enough to manage it. The speed of generation alone tells us little about whether the project needs a different production process.

---

## 1.4 Software Agents Bring AI into the Execution Loop

With access to a repository, terminal, browser, build system, issue tracker, or deployment tool, an agent can carry a single task through multiple steps.

```text
interpret a bounded goal
→ inspect project state
→ choose a local path
→ act through tools
→ observe feedback
→ revise
→ return changes and evidence
```

This already happens in some everyday development tasks. Software engineering agents can interpret open-ended goals within an identified and controlled scope and act through more than one tool.

Expert systems, search and optimization software, robotic process automation, and automated operations already perform complex execution and path selection. The discretion of systems marketed as agents also varies. A coding agent following a strict workflow can make fewer open-ended decisions than a complex optimizer.

Three questions tell us more about the engineering conditions.

```text
Delegated Interpretation
What range of open-ended goals may the system interpret?

Action Surface
What real state can it read, write, or trigger changes to?

Feedback Horizon
How many rounds of environmental feedback can it act on?
```

---

## 1.5 An Agent Is a System for Delegated Execution

For purposes of engineering responsibility, an *Agent* is a software execution system that can interpret and act on a bounded goal across multiple steps with the support of external context, tools, policies, and a runtime.

An agent's role in a project depends on the engineering and organizational arrangements around it. What it can do depends on several things.

- The capabilities of the model and harness.
- The information available for this task.
- Tools and permissions.
- State and environment.
- Workflows and policies.
- Delegation granted by people or automated systems.

These distinctions matter when the project asks an agent to act.

```text
Capability      What the system can technically do
Permission      What it is currently allowed to do
Authority       What kinds of decisions or dispositions it may make
Responsibility  The duty to execute, maintain, respond to, or recover named work
```

A system can be capable of an operation while lacking permission to use it. It can submit a Claim while the project gives someone else authority to decide how that Claim is used.

Responsibility here means a duty attached to the work. Who ultimately explains and corrects an outcome and answers for the organizational consequences is a question of *Accountability*, developed in Chapter 18.

## 1.6 Changes in Who Executes the Work

Suppose AI doubles the speed of generating a local change and a person still understands, applies, and verifies every edit. The main change is in productivity. Delegating a path that crosses files, tools, and rounds of feedback introduces at least five management problems.

### People Stop Specifying Every Intermediate Step

A person may define only the goal, constraints, and non-goals. The agent can search, choose an approach, experiment, and make corrections within its authorized scope. The *Intent Owner* and the decision maker for part of the execution path can be different. The amount of discretion can range from a wide choice of approaches to an almost deterministic procedure.

### People May Have Only Part of the Execution Context

An agent may read, select, and combine a great deal of material. An engineering system can record which information was supplied, made accessible, or read. A manifest alone gives limited evidence about what the model attended to or used.

### Explaining a Change Requires More Than Code

Code remains a core artifact. Explaining how a change came about may also require these records.

- The Intent and its revision.
- State and uncommitted changes in the worktree.
- The sources of context.
- Tools and permissions.
- Observable actions and failures.
- Evidence and its scope.
- The dispositions for acceptance, adoption, or release.

What needs to survive is the external basis for the decisions, at a level of detail proportionate to the risk.

### Production Throughput Can Outrun Understanding and Verification

Agents can produce changes quickly. The number of candidates says little about how much verified value reaches the project. If candidate production persistently exceeds review, test, understanding, and integration capacity for a particular workload and period, judgment and integration can become the bottleneck.

### Capability, Permission, and Responsibility Move Further Apart

Agents, harnesses, tools, policies, gates, and people may each perform different functions. With loose boundaries, a system can collapse technical ability, successful verification, and authorization to adopt into one status. Each answers a different question.

## 1.7 What Software Engineering Has to Manage Expands

Traditional engineering assets include the following.

```text
Code
Data
Configuration
Build artifacts
Runtime systems
```

Delegated execution can also make parts of the production setup into surfaces the team has to manage.

```text
Intent references
Context contracts and manifests
Agent and tool contracts
Permissions and policies
State snapshots and baselines
Evidence and review records
Memory and skill sources
Evaluation and recovery records
```

A small, low-risk, easily reversible task may cover these needs with a short brief and existing tests. The cost of maintaining structured records becomes worthwhile when impact, reuse, conflict, or recovery cost makes informal management unreliable.

---

## 1.8 The Complexity of Delegated Execution

Some projects now have to manage a third kind of complexity alongside product and collaboration complexity. I call it *Delegated Execution Complexity*.

```text
Software Complexity
+ Human Collaboration Complexity
+ Delegated Execution Complexity
```

Several things can contribute.

- Interpretations of an open-ended goal can change.
- Context and state can be incomplete or contradictory.
- Tool capabilities can exceed what the team has authorized.
- Execution can span multiple rounds of feedback.
- Completion claims can reach beyond what the evidence covers.
- Several executors can contend for the same work surface.
- A failure can require reconstruction of the external decision environment.

Its importance differs across projects. It grows with delegated discretion, the action surface, risk, and recovery cost.

---

## 1.9 Two Systems

Chapter 3 defines the two systems that the team engineers.

### Product System

The software that ultimately runs, along with its data, infrastructure, and configuration.

### Production Intelligence System

The agents, harnesses, context, tools, skills, memory, and workflows that participate in production.

Cross-cutting control and evidence capabilities link these systems. They handle Intent, State, Authority, Observation, Evidence, Review, and Recovery. A control plane is one way of organizing these capabilities. The two-system model treats them as capabilities spanning both systems.

---

## 1.10 How the Human Role Changes

Delegating part of the execution path redistributes human work. People may still be responsible for any of the following.

- Value goals and priorities.
- Organizational accountability and acceptance of risk.
- Decisions about complex conflicts and subjective experience.
- Authorization boundaries, policies, and takeover procedures.
- Architecture and long-term evolution.
- Review of the automation itself.

For people to exercise that responsibility, the project needs to let them do concrete things.

- Find the relevant evidence.
- Understand a claim's scope and limitations.
- Pause or veto an action.
- Take over a failed task.
- Change delegations and gates.
- Bind responsibilities to real organizational roles.

Human Authority can be exercised through delegation. Explicit policy can automate low-risk, reversible steps. The source of the delegation and the means of taking over need to remain clear.

---

## 1.11 When to Change the Engineering Process

Start with the work itself.

1. Does the agent directly change real project state?
2. Has it been delegated open-ended path selection?
3. Does it work across files, tools, sessions, or agents?
4. Can State, Intent, and Decision Authority come apart?
5. Could errors affect data, security, release, or irreversible state?
6. Do existing tests and review cover the claim the team needs to make?
7. How easy is it to recover and attribute a failure?

If most answers indicate little change in the operating conditions, traditional engineering practices and light rules for AI use may suffice. If several answers point to increased delegation or risk, make Intent, Context, State, Authority, Evidence, and Recovery clearer before adding executors.

---

## 1.12 Conclusion

Software tools extend what people can express, how quickly they get feedback, and how many people can work together. Software agents continue that evolution and introduce a particular condition in some named engineering tasks. A system can be delegated the interpretation of a bounded goal, part of the choice of path, and actions that change real project state.

Earlier tools already automated choices and actions. What matters here is a change in the relationship between who provides the intent, who executes, and who can make a decision about the result.

```text
Human or organizational intent
        ↓ delegation
Agent execution within boundaries
        ↓ observable change and evidence
Authorized human or automated disposition
```

As that delegation grows, we have to engineer the system that produces the software along with the software itself. The next chapter asks which operating conditions existing practices depend on and when delegation, risk, or scale makes those conditions unreliable.

---

## Principles

1. **Check efficiency and responsibility separately.** Faster generation can fit inside an existing engineering process.
2. **Compare tools and agents by the scope of their delegation.**
3. **Treat agents as systems for delegated execution.** Keep capability, permission, authority, and responsibility distinct.
4. **Keep code and the necessary external record.** Retain the basis for decisions in proportion to risk.
5. **Manage both systems.** The product and the intelligence used to produce it can each introduce defects.
6. **Judge AI-native practices by the work.** Agent count, memory, and autonomy are poor measures of maturity on their own.

---

## Common Anti-Patterns

- Equating code generation speed with engineering productivity.
- Classifying tools and agents as fundamentally different based on perceived intelligence.
- Claiming that agents are the first tools ever to choose a path.
- Putting AI-assisted, Agentic, and AI-native projects on a mandatory progression.
- Assuming the agent owns the implementation path or has project authority by default.
- Upgrading the model while overlooking context, tools, permissions, and state.
- Making people ultimately responsible without giving them access to evidence, a veto, or a way to take over.
- Requiring the same governance infrastructure for every small task.

---

## Checklist

- Did generation get faster, or did execution responsibility move?
- What may the agent interpret and what may it change?
- How open-ended is its path selection? Which steps are prescribed?
- Can we tell capability, permission, authority, and responsibility apart?
- Which inputs, actions, outcomes, and failures can people observe?
- Can review and verification keep up with the volume of output?
- Will the agent touch runtime state, data, or configuration outside the repository?
- Can someone recover, attribute what happened, and take over after a failure?
- Is the maintenance cost of the new records proportionate to the risk?
