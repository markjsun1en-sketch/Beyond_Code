# Chapter 6. Truth and State Architecture
## When Project Records Disagree

Early in the development of AI Game Dev OS, I used a simple rule.

> Doc as Intent, Code as Truth.

It addressed a problem I kept seeing. An agent would read a detailed design document and assume the system already worked that way. The document might describe a feature we still planned to build or an approach we had already abandoned. Checking the code gave the agent a way to see what had actually been implemented.

As the project grew, I found myself asking a different question. Which code was actually running?

A feature could be in the repository and still be disabled in production. The deployed build might come from an earlier commit. A design document could call for one behavior, the source code could implement another, and a runtime trace could show a third. Meanwhile, the tests might still be checking the old behavior, and the agent’s worktree might contain changes from another task. The project could still contain a record of a decision that had since been superseded.

Each record can be accurate about the version or environment it describes. The trouble starts when an agent treats them all as descriptions of the same system at the same moment. Even a more capable model can explain those records so convincingly that you miss the fact that the system it just described never existed.

Before I rely on an agent’s account of the project, I want to be able to check what it’s claiming, where the claim came from, which version it applies to, and what’s still uncertain. That’s the job of Truth and State Architecture. It gives the agent and the people reviewing its work a way to answer two distinct questions. What does the evidence support? And who can authorize us to rely on that claim for the decision at hand?

---

## 6.1 What Question Can the Code Answer?

If I want to know how a feature is implemented in the source, I start with the repository. I need to know which branch and commit I’m looking at and what’s actually in the agent’s worktree. Uncommitted changes, generated source files, and submodule revisions can all affect the answer.

Suppose I ask whether a user can access that feature in production. Now I need to identify the deployed build, check the feature flag in that environment, and look at what happened at runtime. The code might show exactly how the feature works when enabled. A runtime observation can tell me whether a particular user actually saw it.

I now use a more specific rule.

> A source of truth is scoped to a question.

| Question | Where I’d look first |
|---|---|
| What does the source implement? | The repository, commit, and worktree |
| What went into this build? | The build artifact and its metadata |
| Is the feature enabled in this environment? | The active configuration or feature flag |
| Which schema is the database using? | The live schema and its migration records |
| What did the user actually see? | A runtime observation, log, trace, or capture |
| Are we required to keep the old interface compatible? | The decision or policy in force, and the authority under which it was made |

Consider a screenshot that shows two HUD elements overlapping. It can establish that they overlapped in the build and session we captured. Whether the team is authorized to redesign the whole HUD is a different question. To answer it, I’d check the applicable product decision and who had authority to make it.

[Chapter 13](/chapters/13-en.html) calls the record of that permission an *Authority Grant*. It specifies who may act or decide, what they may do, and under which conditions and for how long. The question, domain, scope, and relevant version or time help me check where a grant applies. When I find a decision in a project document, I check whether the grant covered that decision and whether the decision still applies to the work at hand. A document’s timestamp tells me how recent it is. The grant tells me who had authority to decide.

I still use *Doc as Intent, Code as Truth* as a starting point. When a document is written to describe a design, I read it for the intended state. When I inspect a repository at a particular revision, I read it for the implementation at that revision. A document can also record a decision, policy, runbook, observation, proposal, or an earlier decision that has since been superseded. I need to know which role it plays before I can say what it supports.

Once I’ve checked the source, I can write down what I think it establishes in a form someone else can inspect and, if needed, revise. That statement is a *Claim*.

## 6.2 Claims and State Claims

Suppose an agent inspects a repository and records this finding.

> Commit `abc123` contains a migration from save format v2 to v3.

I call that statement a *Claim*. It says something about a specific subject, within a scope that someone else can check. As evidence comes in, we can support the claim, challenge it, narrow it, or withdraw it.

More specifically, this is a *State Claim*. It describes the state of something at a particular time or revision. Here, the subject is the source code, the revision is `abc123`, and the claim is that the migration is present. I can inspect the commit to check it. Recording the claim gives the next person something precise to verify.

Now suppose I run the migration on a v2 save and the converted save loads successfully. That result supports a *Behavior Claim* about what happened to that save in the tested build. If I want to make an *Improvement Claim* that the migration is more reliable than it was in the previous build, I need comparable results from both builds. The same passing test can be relevant to both claims, but it does different work in each. Completion, acceptance, and release each call for their own determination.

Completion Claims, Risk Claims, and Reliance Claims follow the same basic practice. Someone coming back to the record should be able to tell what was asserted, who or what produced it, which scope and revision it covers, what evidence supports or challenges it, what remains unestablished, and what we intend to use it for. The standard of evidence depends on what the claim says.

When a claim starts to influence a decision, I ask two questions.

- **Descriptive support.** What does the evidence establish, and within what scope?
- **Authorized use.** Who has authorized us to rely on the claim, and for which decision?

The person with authority over internal testing may decide that one successful migration is enough to begin testing more saves. The evidence still covers one save in one build. Even after broader testing provides stronger evidence, releasing the build remains a separate decision for whoever has release authority.

A project record needs room for all of these statements.

- We verified this within the stated scope.
- We have yet to establish whether it applies to the current version.
- We found evidence against the claim.
- The evidence conflicts, and the conflict is still open.
- We are authorized to rely on the claim for this particular decision.

A single `true` field would hide what I need to know when I pick up the work later. What did we establish, what remains open, and what did we decide we could do on that basis?

## 6.3 Five Roles in a Save Migration

Suppose a team is preparing to migrate older saves. All five of these statements could appear in the same task brief.

> Older saves should load safely in the current version, and existing v3 saves should keep working.

> Keep the old save compatibility path in place until v1.0.

> The repository contains an implementation of the v2-to-v3 migration.

> Some active users still have v2 saves.

> All three sample v2 saves loaded in the target build after migration.

The first statement belongs in an *Intent Artifact*. It records the outcome we want and why it is worth pursuing.

The second states a requirement made under a particular authority. A *Decision Record* can capture a specific decision. A *Policy Record* can capture a rule that governs a class of future actions. Both tell the team what it should do within the relevant scope. Look to the applicable Authority Grant to see who could set that requirement.

The third is a *State Claim* about an implementation in a particular repository state. The build, deployment, and behavior on real data each need their own evidence.

The fourth is an *Assumption* if the team still needs to verify whether any active users have those saves. We can use it to scope the work and record what depends on it, how to check it, and when it should expire.

The fifth comes from an *Evidence Record*. Such a record points to inspectable material from a named observation, test, measurement, capture, log, or review. Here the record can support a claim about those three samples.

A task brief can refer to all five roles. An immutable test report can serve both as an evidence artifact and as the primary source for what happened in that run. The cost of separate records makes sense when people need to reuse them, their lifecycles differ, a conflict would be expensive, or later work needs to trace them independently. For a local, low-risk task with an immediate check, one brief may cover everything.

The distinction matters at the point of use. An agent can mistake the desired outcome for the current state, repeat an assumption as verified, or pass a test report along as product approval. It can read a decision as evidence that the required change already happened, or treat its own assertion as authoritative. In each case the words may stay the same while the role changes.

## 6.4 What Does a Status Tell You?

A single status for a State Claim can look convenient.

```text
Observed
Verified
Derived
Approved
Stale
Rejected
```

These labels answer different questions. `observed` describes how the claim was formed. `verified-for-scope` describes how far validation reached. `stale-for-current-baseline` concerns applicability to the current baseline. `approved` usually comes from a separate decision. To act on `rejected`, I also need to know who rejected the claim’s use and for what purpose.

| Question | Possible answers |
|---|---|
| Where does the claim apply? | Repository, build, runtime, data, configuration, environment |
| How was it formed? | observed, measured, inferred, reported, declared |
| How far did verification reach? | unverified, partial, verified-for-scope |
| How does the evidence bear on it? | supporting, counterevidence, mixed |
| Are there competing claims? | none detected, unresolved, resolved with record |
| Does it still apply to the baseline? | active, stale, superseded, expired |

Projects can choose labels that fit their work. The questions can have independent answers. A claim about runtime behavior might be inferred, supported only in one scenario, and still valid for the original build even as a new observation conflicts with it for the current version. Writing all that down preserves information a `verified = true` field would hide.

Closing a task, approving a change, and releasing a product are examples of different *Decision Targets*. The applicable authority decides whether a claim can be used for the specified target. A *Claim Use Disposition* records how that external decision treats the proposed use of the claim.

## 6.5 Three Views of the Current State

Before an agent starts a task, we often say, “Give it the current state.” I want to know which of three things we mean.

A *Context Manifest* records which information was assembled, delivered, or made accessible to the agent for this task. It can record sources and versions, the reasons for selecting them, and known omissions. It can also reference tool records of what was actually read. Those records establish access or observed reads. The agent’s attention, understanding, and use are separate questions.

A *State Snapshot* records the states, claims, and source references the system observed within a stated domain, scope, time, and set of capabilities. A feature flag can exist outside what the snapshot captured.

An *Execution Baseline Manifest* records which states, intents, decisions, policies, and explicit assumptions this execution is authorized to rely on when it starts.

```text
State Snapshot reference       Observations within stated bounds
Context Manifest reference     Information supplied for this execution
Intent / Decision references   Desired outcome and applicable decisions
Assumption references          Explicit unknowns
Evidence baseline references   Relevant material available before execution
             ↓
Execution Baseline Manifest    References this execution may rely on
```

The Execution Baseline can work as an index of typed references. It gives the execution contract a place to start and lets someone later recover what the work depended on. An *Evaluation Comparator* serves a different purpose. It specifies what we compare against to judge the change. Later chapters on evidence address whether that comparison is suitable and what conclusions it can support.

The difference matters in a dirty worktree. A `dirty = true` flag leaves me asking who owns the changes, whether they belong to this task, a user, another agent, or an experiment, and whether they overlap the files I need to touch. Depending on the answers, a project might pause the work, isolate it in another worktree, record the diff and proceed within narrower bounds, or explicitly protect the unrelated changes. Automatically cleaning unknown changes can erase provenance and someone else’s work. Establish ownership and authorization before choosing a Git operation.

A worktree isolates repository state. The agent still needs to establish the right intent, the relevant runtime, data and configuration, the applicable authority, and the coverage of its evidence. The same source can behave differently across builds, environments, configurations, and data sets. For a source-only task, a commit and its local changes may be enough. A deployment can also depend on the build identity and live configuration. A migration can depend on data versions, representative samples, backups, and the ability to restore them.

An observation that differs from the baseline could reflect an expected change, concurrent work, an old snapshot, or a check against the wrong environment. Once we know the scope and provenance of the difference, we can decide whether to observe again, update the baseline, narrow the work, block an action, or ask someone with the appropriate authority to decide.

## 6.6 Working With Decisions and Assumptions

Incomplete information is normal. Waiting for an answer to every question can bring work to a halt. Letting the agent fill in every gap leaves the team exposed to decisions it never made. An Assumption lets the team state how it intends to proceed while a particular question remains open.

For an Assumption worth recording, I want to know what we are assuming, why we need it, what would happen if it were wrong, who will check it, when we need an answer, and which actions depend on it.

Consider the assumption that active users still have v2 saves. If that assumption affects an irreversible data migration, it belongs in plain view. The team can check how save versions are distributed, find representative samples, and prepare a recovery path. Until then, the repository can establish that a migration exists. Whether it is safe to run against production data remains open.

The team can check some assumptions during execution when the risk is low and the action is easy to undo. If an assumption could expand the scope or affect several dependents, check it before a checkpoint. When the action affects data, releases, or other high-impact state, use the project’s existing paths for pausing work or obtaining a decision from someone with authority. The choice depends on the consequences of being wrong, reversibility, current authority, and project policy.

Keep the original Assumption as a record of what was unknown at the time. New evidence can support a new or revised State Claim and record whether the assumption was supported, contradicted, or still unresolved. If it was contradicted, revalidate affected claims, reassess plans, revisit decisions, and obtain fresh authorization for affected actions that have yet to run. Keeping the old record makes it possible to see how the team arrived at an incorrect conclusion.

A Decision has a lifecycle of its own. A later reader should be able to find who made it and under what authority, which decision target it addressed, what evidence was considered, where it applied, why the option was chosen, and when it would need review or be superseded.

Some rejected options are worth recording. An agent can otherwise try the same option again under the same conditions. The reason it was rejected and what would justify reconsidering it often matter more than a bare record of the final choice. Likewise, a decision may have been valid for one release, sprint, platform, or risk condition. Check current applicability separately from historical validity.

## 6.7 What Did the Evidence Actually Observe?

A test, measurement, screenshot, log, or review can support, challenge, or limit a claim for a stated scope and intended use. Before I interpret the result, I check which subject the evidence actually observed and whether the observation took place.

The following episodes illustrate specific boundaries. [Chapter 23](/chapters/23-en.html) covers the larger timeline and common provenance. The projects and methods influenced one another, so these episodes provide related observations within that history. Independent cross-project validation would require other evidence.

In D-048 of AI Game Dev OS v4.94, a validator imported local Python modules before the target compile. The imports created a `__pycache__` directory and bytecode files within the directory subject to an exact-inventory check. The second inventory check detected the change and stopped the run. The target compile never ran, so there was no *Target Result* for it.

The run did establish that the validator had changed the inventory used to check what was authorized. For the target compile, the outcome was a `non-result` in the sense used in [Chapter 8](/chapters/08-en.html). The target was never observed, so the run yielded no judgment about whether the compile would succeed. A later record proposed isolating the bytecode side effect. That evidence collection included no successful rerun, so the proposal’s effectiveness remained unverified. See the [case record on the validator’s inventory change](../../Evidence/receipts/ER-20260818-002__CLM-C06-004.md).

The inventory check did its job. It detected a real change. Declared outputs that stay isolated and leave the subject of observation intact can be a normal part of validation. And if a validator changes the inputs but then does observe the target run, we can record the actual `observed_subject` and the result for that changed subject. To use it as evidence about the originally intended subject, we would need a separate basis.

An Evidence Record should let someone check the actual subject, whether the observation completed, whether evidence collection stayed within the declared bounds, what result it produced for the target, and what use the record is intended to support. Scope, revision, time, and provenance help answer those questions. The detail needed depends on the risk and kind of evidence.

Evidence has limits even when collection goes as planned and the tests pass. In D-079, a candidate passed 42 focused tests. The person with authority over the work rejected it as the implementation scope for the current E1 phase because it included work intended for later phases. A subsequent correction removed 262 lines and kept the eight regression cases required by the current contract.

The record distinguishes a test pass, suitability for the current scope, acceptance of evidence, adoption, and release. The long-term quality of the smaller implementation and the merits of a smaller test suite remain open. See the [D-079 test and scope decision record](../../Evidence/receipts/ER-20260818-003__CLM-C09-001.md).

A project can explicitly delegate a narrow decision target to an automated gate. In that case, a test result can trigger the disposition specified by the rules, within the scope of that delegation. Adoption and release require their own authority.

This gives us three questions about authority. Who can change code, configuration, data, or deployment state? Who can submit a Claim or Observation of a given kind? Who can decide whether it may be used for a particular purpose? Different agents, tests, Git controls, automated gates, and people may answer each one.

## 6.8 Conflicting Claims and Older Evidence

When two sources appear to conflict, I first check whether they answer the same question. Different scopes, versions, or times can describe two states that coexist in the record. A binding decision and a runtime observation can reveal a gap between required and actual behavior. A newer version of a record can supersede an older one when it clearly covers the same scope.

Some conflicts can be resolved by checking the applicable authority or making a new direct observation. Others need a decision from someone responsible for product, risk, or user experience. If the evidence remains insufficient or the sources speak to different scopes, the record can say so and limit what depends on the answer.

```text
Conflict unresolved
Dependent action blocked or narrowed
```

The same care applies to freshness. “All migration tests passed on commit `abc123`” can still accurately describe that run after the source changes. If the changes touch the code, data, environment, or observation conditions the claim depended on, its use for the current baseline needs to be checked again.

```text
Historical validity
Does the claim still accurately describe the original version and run?

Applicability to the current baseline
Can it still support the work we are doing now?
```

A change warrants a `needs revalidation` signal when it reaches a declared dependency, scope, or observation condition. Complex or high-risk projects may track Claim Dependencies. For a small task, checking the current files and rerunning the relevant tests is often cheaper.

For a long-lived project, a small *State Index* can help people and agents find the current Snapshot, key State Claims, known conflicts, and their sources. Keep it focused on navigation. The Execution Baseline can continue to reference decisions and assumptions in their own roles.

## 6.9 Tracing the External Decision Environment

An agent’s execution can vary even when the prompt, model name, and code version are the same. For later review, I want the project to preserve the conditions we can inspect. Which version was the target? What state did we start from? What context did the agent actually receive? Which contract and policy applied? Which model and tools did it use? What evidence was it expected to produce, and who made the eventual decision?

I call this *Decision Environment Traceability*. The aim is to recover as much of the external decision environment as possible and identify what is missing. Hidden model reasoning is outside the project’s reliably inspectable record.

A specific task in SP122 retained the pre-execution plan commit, the repair revision, the owner and permitted write scope for each work lane, the run identity, machine checks, human review, conclusions that had yet to be established, and artifact hashes. A later reviewer can use those records to inspect the boundaries of that execution. See the [SP122 decision environment case record](../../Evidence/receipts/ER-20260810-003__CLM-C06-003.md).

The same case preserved active, superseded, and conflicting sources. A commit showed what had been implemented. The approved design direction remained a separate decision. The recorded acceptance was limited to a specific evidence chain. Project adoption and production release had their own decision paths. See the [SP122 authority conflict record](../../Evidence/receipts/ER-20260810-001__CLM-C06-001.md) and the [record of the result package and human decision](../../Evidence/receipts/ER-20260810-002__CLM-C06-002.md).

These episodes show that we can retain and revisit external evidence. Whether a fixed schema would make reconstruction succeed or lower cost remains open. External services can change, tools can disappear, and snapshots can go stale or turn out to be empty. A later reviewer can recover the records that remain and identify missing conditions. Whether a rerun would produce the same result is a separate question.

## 6.10 Let the Cost of Error Set the Weight of the Architecture

Metadata takes time to maintain. It can go stale, and a record can acquire apparent authority that nobody granted. The amount of structure I want depends on what an error would cost.

For a typo, I usually need to check the current file, make the edit, and verify the result. A task spanning several files may need a clearer baseline, explicit assumptions, and retained evidence when it involves several decisions, a dirty worktree, or conflicting sources. Data migrations, production configuration changes, security boundaries, and hard-to-reverse actions can warrant versioned snapshots, explicit authority, independent review, and a way to recover.

Task duration, headcount, and the number of agents or records are weak guides on their own. I want to know what an error would affect, whether the action can be undone, whether current observations can answer the critical questions, whether later work will rely on a disputed claim, and who can decide what happens next.

An Authority Matrix, Claim Graph, State Index, or registry can be useful when the work calls for it. For any consequential decision, the underlying questions are the same. Which claim are we relying on? Where did it come from, which version does it apply to, what is still unknown, and who can decide how to use it?

Intent Engineering identifies the outcome we want. Context Engineering determines which information this task receives. Truth and State Architecture gives each piece of that information a role the agent and its reviewers can check. The agent can tell which item expresses a goal, which records a decision, which makes a state claim, which is an unverified assumption, and which is evidence for a particular scope. It can also see where a conflict remains.

With that starting point, [Chapter 7](/chapters/07-en.html) can ask how to begin an execution with clear bounds. [Chapter 8](/chapters/08-en.html) examines what happened in an attempt and whether we got a result for the target. [Chapter 9](/chapters/09-en.html) then follows those results into evidence and examines who can authorize their use for a later decision.

An action may change the state of the project. Establishing what changed still takes a check. A test pass gives the next decision something inspectable to work with, and adoption or release remains a decision in its own right.
