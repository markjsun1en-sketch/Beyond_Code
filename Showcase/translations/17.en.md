# Chapter 17. Multi-Agent Organization Design
## Designing roles, authority, interfaces, and responsibility for work that agents share

This chapter proposes an organizational model for examining Work, Role, Assignment, Authority, Responsibility, Handoff, Conflict, and Integration. The model makes no claim to completeness, minimality, or necessity across projects. The effects of using multiple agents on quality, speed, and cost depend on the work and remain questions to evaluate.

Several agents can search, plan, implement, review, test, summarize, and launch further agents at the same time. An organization takes shape when you can say how they work together.

Without clear boundaries, adding agents can multiply duplicated work, diverging context, conflicting decisions, overlapping authority, races over shared state, lost information at handoff, common-cause review failures, excess output, coordination costs, and loose ends without an owner.

I use *Multi-Agent Organization Design* for the engineering work of arranging named work, role contracts, subjects, authority, responsibilities, dependencies, handoffs, conflicts, and integration decisions into relationships we can inspect. For a particular outcome, I want to know who owes what, what decisions each participant can make, what inspectable output they owe to whom, and who takes over when something fails or conflicts.

---

## 17.1 Core checks, useful practices, and optional roles

### Core checks

When multiple people, agents, or gates affect the same outcome, I first check whether I can see the work owner, authority boundaries, dependencies, handoffs, conflict and escalation paths, and final disposition. The same questions can help examine a human-only team. Whether these relationships form the minimum set depends on the team and the work.

### Useful

Multiple roles or subjects can help when work is separable, calls for different domain expertise, warrants independent review, or has grown beyond what one context can reasonably cover.

### Optional

Controller, Planner, Specialist, Reviewer, QA, Researcher, Knowledge Miner, Security Agent, and Release Agent are possible role profiles. Low-risk, tightly coupled, or very small tasks may cost less with one agent, clearly scoped tools, and an explicit human checkpoint.

## 17.2 Agent, Subject, Role, Persona, and Skill

An *Agent Instance* is an executing instance at a named time, with an identifiable model, contract, context, tools, and state boundary.

A *Delegated Subject* is a human, agent, gate, or combination identified through an Authority Grant and Assignment to carry out a named action or decision.

A *Role* is a reusable contract for a kind of work. It defines the perspective used to make judgments, responsibilities, inputs, outputs, and escalation paths.

A *Persona* is a prompt-based way of shaping communication, perspective, or exploration. Responsibility and authority require their own definitions.

A *Subject Configuration* references the person, agent, or gate doing the work and the applicable model or version, execution boundaries, context, and tool configuration. You can distinguish two subjects assigned to the same role by their configurations.

A Skill supplies a method, procedure, or tool binding. A role contract addresses the broader work relationship.

~~~text
Agent Instance / Human / Gate
+ Role Contract
+ Assignment
+ Authority Grant
+ Work Reference
→ Delegated Subject for this organizational relation
~~~

One agent instance can take successive roles. Review independence still needs an arrangement that addresses the relevant sources of shared error.

## 17.3 Nine candidate objects for examining an organization

| Object | Question it answers |
|---|---|
| Work Reference | Which piece of Work, as defined in Chapter 7, does this relationship serve? |
| Role Contract | What responsibility, perspective, interfaces, and boundaries apply? |
| Subject Configuration | Which human, agent, or gate takes the Role, and with what configuration? |
| Assignment | Who is assigned to which Work, for what scope and period? |
| Authority Reference | Which actions or decisions may the subject take? |
| Dependency / Coordination Relation | How does this connect to other Work or subjects? |
| Handoff Package / Receipt | What did one party hand over, and what did the recipient accept? |
| Conflict Record | Which claims, decisions, authorities, or resource relationships conflict? |
| Integration Disposition | Which outputs will be kept, rejected, combined, reworked, or escalated? |

A *Work Reference* points to the Work defined in [Chapter 7](/chapters/07-en.html). It tells us which named goal, scope, dependencies, and closure boundary the organizational relationship serves. This uses the existing Work definition. An open-ended prompt leaves that reference underspecified.

A *Role Contract* defines a role’s purpose, responsibilities, decision lens, inputs, outputs, authority, prohibited actions, evidence obligations, and escalation paths.

An *Assignment* records the binding among a Subject Configuration, Role Contract, Work Reference, and Authority Reference for a named period. It lets someone check who is responsible.

An *Integration Disposition* is a decision under named authority about how to accept, combine, reject, rework, or escalate multiple outputs. It is a specific Decision Target for the kind of Disposition defined in [Chapter 9](/chapters/09-en.html). A merge command can execute part of that decision.

~~~text
Work Reference
+ Role Contract
+ Subject Configuration
+ Assignment
+ Authority Reference
→ bounded execution
→ candidate output + Evidence + Unknown
→ Handoff / Review / Conflict
→ Integration Disposition
→ next state and responsibility
~~~

Responsibility and accountability apply throughout this sequence.

## 17.4 What belongs in a Role Contract?

A candidate Role Contract can describe its purpose, decision lens, and responsibilities. Specify which decisions it can and cannot make, the inputs and primary sources it needs, the outputs and evidence it owes, and when to escalate, hand off, stop, or expire.

~~~yaml
role_id: independent-scope-reviewer
version: 3

purpose:
  - assess_candidate_scope_fit

responsibilities:
  - inspect_candidate_and_declared_non_goals
  - identify_over_scope_and_missing_evidence
  - preserve_counterevidence

allowed_decisions:
  - review_disposition_for_scope

prohibited:
  - modify_candidate_source
  - approve_release
  - expand_own_review_scope

inputs:
  - intent_ref
  - candidate_ref
  - baseline_ref
  - evidence_refs

outputs:
  - review_record
  - blocker_or_non_blocker_findings
  - unresolved_unknowns

escalation:
  - authority_conflict
  - missing_primary_source
  - unsafe_action_reachable
~~~

This profile illustrates one design. If a contract merely says “You are the reviewer,” I still have to ask whether that reviewer can reject, block, recommend, or adopt a candidate.

Start a specialist role with an output someone else can use. For example, the UI role for a reward page should describe its default focus, hover state, and scale on first entry, and explain how the page appears when the mouse has never moved. [Section 16.24](/chapters/16-en.html#section-16-24) gives a limited comparison that makes one such output requirement concrete. The comparison helps examine a handoff standard. Establishing an organization-wide performance improvement from adding a UI role would need other evidence.

## 17.5 A library of roles to combine as needed

| Role | Primary output | Typical boundary |
|---|---|---|
| Coordinator / Controller | Work allocation, dependencies, state projection, escalation | Decision authority comes from the applicable grants |
| Planner | Plan Candidate, dependencies, unknowns | Execution authority requires its own grant |
| Builder / Worker | Candidate Artifact, diff, runtime evidence | Adoption requires a decision |
| Specialist | Domain analysis or implementation | Project authority still applies |
| Reviewer | Findings, counterexamples, disposition recommendation | Blocking power depends on the grant |
| Validator | Check results for a named claim | PASS applies to the named Decision Target |
| Challenger | Counterexamples, hidden assumptions, alternative explanations | Any rewrite needs an assignment |
| QA / Tester | Scenarios, results, coverage, defects | Product adoption has a separate decision owner |
| Researcher | Sources, synthesis, uncertainty | Search results need validation before they support a project fact |
| Knowledge Curator | Memory Candidates, provenance, conflicts | Claims still require appropriate support |
| Security / Privacy Reviewer | Threats, boundaries, required controls | Authority stays within the grant after a risk finding |
| Release Role | Release evidence and decision inputs | Release authority requires an explicit grant |

A person can take a role, and roles can be combined.

The original outline used *Cognition Agent*. Attention routing, compression validation, exception detection, the human interface, and organization review each have distinct responsibilities. Give each obligation a clear owner before deciding how many roles to use.

Let actual differences in the work drive the number of roles.

## 17.6 Responsibility, Authority, Permission, and Accountability

*Responsibility* is a role’s obligation to execute, maintain, respond, escalate, or recover a piece of work.

Authority determines which actions or decisions the subject can take. Permission determines what the platform technically allows. A responsibility may require a decision the subject must refer elsewhere.

[Chapter 18](/chapters/18-en.html) defines *Accountability* as the organizational requirement that a named person or role answer for objectives, control design, authorization, review, decisions, operations, or recovery. That may involve explanation, scrutiny, correction, or consequences. Assign this relationship to someone who can answer for it.

Here I examine how assignments and handoffs allocate responsibility. Trace and execution logs can support attribution. Organizational accountability and legal liability each require their own grounds.

~~~text
Worker
responsible for implementation and evidence
not authorized to release

Reviewer
responsible for independent finding
authorized to reject a named Decision Target for closing or continuing that Review Target
not authorized to rewrite policy

Human Product Owner
accountable for product adoption
not authorized to bypass security policy alone
~~~

When you say “owner,” specify whether you mean the work owner, decision owner, recovery owner, artifact maintainer, or accountable person.

## 17.7 Assignment identifies the subject, capacity, and acceptance

An Assignment can begin with this relationship.

~~~text
Agent A → Task B
~~~

That leaves key questions open. Record the Assignment ID, Work Reference, Role Contract version, Subject Configuration, Authority Reference, start and expiry, input and context contract, expected output, dependencies, capacity and budget, stop and cancel conditions, reassignment, and acceptance status.

A subject can respond with `accept`, `reject_out_of_scope`, `request_missing_input`, `request_authority`, `defer_due_to_dependency`, or `return_non_result`.

Treating an incomplete assignment as accepted can turn a missing prerequisite into what looks like a failure of execution.

---

## 17.8 Decompose work at interfaces and risk boundaries

Work is usually easier to do concurrently when the outputs can be described on their own, the inputs are clear, shared write access is limited, dependencies are identifiable, claims can be checked independently, and someone owns integration. A failure in one unit should leave the other units intelligible.

Keep work together when it shares substantial tacit context, needs continuity of creative judgment, or asks questions that change with each previous answer. Splitting can also be too expensive when subjects must edit the same small region of code or state, integration costs more than execution, or responsibility cannot be located separately.

Choose where to run work in parallel, in sequence, or together while preserving decision continuity and responsibility.

---

## 17.9 Coordination topologies and their failure modes

A *Coordination Topology* is the pattern by which roles and subjects allocate work, exchange state, submit decisions, and escalate conflicts.

| Topology | Benefit | Main failure modes |
|---|---|---|
| Central Coordinator | Clear routing and easier flow control | Bottlenecks, concentrated error, context lost in compression |
| Pipeline | Explicit interfaces and outputs suited to stages | Handoff loss, local optimization, delayed feedback |
| Peer Collaboration | Exploration from several perspectives | Authority conflicts, duplicate work, consensus costs |
| Builder–Reviewer | Production and challenge have separate roles | Review capture, repeated rounds of rework |
| Specialist Hub | Reuse of domain expertise | Integration load at the center, knowledge silos |
| Human-led Cell | Clear value and risk decisions | Human bottlenecks and waiting |

One project can use several topologies at once. Choose a topology for the work at hand.

## 17.10 What a Controller coordinates

The original outline gave the Controller responsibility for maintaining the global intent, controlling context, limiting worker scope, combining results, managing cognitive load, and bringing decisions to the human. Those functions can be useful. Give them separate responsibilities and decide which ones the Controller should hold.

~~~text
Intent Custody
Work Coordination
Context Routing
Dependency Tracking
Integration
Attention Routing
Escalation
~~~

A Controller can hold some of these responsibilities. Each further power needs its own basis, including changing human intent, granting authority, displacing a domain reviewer, accepting output, making value judgments on a person’s behalf, and overriding a policy gate. Claims about the state of the project still depend on their sources.

A central Controller’s summary is a derived projection. Keep the source links, unknowns, and conflicts.

---

## 17.11 What a Worker delivers

A Worker can produce candidate artifacts within the assigned Work, retain actual changes and runtime evidence, mark assumptions, unknowns, blockers, and `non-result`, identify issues beyond scope, and stop, decline, or request escalation when conditions expire.

Decide separately who can accept claims or scope, adopt the candidate, integrate it, release it, or expand authority. If the Worker also ran tests, those results support the stated behavior claims within scope. A gate can make a further named decision when the project has expressly delegated it.

Returning a `non-result` can discharge a responsibility if the classification is supported. If the trace confirms that an input, authority, tool, or environmental prerequisite blocked execution before the target, record the target’s `non-result` and the reason. If the action may have executed and only the log or observer failed, keep the result unknown. For a possible external side effect, record `external-effect-unknown` as described in [Chapter 8](/chapters/08-en.html). Before retrying, find affirmative evidence about whether the target or side effect was reached.

---

## 17.12 Controller and Worker can hold different kinds of authority

A Controller can allocate Work. Domain judgment and decision authority may still sit with the Worker or another subject.

A Worker can send a signal back when the assignment conflicts with source state, the original scope cannot produce the required evidence, a dependency has expired, the actual risk exceeds the grant, another role needs to decide, or continuing is no longer worthwhile.

~~~text
Controller --coordinates--> Work and dependencies
Worker --produces-------> Candidate and execution evidence
Worker --escalates------> changed conditions and missing authority
Reviewer --challenges---> named claim or candidate
Authority Holder --creates-------> Decision Record for named target
Decision Record --records-------> target-specific disposition
~~~

People, policy gates, and domain owners can hold decisions outside the Controller–Worker relationship. Draw the project’s authority relationships separately from its dispatch chain.

---

## 17.13 Planning produces a candidate

A Planner can decompose Work, identify dependencies and a critical path, state assumptions and unknowns, propose sequencing, parallelism, and stop conditions, and flag required authority and evidence.

A *Plan Candidate* is an inspectable proposal for decomposition, order, dependencies, resources, and closure conditions. Record plan acceptance, assignment, and execution authorization as separate events.

When new evidence arrives, a source changes, or a dependency fails, keep the original plan and the reason for a revision. For work whose value lies in exploration, it may be more useful to authorize an initial probe with scope, budget, and a stop condition than to try to anticipate every possibility before starting.

---

## 17.14 Review, validation, and challenge

A *Reviewer* checks how a candidate fits a goal, scope, risk, or completeness requirement under a named Review Contract as defined in [Chapter 10](/chapters/10-en.html), and usually returns findings and a disposition recommendation.

A *Validator* runs a specified check on a named claim, contract, or behavioral condition and answers whether that target held in the declared coverage.

A *Challenger* seeks counterexamples, hidden assumptions, alternative explanations, and limits on applicability. Pressure to agree quickly can defeat that role.

Low-risk work can combine these roles. The record still needs the Review Target and Intended Decision Use, the claim at issue, coverage and exclusions, and whether the outcome is a recommendation, a block, or an authorized disposition. Give a `PASS` a target and a scope.

## 17.15 How organizational topology affects review independence

[Chapter 10’s seven dimensions of Review Independence](/chapters/10-en.html) are the starting point. Here I check what the organization’s topology adds. Do producer and reviewer have distinguishable subject configurations? Do they share context, sources, models, methods, or failure assumptions? Can the reviewer’s finding reach the named decision authority without the producer rewriting it?

Two agents with different names and the same model, prompt, summary, and failure assumptions might provide additional samples. That setup covers only part of the independence question.

An independent reviewer can still be wrong. Separating these dimensions reduces reliance on the same inputs and assumptions by design. The available material does not establish a reduction in actual common-cause failures. Limited competence, missing sources, and a faulty contract remain possible.

Set the degree of independence to match risk, irreversibility, reach, and changes that affect the review of the system itself.

## 17.16 A handoff should make the next action possible

A *Handoff Package* gives the next role sourced state, artifacts, decisions, evidence, unknowns, and risks. The recipient should be able to tell what is being offered, which conclusions are decided, which are still candidates, which prerequisites are open, and what authority the next action needs.

~~~yaml
handoff_id: HO-017
work_unit_ref: WU-042

from:
  subject_ref: agent-builder-2
  role_ref: bounded-builder-v3
to:
  requested_role_ref: scope-reviewer-v2

goal_and_intent_ref:
  - INT-008

candidate_and_baseline:
  candidate_ref: commit-or-artifact-ref
  baseline_ref: scoped-baseline-ref

current_state:
  completed:
    - bounded_implementation
  actual_changes:
    - source_diff_ref
  in_flight:
    - none

decisions:
  - decision_ref: DEC-021
    status: accepted_for_evaluation

assumptions:
  - external_contract_unchanged
evidence_refs:
  - EV-101
counterevidence_refs:
  - EV-104
unknowns:
  - production_latency
non_results:
  - target_ref: scenario_x
    reason: precondition_blocked_before_target
    trace_ref: preflight_stop_trace_ref
blockers:
  - none
open_risks:
  - shared_state_race

requested_next_action:
  - review_scope_fit
requested_authority:
  - review_disposition_only

source_links:
  - task_ref
  - diff_ref
expires_at: named-condition-or-time
~~~

Use this example as a design profile and scale it to the work. The `non_results` entry assumes that the trace confirms a stop before the target. If a different write was sent and the log went missing afterward, put that request and `external-effect-unknown` in `unknowns`. Read back state before taking another action. A completed handoff alone provides no basis to retry that write.

A small handoff can be brief if it captures the unknowns, counterevidence, and authority boundaries likely to change the recipient’s decision.

## 17.17 The recipient records acceptance

A *Handoff Receipt* records readability, scope, missing inputs, and what the recipient is taking over. Possible statuses include `accepted_for_named_work`, `partially_accepted`, `rejected_out_of_scope`, `missing_required_input`, `authority_not_available`, `dependency_not_ready`, and `superseded`.

State which work and artifact custody the recipient accepts, what continuing duties begin and when, which inputs remain unverified, which decision rights stay elsewhere, and who receives a declined handoff.

Acceptance transfers named work or custody. It leaves separate questions about claim support, adoption, ownership of remaining risks, transfer of authority, and the sender’s accountability for decisions already made.

## 17.18 Keep shared state small and project context by role

*Shared Organizational State* is an index of Work, Assignment, Dependency, Decision, Authority, and Handoff records made available for coordination.

~~~text
authoritative source records
        ↓
small shared coordination index
        ↓
role-specific Context Projection
        ↓
Source-linked decisions and outputs
~~~

Give shared state identity, version, freshness, source links, and conflicts. Send each role the information its contract needs and give the subject a way to open the primary records.

An unsourced global summary can become a competing state store. Access to the original files only tells us that the subject can inspect them. Applicability still needs to be checked.

## 17.19 What is in conflict?

A *Conflict Record* retains incompatible claims, decisions, grants, policies, dependencies, resource requirements, or creative directions and their unresolved status. Identify the kind of conflict first.

| Conflict | Question | Inadequate response |
|---|---|---|
| Observable State Conflict | Are there different observations of the same state? | Vote by agent reputation |
| Evidence Interpretation Conflict | Do the parties agree on the evidence and differ on what it supports? | Count files |
| Design / Strategy Conflict | Do the options protect different goals or trade-offs? | Pretend the choice is a factual question |
| Authority Conflict | Do grants overlap or contradict one another? | Let the faster subject win |
| Policy / Instruction Conflict | Does a local task conflict with a higher-level constraint? | Let the local prompt override policy |
| Dependency / Resource Conflict | Are sequence, capacity, or shared write surfaces incompatible? | Attribute the problem to lack of intelligence |
| Creative / Value Conflict | Do people differ on aesthetics, direction, or experience? | Make up a precise score |
| Responsibility Conflict | Is anyone willing and able to take the next step? | Mark the task Done |

The classification points to the relevant sources, Decision Target, and authority.

## 17.20 Examine the conflict before deciding what to do

The original outline named the priority of facts, role authority, evidence strength, risk escalation, and human decision. Use those as questions. Their order depends on the conflict.

1. Name the objects in conflict and the current Decision Target.
2. Identify the observable facts, contemporaneous judgments, retrospective inferences, and recommendations.
3. Note the identity, version, freshness, and applicability of each source.
4. Check whether the evidence fits the kind of claim.
5. Find overlapping, missing, or expired authority.
6. State what objective and guardrail each option protects and what it costs.
7. Decide whether to clarify, test, narrow, split, defer, escalate, or reject, given the risk.
8. Have the subject with authority over the target record the disposition.
9. Retain minority positions, unknowns, and conditions for reopening.

“Stronger evidence” helps when the evidence is comparable and speaks to the same claim. A runtime claim and a value judgment need different grounds.

Use human decision where the person actually holds authority over the value choice, risk acceptance, or organizational design.

## 17.21 Deadlock and livelock can arise from work and authority relationships

*Deadlock* occurs when work, subjects, or authority holders are waiting on one another and none can proceed under current conditions. It can arise from circular dependencies, cross-approvals, an unowned Decision Target, a handoff where each party waits for the other to take over, or revocation without a recovery owner.

*Livelock* occurs when the system keeps producing replies, reviews, or follow-up work without getting the original target closer to a decision. Typical examples include an endless reviewer–worker revision cycle, a Controller spawning meta-tasks, a governance record that triggers another record, growing agent participation in an undefined decision, or an Automatic Successor without a termination condition.

Check dependency graphs before creating work. Give review loops a return type, budget, and escalation condition. Set observable deadlines and investigate the cause of a timeout. Block automatic follow-ups that lack authority. When no one can advance, produce a Blocked Receipt that explains why.

## 17.22 Parallel execution needs isolation and integration decisions

Parallel work can increase throughput. It can also compound races over shared write surfaces, baseline drift, duplicate changes, interference between tests and environments, incompatible assumptions, and semantic conflicts that survive a successful merge.

As risk rises, make these boundaries explicit.

- Artifact ownership and write surface
- Worktree, sandbox, and environment isolation
- Locks or reservations for shared resources
- Baseline identity and rebase or refresh conditions
- Integration order, conflict owner, and recovery point

Integration dispositions can include `accepted_as_is`, `accepted_with_narrowing`, `combined_with_other_candidate`, `returned_for_rework`, `rejected`, `deferred`, `superseded`, and `non_integrable_for_current_baseline`.

An Integration Owner makes the disposition. A merge, adoption, or release requires a grant covering that action.

## 17.23 Authority in a delegation chain

When a Controller or Worker creates a downstream agent, check five powers independently.

- Creating an Assignment
- Redelegating particular decision rights
- Expanding the scope of Work
- Allocating a credential or tool permission
- Accepting downstream output

Record the maximum delegation depth, which authority can transfer, delegated scope, evidence requirements, expiry, revocation, disposition of in-flight work, and how credentials and memory will be reclaimed.

If an upstream grant is revoked, check whether downstream grants expire with it. Revocation also leaves work to do. Account for external side effects already produced, handoffs in progress, credentials, Memory Candidates, and artifacts awaiting disposition.

---

## 17.24 Control the flow of output to decision makers

Multiple agents can produce candidates, findings, questions, evidence, conflicts, handoffs, exceptions, and Work proposals at once. Forwarding all of it to a person can leave the machine work parallel and the judgment work serial.

A project can cap work in progress, group outputs by Decision Target, combine duplicate findings while keeping their sources, and distinguish blockers, risks, unknowns, and informational updates. Escalate when new authority is needed. Automate low-risk dispositions inside an existing grant. Keep primary source links and a way to drill down, and sample summaries for omissions.

Check whether compression actually reduces the work of deciding. If the person needs to reread every source or the summary routinely drops counterevidence, the cost has moved.

---

## 17.25 Put people at the decisions they own

People can own intent, product or creative direction, policy, risk acceptance, domain review, organization design, exceptions, recovery, or executive accountability.

“Human in the loop” leaves the important questions open. Which person? What decision? With what evidence? Are they approving, overriding, hearing an appeal, or taking over? Do they have the competence and time to handle it? Which policies constrain even their authority?

A gate with a clear grant can handle some low-risk decisions automatically. A person’s override can be limited by security policy, regulation, multiple-party authorization, or separation of approvals.

Give decisions about values, risk, direction, and organization to real people who can answer for them.

---

## 17.26 Allocate roles to present capabilities and conditions

The original outline imagined people taking more responsibility for intent, rules, risk, final decisions, organization design, and value judgments as agents did more implementation. Treat that as one possible redistribution of work.

In the same project, one person might edit code with high semantic density, review an agent’s candidate, define product intent, handle an exception, authorize a high-risk disposition, and change roles or grants.

*Capability-relative Role Allocation* assigns roles according to capability, risk, and current conditions. Review the allocation as model capability, tool reliability, business knowledge, project phase, incident state, or human availability changes.

## 17.27 What can we observe about the organization?

*Organization Observability* is the ability to inspect Work, Assignment, Dependency, Authority, Handoff, Decision, and failure state from visible records. Useful queries ask:

- What work exists?
- Who accepted it and under which role?
- Which contract and authority apply?
- What baseline, source, or other work does it depend on?
- Is it running, waiting, blocked, cancelled, or unknown?
- Which candidates, evidence, and `non-result` records did it produce?
- Who received the handoff and did they accept it?
- Which conflicts and decisions remain open?

`running` identifies activity. To establish progress, inspect what the activity achieved. An `idle` subject might be finished, waiting for input, unable to proceed, interrupted, or affected by a detector failure.

Examine visible messages, tool activity, artifacts, state transitions, and decision records. Those are the observable surfaces.

---

## 17.28 Include organization costs in the choice to split work

The total cost of a multi-agent arrangement includes tokens and time, work decomposition, context construction and duplication, assignment and scheduling, waiting and capacity mismatch, handoff loss and acceptance checks, repeated exploration, review and conflict resolution, integration, shared state maintenance, governance artifacts, human attention, and recovery.

Look for a combination of benefits that can exceed those costs.

- Real parallelism
- Distinct domain capabilities
- Meaningful review independence
- Context isolation
- A smaller failure blast radius
- Recoverable specialist output
- Clearer responsibility

Agent count, total output, and concurrency each describe activity. Evaluate effectiveness against the Work and its costs. Tightly coupled work with small outputs, hard-to-separate responsibilities, or expensive integration may be better served by one agent with a clear contract.

## 17.30 Start at a real boundary between collaborators

Choose a piece of work with repeated handoff loss, a need for different domain expertise, a risk the producer cannot review alone, scope that can be safely parallelized, or recurring uncertainty about responsibility or authority. Start with the relationships that concern that boundary.

1. A bounded Work Reference.
2. A Role Contract.
3. A Subject Configuration.
4. An explicit acceptance of Assignment.
5. An Authority Reference.
6. A Handoff Package and Receipt.
7. An Integration Disposition.
8. A path to cancel, revoke, or escalate.

Add a reviewer with meaningful separation from the producer if risk warrants it. A trial can rehearse a handoff that omits a critical unknown, a reviewer and worker arriving at conflicting conclusions, cancellation or revocation while an assignment is in flight, an output that cannot integrate, and a block the original role cannot resolve.

Measure elapsed time alongside duplicate work, handoff clarifications, conflict resolution time, escaped defects or risks, the usefulness of review findings, integration rework, human decision load, and unnecessary work stopped in time.

Keep the simpler single-agent setup when it already completes the work reliably at lower cost.

## 17.32 Principles

1. **Inspect relationships.** Work, Role, Assignment, Authority, Responsibility, Handoff, Conflict, and Integration make an organization inspectable.
2. **Define a role through its contract.** State the decision lens, duties, inputs, outputs, and boundaries.
3. **Reuse methods across roles.** A Skill can serve several Role Contracts.
4. **Record assignment acceptance.** Surface incomplete inputs before treating the assignment as running.
5. **Bound the Controller’s authority.** Coordination and summaries still need grants, sources, and coverage limits.
6. **Treat worker output as a candidate.** Adoption and release have their own decisions.
7. **Assess several dimensions of review independence.** A new name or an extra sample covers little by itself.
8. **Ask for a Handoff Receipt.** Identify what was accepted and when responsibility began.
9. **Project context by role.** Keep shared state small and sourced.
10. **Identify the kind of conflict.** Facts, interpretation, design, authority, and value call for different responses.
11. **Plan isolation and integration.** A successful merge leaves semantic acceptance to a separate check.
12. **Transfer authority explicitly.** A downstream subject receives only the scope allowed for redelegation.
13. **Name the decisions people own.** Give them defined value, risk, and accountability roles.
14. **Compare organizational costs.** Choose a multi-agent arrangement when its benefits exceed its costs.

## 17.33 Common anti-patterns

- Treating a larger agent count as mature organization
- Using an agent name or persona as a role contract
- Renaming the same agent as an “independent reviewer” of its own output
- Giving a Controller implicit authority over intent, truth, integration, and release
- Letting a Planner execute a plan without assignment
- Recording worker delivery, tests, or merge as adoption
- Extending a reviewer’s `PASS` to scope that was never reviewed
- Claiming source independence when the reviewer saw only the producer’s summary
- Copying all context to every agent
- Replacing primary state with a global summary that has no sources
- Treating a sent handoff as accepted
- Dropping `non-result`, counterevidence, or unknowns during handoff
- Ranking every conflict by evidence strength
- Inventing objective scores for creative conflicts
- Adding reviewers when the decision has no owner
- Letting automatic successors continually create governance work
- Giving parallel agents a shared write surface with no owner
- Interpreting a clean merge as successful semantic integration
- Passing every upstream power to agents by default
- Revoking an assignment while leaving credentials, in-flight work, and side effects unaddressed
- Escalating every output to a person
- Making the person a final button with unlimited policy override
- Citing total tokens, output, or concurrency as proof of effectiveness
- Treating v4.94 Dual Review as proof that multiple agents always work better

## 17.34 Checklist

### Work and Role

- Does the Work Reference identify the goal, scope, inputs, outputs, dependencies, and closure conditions?
- Does the Role Contract specify responsibilities, decision lens, and permitted and prohibited decisions?
- Can we distinguish persona, skill, role, and subject configuration?
- Has the assignment been accepted explicitly?
- Can the subject return an out-of-scope response, missing input, or `non-result`?

### Authority and Responsibility

- Can we distinguish responsibility, authority, permission, and accountability?
- Which authority does the Controller actually hold?
- Which Decision Targets belong to the Planner, Worker, and Reviewer?
- Which grants can be passed downstream?
- After revocation, what happens to in-flight work, credentials, memory, and side effects?

### Review

- What named claim and scope does the Reviewer check?
- Does the Reviewer issue findings or recommendations, or an authorized Review Disposition?
- How independent are the producer, contract, context, sources, method, decision, and authority?
- Can the Reviewer see primary sources and counterevidence?
- Has anyone extended a pass to adoption or release?

### Handoff and Context

- Does the handoff retain the goal, state, actual changes, decisions, evidence, unknowns, risks, and next action?
- Is there a Handoff Receipt?
- Which duties move and when?
- Does the record keep truth, adoption, and authority separate from handoff acceptance?
- Does shared state have identity, version, freshness, and source links?
- Can roles drill down to primary records?

### Conflict and Integration

- Does the conflict concern facts, evidence, design, authority, policy, resources, values, or responsibility?
- Is there a Decision Target and owner?
- Are minority positions, unknowns, and reopening conditions visible?
- Do parallel assignments have isolated write surfaces, baselines, and an integration order?
- Does Integration Disposition have its own meaning apart from merge, adoption, and release?

### Flow and Cost

- Are there circular dependencies, endless review loops, or automatic successors with no stopping condition?
- Can we inspect WIP, capacity, timeouts, stops, and escalations?
- Do summaries preserve counterevidence, unknowns, and source links?
- Do people receive decisions that require their authority?
- Do parallelism, domain capability, independence, or isolation justify the coordination cost?
- Is there a simpler single-agent arrangement?

## 17.35 Conclusion

~~~text
bounded Work Reference
+ Role Contract
+ Subject Configuration
+ accepted Assignment
+ Authority Reference
→ candidate output and visible execution state
→ Handoff Receipt / Review / Conflict
→ authorized Integration Disposition
→ explicit next responsibility
~~~

The Controller coordinates under its grant. The Worker delivers candidates and evidence. The Reviewer challenges findings within a defined scope. The handoff transfers named work or records. Conflicts go to the authority responsible for the specific objects and Decision Targets at issue. Adoption, release, claim support, and accountability each need their own grounds.

> **Agent count is not evidence of organization. In this book, we inspect work, role, assignment, authority, responsibility, handoff, conflict and integration as candidate coordination relations.**

When those relationships are invisible, the observable fact is that several instances are running. Establishing a governable organization takes more evidence.

The next chapter asks how to retain Assignment, Handoff, Review, Authority, Decision, and Integration as a traceable chain of responsibility. The records should help us recover what changed, why, on what grounds, who decided, and which assumptions remain open.
