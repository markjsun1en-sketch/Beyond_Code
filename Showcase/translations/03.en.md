# Chapter 3. What Is AI-Native Software Engineering?
## Engineering for Delegated Execution

In Chapter 1, software agents take on open-ended tasks in real projects. They read project materials, choose part of the execution path, and use tools to change project state. Chapter 2 asks when the conditions that people used to sustain informally become unreliable. Longer tasks, higher stakes, more concurrent participants, and harder-to-recover state can all contribute.

These observations explain why the work changes. A term broad enough to cover every use of AI would group code completion, a single agent task, and a governed long-running production system together. An agent count would measure the number of executors while telling us little about the engineering around them. This chapter defines the conditions that prompt a response, which systems the response concerns, and how the problem relates to traditional software engineering, Agentic Development, and Harness Engineering.

---

## 3.1 A Working Definition

The book adopts a definition for its own analysis. It proposes a way to examine project conditions, with the scope and definitions used here.

> **When an intelligent agent takes on part of a real project's execution path, AI-native software engineering is the work of designing, operating, and evolving an engineering response to the impact, reversibility, and authorization risks of that delegation.**

Delegation identifies the problem the book addresses. Engineering adaptation identifies responses worth examining. The need for any particular mechanism comes from the circumstances of the work.

### The Starting Point — Delegated Execution

*Delegated Execution* means an agent carries out part of the actual path within a scope it has been granted. It may do any of the following.

- Read and select project materials.
- Draft or revise a local plan.
- Modify files, configuration, or other controlled state.
- Call tools and continue acting on feedback.
- Produce an engineering result that can be verified, accepted, or rejected.

The project's delegation, policy, and tool boundaries govern what the agent can do. The goal, permission to act, and authority to make a decision remain things the project has to assign.

### The Proposed Response — Engineering Adaptation

As delegation expands the impact, lengthens the work, creates more ways for state to diverge, or raises the cost of recovery, *Engineering Adaptation* can address the risks through mechanisms for the following.

- Intent and task scope.
- The selection, provenance, and updating of context.
- Distinguishing State, Decision, Assumption, and Evidence.
- Tools, data, and write permissions.
- Verification, review, and decisions about use.
- Recovery, takeover, and tracing responsibility after failure.

When people retain the execution path, the book usually describes the work as AI-assisted Development. When an agent has a real execution path and the engineering response falls short of the risk, that is Agentic Execution with a governance gap. A short, low-risk task can keep its boundaries in existing records.

To decide what adaptation belongs in a project, inspect the risk directly. Can the agent change real state? Can the tool reach beyond what the agent is authorized to do? Could an observer change its target? Is recovery difficult? The later chapters offer responses to such conditions.

## 3.2 AI-assisted, Agentic, and AI-native Describe Different Things

### AI-assisted Development

This describes a mode of collaboration.

```text
Human controls the task
→ AI proposes a candidate
→ Human selects, applies and verifies
```

AI can have a large effect on the result. People still control most of the real execution path.

### Agentic Development

This describes a capability to execute.

```text
Human or system delegates a bounded task
→ Agent selects and performs multiple steps
→ Result returns to an authorized decision path
```

An agent can sustain action in a bounded environment. That leaves a separate question about whether the environment provides sufficient state, evidence, recovery, and governance.

### AI-native Software Engineering

This describes how the engineering environment responds when delegated execution becomes a real condition of production. Two axes help describe the distinction.

```text
Axis A: Execution Delegation
Candidate suggestions ←────────────→ Real multistep execution

Axis B: Engineering Adaptation
Ad hoc use ←────────────→ Systematic state, evidence, recovery, and governance
```

One project can have strong agentic capabilities with ad hoc governance. Another can delegate just a few high-risk actions and build strict boundaries around them.

Multiple agents, persistent memory, self-evolution, and high autonomy can add complexity. Each is a design choice whose value depends on the work.

---

## 3.3 Two Systems to Engineer

### Product System

The *Product System* is the software delivered, run, and maintained, including the following.

```text
Code
Data
Assets
Runtime
Infrastructure
Configuration
```

Traditional principles of architecture, testing, deployment, security, and operations still apply directly to this system.

### Production Intelligence System

The *Production Intelligence System* is the intelligent execution environment that helps produce the Product System.

```text
Agents
Harnesses
Context assembly
Tools and permissions
Skills and procedures
Memory sources
Workflow and handoff
Evaluation mechanisms
```

A model is one component in this environment. Put the same model in two projects with different contexts, tools, policies, state, and evaluation arrangements, and different engineering behavior may follow. Evaluate and govern the full production configuration.

---

## 3.4 The Control and Evidence Plane Spans Both Systems

Observation and control of both systems call for a set of shared capabilities.

```text
Intent and Decision references
State and Assumption records
Authority and permission
Execution boundary
Observation and Evidence
Review and disposition
Trace and recovery
Policy and evaluation
```

The book calls these capabilities the *Control and Evidence Plane*. It operates across both engineered systems.

```text
                 Control and Evidence Plane
               ─────────────────────────────
               intent / state / authority
               observation / evidence / review
                         ↓        ↑
Production Intelligence System → Product System
          Agent execution           changed software
```

Evidence can support or challenge a Claim. An authorized person or explicitly delegated gate decides how that Claim may be used for a named purpose. Both are part of the control loop and have different responsibilities in it.

---

## 3.5 How Traditional Principles Extend to the Production System

Modularity, automated testing, version control, least privilege, small changes, observability, and recoverability still matter. The Production Intelligence System gives those principles additional places to apply.

| Traditional concern | Question in the Production Intelligence System |
|---|---|
| Module responsibilities | Do agents, skills, and workflows have clear responsibilities? |
| Interfaces | Are Agent Contracts, tool schemas, and handoffs clear? |
| Versions | Can we identify the versions of the context, policy, skill, and model? |
| Least privilege | What can an agent read, write, execute, and release? |
| Testing | How do we verify the harness, tool, workflow, and target result separately? |
| Observability | Which inputs, actions, artifacts, results, and failures are externally visible? |
| Rollback | How can we reverse or isolate state changes, rule changes, and capability upgrades? |

Use the mapping as a design aid. The behavior of an agent also depends on model versions, context selection, runtime feedback, and its authorization environment.

---

## 3.6 Where Harness Engineering Fits

*Harness Engineering* usually concerns how the intelligent execution environment gets context, tools, state, a sandbox, an execution loop, feedback, and recovery.

The production systems examined here bring further questions.

- Why should the work run?
- Who can change the goal and policy?
- How do results enter the Product System?
- How do people understand the work, take over, and answer for its consequences?
- How does experience enter memory, skills, or later practices?
- Are the costs of these mechanisms worthwhile?

The two areas overlap and the boundary can change with practice. This book uses Harness Engineering mainly for the execution environment itself. Its scope for AI-native software engineering also includes the Product System and organizational responsibility.

## 3.7 From Human Smoothing to Explicit Boundaries

Teams often fill gaps in processes through shared understanding, experience, and conversations as the work unfolds. I call that the *Human Smoothing Effect*. An agent can sometimes spot ambiguity and ask for clarification. How reliably it can do that still depends on the work and the environment.

Making tacit knowledge explicit also carries costs. Records take maintenance, go stale, add cognitive load, and can acquire authority they were never given. Give priority to boundaries and knowledge that have high impact, recur, cross roles, change easily, or are hard to recover after a failure. A local, low-risk, easily checked task can use a lightweight agreement.

The useful external records often concern the following.

```text
Goal and non-goal
State and scope references
Authority and permission
Known assumptions and conflicts
Required observation and evidence
Escalation or recovery path
```

## 3.8 Tight Boundaries, Flexible Execution

> **Tight Boundaries, Flexible Execution.**

State the boundaries of the task, then leave as much discretion inside them as the risk permits. The agent can choose an approach within the delegation the project gives it.

| Boundary | What it answers |
|---|---|
| Goal Boundary | What are we solving? Which outcomes are outside this task? |
| Scope Boundary | Which files, modules, data, or services may change? |
| State Boundary | Which repository, build, runtime, data, or configuration state is the starting point? |
| Authority Boundary | What can the agent propose, execute, or decide? |
| Risk Boundary | Which conditions trigger blocking, isolation, evidence collection, or escalation? |
| Evidence Boundary | What evidence supports which scope of the completion claim? |

These six questions serve as a working checklist. Safety-critical, data-intensive, and regulated projects can need more specific boundaries.

---

## 3.9 Contract over Hidden Reasoning

An external *Contract* gives the project something it can inspect and govern.

```text
Input references
Goal and scope
Allowed actions
Forbidden actions
Expected outputs
Required evidence
Escalation conditions
Completion and handoff rules
```

Tool calls, file changes, test output, errors, checkpoints, and observable messages can all provide evidence about the process. The audit basis is what the project can inspect. It includes inputs, actions, state changes, and results.

---

## 3.10 Encapsulate Execution, Expose Evidence

Within its scope, an agent can search, plan, experiment, implement, and debug with delegated discretion. The work still needs to expose enough for someone to answer the following questions in proportion to risk.

- What actually changed?
- Which versions and states were used?
- Which verification steps actually ran?
- What did they observe?
- Which failures took place before the target could be observed?
- Which claims have only limited coverage?
- Which unknowns, conflicts, and intended uses remain open?

```text
Encapsulated execution
        ↓ produces
Observable changes + Evidence
        ↓ supports / challenges
Claim in Scope + declared Coverage
        ↓ informs
Authority-bound Decision Record
        ├── targets ──> named Decision Target
        └── records ─> Target-specific Disposition
```

---

## 3.11 Evidence over Unsupported Confidence

A diff, static analysis, a test, a runtime capture, a human experience review, and a production metric each answer different questions. Which evidence fits depends on the following.

```text
Claim
Scope
Risk
Intended Use
Observation Boundary
```

A diff can tell us directly whether a change touches a public API. A runtime capture can show whether UI elements overlap in a specific build and scenario. A human reviewer may have the final authority over aesthetic or value trade-offs. A test pass supports the result of the checks that ran. Implementation scope, adoption, and release still have their own decisions.

```text
Evidence / Validation Rule
→ Validation Coverage

Authorized Role or Delegated Gate
→ Acceptance / Adoption / Release Authorization Disposition
```

Where a gate has an explicit, bounded delegation, the same machine result can also trigger the corresponding disposition.

---

## 3.12 Human Cognitive Authority

*Human Cognitive Authority* is the final human authority over matters that require human judgment. To exercise it on consequential decisions, an organization needs practical abilities.

- Find the underlying evidence.
- Understand the claim, scope, and uncertainty.
- Identify overreach by automation or gaps in evidence.
- Veto, pause, take over, and recover.
- Assign value judgments and final accountability to the appropriate people.

Policy can delegate low-risk, reversible dispositions to automation. The organization needs to understand and be able to change the automation boundary, the delegation, and the takeover path.

---

## 3.13 Risk-based Autonomy

Model capability, tool capability, and a grant of autonomy each tell us something different. The strength of governance depends on the combination of factors in the actual work.

```text
Granted Action Surface
× Impact
× Irreversibility
× State Uncertainty
× Verification Difficulty
× Recovery Cost
```

A strong model in an isolated read-only environment may need light governance. A less capable automation system that can write production data may need strict boundaries.

Policy can provide several responses.

```text
continue within scope
narrow
collect evidence
isolate
block
invoke delegated gate
escalate
```

The project's risk and organizational responsibilities determine which responses it needs.

## 3.14 The Engineering Problems Ahead

The remaining chapters give related concerns distinct responsibilities. They can occur together in one task.

### Desired Outcome

- Intent Engineering gives goals, motives, scope, and acceptance targets an identity that can survive execution.

### Supplied Information and Typed Records

- Context Engineering determines which information is selected, assembled, transmitted, and recorded.
- Truth and State Architecture gives State Claims, Decisions, Assumptions, and Evidence a type and a scope of applicability.

### Execution and Trust

- Agent Execution covers permissions, contracts, state changes, and recovery.
- Reliability covers allowed behavior, failure modes, and repeatable evaluation.
- Verification and Evidence covers observation, coverage, counterevidence, and fitness for use.
- Review Engineering covers how people and automated systems share review.

### Human Control

- Cognitive Engineering concerns how people understand high-throughput changes without relying on a misleading summary.
- Governed Autonomy covers delegation, policy, gates, intervention, and takeover.
- Observability and Intervention covers how to know what happened and how to stop work in time.

### Learning and Organization

- Memory Engineering covers which records to retain, invalidate, or retrieve.
- Self-Evolution Engineering covers how skills, policies, and workflows change under control.
- Multi-Agent Organization covers roles, write surfaces, handoffs, and shared state.

### Cross-cutting Concerns

- Traceability and Accountability.
- Security, Privacy, and IP.
- AgentOps, evaluation, and cost.

## 3.15 An Iterative AI-Native Software Development Lifecycle

Existing development practices continue to operate. When delegation creates risks around state, authorization, observation, or recovery, the project can add the control loops that address them.

```text
Intent and trigger
        ↓
Minimum Initial Context
        ↕
Typed Record / Claim Resolution
        ↕
Progressive Retrieval
        ↓ sufficient for current boundary
Planning and Plan Review
        ↓
Governed Execution
        ↕
Continuous Observation
        ↓
Evidence and Claim Coverage
        ↓
Authorized Disposition
        ↓
Integration / Deployment / Rejection
        ↓
Memory and Controlled Evolution, when justified
```

The appropriate steps depend on the task, and the path can loop back. A gap in context can send planning back to retrieval. A new observation can invalidate a State Claim. A gap in evidence can narrow a claim. A human disposition can accept evidence, reject a scope, or defer adoption. Only selected experience should enter memory, skills, or policy.

## 3.16 How Much Process Does the Work Need?

The object model helps explain what a project might need to keep. A local, low-risk, easily verified task can capture intent, scope, a state reference, and an evidence requirement in a short brief.

Stable IDs, manifests, independent reviews, or recovery records become more useful under conditions like these.

- The work crosses sessions or roles.
- The impact is large.
- Relevant states can diverge.
- Data or release changes are irreversible.
- Sources of authority can conflict.
- Reconstructing a failed execution would be costly.

The engineering objective is to reduce current risk with governance the project can afford to maintain.

---

## 3.17 When a Project May Need Stronger Mechanisms

Look for the conditions that make a mechanism worthwhile.

1. Does the agent directly change real project state?
2. How much open-ended path selection has been delegated?
3. Can current State, Intent, and Decision Authority diverge?
4. Does the work cross sessions, agents, or repositories?
5. How easily can we recover if it fails?
6. Does verification cover the actual claim?
7. Does automation have explicit authority to write and decide?
8. Can people locate key evidence without reading all raw output?
9. Can memory, skills, and policy go stale or expand permissions?
10. Are final accountability and takeover paths clear?

Each answer concerns a particular mechanism. Use the answers to decide which gaps deserve attention.

---

## 3.18 What AI-Native Software Engineering Optimizes

*Generation Throughput* measures the production of candidates. *Engineering Productivity* concerns the work it takes to deliver an outcome. Evaluating that work calls for separate observations.

- **Outcome Quality.** Did the result solve the original problem?
- **Reliability.** Can we continue getting acceptable results under comparable conditions?
- **Evidence Coverage.** Which part of the completion claim is supported?
- **Human Cognitive Cost.** What does it take for people to understand and decide?
- **Recovery Cost.** How hard is recovery after failure, drift, or interruption?
- **Governance Cost.** What do the boundaries, reviews, and records cost?
- **Learning Efficiency.** Can useful experience be selected, reused, and withdrawn?

These measures can conflict. More complete traces can help recovery and increase governance and cognitive costs. The trade-off has to make sense for the particular task.

## 3.19 Conclusion

Agents can be entrusted with real execution in projects. This book uses AI-native software engineering for how the project adapts to those conditions.

```text
Delegated execution
+ Engineering adaptation
= AI-native software engineering in this book
```

The work concerns the following systems.

```text
Product System
+ Production Intelligence System
```

The Control and Evidence Plane connects them through Intent, State, Authority, Observation, Evidence, Review, and Recovery. The goal is to expand production capacity while keeping goals traceable, state inspectable, actions authorized, results verifiable, failures recoverable, and accountability assignable.

---

## Principles

1. **Look for both delegated execution and a response that fits it.**
2. **Assess agentic capability and engineering adaptation separately.**
3. **Engineer both the Product System and the Production Intelligence System.**
4. **Share control and evidence capabilities across the two systems.**
5. **Tight Boundaries, Flexible Execution.** Define the goal, scope, state, authority, and evidence. Allow discretion within those constraints.
6. **Contract over hidden reasoning.** Work with observable inputs, actions, state changes, and results.
7. **Choose evidence that fits the claim.** Check scope, risk, and intended use.
8. **Distinguish validation coverage from authorized dispositions.** Delegate automated decisions explicitly.
9. **Make human authority exercisable.** Keep the ability to understand, veto, take over, and change the boundaries of automation.
10. **Fit governance to risk and cost.**

---

## Common Anti-Patterns

- Claiming to be AI-native because an agent is present.
- Treating multiple agents, a large context, or a stronger model as measures of maturity.
- Making the Control Plane a third system that duplicates every object.
- Micromanaging every step in the name of reliability.
- Letting an agent silently change the goal, authority, or policy in the name of autonomy.
- Ranking evidence strength without reference to a claim.
- Reporting a test pass as approval of scope, adoption, or release.
- Making hidden model reasoning a required audit asset.
- Building registries, graphs, and gates of the same weight for every small task.
- Measuring generation speed alone while overlooking verification, recovery, cognition, and governance.

---

## Checklist

- Is the agent generating suggestions or executing a delegated path?
- Have state, authority, evidence, and recovery been adapted to that work?
- Are AI-assisted, Agentic, and AI-native described on appropriate dimensions?
- Are the boundaries between the two engineered systems clear?
- Does the Control and Evidence Plane serve both systems without duplicating their objects?
- Are the Goal, Scope, State, Authority, Risk, and Evidence boundaries explicit?
- Does the contract use external, observable information?
- Does the evidence name a claim, scope, and intended use?
- Can we distinguish Validation Coverage from Acceptance, Adoption, and Release?
- Did the automated gate receive authority over the relevant Decision Target?
- Does autonomy follow the actual action surface, impact, reversibility, and recovery cost?
- Can context and state resolution iterate?
- Can people understand consequential changes, veto them, take over, and hold someone to account?
- Have we accounted for the cost of the new mechanisms?
