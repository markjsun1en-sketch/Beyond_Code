# Chapter 22. Engineering Capability Fit for AI-Native Work
## From Six Maturity Levels to Capability Fitness

This chapter proposes two ways to describe capability and assess fit. The categories are candidates. Teams can choose the surfaces their work calls for. The AI Game Dev OS v4.94 case illustrates why capability presence, governance activity, validation results, and authorized decisions need separate records. It leaves effects on efficiency, quality, safety, and cost open.

“What stage are we at?” is a reasonable question when a team is taking stock, explaining a budget, or planning its next investment. It can help organizations compare which mechanisms they already have and which they still need. The trouble starts when the answer takes this form.

~~~text
more autonomy
+ more agents
+ more registries
+ more evidence
+ more memory
+ more evolution
= higher maturity
~~~

A tool permission can expand what an agent can usefully do and increase its blast radius. Review can add independent scrutiny or produce waits and governance livelock. Memory can improve continuity or propagate stale judgments and contamination. Traces can help someone reconstruct what happened and impose privacy, retention, and cognitive costs. These effects require different judgments.

*Capability Fitness* asks whether the current engineering configuration is sufficient and proportionate for a particular workload, intended use, risk surface, recovery requirement, and operating cost.

> **Do not rank mechanisms by accumulation; evaluate whether a bounded capability configuration is fit for a named workload, risk surface, and operating constraint.**

A team can still plan its development. Start with the need, make a decision, and review the result in operation.

~~~text
identify a bounded need
→ compare required and current capability
→ expose gap, excess and unknown
→ make an authorized disposition
→ observe adoption, outcome, cost and drift
→ re-evaluate
~~~

## 22.1 Start With the Control Floor

Chapter 21 distinguishes necessary, conditional, and optional controls. The minimum is identity for Work and Attempt, scope and allowed effects, named authority, visibility into results, failures, unknowns and `non-result`, and a way to stop, recover, or discard an attempt safely. An issue, version control, sandbox, CI, and human workflow can share those functions.

This chapter asks whether the current capability fits named work and its intended use. The review needs the current configuration and evidence, known gaps, excess, and unknowns, risk and cost boundaries, and an authority that can decide the named target.

Use a formal Engineering Capability Profile and Capability Fit Review when those risks warrant them. The same applies to richer baselines, context, evidence, handoff, memory, evolution, multi-agent records, and re-evaluation. Multi-Agent Topology, Persistent Memory, Self-Evolution, a Human Control Plane, an Execution Epoch, a complete Decision Graph, full tracing, and an organization-wide score are choices. A simple configuration can be sufficient, and a complex configuration still needs to demonstrate fit.

## 22.2 What Does a Maturity Ladder Rank?

A progression model that serves as a roadmap needs to answer these questions.

1. Does each level evaluate the same object?
2. Which shared criterion orders the levels?
3. Does each higher level preserve the necessary boundaries of the preceding one?
4. Why would an increase in one capability call for an increase in another?
5. Are different workloads, scopes, and risk surfaces comparable?
6. Who can assign a level, and on which evidence?
7. What practical decision would a change of level support?
8. When is lower complexity the right choice?

A list of capabilities can be useful for discussion. A phased standard can support access, training, or improvement when it has a stable object, process, and purpose. The original Chapter 22 changed what it evaluated as it moved up the ladder.

## 22.3 The Original Levels Change the Axis of Evaluation

| Original level | What it described | Axis of evaluation | Assumption that needed support |
|---|---|---|---|
| Level 0. Ad Hoc Assistant | Chat, copy and paste, no project memory | Usage and continuity | Memory always represents a higher level |
| Level 1. Supervised Copilot | AI coding with item-by-item human review | Collaboration and supervision | Item-by-item review is a stage on the way to autonomy |
| Level 2. Bounded Workflow Agent | Tool permission, evidence, sandbox, rollback | Authority, validation, and recovery | Bounded execution ranks above a copilot |
| Level 3. Governed Multi-Agent System | Controller / Worker, Context Registry, Review Agent, handoff | Organization and coordination | Multiple agents rank above one |
| Level 4. Cognitive and Evidence-driven Organization | Cognitive Compression, Decision Interface, observability, review budget | Human control, evidence, and operations | These mechanisms belong together as a single organizational stage |
| Level 5. Controlled Self-Evolving Organization | Memory, skill evolution, cross-project transfer, organizational optimization | Learning, adoption, and evolution | Self-Evolution is every organization’s destination |

The first transition changes how people collaborate with AI. The second changes execution permission and recovery. The third changes organization. The fourth changes human control, evidence, and observation. The fifth changes memory, adoption, and evolution. Each transition concerns a different property.

## 22.4 One Project Can Use Several of These Configurations

| Work | Possible configuration |
|---|---|
| Local code completion | A person uses a copilot and reviews each diff |
| Dependency update | A Bounded Agent works in a restricted directory and sandbox and runs tests |
| Production release | One Release Agent works with independent Human / Security Authority without a Controller / Worker topology |
| Project knowledge maintenance | A person explicitly promotes material to Project Memory, with automatic cross-project transfer disabled |

Code completion resembles Level 1, and the update resembles Level 2. A release can have Level 4 evidence and observability while using one agent. Memory can resemble part of Level 5 while the team elects to keep Self-Evolution out of scope.

Capabilities apply to a workload, action, environment, and decision target. An overall level hides differences that affect real engineering decisions.

---

## 22.5 Keep the Diagnostic Questions

The original levels give us questions worth asking. Is AI use mostly occasional conversation? Who reviews individual changes? Can an agent use tools and change state? Does the work cross agents, roles, and handoffs? What strains human attention and Review Bandwidth? Can Memory, Skills, Policy, or Workflow change?

A single project can answer those questions differently for each workload. Begin with the named workload and look at the capabilities it calls for.

---

## 22.6 Maturity as the Ability to Recalibrate

If the term *engineering maturity* is useful, this book proposes a scoped definition. Over a named scope and observation window, can the team repeatedly identify a need, configure the work at or above the protected floor, observe how the configuration performs, and revise or retire it when it becomes unsuitable, costly, or subject to drift?

~~~text
identify
configure
bound
observe
decide
revise
retire
~~~

The response can be to add capability, narrow overbroad authority, remove a gate whose output serves no decision, merge duplicate registries, stop ineffective automation, keep a simple process that suffices, record an unknown, or reassess after a change in use or environment. This is one candidate meaning of maturity for the book.

## 22.7 Specify Scope, Workload, and Intended Use

“Do we have evidence?” “Can our agent act autonomously?” “Is our memory good enough?” Each question needs a scope.

- Organization, project, repository, or service.
- Work type and workload population.
- Users, affected parties, and intended use.
- Actions, data, tools, environment, and external effects.
- Impact, reversibility, and recovery time.
- Duration, concurrency, and handoff.
- Decision target and decision authority.
- Evaluation window and known coverage.
- Policy, contract, rights, and protected control floor.
- Current time and revision, and triggers for re-evaluation.

A read-only retrieval agent may fit an internal code search. Let it send source code to an external processor without authorization and the security, privacy, confidentiality, and contract boundaries change. The same mechanism can therefore lead to different findings for different uses.

This chapter introduces the *Engineering Capability Profile* and the *Capability Fit Review*. The profile describes the current configuration. The review compares it to what a named use requires and connects its findings to an authorized decision.

The earlier chapters define the objects the profile and review refer to.

- Chapter 4 defines Intent, Scope, and Acceptance Targets.
- Chapters 5–6 cover Context, State, Decision, Assumption, and Conflict.

A profile points to these records in their original roles and scopes.

## 22.9 The Engineering Capability Profile Describes the Available Configuration

An *Engineering Capability Profile* describes observable mechanisms, their boundaries, evidence, and known gaps at a specified time and scope. It says which work and uses the team intends to support, what mechanisms exist, which enter real work, and what scope, authority, failure, and recovery boundaries apply. It records evidence and observation coverage, unknowns, expiry, conflicts, drift, and the cost of running, waiting, reviewing, maintaining, and understanding the configuration.

~~~yaml
profile_ref: local-refactor-profile
profile_at: 2026-08-27

scope:
  repository: example-project
  workload: local_reversible_refactor
  environment: developer_worktree
  intended_use: prepare_change_for_human_review

current_configuration:
  intent_and_scope: short_work_brief
  context_and_state: pinned_head_plus_dirty_state_check
  execution_and_authority: path_limited_write
  evaluation_and_decision: focused_tests_plus_diff_review
  human_control: final_scope_disposition
  recovery: preserve_diff_and_revert_named_change

known_gaps:
  - no_cross_session_handoff

not_needed_for_current_scope:
  - multi_agent_controller
  - persistent_memory
  - self_evolution

re_evaluate_on:
  - production_write_added
  - repository_scope_expanded
  - recovery_path_changes
~~~

A paragraph, table, configuration file, query, or composite view can express the profile.

## 22.10 Describe the Current State

A plan for independent review, a future rollback mechanism, a requirement for a complete trace, a proposal to let an agent optimize a workflow, and a claim that a team follows risk governance all have their own roles. Describe the current configuration using evidence of its actual state.

| Type | Example |
|---|---|
| Observable Presence | The repository contains a configuration, tool, or workflow |
| Operational Use | The mechanism ran on an actual path within the stated scope |
| Declared Boundary | Policy or contract states what is allowed and prohibited |
| Observed Behavior | The record shows what happened at runtime |
| Evidence Coverage | What the current checks observed and which cases they leave open |
| Desired Capability | A plan, goal, or candidate change |
| Unknown | Presence, use, boundary, or outcome remains unconfirmed |

Check each claim at its own level. A file can exist unused. A mechanism can run with the wrong boundaries. Runtime can depart from policy. One successful run provides evidence about that run.

---

## 22.11 Bound a Profile by Time and Version

A profile may become stale when a model, tool, skill, prompt, or policy changes. Changes to context, data, repository, workload, permissions, credentials, authority, action sink, evaluation, verifier, observer, human role, review capacity or ownership can also matter. Provider terms, prices, retention, or rights can change. An incident, counterevidence, unknown external effect, or loss of recovery, rollback, or sandbox access can invalidate the observation.

~~~text
profile scope
+ observed-at / effective period
+ source or baseline references
+ known gaps
+ invalidation / re-evaluation triggers
~~~

An expired profile can still describe the past accurately. Check its conditions before using it to describe the present.

---

## 22.12 What Capability Does the Work Require?

The *Required Capability Boundary* is what the team compares the current profile against. It describes the minimum engineering functions and protections a named workload and intended use need, given risk, recovery, policy, cost, and available human decision-making.

The boundary may include required functions, the Protected Control Floor, acceptable unknowns and residual risk, required Evidence and Coverage, human decisions, intervention and takeover, recovery and exit, and mechanisms this particular work can omit or must avoid. It can specify that a single agent suffices. Authority still comes from the relevant grant.

---

## 22.13 Compare the Required Boundary With the Current Configuration

A *Capability Fit Review* compares the Required Capability Boundary with the current profile for a named workload, intended use, risk, and cost. It produces findings for an authorized decision.

~~~text
Workload / Intent / Intended Use
          +
Risk / Impact / Reversibility / Constraints
          ↓
Required Capability Boundary
          ↕ compare
Current Engineering Capability Profile
          +
Observable Evidence / Coverage / Unknown
          ↓
Fitness Finding
          +
Named Capability Use / Configuration Change / Adoption Target
          ↓ authorized Decision Record
Fitness Disposition
          ↓
Maintain / Restrict / Experiment / Strengthen / Replace / Retire / Defer
          ↓
Adoption / Operation / Outcome / Cost / Drift
          ↺
Re-evaluation
~~~

Name the Review Target and the downstream Decision Target. They may refer to the same candidate while asking different questions. Can this agent move from read-only access to repository writes? Does the Context mechanism support a migration that spans sessions? Is an independent reviewer needed? Is the trace sufficient to reconstruct a release decision? Should a memory still be retrieved automatically? Should a gate stay, narrow, merge with another control, or retire? Each review needs one such purpose.

---

## 22.14 A Finding Informs a Disposition

A *Fitness Finding* is a scoped Review Finding under Chapter 10. It reflects the current profile, evidence, and known unknowns. The configuration might be sufficient, sufficient only in a narrower scope, missing a required capability, too costly or complex for the use, unknown for lack of evidence, or contested by conflicting sources.

A *Fitness Disposition* is a scoped Decision under Chapter 9. The named authority decides whether to maintain, restrict, experiment, strengthen, replace, retire, or defer a Capability Use, Configuration Change, or Adoption Target. The Decision Record names that target and can cite the finding as input.

Suppose the review finds that rollback has yet to be verified. The decision-maker can add and test rollback, narrow to read-only, have a person execute, restrict to a sandbox, or pause the use. Within a low-impact scope that is easy to restore manually, the decision-maker might document residual risk and allow it to continue. The finding remains the same in each case.

## 22.15 Five Questions, From Presence to Sustained Fit

| Judgment | Question | What still needs support |
|---|---|---|
| Presence | Does the mechanism exist? | Its use in real work |
| Operational Use | Did a real path invoke it? | Correct scope and authority |
| Boundary Adequacy | Do scope, authority, failure handling, and recovery meet the current need? | The target outcome |
| Evidence Adequacy | Does the evidence support this Decision Target? | Continued fit over time |
| Sustained Fitness | Do results, cost, controls, and recovery remain suitable during the window? | Optimality across projects |

Each proposed implication below needs additional evidence, scope, and a decision.

~~~text
review_agent_present
⇒ review_independent

tests_passed
⇒ acceptance_target_covered

rollback_command_exists
⇒ recovery_verified

memory_active
⇒ memory_current_and_applicable

trace_complete_for_one_system
⇒ decision_reconstructable_end_to_end

self_evolution_pipeline_runs
⇒ adopted_change_improved_the_system
~~~

[Records of adoption in DevOS and RandomHeroes](../../Evidence/receipts/ER-20261122-005__CLM-C22-001.md) make the distinction concrete. The Art Kit’s directory, package, registration, use in production work, and human aesthetic acceptance have different sources. An inventory establishes what was listed. An invocation and its artifacts establish what was used. An experience decision records who accepted what for a particular purpose. Leave the latter questions open when the records cover only installation.

## 22.16 Adoption and Fitness Describe Different Things

Experiment, Pilot, Active, Sustained, Restricted, and Deprecated can describe where a mechanism is in its adoption lifecycle. Fitness asks whether it suits the particular use.

| Adoption state | Possible Fitness Finding |
|---|---|
| Experiment | Promising, with insufficient evidence or coverage |
| Pilot | Fit for a narrow scope, with wider use open |
| Active | In real use, with a possible gap or excess |
| Sustained | Used reliably in the past, with possible drift |
| Restricted | Fit within the restrictions |
| Deprecated | Withdrawn from current use, with earlier fit assessed on its own terms |

A capability may be absent because the current scope has no use for it. Check fit at the time and scope relevant to the decision.

The local November 2026 records contain two distinct states. A separate release worktree retained a DevOS v4.98 Beta candidate package, build receipt, and archival record for creating a new Godot project on macOS. Some observations and capability items were still blocked. Full qualification remained open. RandomHeroes had a local v4.98 binding and an adoption result marked `APPLIED` for that application. Its formal backup restoration field was still negative.

Distinguish the distribution slice, local installation, actual workflow use, scoped acceptance, and full qualification. The local records establish their own scope. Online download status and migration support for older projects were outside the check.

## 22.17 Capability Fitness Needs Local Measures

A matrix helps display several judgments. An aggregate score obscures the fact that authority, security, recovery, cost, and human judgment lack a common unit. The relevant weights vary with workload, use, and risk. Strong context or automation cannot supply missing production-write authority. Traces cannot restore an unavailable recovery path. Low token cost cannot settle a privacy or rights issue. An average can conceal a decisive gap in the Protected Control Floor or turn uncertainty into an arbitrary number.

Within one Decision Target, a metric can help. Compare accepted outcome rates for the same workload, human waiting in comparable windows, recovery success for the same scope, coverage under the same review contract, or total production cost before and after a specified change. Keep the comparison bound to that use.

---

## 22.18 Example Findings and Dispositions

A Capability Fit Review can use labels like these.

- `fit_for_scope`. Evidence supports fit within the named scope.
- `constrained_fit`. Fit is limited to a narrower scope, period, or condition.
- `gap`. A required boundary or capability is missing or inadequate.
- `excess`. A mechanism adds disproportionate cost, waits, or complexity.
- `not_needed_for_scope`. The named use has no need for the capability.
- `unknown`. Evidence, coverage, state, or unresolved conflicts leave the finding open.

The authorized role can `maintain`, `restrict`, `experiment`, `strengthen`, `replace`, `retire`, or `defer`.

~~~yaml
decision_target: allow_repository_write_for_local_refactor

fitness_findings:
  execution_scope: fit_for_scope
  recovery: constrained_fit
  cross_session_handoff: not_needed_for_scope
  production_effect: prohibited_by_scope

disposition:
  action: maintain
  constraints:
    - developer_worktree_only
    - no_production_credentials
    - human_diff_disposition_required
  re_evaluate_on:
    - scope_expansion
    - recovery_change
~~~

A project can use its own vocabulary when it can still distinguish observation, finding, decision, and action.

## 22.19 Eight Surfaces for Reviewing Capability

A *Capability Surface* groups related engineering questions for review. The groups are provisional and can be split or combined.

| Capability surface | Question | Related chapters |
|---|---|---|
| Work and Intent | Are the need, intent, scope, acceptance target, and non-goals clear? | 4, 17, 21 |
| Context and State | Can we see the baseline, claims, context, conflict, gaps, and freshness? | 5–6 |
| Execution and Authority | What can the agent do, and how do we stop, recover, or revoke authority? | 7–8, 13–14 |
| Evaluation and Decision | Can we distinguish observation, evidence, coverage, review, and decision? | 9–10 |
| Human Control and Cognition | Can the person understand the decision and retain direction, intervention, and takeover? | 11–12, 14 |
| Organization and Handoff | How do Work, Role, Assignment, Handoff, Conflict, and Integration connect? | 17 |
| Memory, Learning and Evolution | How do candidates form, receive Promotion or Adoption, expire, recover, and exit? | 15–16 |
| Operations, Trace, Security and Economics | How are baselines, drift, traces, protections, and total cost observed? | 18–20 |

A regulated production system may review security, privacy, IP, and traceability independently. A local read-only tool may need only Work, Context, Evaluation, and Human Decision. The number of surfaces in use has no scoring role.

## 22.20 Work and Intent

Ask what triggered the work, who owns intent, who is affected, and whether scope, non-goals, constraints, priorities, and Acceptance Targets are clear. Look for unresolved questions and conflicting intentions, how the work is decomposed, and who can change the goal, cancel work, or accept the result.

Check whether actual Agent Input conveys the intent beyond the final prompt. Inspect whether work opened while goals were in conflict, local acceptance got reported as product success, scope aligns with tools, permission and evaluation, and people retain authority over value, experience, taste, and trade-offs.

Gaps include goals left in conversation, missing non-goals, uncheckable targets, conflicts collapsed into a single priority, and completion criteria mixed up with release criteria. Excess can look like a governance committee for a local reversible change, freezing all acceptance criteria before a trial, using scores for creative judgment, or copying intent into registries with no named decision use.

---

## 22.21 Context and State

Locate the versioned state sources, environment, and dirty state. Check decisions, assumptions, conflicts, unknowns, freshness, Context Contract, Pack, Manifest, and access. Inspect initial selection, progressive retrieval, provenance, compression, loss, and the ability to reach the source. Work needs a response when a saved baseline differs from an observation or information is missing or conflicting.

Ask whether people can locate the baseline, whether the agent can obtain new dependencies during work within the allowed information surface, and whether stale, conflicting, and unknown material stays visible. A Context Manifest records what was provided. Truth and safety require their own bases.

Gaps include summaries without revision references, dirty work treated as a clean baseline, guessing through Context gaps, compressed views with no path to sources, and later writes overwriting conflicts. Excess includes loading the whole repository and history at once, full snapshots for small tasks, more Context in place of clarifying intent or state, and duplicate systems for retrieval, memory, and truth.

---

## 22.22 Execution and Authority

Examine Capability, Permission, Authority Grant, and Responsibility. Locate tools, credentials, data, action sinks, environment, Execution Contract, Attempt, Checkpoint, and Handoff. See how supervision, pause, restriction, revocation, takeover, external effects, blast radius, and reversibility work. Check failure, timeout, unknown effects, `non-result`, sandbox, fallback, rollback, recovery, and safe exit.

Ask whether the agent stays within the grant, new tools or actions acquire permissions deliberately, executors are prevented from expanding grants or lowering the floor, and failure has a clear stop, preservation, and recovery path. Check revocation against actions still in flight, downstream agents, and credentials.

Gaps include inferring permission from an available tool, inferring acceptance authority from execution permission, assuming a success-only path, a nominal sandbox that leaks side effects, and rollback without a target and check. Excess includes release gates for read-only analysis, multiple approvals for every local attempt, qualification-period identity requirements for reversible development, and item-by-item approval of every tool call.

---

## 22.23 Evaluation and Decision

Follow Observation, evidence generation, verifier integrity, Claim, scope, baseline, Intended Use, Validation, Evaluation, Review, counterevidence, Coverage, known gaps, and `non-result`. Distinguish Findings, Acknowledgments, Approvals, and Decisions. Acceptance, Adoption, Integration, Release, and Qualification can require different authorities, expiry conditions, and re-evaluation.

Did Evidence observe the subject of the current claim? What did a test pass cover? Can we distinguish verifier failure, target failure, and target `non-result`? Does Review have the independence the decision needs? Does a gate stay inside its grant? Check evidence against the current decision and any narrower uses it may support.

Common gaps include completion claims without evidence, test count standing in for coverage, review comments treated as decisions, human acknowledgment treated as acceptance, and development checks treated as production qualification. Excess includes repeated tests for unrelated claims, expanding the proof surface without a decision use, ranking all evidence on one weak-to-strong scale, and full independent review of low-impact work that yields no additional information.

---

## 22.24 Human Control and Cognition

Identify the Decision Target that needs a person, information volume, decision complexity, and Review Bandwidth. Consider progressive disclosure, briefs, drill-down, conflict visibility, and which judgments about direction, experience, aesthetics, ethics, and rights belong to people. Locate override, intervention, takeover, and stop authority, and how attention, queues, alerts, escalation, and past decisions are handled.

Does the person see information about the current decision? Does compression keep scope, evidence, conflict, unknowns, and irreversible effects? Can the person reach the underlying sources? Is the queue larger than qualified reviewers can handle? Does the agent signal that a recommendation is pending? Does the person retain meaningful direction and responsibility?

Gaps include dashboards that report counts without a decision target, summaries that omit material conflict, interfaces that offer only approve or reject, ownerless alerts, and automatic scores in place of creative judgment. Excess includes streaming every tool event to people, demanding attention for every low-risk action, adding approvals without new information, and queuing the same finding in multiple interfaces.

---

## 22.25 Organization and Handoff

Trace Work, Role Contract, Assignment, Authority, decomposition, dependencies, concurrency, and integration. Inspect handoff packages, open items, baselines, receipts, controller, worker, reviewer, and human roles. Consider conflict, escalation, reassignment, cancellation, independence, shared context, leakage, and the costs of coordination, waiting, rework, and integration.

Can the work be decomposed? Do agents provide useful parallelism, specialist boundaries, or independent review? Is each assignment explicit about scope, input, output, and authority? Does a handoff preserve open work and unknowns? Is the controller’s authority bounded? Can the integration owner handle conflicts and the combined result?

Gaps include roles with no contract, overlapping writes, a reviewer who shares the same incomplete context as the author, a handoff that says only `done`, and conflicts with no resolution authority. Excess includes splitting tightly coupled work, adding a controller to a simple sequential task, adding reviewers with no independent decision target, and spending more on synchronization than on execution.

---

## 22.26 Memory, Learning, and Evolution

Trace Experience, Observation, Failure, and Candidate, then provenance, scope, applicability, conflict, and expiry. Distinguish promotion, storage, retrieval, use, and effects on behavior. For changes, inspect the candidate, evaluation contract, comparator, adoption, activation, release, observation, rollback, forward recovery, revocation, and retirement, including transfer across sessions, projects, and organizations.

Does completed work generate a candidate? Who can promote it, and to which memory scope? Does retrieval check applicability? Can we observe whether retrieval affected behavior? Does self-modification require an independent adoption decision? Are outcome, guardrails, cost, and drift observed after adoption?

Gaps include automatic memory on `CLOSED`, treating a retrospective as a known root cause, transferring old experience without scope, candidates editing current skills or policy, and adoption without recovery or exit. Excess includes permanent retention of every session, skills for every comment, complex pipelines for rare work, automatic memory injection that expands context and prompt-injection exposure, and treating change frequency as learning speed.

---

## 22.27 Operations, Trace, Security, and Economics

Review the Operational Baseline, workload, evaluation window, outcomes, metric contracts, cost attribution, and human attention. Connect identity, actions, context, decisions, and evidence. Check security, privacy, confidentiality, supply chain, and IP. Look for model, tool, permission, evaluation, economic, and contract drift, and inspect incident response, re-evaluation, fallback, rollback, suspension, retirement, retention, access, deletion, and reconstruction.

Can we identify the running configuration? Can we distinguish outcomes from calls, artifacts, and agent claims? Does the trace support a decision, reconstruction, or accountability? Are data, model processing, tools, dependencies, and rights bounded? Does the comparison count token, human, coordination, failure, governance, and maintenance costs? Does drift refer to a baseline and trigger scoped re-evaluation?

Gaps include call counts without accepted outcomes, averages without workload, denominator, or coverage, traces without authority and decisions, secrets or protected material in ordinary prompts and logs, and old judgments reused after model, provider, or permission changes. Excess includes permanent full payload retention, dashboards for unused metrics, spurious monetary scores for all risks, full regression on every drift, and suppressing statutory, contractual, or reserved human decisions to cut cost.

## 22.28 The Surfaces Overlap

A change can cross several surfaces.

~~~text
Intent changes
→ Scope and Acceptance Target change
→ Context and State requirements change
→ Authority and Evaluation need re-binding
→ Lifecycle path and Operational Baseline may change
~~~

Memory promotion can depend on provenance and applicability, promotion evidence, human authority, security and privacy retention, and operational expiry and drift. Multi-agent handoff can involve decomposition, context projection, authority, trace, integration, and review capacity. The surfaces help organize a review. Use the records and system boundaries that fit the work.

---

## 22.29 Questions to Ask on Every Surface

1. **Purpose.** Why does the workload need this?
2. **Scope.** Which actions, data, environment, and population are covered?
3. **Mechanism.** Which observable mechanism serves the need?
4. **Authority.** Who can use, configure, override, pause, or revoke it?
5. **Evidence.** What establishes presence and fit for the particular use?
6. **Coverage.** What did the evidence observe, and what remains open?
7. **Failure.** How do failure, uncertainty, conflict, timeout, and false positives appear?
8. **Recovery.** How can the work isolate, roll back, transfer control, reauthorize, or exit?
9. **Ownership.** Who maintains it and decides its disposition?
10. **Economics.** What do execution, waiting, review, maintenance, attention, and opportunity cost?
11. **Drift.** Which changes can invalidate the current configuration?
12. **Re-evaluation.** When and by whom will it be reviewed, and on what basis?

These are questions about meaning. A short profile can answer several together while preserving each material boundary.

## 22.30 Keep the Protected Control Floor

For a stated scope, some controls sit outside the ordinary executor’s discretion. Examples include keeping secrets out of ordinary prompts, context, and logs, binding production writes to identity, scope, and authority, preserving target `non-result`, keeping development checks separate from qualification, and preventing agents from expanding their own permissions or grants.

The floor can also include applicable treatment of personal data, confidential material, and IP, human authority over designated direction, exceptions, takeover and reserved decisions, and clear stop and recovery paths for high-impact or irreversible actions. An adequate showing on seven surfaces leaves an eighth surface’s floor requirement in force. Identify the applicable policy, contract, law, risk decision, or human authority that establishes each requirement.

## 22.31 Look for Gaps and Excess

### Capability Gap

A baseline may be hard to locate, permissions and authority ambiguous, evaluation off target, intervention unavailable, or recovery unusable. Memory may lack source, scope, or expiry. Traces may omit material decisions. Drift may never trigger a review. An appropriate response might be narrower scope, less delegation, human execution, stopping the use, or adding a control.

### Capability Excess

Too much context can bury relevant material. More gates can add waits and governance livelock. More tests can leave acceptance coverage unchanged. Reviewers may add no independence or decision use. Multi-agent handoff may cost more than parallelism saves. Precise traces may go beyond reconstruction needs and increase privacy and retention costs. Automatic memory can spread stale information and expand attack surfaces. A dashboard may measure activity without resolving a decision. An evolution pipeline may propose frequent changes without durable adoption or exit paths.

Before removing a mechanism, check whether it serves the protected floor, a legal or contractual requirement, or a recovery function with no adequate substitute.

## 22.32 Compare Incremental Value With Total Production Cost

Account for model and tool costs, context assembly and retrieval, validation, review, decision, waiting and attention, coordination, handoff, integration, failures, rework, rollback, incidents, governance, tracing, retention, compliance, maintenance, drift, migration, and exit. Keep unprotected risks and non-monetary guardrails visible.

~~~text
incremental control or production value
versus
incremental total production cost
+ new failure surface
+ residual uncertainty
+ protected floor constraints
~~~

Some costs can be expressed only as ranges or qualitative judgments. Match controls to the current decision while keeping the protected floor in force.

## 22.33 Replace the Fixed Migration Sequence With Dependencies

The original outline proposed this sequence.

~~~text
Truth
→ Context
→ Evidence
→ Governance
→ Cognition
→ Memory
→ Evolution
~~~

It usefully reminds us that self-evolution depends on more basic boundaries. Actual work can need a different order. Context selection and grounding iterate. Evidence can precede execution or come from execution and operation. Governance bounds action and evidence generation from the start, and human cognition enters with intent and risk. Some cross-session work needs memory early. Some work never needs it. Evolution is a change surface with its own evaluation, adoption, and recovery. A team can address one security gap using the context mechanism it already has.

## 22.34 What Must Be in Place Before the Work Can Proceed?

### Delegated Side Effect

~~~text
Work / Attempt Identity
+ Scope and Allowed Effects
+ Named Human / System Authority
+ Observable Result / Failure / Unknown / non-result
+ Stop / Recovery / Boundary for safely discarding this Attempt
~~~

Duration, concurrency, impact, uncertainty, policy, contracts, rights, downstream use, and recovery demands can call for a deeper Baseline, formal Context, Assumption and Conflict Records, Evidence Plan and Decision Target, exception authority, independent intervention, and a Re-evaluation Case.

### Persistent Memory

When information can influence behavior across sessions, keep these dependencies.

~~~text
Provenance
+ Scope and Applicability
+ Promotion Authority
+ Conflict and Expiry
+ Retrieval / Use Visibility
+ Revocation or Retirement
~~~

### Self-Evolution

When a system may alter skills, policy, workflow, or organization, keep these dependencies.

~~~text
Bounded Change Candidate
+ Comparison Baseline
+ Evaluation and Counterevidence
+ Independent Adoption Authority
+ Activation Boundary
+ Post-adoption Observation
+ Recovery and Exit
~~~

### Multi-Agent

Multiple agents have a clear purpose when work can proceed independently, parallel gains exceed coordination and integration costs, specialists need separate boundaries, review needs separate roles or information, or tools, data, and authority need isolation.

### Human Decision Interface

The need follows from decision complexity, information volume, review bandwidth, risk, intervention, and takeover. The dependencies explain minimum conditions and leave implementation choices open.

## 22.35 Changes Go Through Candidate, Evaluation, Disposition, and Observation

A discovered gap or excess motivates a candidate change. Chapters 16, 20, and 21 provide the path into production use.

~~~text
Observed Need / Failure / Cost / Drift
                ↓
Capability Gap or Excess Hypothesis
                ↓
Bounded Change Candidate
                ↓
Evaluation + Counterevidence + Coverage
                ↓
Authorized Disposition
                ↓
Adopt / Restrict / Replace / Retire / Defer
                ↓
Operation + Outcome + Cost + Drift
                ↺
Re-evaluation
~~~

A candidate can add a Context Manifest, narrow tool permission, add an independent reviewer, merge duplicate gates, pause automatic memory retrieval, move to a single agent, add a recovery check, exit a model or provider, or return from self-evolution to explicit human adoption. Calibration can simplify a system as well as extend it.

## 22.36 A Local, Reversible, Observable Code Change

Consider a refactor in a development worktree. It stays clear of production, has known paths and a preservable diff, uses focused tests, and leaves scope acceptance to a person.

~~~text
short Intent / Scope / Acceptance Target
+ pinned repository and dirty-state observation
+ path-limited write
+ one bounded Attempt
+ focused validation and diff review
+ Human scope disposition
+ preserve / revert named change
~~~

This configuration may need no multiple agents, persistent memory, epoch, HCP dashboard, full tracing, automatic evolution, or ten gates. Keeping the configuration small is a candidate fit for the work. Revisit it if the scope expands across repositories or into production.

## 22.37 A Migration Across Sessions and Repositories

Work across repositories, weeks, and roles may need versioned intent, dependency boundaries and non-goals, each repository’s baseline, dirty state and target version, a Context Manifest and known gaps, an Execution Contract, Attempt and Handoff identities, checkpoints, rebase and conflict decisions, Integration Disposition, an Evaluation Plan and coverage, `non-result`, recovery, partial adoption, forward repair, ownership, expiry, and re-evaluation.

Whether to use multiple agents depends on repository independence, coordination of shared schemas and interfaces, concurrent-write conflicts, separate review context, and the integration owner’s capacity. An epoch is an optional correlation boundary. Work can span sessions without automatically evolving its own rules.

RandomHeroes recovery notes distinguish rebuilding the entry point from recovering active work. Locating documents, configuration, or bindings leaves recovery of running old tasks, databases, and local snapshots open. A fresh checkout should inventory what it actually has, especially when materials were local or ignored. Then choose whether to rebuild the entry, start new work, or recover named state. [Chapter 8, section 8.10](/chapters/08-en.html#section-8-10) gives prerequisites, and [Chapter 18](/chapters/18-en.html) explains what to retain. This review uses those results to assess the particular migration.

## 22.38 High-Impact, Hard-to-Reverse, or Protected-Data Work

A change to production data, protected information, or an external effect that is hard to reverse can require stronger boundaries.

~~~text
affected-party and Intended Use boundary
+ named Data / Tool / Environment / Rights scope
+ independent Security / Privacy / Release Decision Target
+ Protected Control Floor
+ stronger State Observation and Verifier Integrity
+ staged Execution and limited population
+ independent Review where required
+ external-effect observation
+ Incident, Recovery and Re-evaluation path
~~~

The additional mechanisms follow from risk and responsibility. A single executor with clear boundaries and separate authority can be easier to observe and recover than a complex agent organization. Confirm the applicable jurisdiction, contract, and professional advice separately when legal obligations matter.

## 22.43 Principles

1. **Fit for named use, not rank for the whole organization.**
2. **Profile describes; it does not authorize.**
3. **Presence is not operational use.**
4. **Use is not boundary adequacy.**
5. **Evidence is decision-specific.**
6. **Finding is not disposition.**
7. **Adoption is not fitness.**
8. **Gap and excess are symmetric review targets.**
9. **Protected floors are not averaged away.**
10. **Dependencies replace universal stages.**
11. **Calibration can add, restrict, simplify or retire.**
12. **Re-evaluate under drift.** Reopen the judgment after changes to use, version, environment, risk, or cost.

## 22.44 Common Failure Modes

### Feature-count Maturity

Ranking teams by their agents, registries, gates, memory, traces, and automation.

### Whole-project Level

Assigning one level across workloads, actions, and environments.

### Score Washing

Weighting authority, security, cost, judgment, and recovery into a score with no shared measure.

### Adoption Equals Fit

Taking active, sustained, or widespread use as proof of effectiveness.

### Tool Presence Equals Capability

Claiming a capability from an installed tool, model, or extension.

### Documentation Equals Operation

Assuming the real path follows the policy, workflow, or runbook because it exists.

### Higher Autonomy Bias

Assuming reduced involvement always represents progress.

### Multi-Agent Prestige

Splitting work that cannot advance independently to appear more advanced.

### Memory Accumulation

Treating greater retention as learning and injection as applicability.

### Evolution as Destination

Treating self-modification of skills, policy, or workflow as the highest stage.

### Governance Monotonicity

Assuming control can only grow and retiring a gate or narrowing trace is always a regression.

### Efficiency-only Simplification

Removing the protected floor, a rights boundary, or reserved human decisions to reduce waiting or cost.

### Case-to-Rank Generalization

Ranking an organization or industry from one episode in one project.

## 22.45 Review Checklist

### Decision and scope

- [ ] Does the review serve a named Decision Target?
- [ ] Are workload, intended use, action, data, environment, and population explicit?
- [ ] Does the profile identify time, version, baseline, and known invalidation conditions?
- [ ] Is the assessment scoped to the work?

- [ ] Which control functions does this use require?
- [ ] Which mechanisms can be omitted or must be prohibited?
- [ ] Who establishes the protected floor, and for what scope?

- [ ] Can we distinguish presence, use, and desired capability?
- [ ] Can we distinguish policy from observed behavior?
- [ ] Can we locate sources, revisions, environment, and dirty state?

- [ ] Are presence, use, boundary, evidence, and sustained fitness assessed on their own terms?

## 22.46 Conclusion

Evaluate the capability a workload actually needs.

~~~text
named workload and Intended Use
+ risk, recovery and operating constraints
→ required capability boundary

current bounded profile
+ evidence, coverage, unknown and cost
↕ compare

fitness finding
→ authorized disposition
→ adoption / operation / outcome / drift
→ re-evaluation
~~~

An Engineering Capability Profile describes the current observable configuration. A Capability Fit Review compares that configuration with a named use. A finding records the assessment. An authorized disposition can maintain, restrict, experiment, strengthen, replace, retire, or defer.

Preserve the boundaries between presence and use, use and boundary adequacy, evidence and acceptance, adoption and sustained fit. A capability gap can be addressed by limiting the use or changing the execution path. A capability excess still has to be checked against the protected floor before removing it.

The earlier levels highlighted questions from chat and copilots through bounded agents, organization, human control, memory, and evolution. A project with one agent, local context, human promotion, and a short lifecycle can fit its work. A high-impact system can need stronger authority, independent review, trace, security, recovery, and re-evaluation while continuing to make changes through explicit human adoption.

If we retain the word *maturity*, let it describe how well a project can identify needs, establish proportionate capabilities above the floor, and revise them when evidence, cost, risk, or drift changes.

[Chapter 23](/chapters/23-en.html) shows those boundaries in named episodes from AI Game Dev OS and related work. The questions are what actually existed, where it ran, what evidence was produced, which outcomes remained absent, what people decided, and what would require fresh evidence elsewhere.
