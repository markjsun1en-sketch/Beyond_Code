# Chapter 2. When Traditional Engineering Practices Need More Support
## Seven Operating Conditions to Check

Code review, formal methods, SRE, security approval, supply-chain governance, and distributed systems engineering have long dealt with problems familiar from agent work. People can lose track of a change. System state can diverge. Automation can fail. Production may behave differently from what the source suggests.

This chapter offers seven operating conditions to check whether existing practices are enough for the delegation, scale, risk, and recovery cost of the work at hand. AI is one factor that can change those conditions. A practice may still be reliable elsewhere in the same project or for a different kind of task.

---

## 2.1 Operating Conditions

An *operating condition* is a condition an established practice depends on to work at an acceptable cost.

People can review code without knowing the entire project. They usually need several things to do it well.

- A change of a size they can review.
- A way to locate key context.
- A reasonably clear account of the intent and what the change may affect.
- Tests, diffs, and runtime evidence that cover the main risks.
- Sufficient authority to make the relevant decision.

If agents increase change throughput, the range of context, or the amount of concurrent work, manual review can become a bottleneck. The review principle can still hold while the conditions that make it workable change.

Each condition below has three parts.

```text
Condition
When does the existing practice still work?

Failure Signal
What indicates the condition has become unreliable?

Engineering Response
Which part of the practice needs to be extended?
```

---

## 2.2 Condition One — People Can Follow the Main Interpretation and Execution Path

In many development tasks, people directly perform the following steps.

```text
interpret requirement
→ inspect state
→ choose implementation path
→ change code
→ verify result
```

Even with complex tools, people can often explain most of the intermediate choices. Once the agent is delegated real execution, the path might look more like this.

```text
Human or system provides bounded intent
→ Agent inspects selected context
→ Agent chooses local path
→ Agent acts through tools
→ Human sees result and selected evidence
```

The Intent Owner and the delegated decision maker for part of the execution path can be different.

### Failure Signal

- People see only the final diff and cannot tell which state it was based on.
- The agent expands the goal or scope silently.
- Technical ability to use a tool is mistaken for authorization.
- A reviewer cannot explain why the agent changed a given set of files.
- After a failure, nobody can recover the external basis for execution.

### Engineering Response

Make the following visible in proportion to the risk.

- Parent Intent or the triggering source.
- Scope and non-goals.
- State and revision references.
- Delegation, permission, and escalation.
- Observable actions, results, and evidence.

A short, low-risk task can keep these in its existing brief and records. They become more important as the range of interpretation, impact, or cost of recovery exceeds what people can reasonably track themselves.

---

## 2.3 Condition Two — Output Stays Within the Team's Capacity to Understand, Verify, and Integrate It

Engineering productivity depends on several stages of delivery.

```text
Generation
→ Verification
→ Review
→ Integration
→ Deployment
→ Operation and Learning
```

For some tasks and measures, agents may raise the rate at which candidates are generated. Verification, review, integration, and delivery each have their own capacity.

### Failure Signal

- Diffs routinely exceed what reviewers can handle.
- The test count rises while real risks remain uncovered.
- Many implementation candidates await a human choice.
- Integration, rollback, and understanding cost more time than generation saved.
- The team can only rely on the agent's summary to accept a change.

### Engineering Response

- Reduce the surface of each change.
- Split work into slices that can be verified independently.
- Bind the Acceptance Target and Required Evidence before execution.
- Generate evidence directed at the risk.
- Record verification, review, recovery, and governance costs.

Adding agents increases the number of producers. Verification and integration bottlenecks need separate attention.

---

## 2.4 Condition Three — Interfaces and Rules Make Execution Sufficiently Predictable

Compilers, test runners, and deployment tools can fail, but their interfaces usually make inputs, state transitions, and errors fairly clear. Given similar open-ended tasks, a software agent may choose different search orders, approaches, or tool paths.

Estimating a distribution requires a sampling protocol.

- Hold model and tool versions fixed or record them.
- Use repeatable task samples.
- Run multiple trials.
- Define what counts as success and failure.
- Control or record differences in the environment.

A single execution can tell us which behavior we observed. The useful objects when evidence is limited are these.

```text
Allowed Behavior Set
+ Observed Variations
+ Known Failure Modes
```

### Failure Signal

- Similar tasks produce very different scopes.
- An agent fills in unknowns when context is missing.
- A tool failure is recorded as a target failure.
- A fluent explanation makes a skipped verification hard to notice.
- A reliability judgment is reused after versions change.

### Engineering Response

- Constrain the goal, scope, permissions, and evidence in a contract.
- Use evaluations and repeated runs to observe variation.
- Distinguish harness failures, tool results, and target results.
- Treat the model version, context, tools, and runtime as test conditions.
- Give high-risk actions boundaries that enable recovery.

## 2.5 Condition Four — Project Knowledge Survives in Code, Documents, and People

Teams have long relied on code and tests, documents and runbooks, issues and historical commits, as well as conversations and the experience of long-standing team members.

Any of those sources can become stale or conflict with another. An agent makes the problem more visible because it assembles its working view from accessible material. It has little access to the understanding a team has built together over time.

### Knowledge Worth Making Explicit First

Explicit records are especially useful when knowledge has high impact, gets reused often, crosses roles, is hard to infer, changes easily, is hard to recover after failure, or concerns safety, security, or authority.

### Knowledge That Can Stay Local

- One-off, low-risk local judgments.
- Facts someone can recover directly from a test or the source.
- Discussions with little reuse value.
- Details that cannot be maintained and could acquire misleading authority after being recorded.

### Engineering Response

Add only the records the work calls for.

- Context sources and provenance.
- References to Decisions and Assumptions.
- Freshness and invalidation.
- Handoff and recovery records.
- Rules for admitting and removing memory candidates.

The aim is to reduce the chance that high-value knowledge is lost when it is transferred, condensed, or recovered.

---

## 2.6 Condition Five — Human Costs Naturally Limit the Number of Executors

Hiring people adds recruiting, communication, and coordination costs. Agents can lower the marginal cost of starting another executor. The work still has to be divided, context allocated, conflicts over writes handled, results integrated and reviewed, and responsibilities assigned.

### Failure Signal

- Several agents change the same worktree or use a shared index.
- Agents work from different Parent Intents.
- The reviewer receives only a summary written by the worker.
- The handoff loses a conflict, an assumption, or an unfinished check.
- Output increases as integration into the main line slows.

### Engineering Response

- Split work by responsibility and permitted write surface.
- Isolate worktrees, indexes, environments, or data.
- Use clear contracts and handoffs.
- Retain the underlying evidence independent review needs.
- Serialize writes and decisions that cannot safely be concurrent.

Organizational design is part of multi-agent work. Its outcomes also depend on technical isolation in filesystems, Git, runtimes, and tools.

---

## 2.7 Condition Six — Human Review Covers the Main Higher-Level Risks

Human review is especially valuable for architecture, product and experience judgments, acceptance of risk, conflicts between intents, and decisions with insufficient evidence. How well it works depends on the quality of its inputs and how much a reviewer must understand.

### Verification Gap

A *Verification Gap* can arise when output grows faster than the capacity to verify it.

```text
Generated Change Surface
>
Verified and Understood Change Surface
```

Use this as a diagnostic relationship.

### Failure Signal

- The reviewer can only sample a large diff.
- A test pass is reported as closure of every risk.
- A review mixes observations, recommendations, and decisions about evidence use.
- Automated and human review cover the same surface while missing runtime or data.
- Evidence is detached from its claim and scope.

### Engineering Response

Review can be distributed across the work.

- Before execution, establish intent, scope, risk, and the evidence target.
- During execution, look at key changes in state, permissions, and anomalies.
- After execution, check claim coverage, counterevidence, and the decision target.
- Over time, examine failure modes, the cost of rules, and the effectiveness of review.

Established tests and a light human check can still suffice for low-risk work.

## 2.8 Condition Seven — People Can Reconcile the Current System State

A project can contain all of the following at once.

```text
Repository State
Build / Deployment State
Runtime Observation
Data and Configuration State
Approved Decisions
Open Assumptions
Context and Memory Sources
```

These sources answer different questions, so any order of authority depends on the question.

- Repository State answers questions about implementation in source.
- Runtime Observation supports behavioral claims in a particular environment.
- A Decision records an authorized commitment about what should apply.
- An Assumption identifies an explicit unknown.
- Memory and documents are information sources. Their inclusion in context gives them no authority by itself.
- Evidence can support or challenge a Claim. The Claim is the proposition being considered.

### A Conflict in Practice

Suppose an old design document retains an earlier UI rule. The code has already changed structure. A worktree contains uncommitted user changes, and historical memory points to obsolete names.

This mapping would hide the decisions we need to make.

```text
Doc = Intent
Code = Implementation Truth
Runtime = Behavioral Truth
Memory = Memory State
```

I would ask five questions.

1. What kind of source is each item?
2. Which version, time, and scope does it cover?
3. Who or what has authority to answer the current question?
4. Which items are candidate information, and which were observed?
5. Can we resolve the conflict, or must the record preserve it?

### Engineering Response

Chapter 6 uses the following records.

```text
Intent Artifact
Decision / Policy
State Claim
Assumption
Evidence Record
```

It uses question-scoped authority, freshness, conflict, and an Execution Baseline to describe the relationships between them.

## 2.9 Making the Right Parts of Organizational Knowledge Explicit

People handle incomplete information through shared experience, direct communication, and professional judgment. Much of this can remain informal. As path complexity, concurrency, risk, or recovery cost outgrows what people can follow themselves, the boundaries of the work, authority, and evidence of completion need to become visible in proportion to that risk.

The [SP122 case record on multi-agent boundaries and staged disposition](../../Evidence/receipts/ER-20260807-001__CLM-C02-001.md) offers a bounded example. In a task involving several agents, different sources of authority, and staged human decisions, the team used explicit lanes, sources, and evidence records. A named, authorized human accepted the Evidence Chain within a stated scope. Supported Adoption and Production Release remained separate decision targets.

This example leaves open which other factors called for those mechanisms, how much structure other tasks need, whether explicit records improve efficiency, and whether complete records would be enough for eventual adoption. The purpose of the mechanisms here is to control the identified risks.

## 2.10 The Software Engineering Control Surface Expands

If several operating conditions weaken, the project starts to manage all of these together.

```text
Product State
Production Intelligence Configuration
Delegated Action
Evidence and Decision Flow
Recovery and Learning
```

Each of the next chapters gives one class of objects a particular job.

- Chapter 4 covers the Intent Artifact and Desired Outcome.
- Chapter 5 covers context selection, Payload, and Manifest.
- Chapter 6 covers typed state records and where authority applies.
- Chapter 7 covers the Execution Contract and execution state changes.
- Chapter 9 covers evidence coverage, intended use, and decision disposition.
- The governance chapters examine Policy, Gate, Escalation, and cost.

The point is to keep a single status, manifest, or registry from carrying the goal, facts, authorization, execution, and disposition at once.

## 2.11 Governance Follows the Risks in the Work

The original draft linked stronger models directly to heavier governance. Greater capability can expand the potential action surface. What matters for governance is the actual exposure the project grants.

```text
Granted Action Surface
+ Impact
+ Irreversibility
+ State Uncertainty
+ Verification Difficulty
+ Recovery Cost
```

Consider four different arrangements.

- A capable model generating candidates inside a read-only sandbox may need little governance.
- A deterministic script that writes to a production database may need strict approval, idempotence, and recovery.
- Permission to run a test and authority to accept release risk are separate grants.
- An automated gate can make a bounded decision when a policy explicitly delegates it.

Match governance to the granted action and decision surfaces.

---

## 2.12 Make the Claims Behind a Delivery Inspectable

Code quality matters. A delivery can also depend on several questions.

- Was the intent correct?
- Did the context include the relevant sources?
- Did execution start from the right state baseline?
- Did the agent stay within scope and permission?
- Did the test actually observe its target?
- Was the evidence coverage enough?
- Did someone with authority make the applicable decisions about implementation scope, adoption, and release?

A score or status would obscure those distinctions. For every consequential claim, keep the inputs, state, changes, observations, evidence, limits, and disposition for the intended use available for inspection.

```text
Test PASS
≠ implementation scope necessary
≠ adoption accepted
≠ release authorized
```

## 2.13 Traditional Principles With a Wider Reach

### Small Changes

Limit the change surface so people can verify, review, and roll back the work.

### Automated Testing

Use repeatable feedback for behavior and specify the target, scope, and environment of the test.

### Clear Architecture

Reduce the implicit coupling the agent has to understand together. Give it a way to find responsibilities and interfaces.

### Version Control

Retain repository state, change history, and recoverable baselines. Use the appropriate sources for other kinds of state.

### Least Privilege

Limit what tools and data an executor can act on. Record capability and permission separately.

### Observability

Expose inputs, state changes, tool results, target results, and failure boundaries. These are external records the project can inspect.

### Recovery

Give people or systems a way to isolate an error, roll back, retry, or take over.

## 2.14 A Conditional Starting Point

```text
Delegated execution
+ higher throughput or concurrency
+ state / authority divergence
+ meaningful risk or recovery cost
        ↓
some existing operating conditions become unreliable
        ↓
extend engineering mechanisms proportionally
```

The goals remain to build correct software, manage complexity and risk, support collaboration and maintenance, keep the system able to evolve, and make results and responsibilities traceable. The change is that intelligent execution systems take on part of the production path. Some existing practices may need to cover that delegation explicitly.

## 2.15 Conclusion

The seven questions in this chapter are a retrospective diagnostic. Historical prevalence and the extent to which each condition has changed are separate empirical questions.

1. Can people still follow the main interpretation and execution path?
2. Is throughput within the capacity to understand, verify, and integrate it?
3. Can the interfaces and rules sufficiently constrain behavior?
4. Can high-value knowledge be passed on reliably?
5. Is the coordination cost of adding executors manageable?
6. Does human review still cover the main risks?
7. Can people still reconcile current state and authority?

When a condition becomes unreliable, turn the specific dependency on implicit intent, context, state, authority, evidence, or recovery into something people can check. Let the risk determine how much structure it needs. The next chapter defines which kind of delegation and engineering adaptation the book calls AI-native.

---

## Principles

1. **Treat operating conditions as a diagnostic.** They help check where a practice applies.
2. **Identify the concrete failure signal.** A changed condition can call for an adaptation that preserves the underlying principle.
3. **Make boundaries explicit in proportion to risk.** Persist the knowledge worth maintaining.
4. **Use a sampling protocol to estimate behavior distributions.** A single execution can show a variation.
5. **Bind sources to typed records and authority to questions.**
6. **Base governance on actual granted actions, impact, and recovery cost.**
7. **Distinguish Test, Acceptance, Adoption, and Release.** Each has its own scope.

---

## Common Anti-Patterns

- Presenting a retrospective diagnostic as historical consensus among designers of software engineering practices.
- Using one agent case to argue for structuring all tacit knowledge.
- Claiming a stable distribution after observing one different execution path.
- Adding agents to relieve a verification or integration bottleneck.
- Treating the source, documents, runtime, and memory as fixed levels of truth.
- Assuming governance grows monotonically with model capability.
- Treating a test pass as trust in the entire production process.
- Introducing a registry, graph, and gate for every failure signal.

---

## Checklist

- Are we discussing an observation, a retrospective diagnosis, or a recommendation?
- Which condition does the existing practice depend on?
- What indicates the condition is unreliable?
- What execution path and action surface have been delegated?
- Do production, verification, review, and integration throughput match?
- Was the distribution actually estimated from repeated samples?
- Which tacit knowledge affects high-impact, frequently repeated, or costly-to-recover work?
- Do agents have isolated write surfaces and clear handoffs?
- Does the review input identify the claim, scope, and underlying evidence?
- Can we distinguish state, decisions, assumptions, evidence, and memory?
- Does governance reflect actual permissions, impact, reversibility, and recovery cost?
- Did we account for maintenance costs and the risk that a record acquires misleading authority?
