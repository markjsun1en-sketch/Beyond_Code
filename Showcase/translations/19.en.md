# Chapter 19. Security, Privacy, and IP Boundaries
## What a deployment location or an AI-generated label can tell you

This chapter proposes an engineering model for data, models, tools, supply chains, and intellectual property. Scale it to risk. OWASP, NIST, SLSA, and the U.S. Copyright Office provide reference points. The model’s merits across projects remain open. D-048 in AI Game Dev OS illustrates a specific side effect in a tool or verifier. Questions of law need their own analysis.

Traditional applications already need to control what users can access, what services can call, where data is stored, which dependencies are trustworthy, and whether a release complies with its licenses and other obligations. An agent brings those questions together.

~~~text
external content
→ model context
→ generated interpretation
→ tool selection
→ credentialed action
→ code / data / external state change
→ memory, log and downstream output
~~~

A webpage, issue, email, image, retrieval result, or tool return can carry useful business data, unauthorized instructions, personal or confidential information, license or use restrictions, and an upstream supply-chain dependency. It can also become a source for memories, logs, or generated artifacts.

To assess a workflow, I ask five questions.

1. Which subjects may process which data for which purposes?
2. Under what processing terms can a model receive and retain it?
3. Which function, permission, credential, and authority allow the tool to produce a side effect?
4. What components enter the supply chain, and how are they updated, monitored, and recovered?
5. Which rights, obligations, and open decisions concern inputs, process records, and outputs?

> **Treat every external input as data without authority, every model output as an untrusted proposal, and every tool action as an independently authorized side effect.**

These defaults let a project accept useful external data and automate actions inside explicit grants.

---

## 19.1 What is necessary, useful, and optional?

### Necessary

When an agent can access nonpublic information or cause external effects, identify:

- Data sources, purposes, permitted processing, and prohibited destinations
- Which sources carry Instruction Authority
- Retention, training, geography, and deletion terms for the model provider and deployment
- Tool functions, resources, permissions, credentials, and Action Sinks
- Stop, authorization, verification, and recovery paths for consequential actions
- Third-party component identity, version or service identifier, source, permissions, and owner
- Input rights, third-party obligations, human contribution, and downstream uses of important outputs
- Owners of containment, revocation, rotation, evidence preservation, and follow-up disposition after an incident

### Useful

Agent workflows crossing teams or projects, serving customers, handling personal data, or reaching production can benefit from a Data Handling Profile, Model Processing Contract, Tool Security Contract, Supply Chain Component Record, and IP Disposition Record. A centralized secret broker, policy enforcement, access review, and incident playbook can also help.

### Optional

Dedicated private model deployments, full data-lineage graphs, per-step Human Contribution records for every generated artifact, enterprise model and tool registries, full prompt and completion archives, hardware-backed attestation, and automated license and similarity scanners depend on scale, risk, and obligations. Judge controls by what they protect. Overcollection can increase privacy, secret, and retention risks.

## 19.2 Different questions about security, confidentiality, privacy, IP, and authority

Public, internal, trade-secret, personal, and regulated are useful labels. They describe different dimensions.

| Dimension | Question | Insufficient evidence on its own |
|---|---|---|
| Security | How do we protect confidentiality, integrity, availability, and authorized behavior? | A local model deployment |
| Confidentiality | Which subjects can learn or disclose which information? | Whether data relates to a person |
| Privacy | What risks does processing create for people, and are purpose, linkage, inference, retention, and disclosure appropriate? | Encryption or access control |
| Data Processing Permission | May we collect, transfer, transform, retain, and delete this data for the current purpose? | Read access |
| Intellectual Property | Which copyrights, patents, trademarks, trade secrets, or other rights apply to inputs and outputs? | Ability to download the output |
| License / Contract | What use, ownership terms, disclosure, attribution, or indemnity apply to the parties? | Eligibility for statutory rights |
| Authority | Which subject may create which effect on which target? | A tool’s technical capability |

The voluntary [NIST Privacy Framework](https://www.nist.gov/privacy-framework) addresses how organizations identify and manage risks to individuals. Specific judgments still depend on jurisdiction and contract.

A public webpage can carry copyright, terms of use, hostile instructions, or errors. Employee performance records can be both confidential and personal. Company source code can carry trade-secret and license obligations even without personal data. Permission to read a file can have a narrower scope than permission to send it to a model provider. Contractual permission to use an output leaves copyright eligibility and infringement as separate questions.

For each piece of data, check safety, transmission rights, privacy obligations, and ownership for the use you have in mind.

## 19.3 Start with a Threat Model

A *Threat Model* identifies the assets, subjects, trust boundaries, entry points, action sinks, failure modes, and evidence of controls for a defined scope. It gives the team a basis for choosing controls.

~~~yaml
target:
  work_ref: WU-019
  intended_effect: "Update the internal dependency manifest"

assets:
  - repository_source
  - credentials
  - private_issue_content
  - build_environment

subjects:
  - human_requester
  - agent_instance
  - model_provider
  - tool_server
  - dependency_registry

entry_points:
  - prompt
  - repository_files
  - issue_body
  - web_content
  - tool_return

action_sinks:
  - filesystem_write
  - package_install
  - network_request
  - pull_request

failure_modes:
  - secret_disclosure
  - indirect_prompt_injection
  - dependency_substitution
  - unauthorized_write
  - incorrect_license_disposition

controls:
  - context_filter
  - read_only_default
  - scoped_credential
  - lockfile_and_digest
  - human_release_decision
  - post_action_evidence
~~~

Version the Threat Model with the work’s actual scope. General statements about how smart or trustworthy an agent is leave the failure modes unspecified.

## 19.4 Classify data along several dimensions

*Data Classification* applies actionable labels for access, relationships to people, rights, criticality, regulatory obligations, and lifecycle constraints. An object can have a value in each dimension.

| Dimension | Example values |
|---|---|
| Access | public / internal / confidential / restricted |
| Person Relation | none-known / personal / sensitive-personal / derived-profile |
| Rights | owned / licensed / permitted-for-purpose / unknown / prohibited |
| Integrity Criticality | advisory / operational / release-critical / safety-critical |
| Availability Criticality | reproducible / time-sensitive / business-critical |
| Regulatory / Contract Duty | none-known / policy-bound / contract-bound / jurisdiction-specific-review |
| Instruction Trust | data-only / trusted-reference / authorized-instruction-source |
| Lifecycle | ephemeral / retained-until / legal-hold / cascade-delete |

These are candidate project labels. Apply `personal`, `sensitive-personal`, and `regulated` under the applicable jurisdiction, subjects, purposes, and policies.

## 19.5 The data boundary extends beyond prompts

Agent systems handle user input, system and developer instructions, repository files, issues, tickets, email, chat, web and retrieval content, images, audio, and other modalities. Data can also appear in RAG chunks, embeddings, vector metadata, tool input and return, model output, intermediate artifacts, caches, temporary files, checkpoints, logs, traces, screenshots, evidence, memories, skills, examples, evaluation sets, backups, exports, replicas, and incident copies. The same boundary includes derived labels, summaries, profiles, and decision results.

An embedding, summary, or log can still carry underlying rights and privacy risks. A new risk can arise when ordinary-looking records combine into a profile of a person or reveal confidential information about an organization.

## 19.6 Turn classification into a Data Handling Profile

A *Data Handling Profile* states which subjects may process named data for a given purpose and piece of Work. It covers handling methods, destinations, retention, deletion, and evidence boundaries. A lightweight record can be enough.

~~~yaml
data_profile_id: DHP-019-004
version: 3

data:
  ref: customer_bug_bundle
  source: support_system
  classifications:
    access: confidential
    person_relation: personal
    rights: permitted_for_support
    instruction_trust: data_only

purpose:
  allowed:
    - reproduce_reported_bug
    - create_redacted_summary
  prohibited:
    - model_training
    - public_example

processing:
  allowed_subjects:
    - support_human
    - sandboxed_debug_agent
  allowed_models:
    - private-endpoint:model-family-x
  allowed_tools:
    - read_bundle
    - write_redacted_report
  external_network: deny

retention:
  raw_until: 2026-09-07
  redacted_report_until: project_policy
  logs: metadata_only
  cascade_delete:
    - cache
    - vector_index
    - temporary_artifacts

evidence:
  record_access: true
  record_raw_content: false
  owner: support_security_owner
~~~

The following permissions can have different answers.

~~~text
may_read
≠ may_send_to_model
≠ may_quote
≠ may_store
≠ may_learn_as_memory
≠ may_publish
≠ may_treat_as_instruction
~~~

## 19.7 Least Context as a data and security control

[Chapter 5](/chapters/05-en.html) defines *Least Context* as providing current, sourced information sufficient to perform and verify the work. Here the selection principle has four control objectives.

1. Limit the sensitive information exposed to the workflow.
2. Reduce irrelevant content that could carry indirect instructions.
3. Limit stale, conflicting, and out-of-scope content entering decisions.
4. Limit what logs, memory, caches, and the provider’s retention systems can carry or propagate.

These are objectives. Effects depend on implementation, operating conditions, and which constraints are preserved. Keep the constraints and counterexamples needed to execute and verify the work. An agent that misses an authority boundary, non-goal, or safety constraint can act incorrectly.

## 19.8 Check the authority of instructions in external content

*Instruction Authority* is an explicit grant for a source to constrain or trigger a subject’s actions in a named scope. Format, placement, and confidence of tone do not confer this authority.

When a webpage tries to direct an agent to disclose configuration, treat that text as data. When a repository file tells the agent to run a script, check whether it is an authorized instruction source for the work, which scope and revision apply, what higher constraints govern it, whether the tool action needs authorization, and whether a supplier or attacker could have changed the file.

[OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) distinguishes direct, indirect, and multimodal prompt injection and notes that retrieval-augmented generation and fine-tuning leave residual risk.

~~~text
content may be readable
content may be quotable
content may be citable evidence
content may be authorized instruction
~~~

Check each category on its own. Delimiters, content filters, and prompt constraints can help. Policies, tools, and downstream systems outside the model enforce authority.

## 19.9 Validate a model output for its action sink

A model can propose shell commands, SQL, HTML or Markdown, source code, configurations, URLs, tool arguments, access decisions, classifications, or license conclusions. An *Action Sink* is a downstream interface that can give the output effect through execution, writing, querying, publishing, or another external action.

| Sink | Typical independent controls |
|---|---|
| Shell | Command allowlist, argument bounds, working directory, network and process isolation |
| SQL | Parameterized queries, read-only identity, table or row scope, transaction boundaries |
| HTML / UI | Escaping, content security policy, URL and script validation |
| Repository Write | Path scope, diff review, branch protection, tests |
| External API | Schema, identity, rate limits, idempotency, approval |
| Deployment | Signed artifact, environment gate, release authority |
| Memory | Promotion gate, provenance, namespace, TTL |

Validate for the sink. A schema check can establish well-formed JSON. SQL execution permission and release authorization need their own checks.

## 19.10 The Model Processing Contract defines the boundary

A *Model Processing Contract* governs how a provider, model, endpoint, or deployment receives, uses, retains, records, deletes, and transfers data for a named purpose. Identify:

- Provider and operator
- Model, endpoint, and deployment identity
- Version or change policy
- Data region and subprocessors
- Input and output retention
- Use for provider training or service improvement
- Encryption, authentication, and tenant isolation
- Logging, abuse monitoring, and support access
- Deletion and incident terms
- Output use, ownership, and restrictions
- Boundaries for tools, network, files, memory, and retrieval
- Evaluation, fallback, and owner

~~~yaml
model_contract_id: MPC-019-002
provider: provider-a
endpoint: enterprise-private-endpoint
model_family: model-x
version_policy: provider_managed_with_change_notice

data_terms:
  region: approved-region
  provider_training: prohibited_by_contract
  retention: 0_days_application_data
  abuse_log_exception: review_required
  subprocessors: approved_list_ref

runtime:
  tools: none
  external_network: deny
  retrieval_sources:
    - redacted_internal_index

change_control:
  owner: ai_platform_owner
  re_evaluate_on:
    - model_version_change
    - terms_change
    - region_change
    - incident_notice
~~~

The same product name can appear in contracts with different terms.

## 19.11 Define local, private, and cloud at the project level

A *Local Deployment* executes a model or agent runtime on a machine under the organization’s control, with core inference data staying on that host by default. A *Private Deployment* runs in a dedicated or explicitly isolated environment managed by the organization or a delegate. A *Cloud Service* processes requests through an externally managed remote service that may be shared, dedicated, or accessible through a private network.

Make these definitions concrete. A private tenant, private endpoint, self-hosted VPC deployment, and local cluster have different controls.

| Topology | Risks it may reduce or benefits it may offer | Risks that stay or arise |
|---|---|---|
| Local | External transfer, provider retention, some jurisdiction issues | Host compromise, unpatched dependencies, physical access, backup exposure, broad tool permissions |
| Private | Tenant or network isolation, organizational control of configuration | Operational complexity, misconfiguration, insider access, provider or platform dependence |
| Cloud | Reduced self-hosting burden, potential access to mature identity and monitoring | External processing, contract changes, subprocessors, regions, service drift, vendor concentration |

> **Locality changes the trust boundary; it does not eliminate it.**

## 19.12 Route models using all applicable constraints

Routing can depend on processing permission, confidentiality and privacy risk, provider contract, required capability, tool and network needs, latency, cost, availability, version stability and evaluation coverage, incident response, recoverability, applicable law, policy, customer commitments, and maintenance capacity.

| Disposition | Meaning |
|---|---|
| `cloud_allowed` | The current purpose and Data Handling Profile allow a specified cloud contract |
| `private_required` | Process only in the specified dedicated environment with its controls |
| `local_required` | Keep inference data inside the specified local boundary |
| `redaction_required` | Send only data transformed according to the stated rules |
| `model_context_denied` | Keep the data out of model context, including on local deployments |
| `human_only` | Current risk, rights, or capability constraints require a person |

Keep `model_context_denied` available where secrets, key material, customer records, legal-hold material, or restricted source code need exclusion even from a local model.

## 19.13 Capability, permission, authority, and credentials

[Chapter 13](/chapters/13-en.html) distinguishes Capability, what the subject can technically do, Permission, what the environment allows it to access, and Authority, the effect the organization allows it to produce for a named goal. Tool security also depends on credentials and functions.

~~~text
Tool exposes Function
Credential obtains Permission
Assignment and Decision provide Authority
Model proposes Arguments
Policy Enforcement decides whether the side effect may occur
~~~

Watch for these mismatches.

~~~text
Permission > Authority
Functionality > Work Need
Credential Lifetime > Task Lifetime
Network Reach > Approved Destination
Write Scope > Recovery Capability
~~~

[OWASP LLM06:2025](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/) provides an external reference for distinguishing excessive functionality, permission, and autonomy.

## 19.14 A Tool Security Contract bounds side effects

A *Tool Security Contract* specifies subjects, resources, arguments, credentials, environments, side effects, approvals, evidence, and recovery for a named function.

~~~yaml
tool_contract_id: TSC-019-008
tool: repository_file_writer
function: replace_file

scope:
  subject: agent-instance-42
  work_ref: WU-019
  paths:
    allow:
      - OptimizedDocs/
      - RevisedResult/
    deny:
      - OringinalDocs/
      - .git/

arguments:
  no_symlink_escape: true
  max_bytes_per_file: 500000

credential:
  type: task_scoped
  expires_at: 2026-08-24T18:00:00+08:00

effects:
  external_network: deny
  process_spawn: deny
  destructive_delete: deny

control:
  precondition: current_worktree_captured
  approval: human_for_original_docs
  postcondition:
    - path_scope_check
    - git_diff_review
  recovery: forward_patch_or_version_restore
~~~

Enforce the contract through tool adapters, sandboxes, operating systems, databases, API gateways, or other downstream controls. A prompt can describe the policy. Verify enforcement where the effect occurs.

## 19.15 Keep secrets outside prompts and credentials short-lived

A *Secret* is information whose disclosure could directly or indirectly yield identity, access, signing, decryption, or other protected capability. Examples include API keys, passwords, session tokens, private keys, database connection strings, recovery codes, signing material, and configurations or combinations that expose the same capabilities.

[OWASP LLM07:2025](https://genai.owasp.org/llmrisk/llm072025-system-prompt-leakage/) cautions against relying on the system prompt as a secret or security control.

- Keep credential values out of system prompts, skills, memory, and ordinary logs.
- Give agents short-lived credentials scoped to the immediate function.
- Let a Secret Broker or tool adapter attach credentials where possible.
- Log credential identity, scope, and use events. Keep secret values in their protected store.
- Support revocation, rotation, and abnormal-use detection.
- When a user delegates an action, use the user’s identity and scope where feasible.

Prompt confidentiality can add defense in depth. Authority is enforced independently.

## 19.16 State what the sandbox isolates

A *Sandbox* bounds execution through named constraints on processes, filesystem, network, credentials, devices, resources, or time.

Specify readable, writable, and hidden paths and controls on symlinks, mounts, and parent directories. Describe executable and child processes, network destinations, protocols and DNS, visible environment variables and credentials, resource limits, device and clipboard access, browser sessions and GUI access, host or container or VM or account boundaries, output export, evidence retention, and the sandbox’s version, configuration, and known limits.

A sandbox can limit the blast radius. Inspect permitted writes, outbound data rights, output vulnerabilities, dependency and runtime integrity, and remaining escape risk on their own grounds.

## 19.17 External side effects need transaction and recovery semantics

For writes, messages, purchases, deployments, deletion, publication, or migration, define:

- Atomicity. Is the action all-or-nothing?
- Idempotency. Does a retry repeat the effect?
- Reversibility. Can we roll back?
- Forward Recovery. How do we correct a change that cannot be rolled back?
- Confirmation. How do we establish the actual effect after submitting the request?
- Rate and Budget. What limits apply per time period and in total?
- Blast Radius. How far can one failure reach?
- Concurrency. Can agents overwrite one another?
- External Authority. Which identity and policy does the receiving system apply?

Irreversible, consequential, and cross-organization actions generally call for narrower scope, stronger confirmation, and an independent decision authority. Another model check can be useful. Transaction guarantees need enforcement at the action boundary.

---

## 19.18 Use approval where someone needs to decide

Human approval can degrade into routine clicking. A brief may omit scope, effect, or recovery. The tool may accept parameters or scope that differ from what the person saw. Bind approval to the action.

~~~text
Decision Target
+ exact or bounded Effect
+ Subject / Tool / Credential
+ Data and Destination
+ Baseline / Preconditions
+ Expiry
+ Evidence and Recovery
~~~

Use approval for consequential actions requiring business judgment, questions of scope or rights or exceptions policy cannot settle, irreversible or costly-to-recover actions, first occurrences, and insufficient evaluation coverage. Repeated, low-risk, verifiable, reversible actions can run under preauthorized policy and automated gates.

## 19.19 Keep protected controls and revocation outside the agent

[Chapter 13](/chapters/13-en.html) defines the *Protected Control Floor* as the minimum set of controls the executing subject cannot bypass for an action under current policy. In security, privacy, and IP work, it can cover these controls, which require the designated authority and evidence to change.

- Keep secrets out of prompts and logs.
- Enforce downstream authorization for high-risk actions.
- Bound production writes by identity and scope.
- Preserve immutable or append-only evidence boundaries.
- Keep emergency stop and credential revocation available.
- Deny default cross-tenant or cross-project access.
- Preserve incident evidence.
- Respect designated read-only surfaces such as `OringinalDocs/`.

When a grant is withdrawn, credentials expire, or policy changes:

1. Stop new side effects.
2. Mark in-flight actions and unknown results.
3. Revoke or rotate related credentials.
4. Observe external state again.
5. Retain incident evidence.
6. Have a named authority decide about recovery, forward correction, or fresh authorization.

Give break-glass access a scope, expiry, reason, record, and subsequent review.

## 19.20 Include components that can change behavior in the supply chain

The *AI-native Supply Chain* includes internal and external components that can influence input, context, decisions, actions, builds, runtime, or outputs, together with their sources, versions, and dependencies.

It can include packages and lockfiles, scripts and launchers, plugins and extensions, skills, MCP and tool servers, adapters, models and endpoints, routing policies, fine-tunes, guard models, datasets, evaluations and synthetic-data generators, embedding models, vector stores, retrieval pipelines, prompt templates, policy packs, system instructions, containers and VM or CI images, build tools, external APIs, hosted services, browser automation, and generated code, configuration, and binaries.

Include a component when it can materially change system behavior, engineering evidence, or external results. Package management covers only some components.

## 19.21 Keep static identity and operating boundaries in the component record

A *Supply Chain Component Record* identifies a behavior-relevant component and its source, version, rights, permissions, changes, checks, owner, and recovery information, in proportion to risk.

~~~yaml
component_id: CMP-019-031
kind: tool_server
name: issue-tracker-adapter
owner: developer-platform

identity:
  source: internal_repository_ref
  revision: commit-or-release-id
  artifact_digest: sha256:...
  signer: build-service
  provenance: slsa-provenance-ref

rights:
  license: internal
  use_restrictions: company-projects-only

runtime:
  functions:
    - read_issue
    - add_comment
  credential_scope: project-a-only
  network_destinations:
    - issue.example.internal
  data_access:
    - internal
    - confidential-if-authorized

change:
  update_policy: pinned_release
  monitor: owner-alerts
  re_evaluate_on:
    - function_change
    - permission_change
    - credential_change
    - provider_incident

recovery:
  disable_switch: tool-registry-policy
  fallback: read_only_manual_workflow
~~~

An entry can link to the primary SBOM, Git, contract, and test records.

## 19.22 What provenance can establish

[SLSA v1.2](https://slsa.dev/spec/v1.2/provenance) defines provenance as verifiable information about where, when, and how an artifact was produced. Match other claims to their own evidence.

| Claim | Better-suited evidence |
|---|---|
| An artifact came from a specified source and build | Provenance, signature, digest |
| A component has no known vulnerability in scope | Current vulnerability and advisory checks plus their coverage |
| A tool only performs permitted functions | Interface, policy, permission tests, runtime observations |
| A model is reliable for this task | Claim-specific evaluation and drift monitoring |
| A dataset may be used for this purpose | Contract, license, consent or policy, and jurisdiction-specific review |
| A component is suitable for production | Security, reliability, cost, operations, and an adoption decision |

A correctly signed program can still be malicious. A sourced model can still be unsuitable for the language, risk, or tool scope.

> Provenance is evidence of origin and production, not a certificate of behavior or fitness.

## 19.23 Govern third-party services after procurement

[NIST AI 600-1](https://doi.org/10.6028/NIST.AI.600-1) treats third-party inventory, provider lists, supplier risk assessment, contracts, monitoring, incident response, and fallback as distinct concerns. In practice, ask:

- Which providers can access organizational content?
- Which services embed undeclared models or tools?
- Can the provider, subprocessors, region, terms, or models change?
- What are the shutdown, degradation, exit, and export paths?
- What notice and support does an incident trigger?
- Who tracks changes and initiates re-evaluation?
- Does the contract cover the security, privacy, IP, and audit requirements?

A remote API may lack a pin-able binary digest. Record the service or endpoint, contract version, model alias and known snapshots, change notice policy, observed baseline, evaluation results, fallback, and disable switch. Record drift even when the version cannot be fixed. [Chapter 20](/chapters/20-en.html) examines model and tool drift and cost monitoring.

## 19.24 Nine questions for an IP decision

An *IP Disposition* is a named authority’s recorded decision about using, retaining, modifying, publishing, licensing, or transferring an input, process artifact, or output. It is a target-specific form of the Disposition in [Chapter 9](/chapters/09-en.html). Preserve rights, obligations, unknowns, and jurisdiction. An `AI-generated` label settles none of these on its own.

1. **Input Access.** May the project read the input?
2. **Input Processing.** May it copy, transform, or transmit it to a provider for this purpose?
3. **Confidentiality / Trade Secret.** What nondisclosure and confidentiality terms apply?
4. **Provider Terms.** What are the terms for input, output, retention, training, and indemnity?
5. **Third-party License.** What license, attribution, or notice obligations cover code, text, images, datasets, or models?
6. **Human Contribution.** What identifiable expression, selection, arrangement, modification, or design did a person contribute?
7. **Output Provenance.** Which model, version, input class, retrieval sources, and process records are relevant?
8. **Similarity / Infringement Risk.** Does the material warrant further review for copying, trademarks, patents, trade secrets, or other rights?
9. **Intended Use / Jurisdiction.** Is it for internal drafts, open source, commercial release, customer delivery, or registration? Which jurisdiction applies?

These questions help route engineering decisions to the appropriate authorities. Other legal questions may apply.

## 19.25 Record uncertainty in an IP Disposition Record

An *IP Disposition Record* is a versioned Decision Record for an IP target that links input permissions, contract, third-party obligations, human contribution, provenance, risk checks, use, jurisdiction, authority, and disposition to a named artifact.

~~~yaml
ip_disposition_id: IPD-019-014
artifact_ref: marketing-concept-art-v3
intended_use: public_campaign
jurisdictions:
  - CN
  - US

inputs:
  - ref: internal_style_guide
    permission: allowed_for_campaign
    transmission: private-endpoint-only
  - ref: licensed_reference_pack
    license_review: required

generation:
  provider_contract: contract-ref-v7
  model_ref: model-endpoint-snapshot
  output_provenance: provenance-ref

human_contribution:
  - authored_composition_spec
  - selected_and_rearranged_elements
  - manual_paintover_layers_ref

third_party:
  attribution: pending
  similarity_review: pending
  trademark_review: pending

disposition:
  status: hold_for_legal_and_brand_review
  authority: product_legal_brand
  decided_at: null
~~~

Allow `unknown`, `pending`, and `not_assessed`. An agent asked to select `owned` without evidence can create false certainty.

## 19.26 Human contribution and copyrightability depend on jurisdiction

The [U.S. Copyright Office’s 2025 Part 2 report](https://www.copyright.gov/ai/Copyright-and-Artificial-Intelligence-Part-2-Copyrightability-Report.pdf) addresses U.S. copyright protection. It explains that using AI as an assistive tool can be compatible with protection. Identifiable original human expression can still qualify. Human selection, coordination, arrangement, or modification calls for individual assessment. Under the generally available technology the report considered, prompts alone usually did not demonstrate control over expressive elements.

For important generated content intended for registration, licensing, or commercial use, retain actual human contributions, version relationships, selections, and edits alongside prompts. Refer the decision to the appropriate authority in the applicable jurisdiction. The contribution record preserves facts for that decision.

## 19.27 Review generated code for licenses and security

Generated code can contain a new implementation of the problem constraints, third-party code supplied through retrieval or context, structures or expression similar to an existing project, and automatically introduced packages, snippets, templates, or generated clients. It can also be insecure, hard to maintain, or incompatible with the intended license.

~~~text
code compiles
≠ code is secure
≠ code is licensed for this use
≠ code is non-infringing
≠ code may be open-sourced
≠ code is accepted for release
~~~

Keep retrieval and source references. Scan packages and transitive dependencies. Check licenses, notices, attribution, secrets, security, and quality. Review provenance and similarity for important or suspicious code. Have a named authority decide adoption and release. A scanner can flag material for further review. Infringement requires its own assessment.

## 19.28 Governance and ownership of skills, memory, and process records

Skills, memories, prompt templates, evaluation sets, handoffs, incident reviews, and workflow records can carry organizational know-how, contributions by employees, contractors, and third parties, customer or project secrets, personal data, licensed inputs, provider terms, and cross-project restrictions. Departure, migration, deletion, and portability can also matter.

For organization-level use, identify who can promote a Skill or Memory, which sources may be reused between projects, whether they include performance assessments or personal profiles, whether deleting original data triggers deletion of derived memories, what terms apply to outside contributions, what can move to a new model or tool, and whether the process record is operational evidence, organizational knowledge, or restricted material.

[Chapter 15](/chapters/15-en.html) defines memory admission, retrieval, applicability, and deletion. Apply security, privacy, and rights boundaries to those mechanisms.

## 19.29 The same artifact can need several dispositions

| Question | Security Review | Privacy Review | IP / License Review | Authority Review |
|---|---|---|---|---|
| Can an agent access customer logs? | Secrets, access, integrity | People, purpose, retention | Contractual use and disclosure rights | Who can authorize the work? |
| Can web content enter retrieval? | Injection, malicious content, source | Does it contain personal data? | Scraping, copying, license | Does it have instruction authority or only data status? |
| Can a model output be published? | Vulnerabilities, secrets, unintended effects | Disclosure or inference of personal data | Ownership, license, similarity, trademarks | Who can release it? |
| Can a skill be reused across projects? | Secrets, tool permission | Profiling, linkage, retention | Contributor, customer, or license rights | Who can promote it? |
| Can a cloud model process source code? | Provider, credentials, incident handling | Processing, retention, region | Confidentiality, contract, output terms | Who can authorize transfer and adoption? |

A pass applies to its own question. A named owner can cover several checks in a simple profile for low-risk work and record the answers separately.

## 19.30 Start incident response with containment

A leaked secret, unauthorized write, prompt injection, malicious component, provider incident, mistaken data transfer, or IP concern can call for these steps.

~~~text
contain
→ stop new side effects
→ revoke / rotate
→ preserve bounded evidence
→ determine observed scope and unknowns
→ notify the required authority
→ restore or forward-correct
→ delete / cascade-delete where authorized
→ reassess downstream artifacts and controls
~~~

A *Security Incident Record* preserves observed facts, impact scope, unknowns, containment, credential, data and artifact dispositions, authority, and follow-up verification. Start with those records and investigate root cause separately.

Distinguish confirmed exposure, possible exposure, an unauthorized attempt, a prevented effect, an unknown external result, affected artifacts, revoked credentials, and required legal or contractual review. Notice deadlines, recipients, and data subject rights depend on jurisdiction, contract, and incident type.

## 19.31 What D-048 shows about tool integrity

In D-048, the launcher imported local code before target compile and changed the manifest surface used to establish authority. The exact-inventory check observed a real change and failed closed. The target never executed, so its outcome was a `non-result`. A trusted tool can produce an undeclared side effect. Preconditions and postconditions can protect a controlled surface. Verifier failure, target result, and authorization to repair each need their own record.

The case leaves open which side effects can be accepted and which alternatives to exact inventory could suffice. It is a verifier side-effect case. A fail-closed check describes one control response, with system safety still an open question. The historical harness was not rerun. The effectiveness of the proposed fix and necessity of other component record fields remain unestablished.

[Chapter 23](/chapters/23-en.html) describes the full event and counterevidence. ## 19.32 Increase controls with risk

### Level A. Read-only, public, disposable

- Treat external content as data without Instruction Authority.
- Use no credentials, writes, or external side effects.
- Keep context temporary and outside long-lived memory.
- Check output sources and basic facts.

### Level B. Internal development

- Data Handling Profile and provider allowlist.
- Repository path and network scope.
- Minimal tool functions and short-lived credentials.
- Diff, tests, dependency and license checks.
- Named adoption and release authority.
- Component identity and version references.

### Level C. Confidential or personal data, or production impact

- Named Threat Model.
- Model Processing Contract and transfer disposition.
- Downstream authorization, sandbox, and Secret Broker.
- Approval for consequential actions, atomicity, and recovery.
- Access and action audit and incident playbook.
- Retention, deletion, region, and subprocessor review.
- Supply-chain monitoring and fallback.
- Privacy, legal, or security authority where needed.

### Level D. Safety-critical, heavily regulated, or irreversible work

- Independent architectural and risk review.
- Formal policy or safety constraints.
- Strong identity, signatures, isolation, and dual control.
- Claim-specific adversarial evaluation.
- Continuous monitoring, emergency stop, and drills.
- Specific regulatory, customer, and incident-reporting processes.
- A route for human-only work or no automation when evidence is insufficient.

One organization can run work at all four levels. Choose according to the work.

## 19.33 Common anti-patterns

### Anti-pattern 1. Local Means Safe

Assuming the absence of an external provider removes security, privacy, and supply-chain risk.

### Anti-pattern 2. Private Data Is the Only Sensitivity

Overlooking confidentiality, trade secrets, licensing, integrity, and instruction trust.

### Anti-pattern 3. System Prompt as Firewall

Relying on “do not disclose or exceed authority” for downstream authorization and secret boundaries.

### Anti-pattern 4. One Powerful Tool

Giving an agent broad shell, URL, file, and database operations in one tool for convenience.

### Anti-pattern 5. Human Approval Everywhere

Asking people to approve every action without context, scope, or recovery information.

### Anti-pattern 6. SBOM Completes AI Supply Chain

Recording packages and omitting models, tool servers, datasets, prompt templates, APIs, and service drift.

### Anti-pattern 7. Signed Means Safe

Treating signatures or provenance as evidence about vulnerabilities, behavior, permissions, or fitness.

### Anti-pattern 8. AI-generated Means Owned

Combining provider permission, copyright eligibility, infringement, and downstream licensing into one conclusion.

### Anti-pattern 9. Log Everything for Audit

Copying secrets, personal data, and restricted material into prompts, traces, screenshots, and memories and exposing the material again.

### Anti-pattern 10. Security Review Settles Privacy and IP

Assuming a successful access-control check settles purpose, retention, licenses, human contribution, and jurisdiction.

## 19.35 Principles

> **Readable does not imply transmittable.**

> **External content is data unless a named authority grants it instructional scope.**

> **Model output is a proposal at every action sink.**

> **Capability is not Permission, and Permission is not Authority.**

> **System prompts guide behavior; they do not replace security controls.**

> **Locality changes the trust boundary; it does not eliminate it.**

> **Provenance supports origin claims; it does not establish fitness claims.**

> **Contract rights, statutory rights, and non-infringement are different decisions.**

> **Retain only the evidence that the control and accountability question require.**

## 19.36 Checklist

### Data

- [ ] Can you distinguish source, purpose, access, relationship to people, rights, and instruction trust?
- [ ] Are `may_read`, `may_send_to_model`, `may_store`, `may_learn`, and `may_publish` separate?
- [ ] Does the processing boundary cover prompts, tool returns, embeddings, caches, logs, traces, memory, and backups?
- [ ] Does Least Context retain the needed constraints?
- [ ] Are retention, deletion, derived data, and cascade deletion clear?

### Model

- [ ] Can you identify the provider, endpoint, model, version or change policy, and owner?
- [ ] Have region, retention, training, subprocessors, support access, and incident terms been reviewed?
- [ ] Does the project define local, private, and cloud?
- [ ] Is any material marked `model_context_denied`?
- [ ] Does a model change trigger re-evaluation?

### Tool and Agent

- [ ] Does external content enter without Instruction Authority by default?
- [ ] Are functionality, permission, credentials, and authority each constrained?
- [ ] Are secrets excluded from prompts, skills, memory, and logs?
- [ ] What does the sandbox isolate?
- [ ] Does each action sink have specific validation and downstream authorization?
- [ ] Do consequential actions specify scope, effect, expiry, evidence, and recovery?
- [ ] Can you stop, revoke, rotate credentials, and observe state again?

### Supply Chain

- [ ] Does the inventory cover scripts, plugins, skills, tool servers, models, datasets, templates, APIs, and services?
- [ ] Are identity, version or contract, source, license, permission, owner, and update policy traceable?
- [ ] Are provenance conclusions limited to origin and production?
- [ ] Are vulnerabilities, behavior, use-case fitness, monitoring, and recovery checked independently?
- [ ] Can you disable, fall back, or respond to an incident after a provider or component changes?

### Privacy and IP

- [ ] Can you distinguish security, confidentiality, privacy, processing permission, IP, licenses, and authority?
- [ ] Is input access separate from permission to send it to a model or provider?
- [ ] Have you identified provider terms, third-party licenses, and downstream uses?
- [ ] Do important outputs retain human contribution and output provenance?
- [ ] Are similarity and license scans treated as limited evidence?
- [ ] Are jurisdiction and legal or business authority explicit?
- [ ] Are `AI-generated`, `Provider allows use`, and `scan passed` treated as inputs to the rights decision?

### Incident and Trace

- [ ] Does response first contain, stop, revoke, or rotate before inferring causes?
- [ ] Can you distinguish confirmed, possible, prevented, and unknown results?
- [ ] Can you preserve evidence without copying unnecessary secrets or personal data?
- [ ] Who handles security, privacy, IP, recovery, and notification?

## 19.37 Conclusion

Security boundaries come from relationships you can inspect and enforce.

~~~text
Data + Purpose + Processing Permission
→ Model Processing Contract
→ Context and Instruction Boundary
→ Tool Function + Credential + Authority
→ Action Sink Control + Evidence + Recovery
→ Supply Chain Identity + Monitoring
→ Privacy / IP Disposition + Accountability
~~~

Apply public, internal, confidential, personal, and regulated labels on the dimensions they describe. Assess trust against the topology and processing terms of a local, private, or cloud deployment. Match provenance, signatures, SBOMs, and scanner results to limited claims. For AI-generated material, determine input rights, output ownership, copyright eligibility, license compliance, and infringement separately.

Give external data explicit instruction authority if appropriate. Validate model output at each action sink. Check tool permission against organizational authorization. Treat provider terms as contractual evidence. Assess component behavior alongside its production record. Retain logs under a stated purpose and time limit.

[Chapter 20](/chapters/20-en.html) examines what happens when models, tools, costs, latency, permission use, or evaluation coverage change. Keep observing and re-evaluating the boundary, and withdraw authorization when warranted.
