## 1. 这份记录解决什么问题

AI Game Dev OS 与 lessismore 继续构成全书的纵向 Case Spine。它们能够展示问题何时出现、判断如何变化、哪些机制被保留或撤回，但两个仓库共享作者、方法背景和开发反馈链，不能作为两个独立样本，也不能独自证明前22章理论。

本记录选择少量公开案例，为后续章节提供四种横向作用：

- `precedent`：说明某个问题或控制关系在 AI 之前已经存在；
- `mechanism comparison`：比较不同系统如何处理相近问题；
- `counterexample`：迫使本书收窄定义、条件或适用范围；
- `transfer test`：检查本书对象模型换到另一种环境后还能解释什么。

案例不是按章节分配的装饰材料。候选映射只回答“哪里可能有比较价值”，不授权将案例事实直接写入 `PolishedDocs/`。

## 2. Epistemic 与 Evidence 边界

### Observable Facts

- 本轮来源均为官方项目文档、官方工程记录、公开规范或原始研究论文；没有用二手行业总结替代项目自身材料。
- OpenAI 与 Anthropic 材料主要是团队对自身系统的第一方工程报告；它们可以说明该团队报告了什么、采用了什么机制和公开承认了什么限制。
- Kubernetes、Google SRE、Rust RFC 与 SLSA 提供成熟的非 Agent 工程先例，但并不研究 AI Agent。
- SWE-agent 论文报告了特定 ACI 在具名 benchmark 与实验设置中的结果。
- SLSA 已在 [ER-20260824-005](../Evidence/receipts/ER-20260824-005__CLM-C19-002.md) 中按第19章供应链边界正式取证；本记录只复用该窄边界，不重新扩大 Claim。

### Retrospective Inference

- 非 AI 项目能够帮助识别哪些对象关系不是 Agent 独有问题，减少把既有软件工程治理重新包装成 AI 专属概念的风险。
- 第一方 Agent 案例最有价值的部分不是效果数字，而是具体失败、接口选择、状态边界和作者公开保留的未知。
- 同一案例跨章复用只有在观察对象不同且不重复背书时才有价值。

### Current Recommendation

- 先维持九个案例族，不追求更多数量；章节正式采用时可以删除弱案例。
- 默认不在正文复述厂商的速度、成本或质量提升数字。若某个效果数字成为论证必要部分，应单独按 Evidence Intensity Routing 处理。
- 每次进入正文前重新确认来源日期、版本、支持上限和与作者项目的关键差异。
- 第1、6章已经成为 Human 暂时接受的声音基线，不为案例组合的对称性回头插入材料；第12章默认检验“不需要外部案例”；第23章只保留少量 Transfer Questions，不增加平行案例叙事。

## 4. 案例卡

### 4.1 OpenAI Harness Engineering

**Primary source**：[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)，OpenAI 第一方工程记录，2026-02-11。

**可以形成的比较**：

- 该团队把早期进展问题解释为环境欠明确，并将工程工作转向让能力、工具、文档、反馈和约束对 Agent 可见且可执行；
- Repository-local、versioned knowledge、Execution Plans、Worktree 隔离、可观察性与结构性检查构成一个具名实践组合；
- 原文明确说明端到端行为高度依赖该仓库的具体结构和工具，也保留了长期架构一致性与模型变化的未知。

**不能据此推出**：

- 相同 Harness 能在其他项目获得相同速度、质量或成本结果；
- “没有手写代码”意味着没有 Human Engineering；
- 所有 Agent 项目都应采用相同目录、合并策略、自治程度或垃圾回收机制。

### 4.2 Anthropic Long-running / Managed Agents

**Primary sources**：[Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)，2025-11-26；[Scaling Managed Agents: Decoupling the brain from the hands](https://www.anthropic.com/engineering/managed-agents)，2026-04-08。二者均为 Anthropic 第一方工程报告。

**可以形成的比较**：

- 长任务跨离散 Session 时，进度文件、Git 历史、初始化与增量交接可以作为一种外部连续性设计；
- 长时运行文章将其方案明确称为“一种可能的解决组合”，并保留跨任务类型、单／多 Agent 等开放问题；
- Managed Agents 又将 Session、Harness 与 Sandbox 分离，说明 Harness 假设可能随模型能力与产品约束变化，不能把当前实现冻结成永恒对象模型。

**不能据此推出**：

- Compaction 在所有 Agent、模型和任务上都不够；
- `claude-progress.txt`、双 Agent 或 Session／Harness／Sandbox 分层是唯一正确架构；
- Web App 实验能够直接推广到游戏、企业治理或长期维护。

### 4.3 Anthropic Agent Evals

**Primary source**：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)，Anthropic 第一方方法与工程说明，2026-01-09。

**可以形成的比较**：

- 原文将 Transcript、Outcome、Evaluation Harness、Agent Harness 与 Evaluation Suite 分开；
- Transcript 中 Agent 声称完成，与环境最终状态是否改变可以是两个不同问题；
- Code、Model 与 Human grader 覆盖不同判断面，评价基础设施本身也可能产生错误。

**不能据此推出**：

- 一套统一 grader 能覆盖所有 Agent 工作；
- Outcome 可以替代过程、安全、授权或 Human Experience 判断；
- Anthropic 的方法、指标或工具组合已经被证明为跨领域最优。

### 4.4 SWE-agent ACI

**Primary sources**：[SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering](https://arxiv.org/abs/2405.15793)，论文 v3，2024-11-11；[SWE-agent repository](https://github.com/SWE-agent/SWE-agent)。

**可以形成的比较**：

- 论文在 SWE-bench 与 HumanEvalFix 的具名设置中研究 Agent-Computer Interface 如何影响 Agent 的代码编辑、仓库导航和测试行为；
- 它为“模型能力不能脱离工具接口和 Harness 评价”提供一个可检验的外部案例。

**不能据此推出**：

- benchmark pass rate 等于生产可靠性、可维护性或 Release Approval；
- ACI 对所有模型、仓库和软件任务具有同样影响；
- 接口改善自动解决 Intent、Authority、Evidence 或 Human Decision 问题。

### 4.5 Anthropic Multi-agent Research

**Primary source**：[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)，Anthropic 第一方生产案例，2025-06-13。

**可以形成的比较**：

- 该系统使用 orchestrator-worker 结构，让 Lead Agent 分解并行 research work，再整合 Subagent 结果；
- 原文同时记录任务边界重复、协调复杂度、Token 成本、状态恢复、Tracing、部署一致性和异步错误传播问题；
- 原文明确指出，多 Agent 更适合可独立并行的 breadth-first research，而许多依赖较强的 coding tasks 并不适合当前方案。

**不能据此推出**：

- Multi-agent 普遍优于 Single-agent；
- 内部研究 Evaluation 的效果数字能够推广到软件开发或游戏生产；
- Role 名称、并行数量或 Orchestrator 存在就能产生良好 Organization Design。

### 4.6 Kubernetes Controllers / KEP

**Primary sources**：[Kubernetes Controllers](https://kubernetes.io/docs/concepts/architecture/controller/)；[Kubernetes Enhancement Proposals](https://github.com/kubernetes/enhancements/blob/master/keps/README.md) 与 [KEP Process](https://github.com/kubernetes/enhancements/blob/master/keps/sig-architecture/0000-kep-process/README.md)。

**可以形成的比较**：

- Controller 文档明确区分 Desired State 与 Current State，并以持续控制循环把当前状态向目标状态靠近；系统整体可能始终处于变化之中；
- KEP 用版本化提案协调非平凡变更，留下设计、讨论、风险、阶段和历史记录；
- 两类机制可以分别帮助检验 Intent／State／Execution 与 Proposal／Decision／Implementation／Release 的边界。

**不能据此推出**：

- Agent Work 等同 Kubernetes Reconciliation；
- Desired State 本身产生 Authority，或 Current State 自动决定 Human Acceptance；
- KEP 获得接受就等于功能已经实现、采用、激活或发布。

### 4.7 Google SRE Error Budget / Postmortem

**Primary sources**：[Example Error Budget Policy](https://sre.google/workbook/error-budget-policy/)；[Postmortem Culture: Learning from Failure](https://sre.google/workbook/postmortem-culture/)。

**可以形成的比较**：

- Error Budget Policy 把具名指标、适用窗口、例外、停止发布、可靠性工作和升级 Authority 连接起来；
- Postmortem 实践把事实记录、多方视角、行动项、Owner、优先级与可验证终态连接起来；
- 这些材料说明 Evidence-to-Action、Accountability 与组织 Memory 并不是 Agent 出现后才产生的问题。

**不能据此推出**：

- 示例阈值或停止规则适用于所有团队；
- Error Budget 可以直接评价 Agent 的正确性、Human Experience 或设计质量；
- Postmortem 自动识别唯一 Root Cause，或写下行动项就等于已经完成改进。

### 4.8 Rust RFC Process

**Primary source**：[The Rust RFC Book](https://rust-lang.github.io/rfcs/)。

**可以形成的比较**：

- Rust 将重大设计变更与普通实现修改分开，要求提案陈述动机、替代方案和缺点，并通过公开讨论形成有权决定；
- RFC 被接受只表示可以朝实现推进，不表示已经分配优先级、有人实施、最终设计不变或已经进入 Release；
- 这一过程可用于压力测试 Intent Artifact、Decision、Acceptance、Implementation、Adoption 与 Release 的分离。

**不能据此推出**：

- 任何项目或任何变更都需要 RFC；
- 社区共识等于技术 Truth；
- Rust 的团队 Authority 与作者个人项目、企业组织或 Agent 权限结构可以直接互换。

### 4.9 SLSA Provenance

**Primary source**：[SLSA v1.2 Provenance](https://slsa.dev/spec/v1.2/provenance)。

**Existing Evidence boundary**：[ER-20260824-005 / CLM-C19-002](../Evidence/receipts/ER-20260824-005__CLM-C19-002.md) 已将其限定为 Artifact 来源／产生过程与更广 Component Risk 记录之间的部分支持，Human Status 仍为 `unreviewed`。后续应复用这一 Coverage，不再为相同边界重复建 Receipt。

**可以形成的比较**：

- SLSA 将 Provenance 定义为关于 Artifact 在哪里、何时、如何产生的可验证信息；
- 它为 Artifact Identity、Build 过程与供应链 Trace 提供成熟边界，可帮助避免把 Traceability 写成自由文本时间线。

**不能据此推出**：

- Provenance 能证明 Artifact 正确、安全、符合 Intent 或已经获得发布授权；
- 具备 Build Provenance 就具备完整 Accountability、Human Decision 或 Runtime State；
- SLSA 的供应链范围能够覆盖全书所有 Trace 关系。

## 6. 进入正文前的最小路由

每个拟采用案例先完成一张私有 Source Map：

```text
source and source type
publication date / version
role: precedent | mechanism comparison | counterexample | transfer test
relevant similarity
material difference
can support
cannot support
target paragraph or chapter question
Evidence Receipt trigger: yes | no | unresolved
```

以下情况不能从本记录直接进入 `PolishedDocs/`：

- 依赖精确仓库历史、Runtime 行为或 Artifact；
- 使用速度、成本、质量、可靠性或安全效果数字；
- 从两个以上案例推出跨项目、组织或行业结论；
- 涉及安全、隐私、法律、IP 或其他高风险事实；
- 结论会直接改变 AI Game Dev OS Workflow、Authority 或 Runtime 行为；
- 来源之间存在实质冲突。

这类内容先返回主任务，由其决定是否更新 `OptimizedDocs/`、建立 Claim／Receipt 或请求 Human 裁决。没有 formal trigger 的概念类比、窄范围先例或明确标注的设计刺激，可以通过普通逻辑审阅进入工作稿，但仍需自然语言来源与支持上限。
