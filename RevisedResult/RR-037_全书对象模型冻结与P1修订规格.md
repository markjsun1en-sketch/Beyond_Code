## 3. 建议冻结的上位对象模型

以下定义最初作为待 Human 裁决的推荐值提出，现已由作者全部接受。它们是后续改稿的对象边界约束，不因此成为经验事实、效果证明或普遍性 Claim。

### 3.1 描述层：Claim、Evidence 与 State

#### Claim（声明）

本书建议把 Claim 定义为：

> 对具名对象、范围、时间或版本提出的可被支持、挑战、限定或撤回的命题。

Claim 至少需要能够回答：

- Statement 是什么；
- Target 是什么；
- Scope 与 Reference Time / Revision 是什么；
- 谁或什么产生该 Claim；
- 有哪些 Evidence 与 Counterevidence；
- 当前允许怎样使用；
- 哪些结论仍未成立。

`State Claim`、`Behavior Claim`、`Completion Claim`、`Risk Claim`、`Reliance Claim` 与 `Improvement Claim` 是 Target 或用途不同的 Claim 子类型，不应因为共享 Claim 名称而自动共享相同验证标准。

#### Evidence（证据）

> Evidence 是支持、挑战或限制某个 Claim 在具名 Scope 与 Intended Use 中可被依赖程度的可检查记录。

Evidence 不自动完成：

- Claim Acceptance；
- Change Adoption；
- Release Authorization；
- Production Qualification；
- 对组织责任的分配。

#### State Claim（状态声明）

> State Claim 是关于某对象在具名时间或版本下描述性情况的 Claim。

它可以描述：

- Artifact 是否存在；
- 某 Attempt 是否发生；
- 某测试在具名运行中是否 PASS；
- 某 Revision 是否包含某 Change；
- 某服务在观测时是否可用。

它不应把“允许采用”“应当发布”“可以依赖”“已经接受”等规范性处置内容混为同一个 State Claim。

#### Lifecycle Status（生命周期状态）

`accepted`、`blocked`、`adopted`、`released` 等词如果用于 Lifecycle，应命名为 `Lifecycle Status` 或 Target-specific Status。

它们是对已记录 Transition 与 Disposition 的投影，不是对 Implementation State 的证据替代物。

### 3.2 规范层：Authority、Decision、Policy 与 Disposition

#### Authority Grant（授权记录）

> Authority Grant 记录某个 Subject 为什么可以在具名 Scope、时间和约束下执行某类 Action 或作出某类 Decision。

它回答“谁有权做什么”，不回答一个描述性 Claim 是否为真。

#### Decision Target（决策目标）

> Decision Target 是一次规范性裁决所针对的具名对象与用途。

示例包括：

- 某 Evidence 是否可用于关闭某 Review；
- 某 Change 是否可被接受；
- 某 Capability 是否可被采用；
- 某 Artifact 是否可被发布；
- 某 Risk 是否允许在给定 Scope 中被承担。

#### Decision Record（决策记录）

> Decision Record 是具名 Authority 针对具名 Decision Target 作出的规范性判断及其范围记录。

Decision Record 应引用其 Authority Grant、考虑过的 Evidence、适用 Scope、Decision、限制、开放项和复核条件。

Decision Record 具有规范效力，但不因此成为 Authority 的来源，也不把描述性 Claim 改造成事实。

#### Policy Record（政策记录）

> Policy Record 是对一类未来 Decision 或 Action 持续适用的规范性约束。

Policy 与单次 Decision 的差异主要是适用对象、持续时间和复用方式，不是“一个有 Authority、另一个没有 Authority”。

#### Disposition（处置）

> Disposition 是 Decision Record 的一种结果关系：具名 Authority 对具名 Decision Target 指定其允许的下游状态、用途或下一步动作。

本书不再使用没有 Target 的裸 `Disposition`。

建议使用 Target-specific 名称：

- `Evidence Disposition`；
- `Reliance Disposition`；
- `Result Disposition`；
- `Change Disposition`；
- `Operational Disposition`；
- `Fitness Disposition`。

`Authority disposes Claim` 建议收窄为：

> Authority records a Disposition for a named use of a Claim or another Decision Target.

Authority 可以决定某 Claim 是否被用于具名下游决定；它不能通过授权使 Claim 本身成为事实。

### 3.3 执行层：Work、Contract、Attempt、Outcome 与 Result

#### Work（工作单元）

> Work 是有目标、范围、Owner、约束和关闭语义的可引用工作单元。

Work 不是一次执行本身，也不因为某次 Attempt 成功或失败而自动关闭。

#### Execution Contract（执行契约）

> Execution Contract 描述某次或某类 Attempt 的 Target、允许动作、输入边界、Context、资源、停止条件、Evidence 要求与恢复边界。

Execution Contract 不是 Authority Grant，但必须引用或服从有效 Authority。

#### Attempt（执行尝试）

> Attempt 是在具名 Execution Contract、输入快照、Context 与执行主体下发生的一次有边界执行。

多次 Attempt 可以服务同一个 Work；不同 Attempt 的 Result 不应静默覆盖。

#### Attempt Outcome（尝试后果）

> Attempt Outcome 记录该 Attempt 实际发生了什么，包括完成、部分执行、前置检查失败、超时、中止、崩溃或未触达 Target。

#### Target Result（目标结果）

> Target Result 是在 Target 实际获得足够执行时，对其输出或行为形成的有类型结果。

若 Verifier 在 Target 前失败，Target 没有可评价结果，应记录 `non-result` 或等价的显式 absence classification，而不是记录 Target Failure。

#### Evaluation Result（评价结果）

> Evaluation Result 是某个 Check、Test、Verifier、Review 或 Human Evaluation 对具名 Target 与运行产生的结果。

`PASS` 只说明具名评价在具名运行中没有触发其失败条件，并为它所编码的断言提供有范围 Evidence。它不等于整个 Behavior Claim、Acceptance、Adoption 或 Release 已成立。

### 3.4 下游处置：Acceptance、Adoption 与 Release

这些词必须带 Decision Target，不应作为无对象的阶段名使用。

#### Acceptance

> Acceptance 是具名 Authority 判断某个 Target 在具名 Criteria 与 Scope 下可以被接受的 Decision / Disposition。

Target 可以是 Evidence、Result、Change、Baseline 或其他对象；不同 Target 的 Acceptance 不能互相替代。

#### Adoption

> Adoption 是具名 Authority 决定让某个 Change、Capability、Policy、Workflow 或其他 Target 进入持续治理基线的 Decision / Disposition。

Acceptance 不自动产生 Adoption。

#### Release Authorization

> Release Authorization 是允许某个具名 Target 进入分发、部署、发布或生产推进的规范性决定。

#### Release Execution

> Release Execution 是执行分发、部署、发布或推进的一次或多次 Attempt。

#### Release Outcome

> Release Outcome 是 Release Execution 的可观察后果。

三者必须允许以下情况存在：

- 已授权但尚未执行；
- 已执行但失败；
- 部分执行；
- 执行后撤回；
- 执行成功但仍未取得更高 Scope 的 Production Qualification。

### 3.5 Responsibility 与 Accountability

#### Responsibility（职责）

> Responsibility 是角色或主体被分配去执行、维护、响应或恢复某项工作的义务。

#### Accountability（问责归属）

> Accountability 是组织对解释、审查、纠正或承担后果的归属安排。

Trace 可以支持 Attribution 与 Reconstruction，但不能自动生成 Accountability。

除非进入法律 Evidence 工作，本书中的 Accountability 不自动等同于法律责任、赔偿责任或个人过错。

### 3.6 Human Authority 术语

推荐保留 `Human Cognitive Authority（人类对需要人类判断之事项保留的最终认知裁决权）` 作为书内原则词。

`Human Decision Right` 不作为第二个平行对象。出现时应：

- 改写为自然语言的“Human 保留裁决权”；或
- 明确映射到某个具名 Human Authority Grant。

Human Control Plane 继续保持：

- 可选；
- 非权威；
- Human-facing Projection；
- 不拥有源 Truth；
- 不创造 Authority；
- 不替代 Human Decision。

### 3.7 Capability Profile 命名

第5章的 Context 层对象建议使用 `Context Capability Profile`。

第22章继续使用 `Engineering Capability Profile`。

前者描述某次 Context 构造可用或需要暴露的能力信息；后者描述工程系统针对具名 Workload 的能力配置、Gap、Excess 与 Unknown。二者可以引用，但不应使用同一个裸 `Capability Profile` 名称。

## 6. 需要 Human 裁决的冻结项

### D-037-01：Decision 与 Disposition 的上位关系

- 推荐：`Disposition` 是 `Decision Record` 针对具名 Decision Target 的结果关系或子类型。
- 备选：Decision 与 Disposition 保持并列对象。
- 推荐理由：可以统一 Evidence、Reliance、Result、Operational 与 Fitness Disposition，同时保留 Target-specific 语义。
- 备选成本：若并列，需要再定义两者何时同时存在、谁先谁后，以及谁携带 Authority。
- Human Status：`accepted`

### D-037-02：State 是否严格保持描述性

- 推荐：`State Claim` 严格描述；规范性状态使用 `Lifecycle Status` 并明确来自 Transition / Disposition。
- 备选：允许 State 同时包含描述性与规范性内容，但必须建立两个显式子类型。
- 推荐理由：避免 `PASS / accepted / adopted / released` 重新混成单一 Current State。
- Human Status：`accepted`

### D-037-03：Attempt / Result 的章节所有权

- 推荐：第7章拥有 Work / Contract / Attempt；第8章拥有 Outcome / Result / Failure / Recovery；第9章拥有 Evidence Use / Disposition；第10章拥有 Review / Finding。
- 备选：继续由第21章统一定义，再由前章回引。
- 推荐理由：符合定义先于使用和章节递进；避免整合章反向拥有基础对象。
- Human Status：`accepted`

### D-037-04：Release 三分

- 推荐：固定 `Release Authorization / Release Execution / Release Outcome`。
- 备选：保留一个 Release 对象，但必须有三个不可互换的字段或子记录。
- 推荐理由：允许已授权未执行、执行失败和资格未成立等真实状态。
- Human Status：`accepted`

### D-037-05：Human Decision Right

- 推荐：不建立第二个平行对象，统一回 `Human Cognitive Authority` 或具名 Human Authority Grant。
- 备选：正式定义 Decision Right 为不可委托或必须保留给 Human 的 Decision Type 集合。
- 推荐理由：减少 Authority 术语重复；若选择备选，需要说明其组织、伦理或法律来源。
- Human Status：`accepted`

### D-037-06：缺章优先级

- 推荐：先补第7、8、10章的最小完整正文，再继续全书压缩。
- 备选：先只增加跨章 Bridge，把完整正文留到后续。
- 推荐理由：当前对象所有权缺口已经影响第11、18、21、22章。
- Human Status：`accepted`

### D-037-07：必要／有用／可选的最低控制底线

- 推荐的 Necessary：Work / Attempt Identity、Scope 与允许影响面、结果可见性、停止／恢复或可丢弃边界、具名 Human / System Authority。
- Conditional / Useful：完整 Assumption Record、Exception Authority、Re-evaluation Case、Capability Fit Review、长期 Memory Promotion、独立 Multi-Agent Role。
- Optional：Human Control Plane、Execution Epoch、Self-Evolution、统一 Dashboard、完整 Decision Graph。
- 备选：按领域风险分别定义多套最低控制底线，不提供一个全书通用最小集。
- Human Status：`accepted`
