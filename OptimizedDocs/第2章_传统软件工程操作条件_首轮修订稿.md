# 第2章 当传统软件工程的操作条件不再可靠
## 从“隐含假设失效”改为条件式风险诊断

> 工作稿状态：首轮逻辑修订稿，不替代 [第2章原稿](../OringinalDocs/第2章.md)。
> 回接说明：[RR-020](../RevisedResult/RR-020_前六章首轮分别调整说明.md)。
> 适用边界：本章把传统机制的七项隐含假设改写为条件式风险诊断；它不声称传统软件工程整体失效，也不把 AI 视为这些操作条件失效的唯一原因。

传统软件工程并不是建立在一组从未被质疑的简单假设上。

Code Review、形式化方法、SRE、安全审批、供应链治理和分布式系统工程，早已面对：人类无法理解全部变化、系统状态会分叉、自动化会失败、生产环境与源码不一致等问题。

因此，本章不再声称“传统软件工程共同相信了七件错误的事”。

更准确的定位是：

> 本章提供七个操作条件，用来检查现有工程机制在当前 Agent 委托、规模、风险与恢复成本下是否仍然足够。

这些条件可能在一个项目中仍然成立，在另一个项目中已经不可靠；也可能只对某类任务失效。

---

# 2.1 操作条件不是历史动机

“操作条件”回答：

> 某个既有机制需要哪些环境条件，才能继续以可接受成本工作？

例如，人工 Code Review 并不要求 Reviewer 理解整个世界，但通常需要：

- 修改规模处于可审查范围；
- 关键上下文能够被定位；
- 变化意图和影响边界相对清楚；
- 测试、Diff 与 Runtime Evidence 能覆盖主要风险；
- Reviewer 有足够 Authority 作出相应裁决。

如果 Agent 让修改吞吐、上下文跨度或并发数量上升，人工 Review 可能从有效机制变成瓶颈。这不是 Code Review 原则错误，而是其运行条件发生了变化。

因此后续每一节都区分：

```text
Condition
什么情况下现有机制仍然工作？

Failure Signal
什么现象表示该条件不再可靠？

Engineering Response
需要扩展什么，而不是默认新增完整体系？
```

---

# 2.2 条件一：人类仍能持续掌握主要解释与执行路径

在许多传统开发任务中，人类直接完成：

```text
interpret requirement
→ inspect state
→ choose implementation path
→ change code
→ verify result
```

即使使用复杂工具，人类仍可以连续解释大多数中间决定。

当 Agent 被委托真实执行以后，这条路径可能变成：

```text
Human or system provides bounded intent
→ Agent inspects selected context
→ Agent chooses local path
→ Agent acts through tools
→ Human sees result and selected evidence
```

这里发生的不是“人类拥有目标、Agent 天然拥有路径”。更准确的是：

> Intent Owner 与部分执行路径的被委托决策者可能分离。

## Failure Signal

- 人类只看到最终 Diff，不知道修改基于哪个 State；
- Agent 静默扩大 Goal 或 Scope；
- Tool 能力被误当成授权；
- Reviewer 无法解释为何某组文件进入修改；
- 失败后无法恢复当时的外部执行依据。

## Engineering Response

按风险显式化：

- Parent Intent 或触发来源；
- Scope 与 Non-goal；
- State 与版本引用；
- Delegation、Permission 与 Escalation；
- 可观察动作、结果和 Evidence。

低风险短任务不需要完整 Registry。只有解释跨度、影响或恢复成本超过人类可以持续直接理解的范围时，这些记录才逐步变得必要。

---

# 2.3 条件二：生产吞吐不会长期超过理解、验证与集成能力

工程生产率不是代码生成量。

一个团队的实际交付受到多个能力共同限制：

```text
Generation
→ Verification
→ Review
→ Integration
→ Deployment
→ Operation and Learning
```

Agent 可以显著提高 Generation Throughput，却不自动提高其他环节。

## Failure Signal

- Diff 规模持续超过 Reviewer 可处理范围；
- 测试数量增加，但实际风险没有被覆盖；
- 大量候选实现等待人工选择；
- 集成、回滚和认知成本超过生成节省的时间；
- 团队只能依赖 Agent 的摘要接受变化。

## Engineering Response

- 减少单次 Change Surface；
- 把任务拆成可独立验证的 Slice；
- 在执行前绑定 Acceptance Target 与 Required Evidence；
- 自动生成面向风险的证据，而不是只生成更多代码；
- 记录 Verification、Review、Recovery 与 Governance Cost。

“更多 Agent”只会增加生产者数量，不能自动解除验证和集成瓶颈。

---

# 2.4 条件三：执行行为可以由接口和规则充分预测

编译器、测试 Runner 和部署工具也会失败，但其输入、状态转换和错误通常有相对明确的接口。

软件 Agent 接受开放式目标后，可能在相似输入下选择不同搜索顺序、方案或工具路径。

这不意味着一次运行就观察到了“概率分布”。Distribution 需要：

- 固定或记录模型与工具版本；
- 可重复任务样本；
- 多次运行；
- 明确成功与失败判据；
- 对环境差异的控制或记录。

在没有这些条件时，更严谨的工程对象是：

```text
Allowed Behavior Set
+ Observed Variations
+ Known Failure Modes
```

## Failure Signal

- 相似任务产生差异很大的 Scope；
- Agent 在缺失 Context 时自行补全未知；
- Tool failure 被误写成目标 failure；
- 流畅解释掩盖了未运行的验证；
- 版本变化后继续复用旧可靠性判断。

## Engineering Response

- 用 Contract 约束 Goal、Scope、Permission 和 Evidence；
- 用 Eval 和重复运行观察变异；
- 分开 Harness failure、Tool result 与 target result；
- 把模型版本、Context、Tool 和 Runtime 作为测试条件；
- 对高风险动作设置可恢复边界，而不是追求行为完全确定。

---

# 2.5 条件四：项目知识可以由代码、文档与人类记忆自然维持

传统团队依赖多种知识载体：

- Code 与测试；
- 文档与 Runbook；
- Issue 与历史提交；
- 会议、即时沟通和资深成员经验。

这些载体从来都可能过期或冲突。Agent 让问题更明显，是因为它必须从可访问材料中装配当前工作表面，而不会天然共享团队长期默契。

但结论不是“所有隐性知识必须文档化”。

## 优先外部化的知识

更值得显式保存的是：

- 高影响；
- 高频复用；
- 跨角色；
- 不直观；
- 容易漂移；
- 失败后难以恢复；
- 涉及 Safety、Security 或 Authority。

## 不必机械外部化的内容

- 一次性、低风险局部判断；
- 可以由测试或代码直接重新获得的事实；
- 没有复用价值的讨论过程；
- 无法稳定维护、写入后反而会制造错误 Authority 的细节。

## Engineering Response

建立可裁剪的：

- Context Source 与 Provenance；
- Decision 与 Assumption 引用；
- Freshness 与 Invalidation；
- Handoff 与恢复记录；
- Memory 候选的进入和删除规则。

外部化的目标不是“把团队脑子搬进数据库”，而是降低高价值知识在传递、压缩与恢复中的丢失风险。

---

# 2.6 条件五：执行者数量受到人力成本的自然限制

人类团队增加成员会产生招聘、沟通和协调成本。Agent 可以降低新增执行实例的边际启动成本，但不会消除：

- 任务分解；
- Context 分配；
- 写入面冲突；
- 结果集成；
- Review；
- 责任归属。

## Failure Signal

- 多个 Agent 修改同一 Worktree 或共享 Index；
- 不同 Agent 依据不同 Parent Intent；
- Reviewer 只收到 Worker 自己的摘要；
- Handoff 丢失 Conflict、Assumption 或未完成验证；
- 产出数量增加但主线集成速度下降。

## Engineering Response

- 以职责和写入面拆分任务，而不是只增加 Agent；
- 隔离 Worktree、Index、环境或数据；
- 使用清晰的 Contract 与 Handoff；
- 保留独立 Review 所需的原始 Evidence；
- 串行化不能安全并发的写入和裁决动作。

多 Agent 问题包含组织设计成分，但不应被化约成“本质上只是组织设计”。共享文件系统、Git、Runtime 和 Tool 的技术隔离同样决定结果。

---

# 2.7 条件六：人工 Review 可以承担主要高层质量防线

人工 Review 仍然重要，尤其适合：

- 架构方向；
- 产品和体验判断；
- 风险接受；
- 多方 Intent 冲突；
- 证据不足时的裁决。

但人工 Review 的有效性依赖输入质量和认知范围。

## Verification Gap（验证缺口）

当产出增长快于验证能力时，可能出现：

```text
Generated Change Surface
>
Verified and Understood Change Surface
```

这不是一个固定数学公式，而是一种诊断关系。

## Failure Signal

- Reviewer 只能抽查大规模 Diff；
- 测试通过被写成所有风险已关闭；
- Review 意见混合事实、建议和用途裁决；
- 自动审查与人工审查重复同一表面，却遗漏 Runtime 或 Data；
- Evidence 不绑定 Claim 和 Scope。

## Engineering Response

Review 从单一角色扩展为系统能力：

- 执行前：Intent、Scope、风险和 Evidence Target；
- 执行中：关键状态变化、权限和异常；
- 执行后：Claim Coverage、Counterevidence 与 Decision Target；
- 长期：失败模式、规则成本与 Review 本身的有效性。

这不表示每个任务都需要完整 Gate。低风险任务仍可依赖测试与轻量人工检查。

---

# 2.8 条件七：当前系统状态容易由人类整合

软件项目可能同时存在：

```text
Repository State
Build / Deployment State
Runtime Observation
Data and Configuration State
Approved Decisions
Open Assumptions
Context and Memory Sources
```

它们不是多个平级“现实”，更不构成固定 Truth Hierarchy。

- Repository State 回答源实现问题；
- Runtime Observation 支持特定环境中的行为 Claim；
- Decision 是规范性授权，不是描述性 State；
- Assumption 是显式未知；
- Memory 与文档是信息来源，进入 Context 后也不会自动获得 Authority；
- Evidence 支持或反驳 Claim，不等于 Claim 本身。

## 一个冲突场景

假设设计文档保留旧版 UI 规则，代码已经切换结构，Worktree 还有用户的未提交修改，历史 Memory 又引用过期命名。

此时不能简单写成：

```text
Doc = Intent
Code = Implementation Truth
Runtime = Behavioral Truth
Memory = Memory State
```

更稳妥的处理是逐项询问：

1. 每个来源是什么类型？
2. 它绑定哪个版本、时间与 Scope？
3. 谁或什么有权回答当前问题？
4. 哪些只是候选信息，哪些已经被观察？
5. 冲突是否能够解决，还是必须保留？

## Engineering Response

后续第6章使用：

```text
Intent Artifact
Decision / Policy
State Claim
Assumption
Evidence Record
```

以及 question-scoped Authority、Freshness、Conflict 和 Execution Baseline 来表达状态关系。

---

# 2.9 从隐性组织能力到风险相称的系统能力

人类组织通过共享经验、即时沟通和专业判断补足不完整信息。这些能力不能也不应该全部被形式化。

本书更窄的主张是：

> 当执行路径的复杂度、并发度、风险或恢复成本超过人类可以持续直接理解的范围时，关键边界、Authority 和完成 Evidence 需要按风险逐步显式化。

现有 SP122 Evidence Receipt 支持的是一个有限范围：在多 Agent、跨 Authority 来源、需要分阶段人工裁决的任务中，显式 Lane、来源、Evidence 与 Human Disposition 被实际使用，并成功区分了“Evidence Chain 被接受”与“Supported Adoption / Production Release 尚未批准”。

它不能证明：

- Agent 是这些机制的唯一原因；
- 所有任务都需要同样重量；
- 显式化必然提高效率；
- 完整记录足以保证最终采用。

因此，显式机制是风险控制手段，不是工程进步的单向成熟度。

# 2.10 软件工程控制面的扩展

当多个操作条件变得不可靠时，软件工程开始同时管理：

```text
Product State
Production Intelligence Configuration
Delegated Action
Evidence and Decision Flow
Recovery and Learning
```

这并不要求建立一个吸收所有对象的超级 Control Plane。每个后续章节只拥有一种主要语义：

- 第4章：Intent Artifact 与 Desired Outcome；
- 第5章：Context 的选择、Payload 与 Manifest；
- 第6章：Typed State Records 与 Authority Applicability；
- 第7章：Execution Contract 与执行状态变化；
- 第9章：Evidence Coverage、Intended Use 与 Decision Disposition；
- 后续治理章节：Policy、Gate、Escalation 与成本。

这种分工的目的，是避免同一个 Status、Manifest 或 Registry 同时承担目标、事实、授权、执行和裁决。

---

# 2.11 能力更强不自动意味着治理更重

原稿倾向于把“模型能力更强”与“治理要求更高”直接相连。

能力确实可能扩大潜在行动面，但治理针对的是实际被授予和暴露的风险，而不是抽象模型能力。

更可操作的检查是：

```text
Granted Action Surface
+ Impact
+ Irreversibility
+ State Uncertainty
+ Verification Difficulty
+ Recovery Cost
```

例如：

- 高能力模型在只读 Sandbox 中生成候选，可能只需轻量治理；
- 确定性脚本拥有生产数据库写权限，可能需要严格审批、幂等和恢复；
- Agent 可以运行测试，不表示它有权接受发布风险；
- 自动 Gate 可以作出限定裁决，但前提是 Policy 明确委托。

治理应与被授予的行动和决策面匹配。

---

# 2.12 从“代码可信”到生产链 Claim 可检查

代码质量仍然重要，但一次交付还可能依赖：

- Intent 是否正确；
- Context 是否包含关键来源；
- State Baseline 是否识别正确；
- Agent 是否越过 Scope 或 Permission；
- Test 是否真正观察目标；
- Evidence 覆盖是否足够；
- 实现范围、Adoption 和 Release 是否得到相应裁决。

因此“生产链可信”不应被写成一个总分或单一状态。

更准确的是：

> 对每个重要 Claim，能够定位其输入、状态、变化、观察、Evidence、限制和用途裁决。

一个环节通过，不自动替代另一个环节：

```text
Test PASS
≠ implementation scope necessary
≠ adoption accepted
≠ release authorized
```

# 2.13 哪些传统原则反而更重要

Agent 不会使传统原则失效，反而会让某些原则扩展作用面。

## Small Changes

限制 Change Surface，使验证、Review 和回滚仍然可行。

## Automated Testing

为重复行为提供快速反馈，同时明确 Test 的目标、Scope 和环境。

## Clear Architecture

减少 Agent 必须同时理解的隐式耦合，让职责和接口可定位。

## Version Control

保存 Repository State、变更历史和可恢复基线，但不把 Git 当作全部现实。

## Least Privilege

限制 Tool 和 Data 的行动面，并把能力与权限分开。

## Observability

暴露输入、状态变化、Tool 结果、目标结果和失败边界，而不是读取隐藏推理。

## Recovery

让错误可以被隔离、回滚、重试或由人接管。

# 2.14 一个条件式理论起点

本书的理论起点不需要宣称旧软件工程已经失效。

它可以写成：

```text
Delegated execution
+ higher throughput or concurrency
+ state / authority divergence
+ meaningful risk or recovery cost
        ↓
some existing operating conditions become unreliable
        ↓
extend engineering mechanisms proportionally
```

核心目标仍然是：

- 构建正确的软件；
- 控制复杂性和风险；
- 支持协作与维护；
- 让系统能够长期演化；
- 对结果和责任保持可追踪。

变化的是：部分生产路径开始由智能执行系统承担，而现有机制未必覆盖这种委托。

# 2.15 本章结论

本章没有证明七项传统假设在历史上普遍存在，也没有证明它们已经全部失效。

它提供了七个诊断面：

1. 人类是否仍掌握主要解释与执行路径；
2. 生产吞吐是否仍处于理解、验证和集成能力内；
3. 行为是否仍能由接口和规则充分约束；
4. 高价值项目知识是否能被可靠传递；
5. 执行者增加是否仍受可管理的协调成本约束；
6. 人工 Review 是否仍覆盖主要风险；
7. 当前状态与 Authority 是否仍容易整合。

这些条件失效时，结论不是“建立更多 Registry”。更准确的是：

> 按当前风险，把关键 Intent、Context、State、Authority、Evidence 和 Recovery 从不可持续的隐式依赖转成可检查的工程接口。

下一章将据此定义：什么样的执行委托和工程适配，构成本书所说的 AI 原生软件工程。

---

# 本章原则

1. **操作条件不是历史事实。** 它们是检查机制适用边界的 retrospective lens。
2. **条件性失效不等于传统原则失效。** 先找出具体 Failure Signal。
3. **显式化应按风险发生。** 不是所有隐性知识都值得持久化。
4. **行为分布需要采样协议。** 单次路径变化只说明已观察变异。
5. **状态来源不构成固定 Truth Hierarchy。** 使用 Typed Records 与 question-scoped Authority。
6. **能力不自动决定治理强度。** 关注被授予的行动面、影响和恢复成本。
7. **Test、Acceptance、Adoption 与 Release 分开。** 一个环节不能静默覆盖另一个环节。

---

# 常见反模式

- 把作者的诊断框架写成传统软件工程设计者的共同历史信念；
- 用一个 Agent 案例证明所有隐性知识都必须结构化；
- 一次运行路径不同就声称观察到了稳定概率分布；
- 用更多 Agent 直接解决验证和集成瓶颈；
- 把 Doc、Code、Runtime 与 Memory 固定映射成多种 Truth；
- 把模型能力与治理强度写成单调关系；
- 把 Test PASS 当成整条生产链可信；
- 看到条件失效就建立完整 Registry、Graph 和 Gate。

# 本章检查清单

- 当前讨论的是可观察事实、回顾性诊断，还是当前建议？
- 哪个既有机制依赖什么操作条件？
- 有什么 Failure Signal 表示该条件不再可靠？
- Agent 被委托了什么执行路径和行动面？
- 生产、验证、Review 与集成吞吐是否匹配？
- “行为分布”是否真的来自重复采样？
- 哪些隐性知识具有高影响、高复用或高恢复成本？
- 多 Agent 是否拥有隔离写入面和明确 Handoff？
