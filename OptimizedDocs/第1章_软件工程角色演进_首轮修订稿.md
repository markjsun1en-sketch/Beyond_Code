# 第1章 软件工程的角色演进
## 从工具增强到受托执行

> 工作稿状态：首轮逻辑修订稿，不替代 [第1章原稿](../OringinalDocs/第1章.md)。
> 回接说明：[RR-020](../RevisedResult/RR-020_前六章首轮分别调整说明.md)。
> 适用边界：本章只建立从工具增强到受托执行的历史叙事与问题入口；AI-assisted、Agentic 与 AI-native 的工作定义由第3章统一，本章不把它们排成单向成熟度阶梯。

软件工程的历史经常被写成工具能力不断增强的历史：高级语言、IDE、版本控制、自动化测试、持续集成、云平台，再到生成式 AI 与软件 Agent。

这条叙事有解释力，但不能被误读成一条简单的技术升级阶梯。

不同工具改变的对象并不相同。有的提高表达层级，有的缩短反馈时间，有的降低协作成本，有的扩大自动执行范围。今天的软件 Agent 带来的关键变化，也不只是“比过去的工具更智能”，而是：

> 在一部分真实工程任务中，软件系统开始被委托解释开放式目标、选择部分路径，并通过工具改变项目状态。

本章讨论的就是这种角色变化。

---

## 1.1 软件工程长期管理两类复杂性

第一类是 Product Complexity（产品系统复杂性）。

软件规模扩大以后，开发者需要处理更多模块、接口、状态、依赖、数据和运行环境。模块化、抽象、封装、测试和架构设计，都是为了让局部变化仍然可以被理解和控制。

第二类是 Collaboration Complexity（协作复杂性）。

软件通常由多人跨时间、角色和环境共同维护。需求需要传递，修改需要合并，决定需要追踪，缺陷需要复现，系统还要在原始开发者离开后继续演化。

版本控制、Issue、Code Review、CI/CD 和项目管理机制，主要在处理这种跨人、跨时间的协调成本。

传统软件生产常被简化为：

```text
Human Intent
→ Human Interpretation and Design
→ Human-authored Change
→ Deterministic or Bounded Tools
→ Running Software
```

这个模型从来不是绝对事实。编译器、优化器、调度器、搜索系统和自动运维早已承担复杂选择。它更准确地描述一种长期常见的责任关系：

> 人类通常直接控制目标解释与主要工程路径，工具在既定接口和规则内完成转换、检查或执行。

---

## 1.2 工具演进不断提高表达、反馈与协作能力

软件工具的演进可以从三个反复出现的方向理解。

### 提高表达层级

高级语言、框架和声明式配置让人类可以用更接近问题领域的结构描述工作，把一部分机器细节交给编译器、Runtime 或平台。

这并没有消除工程责任。它把责任从“手工完成每个细节”转移到：

- 选择正确抽象；
- 理解抽象边界；
- 验证自动转换结果；
- 处理抽象泄漏和失败。

### 缩短反馈回路

IDE、静态分析、测试与 CI 把错误反馈带回开发现场。它们让某些检查从人类记忆和人工步骤进入可重复机制。

但这些机制只对已经形式化的规则负责。测试可以确认声明范围内的行为，不能自动判断产品方向、体验取舍或发布风险。

### 扩大协作规模

版本控制、Code Review、Issue 和部署系统让多人能够在共享历史上工作。它们保存了变化、责任与决策的一部分外部记录。

这些机制同样不是完整现实。Git 能描述 Repository State，却不能单独回答当前部署、数据、配置或产品授权。

因此，工具增强从来不等于人类责任消失。它不断重分配：什么由人直接完成，什么由系统执行，什么必须被外部记录和验证。

---

## 1.3 AI 首先作为新的认知与生成工具进入开发

代码补全、问答和生成式助手首先扩展的是人类的局部认知与表达能力。

常见模式是：

```text
Human frames a local problem
→ AI proposes code or explanation
→ Human selects and applies
→ Existing engineering process verifies
```

这里的 AI 输出主要是候选。即使候选质量很高，真实执行路径仍大多由人类控制。

这种模式可能显著提升速度，但不必然要求重新设计整个软件生产系统。原有的 Scope、版本控制、测试和 Review 仍可能足以管理结果。

因此，不能用“生成速度更快”判断项目是否进入了新的工程形态。

---

## 1.4 软件 Agent 把 AI 带入执行闭环

当 Agent 获得 Repository、Terminal、Browser、Build、Issue 或部署工具后，它可以在一个任务中连续完成：

```text
interpret a bounded goal
→ inspect project state
→ choose a local path
→ act through tools
→ observe feedback
→ revise
→ return changes and evidence
```

部分日常开发任务已经出现这种能力：软件工程 Agent 可以在具名、受控的范围内解释开放式目标，并通过多个工具行动。

这里应避免两个过强结论。

第一，这并不是历史上第一次出现自动规划或路径选择。专家系统、搜索、优化、RPA 和自动运维都可能完成复杂执行。

第二，不是所有被称为 Agent 的系统都拥有同等裁量。一个由严格 Workflow 驱动的 coding agent，实际开放式决策可能少于一个复杂优化器。

更可操作的区别不是“是否智能”，而是三个工程维度：

```text
Delegated Interpretation
被委托解释多大范围的开放式目标？

Action Surface
可以读取、写入或触发哪些真实状态？

Feedback Horizon
能够根据多少轮环境反馈继续行动？
```

---

## 1.5 Agent 是受托执行系统，不是天然员工

为了讨论工程责任，本书把 Agent 视为：

> 在外部 Context、Tool、Policy 与 Runtime 支持下，能够对限定目标进行多步解释和行动的软件执行系统。

这个定义不要求把 Agent 拟人化。

Agent 没有天然组织身份、长期责任或项目所有权。它能做什么，取决于：

- 模型与 Harness 能力；
- 当前获得的信息；
- Tool 和 Permission；
- State 与环境；
- Workflow 与 Policy；
- 人类或自动系统授予的 Delegation。

因此需要区分：

```text
Capability   系统技术上能做什么
Permission   当前被允许做什么
Authority    能否对某类目标或裁决作决定
Responsibility 对具名工作承担执行、维护、响应或恢复义务
```

Agent 能执行某项操作，不表示它已经获得使用该能力的权限；能提出一个 Claim，也不表示它拥有项目裁决权。

Responsibility 在这里描述工作义务。结果最终由谁解释、纠正并承担组织后果，属于第18章展开的 Accountability（问责关系），不能压回 Responsibility。

## 1.6 生产者变化为什么不同于效率变化

假设 AI 只把一段局部代码的生成速度提高一倍，但人类仍然理解、应用并验证每项修改。这里主要发生的是生产率变化。

当 Agent 被委托跨文件、跨工具和多轮反馈的执行路径后，至少出现五类新的管理问题。

### 中间路径不再由人类逐步指定

人类可能只定义 Goal、Constraint 和 Non-goal。具体搜索、方案选择、试验与修正由 Agent 在受控范围内完成。

这不表示“Agent 拥有实现路径”。更准确地说：

> Intent Owner 与部分执行路径的被委托决策者可能分离。

委托范围可以很宽，也可以接近确定性步骤。

### 人类不再天然拥有全部执行上下文

Agent 可能读取、筛选和组合大量材料。工程系统能记录哪些信息被提供、开放或读取，却不能仅凭 Manifest 证明模型注意或使用了什么。

### 代码不再完整表达生产过程

代码仍是核心产物，但解释一次变化还可能需要：

- Intent 与版本；
- State 与 Dirty Worktree；
- Context 来源；
- Tool 与 Permission；
- 可观察动作和失败；
- Evidence 与 Scope；
- Acceptance、Adoption 或 Release 的裁决。

项目不需要保存隐藏推理，但需要保存与风险相称的外部决策依据。

### 生产吞吐可能超过验证与理解吞吐

Agent 可以快速产生大量修改。更多输出不等于更多被验证价值。如果在某类 Workload 和相关时间窗内，候选产生能力持续快于 Review、测试、认知和集成能力，瓶颈就可能向判断与集成迁移。

### 能力、权限与责任进一步分离

Agent、Harness、Tool、Policy、Gate 和 Human 可能分别承担不同动作。没有明确边界时，系统容易把“可以执行”“验证通过”和“允许采用”写成同一状态。

## 1.7 软件工程的管理对象由此扩展

传统工程资产包括：

```text
Code
Data
Configuration
Build artifacts
Runtime systems
```

受托执行还会让一组生产配置成为需要管理的工程表面：

```text
Intent references
Context contracts and manifests
Agent and tool contracts
Permissions and policies
State snapshots and baselines
Evidence and review records
Memory and skill sources
Evaluation and recovery records
```

这些对象不是每个任务都要建立独立文件。小型、低风险、易恢复的任务可以把它们压缩进短任务说明和现有测试流程。

只有当影响、复用、冲突或恢复成本使隐式管理不再可靠时，结构化记录才值得其维护成本。

---

## 1.8 从两个复杂性到第三个受托执行问题

Agent 的进入没有取消 Product Complexity 和 Collaboration Complexity，而是在某些项目中增加了 Delegated Execution Complexity（受托执行复杂性）：

```text
Software Complexity
+ Human Collaboration Complexity
+ Delegated Execution Complexity
```

它来自：

- 开放式目标解释可能变化；
- Context 与 State 可能不完整或冲突；
- Tool 能力与授权范围可能不一致；
- 执行路径可能跨多个反馈回合；
- 完成 Claim 可能超出 Evidence 实际覆盖；
- 多个执行者可能争用同一工作面；
- 失败后需要重建外部决策环境。

这不是所有项目都会同等面对的新复杂性。它随着受托裁量、行动面、风险和恢复成本增加而变得重要。

---

## 1.9 两个系统的预告

第3章会正式定义两个被工程化的系统：

### Product System

最终运行的软件、数据、基础设施与配置。

### Production Intelligence System

参与生产的 Agent、Harness、Context、Tool、Skill、Memory 与 Workflow。

二者之间还需要横切的 Control and Evidence 能力，处理 Intent、State、Authority、Observation、Evidence、Review 和 Recovery。

本章只建立问题入口，不在这里定义第三个成熟度层级，也不把 Control Plane 当作第三个同级产品系统。

---

## 1.10 人类角色不会简单消失

执行路径的一部分被委托以后，人类工作会重新分配。

人类仍然可能承担：

- 价值目标和优先级；
- 组织责任与风险接受；
- 复杂冲突和主观体验裁决；
- 授权边界、Policy 与接管路径设计；
- 架构和长期演化判断；
- 对自动化制度本身的审查。

但“人类保留最终责任”不能只是一句口号。项目还需要让人能够：

- 定位关键 Evidence；
- 理解 Claim 的 Scope 与限制；
- 暂停或否决动作；
- 接管失败任务；
- 改变 Delegation 和 Gate；
- 将责任绑定到真实组织角色。

Human Authority 不等于人工批准每一步。低风险、可逆、由 Policy 明确委托的动作可以自动化；重要的是委托来源和接管能力仍然清楚。

---

## 1.11 哪些情况下角色变化值得工程化响应

不是每一次 AI 使用都需要新的基础设施。可以先检查：

1. Agent 是否直接改变真实项目状态？
2. 是否被委托了开放式路径选择？
3. 任务是否跨文件、跨工具、跨会话或跨 Agent？
4. State、Intent 与 Decision Authority 是否可能分离？
5. 错误是否影响数据、安全、发布或不可逆状态？
6. 现有测试和 Review 能否覆盖实际 Claim？
7. 失败后是否容易恢复和归因？

如果大多数答案为否，传统软件工程加轻量 AI 使用规范可能已经足够。

如果多个答案为是，项目需要的不是“更多 Agent”，而是更明确的 Intent、Context、State、Authority、Evidence 和 Recovery。

## 1.12 本章结论

软件工具不断提高表达层级、反馈速度和协作规模。软件 Agent 延续了这条演进，并在部分具名工程任务中形成一种新的生产条件：

> 软件系统可以被委托解释限定目标、选择部分路径并改变真实项目状态。

这不是对传统软件工程的否定，也不是未经限定的历史“首次”。真正需要处理的是责任关系变化：

```text
Human or organizational intent
        ↓ delegation
Agent execution within boundaries
        ↓ observable change and evidence
Authorized human or automated disposition
```

当这种委托扩大时，软件工程的管理对象从 Product System 延伸到生产它的智能系统。

下一步不是立即宣布传统假设全部失效，而是逐项检查：现有机制依赖的哪些操作条件，在当前委托、风险和规模下已经不再可靠。

---

## 本章原则

1. **区分效率变化与责任变化。** 生成更快不自动产生新的工程形态。
2. **工具与 Agent 的差异绑定委托范围。** 不作简单本体二分。
3. **Agent 是受托执行系统。** 能力、权限、Authority 与责任必须分开。
4. **代码仍是核心资产，但不是完整生产记录。** 只保存与风险相称的外部依据。
5. **管理两个系统。** Product System 与 Production Intelligence System 都可能产生缺陷。
6. **AI-native 不等于最大自治。** 多 Agent、Memory 与自治程度不是成熟度本身。

---

## 常见反模式

- 把代码生成速度等同于工程生产率；
- 用“是否智能”给工具和 Agent 作本体分类；
- 声称 Agent 在历史上首次拥有任何路径选择能力；
- 把 AI-assisted、Agentic、AI-native 排成所有项目必经的升级路线；
- 认为 Agent 天然拥有实现路径或项目 Authority；
- 只升级模型，不检查 Context、Tool、Permission 和 State；
- 让人类承担最终责任，却不给定位 Evidence、否决和接管能力；
- 为所有小任务建设同等重量的治理设施。

---

## 本章检查清单

- 当前变化主要是生成更快，还是执行责任发生了转移？
- Agent 被委托解释什么，又被允许改变什么？
- 这种路径选择是开放式的，还是由确定 Workflow 约束？
- Capability、Permission、Authority 和 Responsibility 是否分开？
- 人类能观察到哪些输入、动作、结果和失败？
- 现有 Review 与验证能否跟上产出规模？
- Agent 是否会接触 Repository 之外的 Runtime、Data 或 Configuration？
- 失败以后能否恢复、归因和接管？
- 新增记录的维护成本是否与风险相称？
